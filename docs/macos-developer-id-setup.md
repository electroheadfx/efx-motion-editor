# macOS Developer ID Setup

This runbook prepares the Apple-owned credentials and Keychain state required to sign EFX Motion Editor with a **Developer ID Application** identity and authenticate notarization with an App Store Connect API key.

> **Current status:** Repository preparation and the credential-free CLI preflight have passed on the release Mac. A real credentialed release, Apple notarization, ticket stapling, external-download verification, and normal visible launch have not yet been executed. Do not interpret this guide as release success or distribution acceptance.

For the build, notarization, and verification procedure, see [macOS Signed Release](macos-signed-release.md).

## Security rules

- Keep certificates, `.p12` files, `.p8` files, passwords, issuer values, key values, and private keys outside the repository.
- Do not store release credentials in an app-local or repository-local `.env` file.
- Do not paste personal Apple values, private-key contents, certificate fingerprints, or passwords into tickets, chat, logs, screenshots, or documentation.
- A downloaded public `.cer` certificate is not itself the private key, but it should still be handled outside the repository as part of the release operator's credential workflow.
- Never manually force an Apple certificate to **Always Trust**. A valid Developer ID chain should become trusted when the correct Apple intermediate is installed.

## 1. Confirm the Apple command-line capabilities

Full Xcode is not required on the prepared release Mac. Its selected developer directory is `/Library/Developer/CommandLineTools`, and the required capabilities were found there or through system paths.

This is a capability-based conclusion, not a promise about every Command Line Tools installation. Always probe the actual machine:

```bash
/usr/bin/xcode-select -p
test -x /usr/bin/codesign
test -x /usr/bin/security
/usr/bin/xcrun --find notarytool
/usr/bin/xcrun --find stapler
```

Expected output shape:

```text
/Library/Developer/CommandLineTools
/path/resolved/by/xcrun/notarytool
/path/resolved/by/xcrun/stapler
```

The two `test -x` commands are silent when successful. If either `xcrun --find` command fails, install or select a current Apple toolchain before continuing. Do not assume that another standalone Command Line Tools installation includes `notarytool` and `stapler` merely because this Mac does.

The project script performs these probes again:

```bash
bash scripts/macos-release.sh preflight
```

A successful credential-free run ends with:

```text
PREFLIGHT PASS: release configuration, Apple CLI capabilities, resources, and private-asset guards
```

## 2. Create the certificate signing request in Keychain Access

Use the macOS **Keychain Access** application, named **Trousseaux d’accès** in French. Do not use the Passwords/passkeys application.

1. Open **Trousseaux d’accès** (`Keychain Access`).
2. Choose the French menu path:
   **Trousseaux d’accès > Assistant de certification > Demander un certificat à une autorité de certification…**
   
   In English this is:
   **Keychain Access > Certificate Assistant > Request a Certificate From a Certificate Authority…**
3. Enter the Apple Developer account email in **User Email Address**.
4. Enter a recognizable operator or organization name in **Common Name**.
5. Leave **CA Email Address** blank.
6. Select **Saved to disk** rather than emailing the request.
7. Keep the default key-pair settings: **RSA**, **2048 bits**. If macOS does not show an advanced key-pair screen, the defaults are sufficient.
8. Save the CSR in a secure location outside `/Users/lmarques/Dev/efx-motion-editor`.

Keychain Access creates the private key locally. The private key must remain available in the keychain used for the CSR; the Apple Developer portal never receives or returns it.

## 3. Issue the correct Developer ID certificate

In the Apple Developer Certificates portal:

1. Start creation of a new certificate.
2. Select **Developer ID Application**.
   - Do **not** select **Developer ID Installer**. This project distributes a signed Tauri application and DMG; the release script requires an identity whose full name begins with `Developer ID Application: `.
3. Select the modern **G2 Sub-CA** option.
   - Do **not** select **Previous Sub-CA**.
4. Upload the CSR created on this Mac.
5. Download the issued leaf certificate.
6. Install the downloaded certificate with Keychain Access.

A leaf certificate becomes a usable signing identity only when Keychain can pair it with the private key generated by the CSR.

## 4. Install the Developer ID G2 trust chain

Download the public **Developer ID – G2** intermediate certificate from Apple's official PKI certificate page, then install it into the **System** keychain.

The intended chain is:

```text
Developer ID Application leaf certificate
  -> Developer ID Certification Authority G2 intermediate
    -> Apple root certificate
```

Keep the public G2 intermediate in **System**. Do not change its trust policy to **Always Trust**. The default system trust settings are correct when the chain is complete.

The older Developer ID intermediate that expires in 2027 does not complete a leaf certificate issued from the modern G2 Sub-CA. The required G2 intermediate is the one whose validity extends into 2031.

## 5. Place certificates and keys in the correct keychains

Use this placement:

| Item | Keychain | Reason |
|---|---|---|
| CSR-generated private key | Login or the active session keychain | It is personal private material and must remain paired with the leaf certificate. |
| Personal Developer ID Application leaf/identity | The same login/session keychain as the private key | `codesign` needs one usable certificate/private-key identity. |
| Public Developer ID G2 intermediate | System | It completes the public trust chain for Developer ID validation. |

If the personal leaf certificate was installed into **System** while its private key remained in the login/session keychain, move or copy the leaf into the private key's keychain. In Keychain Access, copy/paste can work when drag-and-drop between keychains does not.

After confirming that the session/login copy is paired and usable, remove only the duplicate personal leaf certificate from **System**. Retain the public G2 intermediate in **System**. Be careful not to delete the private key or the G2 intermediate.

## 6. Verify exactly one usable signing identity

Run:

```bash
/usr/bin/security find-identity -v -p codesigning
```

Expected output shape:

```text
  1) <CERTIFICATE-FINGERPRINT> "Developer ID Application: <LEGAL-NAME> (<TEAM-ID>)"
     1 valid identities found
```

The exact quoted identity is later assigned to `APPLE_SIGNING_IDENTITY`. An Apple email address or Team ID by itself is not a signing identity.

The release script requires exactly one usable identity matching the requested full quoted name. If the command reports `0 valid identities found`, the leaf certificate is not paired with its private key, the chain is incomplete, or the keychain is unavailable. If the same fingerprint appears twice, remove only the duplicate personal leaf from the wrong keychain and rerun the command.

In Keychain Access, verify the public **Developer ID Certification Authority** in **System > Certificates** shows a validity date extending into September 2031 and reports that the certificate is valid. Do not open or search for personal certificate files, and do not apply a custom **Always Trust** setting.

## 7. Create App Store Connect API access

Notarization uses an App Store Connect Team API key, not the Apple account password.

1. Open **App Store Connect**.
2. Go to **Users and Access**.
3. Open **Integrations**.
4. Select **App Store Connect API**.
5. Open **Team Keys**.
6. If API access is not enabled, request access and wait for approval.
7. Create a Team Key with the minimum role required by this workflow: **Developer**.
8. Download the `.p8` private key when it is offered.
   - Apple permits this download only once.
   - Store it securely outside the repository.
9. Record the displayed identifiers in a secure credential manager:
   - **Issuer ID** maps to `APPLE_API_ISSUER`.
   - **Key ID** maps to `APPLE_API_KEY`.
   - The absolute path to the downloaded `.p8` maps to `APPLE_API_KEY_PATH`.

Do not rename or relocate the key into the project for convenience. The release script rejects an API key path inside the repository.

## 8. Back up the complete Developer ID identity

Export a password-protected `.p12` backup from Keychain Access after the personal leaf certificate is correctly paired with its private key:

1. In the login/session keychain, locate the **Developer ID Application** identity.
2. Expand it and confirm that the private key appears beneath the certificate.
3. Select the identity and export it as a `.p12` file.
4. Protect the export with a strong, unique password.
5. Store the `.p12` and its password in separate secure external locations with appropriate backup controls.
6. Keep both outside the repository and outside application data directories.

A `.p12` restores an already issued certificate and matching private key. Importing it does not issue a new Apple certificate.

## Troubleshooting record

These issues occurred during setup and were resolved as follows.

### The Passwords/passkeys app was opened instead of Keychain Access

The Passwords application manages passwords and passkeys; it does not provide the certificate assistant needed for a CSR. Open **Trousseaux d’accès** (`Keychain Access`) and use its **Assistant de certification** menu.

### Developer ID Installer was selected

`Developer ID Installer` is the wrong certificate type for this workflow. Issue a **Developer ID Application** certificate. The release script rejects any `APPLE_SIGNING_IDENTITY` that does not begin with `Developer ID Application: `.

### Previous Sub-CA was selected

Issue the certificate using the modern **G2 Sub-CA**, not **Previous Sub-CA**. The matching G2 intermediate must also be installed.

### The personal certificate landed in System while the private key remained in session

This split produced:

```text
0 valid identities found
```

The certificate and its CSR-generated private key must be in the same login/session keychain. Copy the personal leaf into the keychain containing the private key, then verify that Keychain Access shows the certificate and private key as one identity.

### The certificate appeared untrusted

Only the older Developer ID intermediate, expiring in 2027, was installed. Installing the public **Developer ID G2** intermediate, expiring in 2031, completed the chain. No trust settings were changed.

### Dragging between keychains failed

Keychain Access drag-and-drop did not move the certificate successfully. Copying and pasting the personal leaf certificate between keychains succeeded.

### Two identical usable identities appeared

Copying the personal leaf produced two `security find-identity` entries with the same certificate fingerprint. Removing only the duplicate personal leaf from **System**, while retaining the paired session/login identity and the public G2 intermediate, produced the required result:

```text
1 valid identities found
```

Never delete the G2 intermediate or private key while removing a duplicate leaf.

## v0.8.1 packaging hotfix

The v0.8.0 release proved that correct credentials and signing are not sufficient: the packaged app contained no frontend entry (`dist/index.html` was never emitted because `motion-canvas:project` sets `build.rollupOptions.input`, suppressing Vite's default HTML entry) and shipped the template placeholder icon. Signing, notarization, and Gatekeeper checks all passed over that broken content.

For v0.8.1 the pipeline around the credentialed steps was hardened so credential setup is the only remaining manual surface:

- The Vite production build restores the `index.html` entry alongside the Motion Canvas project bundle and fails closed via a `writeBundle` bundle guard when the emitted frontend is incomplete — Tauri packaging cannot start from a broken `dist/`.
- The real EFX icon set is generated from the canonical `SPECS/efxmotioneditor-icon.png` (1024x1024 RGBA) and pinned through the exact 5-file `bundle.icon` array; preflight validates the array, file presence, ICNS magic bytes, and the canonical source dimensions.
- Preflight enforces version agreement between `tauri.conf.json` and the script's `PRODUCT_VERSION` (dynamic comparison, no hardcoded version), and the DMG artifact glob interpolates `PRODUCT_VERSION`.
- Preflight proves codesign runtime resolution with a simulated system-first PATH check (`command -v codesign` must print `/usr/bin/codesign`), and the Tauri build runs with `/usr/bin:/bin:/usr/sbin:/sbin` prefixed so Apple's tools cannot be shadowed by PATH wrappers.
- `verify_app()` now also checks the packaged `Info.plist` (`CFBundleShortVersionString`, `CFBundleVersion`, `CFBundleIconFile`) and the bundled icon's presence and `icns` signature, in both the local release and downloaded-artifact paths.

All keychain, certificate, App Store Connect key, and credential-handling guidance above is unchanged and still applies verbatim.
