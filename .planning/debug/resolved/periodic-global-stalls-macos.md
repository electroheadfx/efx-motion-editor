## Current Focus

hypothesis: 52.1's Rust decode path (`decode_webp_frame`) crosses the Tauri IPC as typed JSON — `bytes: Vec<u8>` in, `DecodedWebpFrame { rgba: Vec<u8> }` out — so every decoded frame is marshalled as a JSON number array (~33 MB of JSON for a 1920×1080 RGBA frame) stringified/parsed and converted on the webview main thread, while the sibling `encode_webp_frame` path was explicitly built raw to avoid exactly that cost. Secondary contributors to separate by measurement: generated-frame render bursts (PNG renders on enumeration paths) and the autosave full-document re-serialization (base64 frame bytes).

## Symptoms

expected: Smooth playback and idle interaction in the native app — no interface-wide slowdowns, no macOS beachball.
actual: Periodic interface-wide stalls + macOS spinning beachball, occurring even before painting (idle) and mid-playback. Pattern: after each stall, everything renders in order and is fast again — then recurs periodically (cache-thrash / decode-storm signature). Host has 64 GB RAM, so per-process limits / main-thread stalls are suspected over system RAM. Content: 2 paint layers, ~30 rails.
errors: none reported (no crash — beachball + slowdown only)
reproduction: Native app with the user's real project (2 layers / ~30 rails). 2-minute script: idle → paint → playback → playback loop.
started: Not present before Phase 52.1 (HD runtime: Rust WebP-lossless decode, bytes/ImageBitmap path, 512MB LRU frame cache, cap 1920) at this content weight.

## Reporter Hypotheses (verify, do not trust)

1. 512MB LRU thrash: decoded HD frames ≈ 8MB each; 2 layers × 30 rails may exceed capacity; playback walks the timeline and re-decodes freshly evicted frames → periodic storms.
2. Decode on the main thread (Rust/WASM or createImageBitmap bursts) blocking input → beachball.
3. Roto live-pixel cache growth (deferred footprint item) pressuring memory/GC.
4. WKWebView per-process memory cap → jetsam warnings / GC storms despite 64 GB system RAM.

## Resolution

root_cause: Ranked measured result (instrumented capture /tmp/efx-stall-capture.json, 133 s, real 2-layer/~30-rail project). (1) DOMINANT — four near-identical ~4.4 s global main-thread blocks (7.8–12.2, 39.8–44.2, 56.3–60.9, 67.8–72.2 s; 17.3 s = 64% of the 26.9 s stall total) with no decode correlation (A/D have zero decode activity with a flat cache; the six-decode burst produced no such block; decode #5 completed exactly as block B ended — decodes queue behind these blocks). Uniform fixed cost + exact 60.0 s start-to-start spacing + debounce-after-version-bump alignment match the autosave full-document serialize path: every save deep-copies the whole document (`toTransportPayloadInner`), base64s ALL real-key bytes (`bytesToBase64`, ~180–400 ms per 10 MB) and JSON-serializes the tens-of-MB payload across IPC to Rust (autoSave.ts 2 s debounce + 60 s safety interval; saveProject → savePaintData → ipcProjectSave). Evidence grade: converging signature evidence; the save path carries no counters in this capture, so one save-path timing measurement remains to close it. (2) CONFIRMED, secondary — decode responses cross the Tauri IPC as JSON number arrays (rgbaIsJsonArray 11/11, typed 0): solo decode round trip 427–665 ms vs Rust codec 67.7 ms median (convert 6 ms, createImageBitmap 1–35 ms); under contention the round trip queues and reports 3.3–6.7 s. Real per-decode tax (fan-out amplifies: 310 prefetch calls → 11 decodes after 57 inflight dedupes) but not the multi-second stall engine. (3) Paint-path measured cost — 19×~300 ms stall cluster matches `paint-grain-readback` (count 19, median 335 ms); trace magnitudes also show stroke-finalization 12.9 s and first-raster publication wait 12.6 s. (4) REFUTED — 512 MB LRU thrash (12 entries / 99.5 MB of 536.9 MB, zero evictions, 82% hits), createImageBitmap bursts, WKWebView memory-cap signature (footprint 99.5 MB, no pressure signal); reporter H3 (roto live-pixel cache) unmeasured, no signal.
