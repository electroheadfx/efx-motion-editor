# Phase 52.3: Paint content export — per-frame compositor enumeration - Research

**Researched:** 2026-09-19
**Domain:** In-repo export path — frameMap enumeration, exportRenderer canvas lifecycle, selectedSequenceOnly filter semantics
**Confidence:** HIGH

## Summary

The diagnosis is complete and uncontested (quick 260919-azh, verdict NEVER-WIRED): the fx overlay RENDER leg works — `renderGlobalFrame` draws physic-paint layers through the CMP-01 `getFlattenedFrame` seam for any global frame inside an fx span — but `frameMap` materializes `FrameEntry` objects only from `kind === 'content'` keyPhotos, so a paint-only project yields an empty map and `startExport` hard-errors. This phase is pure in-repo design work: a discriminated `FrameEntry` variant for paint-carrying frames, a paint enumeration branch in the `frameMap` computed, a top-level canvas clear in `renderGlobalFrame`, and a re-pinned `selectedSequenceOnly` semantic for fx actives. Every load-bearing seam was re-verified against the working tree this session; no external packages, APIs, or services are involved.

Two findings go beyond the CONTEXT.md framing and shape the plan. First, the paint enumeration branch can only ever fire when zero content entries exist — with any content present, the existing tail pad already fills `[0, N)` and D-02/D-03 (content wins, tail-hold preserved) fall out for free; the branch reduces to a clean `entries.length === 0` guard. Second, a latent positional-vs-global conflation in `renderGlobalFrame`'s overlay leg (it gates overlays on the positional frame index, not the entry's `globalFrame` field) means a `selectedSequenceOnly` export of an fx sequence with `inFrame > 0` would render all-transparent even after D-08 — the overlay gate skips every positional frame. The fix is a one-line read of the entry's own `globalFrame` field and is required for D-08 correctness beyond the `inFrame: 0` case.

**Primary recommendation:** Implement the paint enumeration branch as a dense fill of `[0, N)` gated on `entries.length === 0`, enumerating coverage with the *same* `getTimelineOverlaySequenceOutFrame` predicate the renderer's overlay leg gates on (so enumeration and render gating can never drift), materialize `FrameEntry` as a house-style discriminated union (`content` / `paint` / `gap` mirroring `EfxPaintBackgroundFrameResolution`), add the D-06 clear gated on `!hasContentEntry`, and fix the overlay leg to gate on `entry.globalFrame` in the same pass.

### Locked Decisions

**Paint FrameEntry ownership (Q1)**
- **D-01:** Paint-carrying frames are materialized as an **explicit discriminated FrameEntry variant** (e.g. `kind: 'paint'`) carrying the owning fx `sequenceId` and the paint layer identity — **no `keyPhotoId`/`imageId`**. Fail-closed by type: TypeScript forces every FrameEntry consumer to confront the variant rather than tolerating sentinel ids. This keeps the parked Case C contract (`frameMap` length 5 for a 5-key paint-only project) reinstatable as written. — **Reversibility:** costly — the variant enters the shared `FrameEntry` type consumed by frameMap, exportRenderer, preview, and test harnesses; removing it later means touching every discriminated consumer the compiler surfaces.
- **D-02:** Per frame, **content wins**: a paint-kind entry exists only where no content entry covers that frame. Mixed frames stay ordinary content entries; paint draws via the fx overlay leg exactly as it does today (Control B stays green). The content branch (`exportRenderer.ts:148-298`) renders nothing for a paint-kind entry — `hasContentEntry` semantics are preserved, not broadened.
- **D-03:** When paint extends beyond the content clip's span in a mixed project, the frames beneath the paint keep the **clip's last content frame** — today's tail-pad hold behavior (pinned green by Control B) is preserved as the designed behavior, not an accident.

**N derivation + clamp owner (Q2)**
- **D-04:** Export length N follows the **existing `getTimelineRequiredFrameCount` law** (`frameMap.ts:244-259`): `N = max(content end, every visible sequence's authored end, seqStart + loop-aware paint extent)`. Paint keys are **never clipped** by a shorter authored fx span; a longer authored span yields trailing fond-blank frames. No new clamp semantics — the user owns the span (260918-o0n), paint owns its extent, export takes the union.
- **D-05:** WYSIWYG invariant: export length always equals what the timeline shows (`totalFrames` already reads the same law). Enumeration spans `[0, N)` with fond-blank frames where neither content nor paint exists, and **frameMap stays dense** over that range so positional indexing (`renderGlobalFrame` reads `fm[frameIndex]`, `exportRenderer.ts:138`) remains valid.

**Canvas clear lifecycle (Q3)**
- **D-06:** A **single top-level canvas clear** is added at the start of `renderGlobalFrame`, gated on `!hasContentEntry` (identity-transform `clearRect`, same style as the GL transition path at `exportRenderer.ts:206`). Content frames keep byte-identical behavior (the content branch's own `clearCanvas=true` renders are untouched, including both cross-dissolve sub-paths). Paint-kind and gap frames start from clean pixels — no uncleared-canvas ghosts (Q3 regression pin).
- **D-07:** Fond/paper arrives via the flattened raster wherever an fx span covers the frame (the internal compositor owns the fond — v1.0 rendering law). True gap frames (inside N but outside every content/fx span) export **transparent**. Scope is the export path only; preview rendering is unchanged.

**selectedSequenceOnly for fx actives (Q4)**
- **D-08:** With an fx sequence active, 'Selected sequence only' **filters by the fx sequence id** — the existing `fm.filter(e => e.sequenceId === activeId)` predicate (`exportEngine.ts:145-150`) now matches that sequence's paint-kind entries. - **D-10:** The 'No frames to export (timeline is empty)' refusal stays reachable only for genuinely empty timelines (no content AND no paint). It is unreachable for fx-with-paint. Case E is re-pinned from the error characterization to the new filter behavior.

### Pattern 1: Discriminated union, house style (D-01)

**What:** Convert `FrameEntry` from a flat interface to a discriminated union. Content entries gain `kind: 'content'`; paint entries carry `kind: 'paint'` with the owning fx `sequenceId` and no `keyPhotoId`/`imageId`.

**When to use:** D-01 mandates fail-closed-by-type so every consumer is compiler-surfaced.

**House-style precedent** (verbatim, [VERIFIED: app/src/efx-paint/compositor/efxPaintBackgroundResolution.ts:50-53]):

```typescript
export type EfxPaintBackgroundFrameResolution =
  | { readonly kind: 'content'; readonly clipId: string; readonly sourceRef: string }
  | { readonly kind: 'gap' }
  | { readonly kind: 'missing'; readonly clipId: string; readonly missingRefs: readonly string[] };
```

Note the precedent's `gap` arm "deliberately carries no clipId" (:45) — the same move is available for gap frames (no `sequenceId` ownership).

Current `FrameEntry` (verbatim, [VERIFIED: app/src/types/timeline.ts:26-35]):

### Pattern 2: Enumerate with the renderer's own predicate (D-04/D-05)

**What:** The paint branch fills `[0, N)` densely, but only when no content entries exist (Finding F1). Coverage per fx sequence uses `getTimelineOverlaySequenceOutFrame(seq, N)` — the *identical* function the overlay leg gates on at `exportRenderer.ts:306` — so enumeration and render gating can never drift.

**Why the guard reduces to `entries.length === 0`:** content sequences tile `[0, contentEnd)` contiguously (`frameMap.ts:23-39`), and the tail pad (`:41-45`) extends to `targetLength` whenever a content entry exists. Therefore with any content, every frame in `[0, N)` already carries a content entry, D-02 (content wins) and D-03 (tail-hold) are satisfied structurally, and Control B stays byte-green. The paint branch fires only in content-empty projects. [VERIFIED: app/src/lib/frameMap.ts:16-47 read in full]

**N is already correct and reactive:** `getTimelineRequiredFrameCount` (`frameMap.ts:244-259`) already iterates fx sequences, extends by `timelineRange.globalEndExclusive` and `seqStart + rotoEnd` via `getPhysicPaintRotoDisplayEndFrame` (`:227-242`, loop-aware), and skips `visible === false` sequences (`:247`, matching D-04's "every visible sequence"). The `frameMap` computed subscribes `physicPaintVersion` (`:17`), and `replaceRotoPhysicalDocument` bumps the global clock via `bumpTrackRevision` (`physicPaintStore.ts:3482-3483`) [VERIFIED: both read this session]. No new N logic, no new clamp (D-04).

**Gap-frame ownership (discretion, with a constraint):** frames in `[0, N)` outside every fx coverage occur only when a paint-only project's first fx starts at `inFrame > 0`. Two options:
- **(a) `kind: 'gap'` entries with empty `sequenceId`** — mirrors the house-style union's `gap` arm; D-07 transparency becomes structurally explicit; selected-fx export excludes them (consistent with content-selected renumbering today).
- **(b) paint-kind entries owned by the nearest fx** — keeps a selected-fx export's PNG numbering aligned with the full export, but mislabels ownership and pollutes the D-08 filter.
Recommendation: **(a)**, paired with the Pitfall 1 overlay-gating fix — without that fix, option (a) makes a selected-fx export of an `inFrame > 0` sequence render all-transparent (positional index `< inFrame` → overlay skipped on every frame). With the fix, (a) is correct in all cases.

### Anti-Patterns to Avoid
- **Broadening `hasContentEntry`:** D-02 preserves it. Paint entries flow through the existing `!!seq && seq.kind !== 'fx'` gate ([VERIFIED: app/src/lib/exportRenderer.ts:140]) → content branch skipped, overlay leg draws. Do not add a paint arm to the content branch.
- **Sentinel ids on paint entries** (`keyPhotoId: ''`, `imageId: ''`): exactly what D-01 forbids — the union exists so the compiler, not convention, polices consumers.
- **A second N law or clamp:** D-04 reuses `getTimelineRequiredFrameCount` unchanged. Any paint-specific clamp re-opens the 260918-o0n span-ownership decision.
- **Iterating internal paint tracks in the export path:** CMP-01 locks `getFlattenedFrame` as the only content seam; the main renderer never iterates internal tracks (Phase 48 D-11).
- **Per-frame `new Image()` / decode in the render loop:** the existing preload (`preloadExportImages` → `collectExportPhysicPaintFrameSources` second loop over fx sequences, `exportRenderer.ts:83-91` → `awaitPhysicPaintDecodes`) already warms every paint frame in range without depending on entry kind — keep it as the only decode gate.
- **Mocking `./frameMap` in the new tests:** the discrimination matrix's power is the real computed over real stores (harness copied verbatim from `exportEngine.test.ts` with only that one deliberate difference).

## Common Pitfalls

### Pitfall 1: Positional-vs-global conflation breaks D-08 for `inFrame > 0` (NEW FINDING)
**What goes wrong:** `startExport` filters `fm` positionally (`exportEngine.ts:148`), then the render loop passes the *positional* index as `globalFrame` (`:241`, `:260`). The overlay leg gates on that param: `if (overlaySeq.inFrame != null && globalFrame < overlaySeq.inFrame) continue;` and computes `fxLocalFrame = globalFrame - (overlaySeq.inFrame ?? 0)` ([VERIFIED: app/src/lib/exportRenderer.ts:305-306, :337]). In a selected-fx export where gap entries are excluded, positional `0` corresponds to true global `inFrame` — every positional index `< inFrame` → overlay skipped → all-transparent export even though the filter matched entries.
**Why it happens:** in full exports positional index === true global frame (map is dense from 0), so the conflation is invisible. It is also a pre-existing quirk for content-selected exports of non-first sequences (their overlays can be silently dropped) — D-08's "overlays always ride" holds today only when the selected sequence starts at global 0.
**How to avoid:** inside `renderGlobalFrame`, derive the overlay-gating frame from the entry itself: `const overlayGlobalFrame = entry ? entry.globalFrame : frameIndex;` and use it for the `inFrame`/`outFrame` gates and `fxLocalFrame` (leave the content branch's positional `seqStart` walk untouched — it is genuinely positional). Add a test: fx at `inFrame > 0`, selectedSequenceOnly → export renders the paint frames (not all-transparent).
**Warning signs:** selected-only exports of later sequences missing their fx overlays; selected-fx export producing N transparent PNGs.

### Pitfall 2: frameMap does not subscribe `efxPaintVersion` (pre-existing, do not "fix" silently)
**What goes wrong:** the paint branch reads `activeTrackId` via `getActiveTrackId` → `getEfxPaintDocument` (`frameMap.ts:128-130`). Document-only mutations (e.g., active-track switch) bump `efxPaintVersion`, which `frameMap` does not subscribe (`:17` subscribes `physicPaintVersion` only). A track switch on a paint-only project could leave enumeration stale until the next paint mutation.
**Why it happens:** pre-existing subscription shape — the N law already reads the same `activeTrackId` path today, so this phase introduces no new dependency of this kind (Phase 48 P05 recorded the same two-clock lesson for the Studio monitor).
**How to avoid:** out of scope to redesign; the planner may add `void efxPaintVersion.value;` beside `:17` as a one-line defensive subscription — but flag it in the plan as a conscious inclusion, not a drive-by.
**Warning signs:** enumeration/extent stale after a track switch until any paint edit.

### Pitfall 3: playback activation behavior changes on paint-only projects (Finding F4)
**What goes wrong:** today `frameMap` is empty for paint-only projects, so `syncActiveSequence` no-ops. With a dense map, playhead entry into a paint frame fires `sequenceStore.setActive(fxId)` + `uiStore.selectSequence(fxId)` ([VERIFIED: app/src/lib/playbackEngine.ts:188-199]). `ensureTrackVisible` is a no-op ([VERIFIED: app/src/stores/timelineStore.ts:149-151]).
**Why it matters:** this is arguably the correct D-08-consistent behavior (fx row activates during playback), but it is a user-visible change riding on the enumeration work, and `sequenceStore.setActive` also clears `selectedKeyPhotoId` (`sequenceStore.ts:1091-1094`).
**How to avoid:** pin the behavior with a test (playback into a paint frame activates the fx sequence) so the change is deliberate, and call it out in the UAT script.
**Warning signs:** surprise sidebar/selection movement during playback on paint-only projects.

### Pitfall 4: Case E re-pin must amend, not delete (D-10)
**What goes wrong:** the green characterization test currently asserts status `'error'` + locked copy. After D-08 the same arrange exports 5 frames with status `'complete'`.
**How to avoid:** amend the existing `it` in place (git history preserves the characterization), assert the new filter behavior: `renderGlobalFrame` × 5, status `'complete'`, and — the D-10 negative — a genuinely empty timeline still refuses with the locked copy (add that arrange: no sequences at all → `'No frames to export (timeline is empty)'`).

### Pitfall 5: Test-side literal churn from the discriminant
**What goes wrong:** adding `kind` to the union fails tsc at every `FrameEntry` literal lacking it: 9 sites in `exportRenderer.test.ts`, 1 in `exportEngine.test.ts`, 1 in `exportEngine.loops.test.ts`, plus literals in `previewRenderer.test.ts` and `keyPhotoNav.test.ts`. `frameMap.test.ts` reads `.imageId` off entries ~15 times (union narrowing errors); it already uses `(entries[0] as any).solidColor`-style escapes for optional fields.
**How to avoid:** one mechanical commit adding `kind: 'content'` to literals + narrow helpers where assertions read content-only fields. Keep it separate from behavior commits (repo convention: test-only commits).

### Pitfall 6: `resumeExport` and motion-blur paths read the same dense map
**What goes wrong:** `resumeExport` re-enters `startExport(resumeFrame)` with positional semantics (`exportEngine.ts:502-506`); motion blur sub-frames floor to the same entry (`exportRenderer.ts:133-134`). Both are compatible with the dense map and the D-06 clear — but only if the clear stays gated on `!hasContentEntry` and the overlay gate uses the entry's `globalFrame` (Pitfall 1), otherwise resumed/motion-blurred paint exports drift.
**How to avoid:** include a motion-blur-enabled paint-only export in the automated matrix (cheap: `exportStore.motionBlurEnabled.value = true` in the harness, assert render calls and non-error status) or explicitly pin it as a native UAT row.
