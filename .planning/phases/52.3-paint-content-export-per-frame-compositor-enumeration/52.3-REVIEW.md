# Phase 52.3: Code Review Report

**Reviewed:** 2026-09-19T12:00:00Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

The FrameEntry discriminated union (D-01), the paint enumeration branch (D-04/D-05), the D-06 canvas clear, and the Pitfall-1 overlay gating fix are internally consistent: enumeration coverage uses the same `getTimelineOverlaySequenceOutFrame` predicate the render gate uses, and the union narrowing is applied at every consumer the phase touched. However, the same D-08 positional-rebase problem that was fixed in the render path (`renderGlobalFrame`, via `entry.globalFrame`) was NOT fixed in the export preload path: `collectExportPhysicPaintFrameSources` still computes a true-global fx window clamped to `fm.length`, which after rebase is an entry count, not a global end. Selected-sequence exports with `inFrame > 0` therefore preload zero physic-paint frames and silently export transparent paint — a data-corruption blocker. Secondary findings: gap entries now deselect the active sequence during playback scrubbing, the D-06 clear regresses cold-decode preview anti-flicker behavior, the single-owner enumeration model contradicts the composite-all render model for three selected-export shapes, and the test matrix misses exactly the regression windows above.

## Critical Issues

### CR-01: Export preload misses every physic-paint frame for rebased (selected-sequence) exports with fx inFrame > 0

**File:** `app/src/lib/exportRenderer.ts:84-92` (overlay leg of `collectExportPhysicPaintFrameSources`, called from `preloadExportImages` at lines 475 and 477)
**Issue:** The overlay leg iterates a true-global window `[start, end)` where `end = Math.max(start, Math.min(fm.length, getTimelineOverlaySequenceOutFrame(seq, fm.length)))`. `fm.length` is used as a global-frame clamp, but for a `selectedSequenceOnly` export the filter at `exportEngine.ts:148` rebases `fm` positionally — `fm.length` becomes an entry COUNT, not a true global end. The Pitfall-1 fix repaired the render gating (`renderGlobalFrame` gates on `entry.globalFrame`, line 152) but not this preload leg.

Two reachable corruption scenarios:

1. **Selected fx export, inFrame > 0 (paint-only project).** fx at inFrame 5 / outFrame 10 → after filtering, `fm` = 5 paint entries (globalFrame 5..9), `fm.length` = 5. Overlay leg: `start = 5`, `end = max(5, min(5, 10)) = 5` → empty window. The content leg (lines 73-82) also skips these entries (`seq.kind === 'fx'` → `continue`). Zero paint sources collected, zero decodes kicked, `awaitPhysicPaintDecodes()` no-ops. In the render loop, `renderGlobalFrame` correctly passes the gate (the Pitfall-1 fix works), `getFlattenedFrame(layerId, 0..4)` cold-misses → returns null → physic-paint branch draws nothing. **All 5 frames are written to disk transparent**, and the export reports `complete`. Case E (`exportEngine.paintEnumeration.test.ts:309`) passes only because it uses inFrame = 0 (`start = 0 < end = 5`). For partial overlap (e.g. inFrame 2 / outFrame 7, `fm.length` = 5) the window `[2, 5)` preloads local frames 0..2 and frames 3..4 export transparent — partial corruption.

2. **Selected content export starting at global > 0 with an fx overlay riding** (RESEARCH Open Question 1 — the render half was fixed, the preload half was not). content-b at global 5..9, fx at 5..10 → filtered `fm.length` = 5; overlay leg `start = 5`, `end = max(5, min(5, 10)) = 5` → empty. The overlay now renders (test `'selected export keeps later-sequence overlays riding'` proves the render call), but its physic-paint layers cold-miss per frame → transparent paint in the delivered frames. Generator layers in the same fx overlay do render (no preload needed), so the corruption is paint-specific and easy to miss on review of the output.

Pre-52.3 these exports either refused (E2) or dropped the overlay entirely (known quirk); 52.3 makes them complete with silently missing paint — worse than refusal. Whether the decode kicked by the render loop's cold miss can complete before `canvasToBlob` is timing-dependent; per the store contract (`exportEngine.loops.test.ts:743`: "the decode is pending, so the flattened delivery is null this tick") the frame is captured without paint.

**Fix:** Drive the overlay leg from the entries, mirroring the render gate so enumeration, render gating, and preload can never drift (the same D-04 argument the phase used for enumeration):

```ts
for (const seq of sequences) {
  if (seq.kind === 'content' || seq.visible === false) continue;
  const seqIn = seq.inFrame ?? 0;
  const seqOut = getTimelineOverlaySequenceOutFrame(seq, Number.MAX_SAFE_INTEGER);
  for (const entry of fm) {
    if (!entry) continue;
    const g = entry.globalFrame;               // true global, rebase-proof
    if (g < seqIn || g >= seqOut) continue;
    addSources(interpolateLayers(seq, g - seqIn), g - seqIn);
  }
}
```

(Equivalent minimal repair: clamp `end` against `fm[fm.length-1].globalFrame + 1` instead of `fm.length`. The entry-driven form is preferred because it matches `renderGlobalFrame`'s per-entry gate exactly.) Add regression tests: selected fx export with inFrame > 0 asserting `preloadPhysicPaintFrames` received every local frame in `[0, outFrame-inFrame)`, and the content-at-global->0 + fx-overlay preload case.

## Warnings

### WR-01: Gap entries deselect the active sequence during playback scrubbing

**File:** `app/src/lib/playbackEngine.test.ts:284-304` (subject: `playbackEngine.ts` `syncActiveSequence`, lines 188-199); root cause in `app/src/lib/frameMap.ts:68`
**Issue:** `syncActiveSequence` reads `frameMap.peek()[cf]` and calls `sequenceStore.setActive(entry.sequenceId)` whenever the entry's sequenceId differs from the active id. Pre-52.3, positions outside any sequence had no entry and preserved the active sequence. Post-52.3, the dense enumeration emits gap entries with `sequenceId: ''`, so scrubbing into a leading gap (paint-only project with fx inFrame > 0) or an inter-fx gap calls `setActive('')` — which also clears `selectedKeyPhotoId` (`sequenceStore.ts:1091-1094`). The sidebar loses the fx properties and the export dialog's "selected sequence" silently becomes none until the playhead re-enters the paint span. The new test pins paint-frame activation but never the gap case, so this behavior change is unpinned and likely unintended (D-08 documentation describes gap entries as "ownerless", not as deselection signals).
**Fix:** Guard in `syncActiveSequence`: `if (entry && entry.sequenceId !== '') { ... }`. Add a test asserting scrubbing onto a gap entry preserves the prior active sequence and key-photo selection.

### WR-02: D-06 clear regresses cold-decode anti-flicker behavior on the shared Preview canvas

**File:** `app/src/lib/exportRenderer.ts:158-164`
**Issue:** `renderGlobalFrame` is shared between export and the live Preview (`Preview.tsx:71-76`). The new top-level clear fires for every no-content frame — including on the live canvas. On a cold physic-paint decode, the overlay pass's `renderFrame(clearCanvas=false)` treats any visible layer as drawable, the physic-paint branch `continue`s on the null flatten, and nothing is drawn — but the D-06 clear has already erased the previous composite. The canvas stays transparent until the decode completes and the 400ms trailing throttle (`useTrailingThrottledSignal`) elapses. Pre-52.3, the same cold-miss path kept the last composite (no clear anywhere in the no-content path — the accidental anti-flicker the 52.1 guard formalized for `clearCanvas=true`). This is a visible flash regression on first scrub to uncached paint frames in paint-only projects. The export motivation for D-06 (stale pixels between frames) does not apply to the single-canvas preview, where keeping the previous frame during decode was the designed behavior.
**Fix:** Scope the clear to export renders (e.g. an explicit `clearNoContentFrames` parameter threaded from `exportEngine`, defaulting to false), or skip the clear when every visible overlay physic-paint layer's flatten is currently null (pending decode). If the flash is an accepted tradeoff, pin it with a comment and a test so the 52.1 anti-flicker contract is consciously amended.

### WR-03: Single-owner enumeration contradicts composite-all rendering for three selected-export shapes

**File:** `app/src/lib/frameMap.ts:62-69`
**Issue:** The enumeration assigns each frame at most one owner (`fxSeqs.find(...)` — first matching physic-paint fx, else gap), but `renderGlobalFrame` composites ALL visible overlay sequences at that frame (lines 326-385). The D-08 filter (`fm.filter(e => e.sequenceId === activeId)`) then refuses selected exports of sequences the full export visibly renders:

1. A **second overlapping physic-paint fx** (two fx paint sequences spanning the same frames): `find` awards ownership to the first; selecting the second yields zero entries → `'No frames to export (timeline is empty)'` despite its paint compositing in full export.
2. An **fx sequence without physic-paint layers** (grain/particles/GLSL) in a content-empty project: every frame enumerates as gap (pinned by the `'side-effect pin'` test at `frameMap.test.ts:487-505`); full export renders the generator via the overlay leg, but selecting that fx refuses.
3. A **content-overlay sequence** in a content-empty project: same gap-ownership refusal; full export renders the overlay.

Case E2 locks the refusal for MIXED projects by design (D-02/D-03), but none of the three content-empty shapes above is covered by that rationale — the refusal there is an ownership-model artifact, not a content-wins consequence.
**Fix:** Either pin the refusal as designed for these shapes (document + test each), or extend the D-08 export filter to include gap frames when the active sequence participates at that frame (e.g. keep entries where `entry.sequenceId === activeId || (entry.kind === 'gap' && activeSeqSpansFrame)`), which matches what the overlay leg will render.

### WR-04: Paint-enumeration export tests miss the CR-01 regression window

**File:** `app/src/lib/exportEngine.paintEnumeration.test.ts:309-323`
**Issue:** Case E covers selected-fx export only at inFrame = 0 — the one geometry where the broken preload clamp (`start = 0 < end`) accidentally works. No case covers inFrame > 0 selected-fx export, and no case covers selected content at global > 0 with an fx overlay (the Open Question 1 arrange exists only as a render-gating test with a stub renderer at `exportRenderer.test.ts:541-581`, which cannot observe preload). Additionally, Case D/E mock `renderGlobalFrame`, so a transparent-canvas regression is structurally invisible to this suite even if preload geometry were exercised.
**Fix:** Add: (a) selected fx export inFrame 2 / outFrame 7 asserting `preloadExportImages` receives a source collection covering local frames 0..4 (spy on `renderer.preloadPhysicPaintFrames` or on `collectPhysicPaintFrameSources`); (b) the content-at-global-5 + fx-overlay selected export asserting the fx paint frames are preloaded.

### WR-05: No test asserts gap-entry playback behavior or enumeration ownership conflicts

**File:** `app/src/lib/playbackEngine.test.ts:256-305`, `app/src/lib/frameMap.test.ts:423-512`
**Issue:** The new playback test pins activation on a paint entry but not the gap-entry path (WR-01). The frameMap paint-enumeration describe pins single-fx, offset-fx, hidden-fx, loop-extension, no-paint-layer, and empty-timeline cases, but never two overlapping physic-paint fx sequences (WR-03 case 1) — the `find`-first ownership tiebreak is unpinned.
**Fix:** Add a gap-scrub test (active sequence preserved) and an overlapping-fx enumeration test documenting which sequence owns the shared frames.

## Info

### IN-01: FX overlay render passes content-local frame as the generator/video `frame` argument

**File:** `app/src/lib/exportRenderer.ts:382`
**Issue:** The fx overlay leg computes `fxLocalFrame` (from `overlayGlobalFrame`, correct post-fix) but passes it only as the 8th (`physicPaintFrame`) argument; the 2nd (`frame`) argument remains `localFrame` — the content-local or positional value. Generator and video layers inside fx sequences animate on the underlying content's local frame rather than the fx-local frame. Preview and export compute it identically, so parity holds today; the semantic is nonetheless surprising next to the Pitfall-1 fix and will bite if fx overlays ever need deterministic fx-local animation. Pre-existing.
**Fix:** Consider passing `fxLocalFrame` as the `frame` argument for fx overlay renders, or document the content-local semantic at the call site.

### IN-02: FormatSelector resets export shutter angle on every mount

**File:** `app/src/components/export/FormatSelector.tsx:51-53`
**Issue:** The mount effect unconditionally copies the preview shutter angle into the export settings, stomping a previously customized export angle each time the export dialog reopens. D-11 describes a default, not a per-mount reset. Pre-existing, unrelated to the count change.
**Fix:** Only seed when the export value was never explicitly set (track a dirty flag), or apply the default at export-settings reset time rather than dialog mount.

### IN-03: Render-body signal writes in CanvasArea sticky paint-mode block

**File:** `app/src/components/layout/CanvasArea.tsx:282-291`
**Issue:** The sticky paint-mode block calls `layerStore.setSelected(...)` and writes `paintStore.paintMode.value` during render — a render-body signal write, which the project's reactivity rules prohibit (it terminates only because the guard becomes false after the write; any future condition change can turn it into a render loop). Pre-existing; the phase touched only the adjacent `frame.kind` guard.
**Fix:** Move the re-selection/deactivation into an event handler or a guarded `effect()`.

### IN-04: Preview `hasContent` counts hidden/empty non-content sequences as content

**File:** `app/src/components/Preview.tsx:56-57`
**Issue:** The second disjunct (`s.kind !== 'content'`) is true for a `visible: false` fx sequence or a content-overlay with no layers, suppressing the "No frames to preview" placeholder when nothing can actually render. Minor UX inaccuracy introduced by the paint-only placeholder fix.
**Fix:** Filter to `s.visible !== false` and require at least one layer.

### IN-05: `PaintFrameEntry.layerId` has no production consumer; `GapFrameEntry.sequenceId` is over-wide

**File:** `app/src/types/timeline.ts:44-58`
**Issue:** Only tests read `PaintFrameEntry.layerId` — `renderGlobalFrame` resolves paint layers from the sequence, and the D-08 filter uses `sequenceId`. `GapFrameEntry.sequenceId` is documented as always `''` but typed `string`; a `''` literal type would make the ownerless law fail-closed at compile time.
**Fix:** Type `GapFrameEntry.sequenceId` as `''`; either wire `layerId` into a consumer (playback/preload ownership) or mark it as reserved for Phase 53.
