<objective>

transition through one commit-point reconciler, in the same transaction and undo step as the
records/loops/breaks write; and a copied, pasted or duplicated rail set carries its motion onto its
fresh identities by a deliberate, tested law.

Purpose: 59-06 defined the transitions and 59-07 made the collection storable, but nothing calls the
transitions — deleting the first key, splitting, merging or moving a rail start would leave the
stored record describing a rail that no longer exists, and a pasted rail would reconstruct the
document without `railMotions` at all (the literal at `physicsPaintRotoRailSetCopy.ts:854-866` omits
the member, which compiles silently because 59-03 made it optional). This plan is the only place
where identity decisions meet real edits.
</objective>

## Reconciler classification (binding)

Inputs are the previous and next document snapshots (ordered real-key records, incoming break key
ids, loop clips) plus the current collection. Derive segments with the real `deriveKeyRailSegments`
for both sides, then classify each record that was ACTIVE on the previous side:

| Observation (previous segment P → next segments) | Transition |
|---|---|
| record railId matches a previous loop clip, and the next document still has that loopId | unchanged |
| record railId matches a previous loop clip, and the loopId is gone | `onDeleteOnlyKey` |
| P has a successor segment N whose `firstKeyId` is P's second key and whose keyIds are a suffix of P | `onDeleteFirstKey(record, N.firstKeyId)` |
| P has no successor sharing any keyId | `onDeleteOnlyKey` |
| P's anchor key survives as N's `firstKeyId`, and a second next segment covers P's tail | `onSplitRail` (head keeps; tail none) |
| a next segment N strictly contains P's surviving keys and starts before P (`N.firstKeyId` is outside P) | `onMergeRails(records, N.firstKeyId, P.firstKeyId, N.firstKeyId)` |
| N has P's exact keyIds and firstKeyId but a different `firstKeyFrame` | `onRailStartMoved` |
| no previous segment contains the record's anchorKeyId | orphan: return unchanged, no transition |

Two records that classify into the same merged segment resolve head-vs-tail inside `onMergeRails`:
the record whose anchor equals the merged `firstKeyId` wins; the other is reported as
`droppedRailId`.
