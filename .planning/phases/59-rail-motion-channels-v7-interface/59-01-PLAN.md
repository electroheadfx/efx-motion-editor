## Gate Ratification (A–D)

These answers are binding for every later plan and are not reopened.

**Gate A — Target: one active rail per track.**
Ratified: yes, one motion target per track, because the rendering law already resolves exactly one
content raster per track per frame. A track therefore has exactly one rail transform to apply; two
simultaneous rails inside one track are not separately drawn and must live on separate tracks
(milestone CONTEXT §3). The authoring surface reinforces this: one expanded motion block at a time
(D-10/D-14), and the gizmo targets the selected rail. The model still stores a motion record per
rail — Gate A constrains application, not persistence.

**Gate B — Identity: `loopId` or `railId`.**
Ratified: a durable `railId` on every motion record. For a Loop Clip rail, `railId = loopId` (no new
id is minted). For a bare Key Rail, a Reveal rail or any rail without a `loopId`, a UUID is minted at
Animate time via the existing `crypto.randomUUID()` mint seam; `anchorKeyId` is persisted as a
recovery hint only and is never used as identity. The truth table is implemented in plan 59-06,
not in the UI:

| Event | Identity | Motion result |
|---|---|---|
| Animate an un-animated rail | loop clip: reuse `loopId`; otherwise mint UUID, stamp `anchorKeyId` | one identity Position key at the rail-local playhead |
| Copy / paste / duplicate a rail set | the copy allocates FRESH identities — a fresh `loopId` for a loop member, a fresh UUID `railId` for a key-rail member; the source `railId` is never reused | motion FOLLOWS the copy: each animated member's record is cloned and re-keyed to the copy's fresh identity, `anchorKeyId` re-stamped to the copy's first key, rail-local key frames unchanged, source record untouched; a member whose destination identity cannot be allocated fails the whole paste closed (never a silent drop) |
| Rail start moves or resizes | `railId` unchanged | rail-local keys unchanged; motion shifts in app time with the rail |
| Delete a non-first drawing key | `railId` unchanged | unchanged |
| Delete the first drawing key of a multi-key rail | `railId` unchanged; `anchorKeyId` re-stamped | rail-local frames NOT rewritten (A3) |
| Delete the only drawing key | rail disappears | motion record deleted in the same undo step |
| Split at a break | head segment keeps `railId`; tail is a new rail with no motion | rail-local keys not rewritten |
| Merge, exactly one side animated | merged rail adopts the animated record, re-anchored | survives without dropping keys |
| Merge, both sides animated | head wins | tail record dropped in the SAME undo step, surfaced by a confirmation row where motion would otherwise vanish silently |
| Orphaned record (`anchorKeyId` gone, no `loopId` match) | `railId` unchanged | retained byte-identically, NOT evaluated, never rebound by heuristic |
| Rail deleted | rail gone | motion record deleted in the same undo step |
| Undo/redo | snapshot identity | motion travels with the physical-edit snapshot |

**Gate C — Time and repeat.**
Ratified: rail-local frame = `appFrame − railStart`, where `railStart` is the Loop Clip's
`placementStart` and, for a Key Rail, the rail's `firstKeyFrame`. Before the first key the first
value holds; after the last key the last value holds for the rest of the rail occurrence. v1 ships
**hold** repeat only (D-16): one occurrence = the rail's full span, and motion interpolates across
the entire occurrence, not per content cycle. `fit-to-span` is deferred and, when added, must be a
per-rail absent-means-hold opt-in. Rotation interpolates linearly in degrees with no wrap. Wiggle is
seeded and deterministic at export. The canonical term is inserted after `loops:` and before
`incoming-breaks:` in both languages.

**Gate D — Quality at scale.**
Ratified: v1 resamples the integer content raster for scale/rotation (no 2× bake, no vector
source); visible softness above ~150% scale is a documented limitation in the UAT, not a silent
omission. The pivot is the union of the rail's key-raster ink bounds, computed once per content
revision and cached in session memory (D-17) — never read from per-frame raster bounds. Plan 59-08
measures the one-time pivot cost on a 24-key rail at 1920px long edge and records the number in its
SUMMARY; the acceptance threshold is ≤ 16 ms per rail per content revision, with a memo-reuse
assertion. Rail motion produces no motion blur (D-18, documented limitation). REL-04 remains a
paint-presence law: the content lookup floors to an integer frame while the transform evaluates at
the fractional time (plan 59-09).

## Open-question resolutions (binding)

1. **Gate B merge/delete rules** — as the Gate B table above.
2. **D-17 pivot** — per-key alpha-bounds union, revision-keyed memo, measured in 59-08.
3. **TS↔Rust `railKind`** — repaired here as the Phase 59 prerequisite, pinned by the shared fixture.
4. **Motion record placement** — document-level `railMotions` collection inside `rotoPhysical`,
   keyed by durable `railId`; one validator, one encoder, one evaluator input. Position is TWO model
   channels (`position-x`, `position-y`) behind one grouped lane (D-11), so a future Split X/Y
   needs no schema change.
5. **Inspector scope** — only channels that carry keys are shown, plus a `+` affordance mirroring
   the lane block; Opacity is always numeric (D-07).
