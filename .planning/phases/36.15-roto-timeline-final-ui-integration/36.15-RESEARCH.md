## Summary

This phase recomposes one existing component — `PhysicsPaintWorkflowStrip.tsx` (962 lines) — plus its CSS, one canvas renderer pass, one layout computed, the Scripts panel toolbar, and `app/index.html`. Every behavior seam the new UI needs already exists: the physical action bundle (`useRotoTimelineActions`) exposes reactive availability + verbatim disabled reasons for Insert/Delete/Drag/Force-Spacing; the script clipboard controller exposes `copyDisabledReason`/`applyDisabledReason`; playback/interpolation props are already fed by `PhysicsPaintStudio.tsx`. No new packages are required (lucide-preact 0.577.0 already installed; all 10 required icons verified present on disk).

The dominant finding is the **geometry gap**: the production strip is 256px tall with 13px cells on a 2px gap inside a hardcoded 1800px lane, a 42px grid header, and a 66px status stack + legend band. The approved contract requires a fixed 155px strip (46/1/28/38/28/14 bands) with 18px abutting cells. This is a full geometry cutover of the strip CSS, not a polish pass. The second dominant finding is that **all current guarded controls use native `disabled`** and must convert to the focusable `aria-disabled` pattern with styled tooltips carrying verbatim controller reasons — and the **styled tooltip component does not exist anywhere in the codebase** (native `title` is the only convention today), so it is genuinely new, subject to the locked 1-second hover-delay contract.

For C-04 (EFX Motion layer markers), the parent store already owns real-key records (`physicPaintStore.getRotoRealKeyRecords(layerId)`), record replacement already bumps `physicPaintVersion` (which `fxTrackLayouts` subscribes), and `TimelineRenderer.drawFxTrack` already has a physic-paint-specific drawing seam (`drawPhysicPaintPlayScriptMarkers`, currently dormant — nothing in production populates `playScriptMarkers`). The marker work is: add a `rotoKeyFrames?: number[]` field to `FxTrackLayout`, populate it in `frameMap.ts`, and add an always-visible diamond draw pass reusing the existing ~9px diamond geometry with `#F5A623`.

**Primary recommendation:** Plan as three waves — (1) Wave 0/1: test-contract updates + styled tooltip component + selection guard + icon/lucide groundwork; (2) strip recomposition (geometry, pills, capsule, icon row, legend/stack removal) with source-contract tests updated in lockstep; (3) EFX Motion layer markers (frameMap field + renderer pass + pure-geometry tests) and Scripts toolbar Discard relocation; close with typecheck + `vitest run` green, then user-owned native visual UAT.

private drawRotoKeyMarker(ctx: CanvasRenderingContext2D, x: number, centerY: number, size = 9): void {
  ctx.save();
  ctx.beginPath();
  ctx.moveTo(x, centerY - size / 2); ctx.lineTo(x + size / 2, centerY);

### Anti-Patterns to Avoid
- **Business logic in the view:** deriving availability from frame type/clipboard presence in the strip (D-12; UI-SPEC §Guarded Script Controls). Use the reason ports; the current local fallback strings in `getRotoKeyUtilityDisabledMessage` (strip lines 352–363) must defer to controller reasons where ports exist.
- **A second status band:** replacing the deleted stack/legend with a toast rail, expandable region, or multiline block (explicitly forbidden by the Fixed Layout Contract).
- **`useEffect` chains copying controller props into local state** (UI-SPEC §Preact and State Ownership; CLAUDE.md Signals guidance). Capsule content = computed derivation over props/signals.
- **Reusing `drawLosange` for C-04 markers:** it hardcodes gold colors + selection/hover shadows; parameterize or add a dedicated function.
- **Tailwind arbitrary values from the reference file:** the reference is color/design only; production uses BEM CSS in `physicsPaintStudio.css` (D-04 + phase boundary).
- **Native `disabled` on guarded controls:** kills focusability and tooltip access (contract requires focusable guarded controls).

## Common Pitfalls

### Pitfall 1: Breaking the drag machinery while recomposing cells
**What goes wrong:** The 962-line strip carries the complete D-07/D-09/D-22/D-24 drag system (pointer capture, 6px threshold, edge scroll rAF, target-signature re-hit-test, focus restoration, caret classes `roto-drag-target-before/after`, committing treatment) keyed to `data-roto-app-frame` / `data-roto-kind` / `data-roto-key-id` attributes.
**Why it happens:** Geometry cutover (13px→18px, lane restructure) tempts a rewrite of the cell render block.
**How to avoid:** Change cell CSS and band structure only; preserve every `data-roto-*` attribute, class hook, pointer handler, and the `classifyRotoDragTarget` hit-test path (`document.elementFromPoint` + `closest('[data-roto-app-frame]')`). The occupied-cell midpoint boundary logic (strip line 444–446) depends on cell rects — it survives width changes automatically, but only if the attributes stay.
**Warning signs:** Drag preview/commit UAT regressions; `data-roto-*` selectors missing in DOM.

### Pitfall 2: Ruler/cell misalignment after pitch change
**What goes wrong:** Ruler ticks are flex-distributed across a hardcoded 1800px while cells are a fixed-pitch grid; changing cell width to 18px without deriving the shared width desynchronizes ruler marks from cells.
**How to avoid:** One derived constant (`120 frames × 18px = 2160px`) feeding ruler width, lane width, and cell grid; tick every 3rd frame at 54px pitch. Remove the inline `style={{ width: '1800px', minWidth: '1800px' }}` (strip line 847).
**Warning signs:** Tick labels drift off cell boundaries at scroll extremes.

### Pitfall 3: Existing source-contract tests failing after icon-only cutover
**What goes wrong:** `PhysicsPaintWorkflowStrip.test.ts` asserts text-button markup (`>Copy Script</button>`, `>Delete</button>` ordering) and existing copy strings ("Generated frame {frame} is render-only." appears in BOTH the disabled-status template and a test assertion) — icon-only buttons and stack deletion break these.
**How to avoid:** Update the test file in the same task as the recomposition (TDD: update contract tests FIRST to the new icon/aria-label/capsule assertions, watch them fail, then implement). Never leave stale assertions for a later wave.
**Warning signs:** `vitest run` failures in the strip test after the first recomposition commit.

### Pitfall 4: Double tooltips (native + styled)
**What goes wrong:** Cells and controls keep `title` while gaining the styled tooltip → both fire, native one at OS timing.
**How to avoid:** Remove `title` from every surface that adopts the styled tooltip (icon row, cells, capsule, interpolation pill). The cell render currently sets `title={dragTitle}` (strip line 901) — route that copy through the styled tooltip instead. Keep aria-labels unchanged.
**Warning signs:** Two overlapping tooltips after 1s hover in UAT.

### Pitfall 5: Selection guard breaking legitimate interactions
**What goes wrong:** App-wide `user-select: none` interferes with number-input editing, LOG text selection, or contenteditable.
**How to avoid:** Use the exact contract CSS with its four exceptions; verify `.physics-paint-log-messages` remains selectable in UAT; do not broaden the exception list.
**Warning signs:** User cannot select LOG text or edit fps/N inputs.

### Pitfall 6: Close button bypassing the close-flush path
**What goes wrong:** A new header close button that destroys the window directly skips the `onCloseRequested` flush (`usePhysicsPaintParentBridge.ts:30`) and the Studio `usePhysicsPaintCloseFlush` (PhysicsPaintStudio.tsx:568).
**How to avoid:** Close intent calls `getCurrentWindow().close()` (browser bridge mode: `window.close()`), which routes through the existing guarded close path. Studio owns this handler; the strip receives a plain `onClose?: () => void` prop.
**Warning signs:** Unsaved-paint loss on header close vs OS-chrome close parity.

### Pitfall 7: Marker coordinate mismatch (layer-local vs timeline-global frames)
**What goes wrong:** `rotoKeyFrames` are layer-local physical `appFrame`s; the FX row draws at timeline-global frames (`fxTrack.inFrame + local`). Drawing at raw appFrame places markers at wrong positions for layers with nonzero inFrame.
**How to avoid:** Mirror the existing `startFrame + kf.frame` computation (TimelineRenderer.ts:1485) and unit-test the exported geometry helper with a nonzero inFrame case.
**Warning signs:** Diamonds offset from the standalone strip's key positions when the layer doesn't start at frame 0.
