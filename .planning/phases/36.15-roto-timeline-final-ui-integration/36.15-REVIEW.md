# Phase 36.15: Code Review Report

**Reviewed:** 2026-07-26T00:00:00Z
**Depth:** standard
**Files Reviewed:** 26
**Status:** issues_found

## Summary

Reviewed the full phase 36.15 surface: styled tooltip controller, guarded icon actions, strip geometry/drag session, status capsule, resizable sidebar sections, canvas roto key diamonds, selection guard, script clipboard controller, and the timeline/store wiring. The event-listener discipline in the new code is generally good (tooltip Escape listener, pane resize drag, and roto drag session all have idempotent cleanup with pointer-capture guards). No security issues found: tooltip content is text-children only, no `dangerouslySetInnerHTML`, drag focus restoration escapes keyIds before building attribute selectors.

The most significant defect is pre-existing from 36.14 but reachable through this phase's reviewed files and routine interaction: the Delete/Backspace keyboard path calls a controller action that throws synchronously when no key is selected. Also found: imprecise sidebar resize drag math (percentage base includes the fixed 64px of grab handles), unguarded `releasePointerCapture` in the custom timeline scrollbar, and a documented "stable bundle" contract that is not actually stable because ten `computed()` signals are recreated on every render.

## Critical Issues

### CR-01: Delete/Backspace shortcut throws an uncaught synchronous error when no Roto key is selected

**File:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:578-584, 297-305` (wired unguarded at `app/src/components/physic-paint/PhysicsPaintStudio.tsx:830` and `app/src/components/physic-paint/view/physicsPaintStudioKeyboard.ts:90-101`)
**Issue:** `ensureSelectedKeyId` throws `Error('No selected Roto key.')` synchronously when `getSelectedKeyId()` returns null. `deleteRotoFrame` (declared `(): Promise<boolean>`) invokes it before returning the promise, so the throw escapes synchronously to the caller. The strip button is guarded (`if (!canDeleteRotoKey) return`), but the keyboard path is not: `dispatchPhysicsPaintStudioKeyDown` calls `actions.deleteRotoKey()` on any Backspace/Delete press whose target is not an interactive element — a routine state (cursor on an empty frame, no real keys yet, or selection cleared after navigation). Every such keypress produces an uncaught exception out of the keydown listener. Introduced in 36.14-06 (6946d26d) but reachable and unfixed in the reviewed surface.
**Fix:**
```ts
// useRotoTimelineActions.ts — fail soft instead of throwing
function ensureSelectedKeyId(input: RotoTimelineActionsInput): string | null {
  return input.getSelectedKeyId?.() ?? null;
}

const deleteRotoFrame = useCallback((): Promise<boolean> => {
  const selectedKeyId = ensureSelectedKeyId(input);
  if (!selectedKeyId) {
    input.publishStatus?.('Select a real Roto key to delete.');
    return Promise.resolve(false);
  }
  return runPhysicalAction({ intent: { kind: 'delete-key', selectedKeyId }, ... });
}, [runPhysicalAction, input]);
```
Apply the same guard to `insertRotoFrame` (currently only safe because the strip button guards it). Alternatively, gate the keyboard dispatch on `rotoPhysicalActions.canDeleteFrame.value` in `usePhysicsPaintStudioKeyboard`.

## Warnings

### WR-01: Sidebar resize drag math uses the full layout height (including the fixed 64px of grab handles) as the percentage base

**File:** `app/src/components/physic-paint/PhysicsPaintRightPanel.tsx:331-362, 396`
**Issue:** `startPaneResize` computes `split = ((clientY - rect.top) / rect.height) * 100` where `rect` is the whole `.physics-paint-right-pane-layout`, but the grid rows are `${brushSplit}fr 32px ${toolSplit}fr 32px ${...}fr` — the fr shares only distribute `rect.height - 64px`. The handle therefore never tracks the pointer exactly; the offset grows with pointer distance from the top (up to `y * 64 / H` px — ~24px at y=300 in an 800px sidebar). Additionally, `resize(event.clientY)` fires once at pointerdown from wherever inside the 32px band the user pressed, so the split jumps at drag start. Handle 2 has the same flaw plus a missing 32px offset for handle 1 (`split - startBrush` ignores the first handle band).
**Fix:** Compute shares against the distributable height and subtract the handle bands:
```ts
const distributable = rect.height - 64; // two 32px handles
// handle 'brush':
const split = ((clientY - rect.top) / distributable) * 100;
// handle 'tool' (rows above: brushPx + 32px handle):
const brushPx = (startBrush / 100) * distributable;
const toolShare = ((clientY - rect.top - 32 - brushPx) / distributable) * 100;
```
Also capture the pointer's offset within the 32px band at pointerdown and subtract it during the drag so the handle does not jump.

### WR-02: Custom timeline scrollbar drag: unguarded releasePointerCapture, no pointerId filter, no unmount cleanup

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:814-842`
**Issue:** `handleTimelineScrollbarPointerDown` calls `target.releasePointerCapture(upEvent.pointerId)` unconditionally in the shared pointerup/pointercancel handler. Pointer capture is implicitly released on pointerup/pointercancel, and on the pointercancel path the pointer may no longer be active — `releasePointerCapture` then throws `NotFoundError`, an uncaught DOMException inside the listener. The pointermove handler also ignores `event.pointerId`, so a second simultaneous pointer (touch) hijacks the scroll, and the target-attached listeners are never removed if the strip unmounts mid-drag. Contrast with `createPhysicsPaintPaneResizeDrag` in the same phase (PhysicsPaintRightPanel.tsx:75-102), which guards with `hasPointerCapture` and filters pointerId — the two drag helpers are inconsistent.
**Fix:** Follow the pane-resize pattern: check `event.pointerId === event.pointerId captured at down` in move/up, guard with `if (target.hasPointerCapture(id)) target.releasePointerCapture(id)`, and register the cleanup in a ref cleared by the strip's unmount effect.

### WR-03: Documented "stable physical timeline action bundle" is recreated on every render

**File:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:225-234, 518-537`
**Issue:** Ten `computed(...)` signals (`canInsertFrame`, `insertDisabledReason`, etc.) are created in the hook body, not inside `useMemo`/`useSignal`. Every Studio render therefore creates ten new computeds; since they are all in the `physicalActions` `useMemo` dependency list, the memo recomputes every render and the bundle identity changes every render — directly contradicting the interface docstring ("Stable physical timeline action bundle exposed by useRotoTimelineActions"). Any consumer memoizing on the bundle (the workflow strip receives it as a prop) re-renders on every Studio render, and there is a stale-closure window: between a store mutation and the Studio re-render it triggers, a dependency signal change (e.g., `selectedKeyId`, `pendingOperationId`) re-evaluates computeds whose captured `input.getRotoKeyRecords` closure still returns the previous render's records array.
**Fix:** Wrap the computeds in a single `useMemo(() => ({ canInsertFrame: computed(...), ... }), [input.pendingOperationId])` (the getters already read live values through `input`, which is recreated per render and read at evaluation time), or hoist them to `useSignal`-backed stable computeds created once per hook instance. At minimum, correct the docstring if per-render recreation is the accepted design.

### WR-04: Color box and hue strip drag refs are never reset on pointercancel

**File:** `app/src/components/physic-paint/PhysicsPaintRightPanel.tsx:411-417, 431-437`
**Issue:** `draggingColorBox.current` / `draggingHue.current` are set true on pointerdown and cleared only on pointerup. On `pointercancel` (touch interruption, OS gesture, pen leaving digitizer range) the ref stays true; the implicit capture release then lets any later pointermove over the element recolor the brush without a press. The new pane-resize helper in the same file handles `pointercancel`/`lostpointercapture` correctly, so this is an inconsistent leftover in the same component.
**Fix:** Add `onPointerCancel={() => { draggingColorBox.current = false; }}` (and the same for the hue strip), or switch to the shared `createPhysicsPaintPaneResizeDrag`-style helper with a `lostpointercapture` guard.

**Issue:** The dependency list includes `frameCells` and `keyIdByAppFrame`, neither of which is referenced inside the callback (hit-testing reads `cell.dataset` directly). The extra deps cause needless callback invalidation whenever the frame window or records change.

### IN-04: Separator pointerdown `preventDefault()` blocks mouse focus on the keyboard-resizable handles

**File:** `app/src/components/physic-paint/PhysicsPaintRightPanel.tsx:332`
**Issue:** `startPaneResize` calls `event.preventDefault()`, which suppresses focus on click — the two `role="separator"` handles support ArrowUp/ArrowDown keyboard resizing but cannot be focused by clicking; only Tab reaches them. Minor a11y regression for a control that advertises keyboard interaction.
**Fix:** Call `event.preventDefault()` only after capture succeeds, or explicitly `(event.currentTarget as HTMLElement).focus()` inside `startPaneResize`.

### IN-05: `cssEscape` does not cover newline/control characters; `querySelector` can throw on malformed selectors

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:225-227, 641, 747`
**Issue:** `cssEscape` only escapes `"` and `\`. `isBoundedKeyId` (useRotoTimelineActions.ts:565-567) accepts any string up to 256 chars, so a keyId containing a newline or other CSS string-breaking character would make the `[data-roto-key-id="..."]` selector a parse error; `scroller.querySelector` then throws `SyntaxError` uncaught inside the drag focus-restoration path. Resolver-generated keyIds are safe today, but the boundary accepts untrusted-shaped input.
**Fix:** Use the platform `CSS.escape()` on the keyId with an attribute-selector form that tolerates it (e.g. `[data-roto-key-id="${CSS.escape(keyId)}"]` is for identifiers — for quoted strings, escape `"`, `\`, and newline via `\\A `), or wrap the `querySelector` calls in try/catch.

### IN-06: Signal writes executed in the Studio render body

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:238-244, 606-607, 715-716, 797`
**Issue:** `rotoScript.updateEngine(...)`, `rotoScript.updateSource(...)`, `resetRotoKeySessionRef.current = ...`, `rotoNavigation.configureRuntimePort/configureDisplayPort(...)`, and the route-ref assignments all run during render. The controllers' identity guards make steady-state renders no-ops, but when the source genuinely changes, `updateSource` writes `sourceState.value` mid-render — a signal write during another component's render that the strip subscribes to via `rotoScript.availability`. This is the codebase's established controller-sync pattern and UAT passed, so it is flagged as a fragility note rather than a bug: any future change that removes an identity guard or adds a new subscription will produce re-entrant render loops.
**Fix:** Longer term, move controller synchronization into a `useEffect` keyed on the source tuple; document the invariant that these calls must remain idempotent during render.
