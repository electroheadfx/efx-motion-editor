## Summary

Reviewed the phase 43.5 source changes: the ToolCase toolbox popover (relocated Interpolation + Key Spacing controls), the directional Push tool (mode-toggle arming, pointer-resolved anchor, suffix moved set, rigid atomic translation, clamp authority, straddle guard, gap/break derivation, one Undo/Redo), and the async settlement re-arm watchdog.

The push set/clamp/break authorities in `physicsPaintRotoPhysicalResolver.ts` are well-structured: the moved set is derived from canonical records/loopClips only, the clamp is a single pure authority shared by the strip preflight and the resolver commit branch (preview-is-the-commit), and the straddle guard fails closed. The `usePhysicsPaintPushDrag` gesture session correctly mirrors the UAT-approved Key Rail drag session and keeps resolver/store/model concerns behind injected ports. The Preact/Signals usage is consistent with CLAUDE.md (signals for shared armed state, `pushPaintTick` subscription instead of effect-mirrored state).

Three WARNING-level issues were found: a stale blocked-direction tooltip/cursor when a blocked drag becomes valid, a round-trip push that leaves a persistent incoming interpolation break on the anchor, and a re-arm watchdog that can undo a manual disarm. Two INFO-level issues concern the click-suppression timeout race and a stale session ref on early return.

## Warnings

### WR-01: Stale blocked-direction tooltip and not-allowed cursor persist after a blocked drag becomes valid

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:1469-1475`
**Issue:** The `onPreviewChange` handler clears `pushDragBlocked` only when `preview === null`. When a drag is live in a blocked direction (clamp fails, prepare rejects, `onBlocked` sets `pushDragBlocked`), and the pointer then moves back so the clamp succeeds and prepare produces a valid preview, `onPreviewChange` is called with a non-null preview and `pushDragBlocked` is NOT cleared. The guarded tooltip (`pushHoverGuardCopy`, line 2279) and the `not-allowed` cursor (`data-push-hover-invalid`, line 2342) therefore stay visible while the drag is actually valid again. The ghost reappears but the blocked treatment lingers until the drop.
**Fix:** Clear the blocked verdict whenever a valid preview is produced, not only on null preview:
```ts
onPreviewChange: (preview) => {
  if (preview === null) {
    pushDragBlocked.value = null;
    pushBlockedPointer.value = null;
  } else {
    // A valid preview means the drag is no longer blocked in the locked direction.
    pushDragBlocked.value = null;
    pushBlockedPointer.value = null;
  }
  pushPaintTick.value += 1;
},
```

### WR-02: Round-trip push (right then left back to a non-zero position) leaves a persistent incoming interpolation break on the anchor

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalResolver.ts:2520-2533`
**Issue:** `derivePhysicPaintPushIncomingInterpolationBreakKeyIds` adds the opened-gap break to the moved set's first key on Push Right, but the reverse-close normalization only removes it when the moved set returns to frame 0 (`movedSetBounds.firstFrame + deltaFrames === 0`). A Push Right by N followed by a Push Left by N that returns the anchor to a non-zero original position (e.g. anchor at frame 4, fixed side ending at frame 2) leaves the break on the anchor. The interpolation state then differs from the pre-push state: the gap frame that was previously interpolated stays empty. The comment documents the frame-0 case only, so the non-zero return is an unhandled gap in the normalization.
**Fix:** Remove the opened-gap break whenever the reverse push closes the gap — i.e. when the moved set's first key lands exactly one frame after the fixed side's end (or at frame 0). The resolver already computes `leftBoundary` in `derivePhysicPaintPushSet`; thread it into this function and delete the break when `movedSetBounds.firstFrame + deltaFrames === leftBoundary` (with `leftBoundary === 0` covering the current frame-0 case).

### WR-03: Re-arm watchdog can undo a manual disarm between commit settlement and mutation-lease release

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:1248-1262`
**Issue:** After a successful push, `onDropCommit` (lines 1418-1440) sets `rearmAnchorRef.current` and keeps it on acceptance. The tool stays armed until the mutation-lease release disarms it (Studio effect cleanup, `PhysicsPaintStudio.tsx:578`). If the user re-clicks the Push button to disarm during that async settlement window, `togglePushTool()` disarms, but the watchdog effect then fires (armed signal changed to false, `rearmAnchorRef.current` still set) and re-arms the tool — undoing the user's explicit disarm. The tool also re-selects the moved rail, which the user may not expect after a manual disarm.
**Fix:** Clear `rearmAnchorRef.current` when the user manually disarms the tool (e.g. in the Push button's `onClick` before `togglePushTool()`, or in the disarm-on-any-other-toolbar-action handler at line 2626), so the watchdog only re-arms for the settlement disarm it was designed for.

## Info

### IN-01: Click-suppression clear races the post-drop click dispatch

**File:** `app/src/components/physic-paint/hooks/usePhysicsPaintPushDrag.ts:205-209`
**Issue:** `clearSuppressionSoon` clears `suppressNextClickRef` via `setTimeout(..., 0)`. The browser dispatches the post-drop `click` event after `pointerup`; if the timeout task runs before the click task, the suppression is cleared before `consumeClickSuppression()` reads it, and the post-drop click passes through as a cursor navigation in `handleLanePushClickCapture` (`PhysicsPaintWorkflowStrip.tsx:1565-1586`). In practice the click is usually dispatched in the same task as pointerup, so this is timing-dependent and fragile rather than a confirmed defect.
**Fix:** Clear the suppression in the click handler itself (after `consumeClickSuppression()`), or use a microtask/`queueMicrotask` so the clear cannot preempt the click task.

### IN-02: Stale session refs when the hook's `onPointerDown` returns early

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:1545-1562`
**Issue:** `handleLanePushPointerDownCapture` sets `armedAnchorRef.current` and `pushSessionRef.current` before calling `pushDragApiRef.current?.onPointerDown(event)`. If the hook returns early (e.g. `sessionRef.current` already non-null from a previous session that missed its pointerup), the refs are left set with no active session, and a later `clampDestination`/`prepareAtDestination` reads a stale session. Edge case (requires a missed pointerup), but the refs should be cleared when the hook declines the pointer-down.
**Fix:** Have the capture handler check the hook's return or clear the refs when `onPointerDown` does not start a session, e.g. by having the hook expose whether a session was accepted.
