## Summary

Phase 43.5 is a **pure additive composition over already-closed architecture** — the same shape as Phases 43.3 and 43.4. Every mechanism this phase needs exists in the codebase and was read this session: the closed intent union + strict parser + canonical serializer in `app/src/types/physicPaint.ts`, the pure resolver with per-intent dispatch branches and stable-key-owned break derivation in `physicsPaintRotoPhysicalResolver.ts`, the prepare/commit publication pair in `useRotoTimelineActions.ts`, the injectable pointer-session drag hooks (`usePhysicsPaintGroupRailDrag.ts`, `usePhysicsPaintKeyRailDrag.ts`), the single product-reason mapper idiom, and the styled-tooltip/guarded-copy presentation idiom. The UI-SPEC (43.5-UI-SPEC.md, approved 2026-08-17) locks all presentation geometry, copy, and color; research here covers the implementation seams.

The toolbox consolidation is a relocation, not a rebuild: the Interpolation pill (strip L547–549) and the Key Spacing form (strip L2102–2141) move into a Studio-local anchored popover with identical props/callbacks — the state authority stays in the timeline/store. The Push tools add one new closed-union intent (direction field, per Claude's-discretion D-ref) whose resolver branch composes the proven rigid-translation algebra (`buildMoveGroupClipCandidate` / `buildMoveGroupCandidate`) over the directional suffix/prefix set of Rails, the proven clamp pattern (`clampPhysicPaintKeyRailDragDestination`), and the proven break derivation (`deriveMoveGroupIncomingInterpolationBreakKeyIds`), plus one new fail-closed guard (shared-source straddle).

**One cross-cutting hazard found:** the keyboard dispatcher's Delete guard (`physicsPaintStudioKeyboard.ts:42`) suppresses Delete/Backspace whenever any `[role="dialog"]` exists in the document. The popover is `role="dialog"` (UI-SPEC locked), which would break D-02 ("Delete/Backspace keep their normal routing while the popover is open"). The plan must refine that guard (e.g. scope to `aria-modal="true"` or exclude the toolbox popover) — see Pitfall 1.

**Primary recommendation:** mirror the 43.3/43.4 plan decomposition — Wave 0/1 extends the transport union + resolver intent + break derivation + clamp authority with tests; Wave 2 adds the prepare/commit pair + product-reason mapper; Wave 3 adds the popover relocation and the armed push session hook + strip paint; Wave 4 native UAT from a fully restarted frozen-code session.

### Pattern 3: Break derivation for opened/closed gaps (43.1 machinery, complete-collection replacement)

**What:** The resolver emits the complete next `incomingInterpolationBreakKeyIds`; `finalizeProposal` threads it through validation, revision, and history.
**Example — the 43.3 move-group derivation (`physicsPaintRotoPhysicalResolver.ts:2292-2355`)** implements the two rules the push generalizes:

- (a) Vacated-gap ownership is a **pre-move fact**: select the next external real key from pre-move frames, carry only its keyId through the translated mapping (L2314-2330).
- (b) A source-attached move opens a landing gap only against an external predecessor; the break belongs to the moved set's first source key (L2332-2346).

For Push Right: the opened gap sits between the fixed left side and the moved set's first key ⇒ that first key owns the break (travels with the set). For Push Left: the opened gap sits between the moved set's right edge and the fixed right side ⇒ the fixed right side's first key owns/reuses the break. A later reverse push that closes the gap normalizes the collection (CONTEXT carried D: existing breaks reused, never duplicated). `finalizeProposal` receives `incomingInterpolationBreakKeyIds` as its last parameter at every existing call site (e.g. resolver L3886).

- **Deviation for push:** the anchor is any non-empty cell OR rail band (D-07), and plain click under threshold performs normal frame cursor navigation while staying armed (D-09) — the session must not swallow the sub-threshold click; it lets the strip's normal cell click run.

### Pattern 6: Popover via existing idioms (no library)

- `useStyledTooltip` (`PhysicsPaintStyledTooltip.tsx`, read this session) provides the hover/focus/Escape-hide tooltip idiom reused for the ToolCase guarded tooltip.
- The popover itself is a Studio-local anchored surface: `role="dialog"`, `aria-modal="false"`, `aria-label="Timeline tools"`, outside-pointerdown + Escape dismiss, no focus trap, no backdrop (UI-SPEC T1/T2 locked geometry: bottom edge 4px above the strip, width 232–280px, `max-height: 240px`, z-index 60).
- Relocated controls render with **existing classes and props verbatim**: interpolation pill (`physics-paint-pill physics-paint-pill--interpolation physics-paint-roto-interpolation-controls`, strip L547-549) and spacing form (`physics-paint-pill physics-paint-pill--apply-spacing physics-paint-roto-force-spacing-controls`, strip L2104-2134). `isPhysicsPaintShortcutTarget` already excludes `input/textarea/select` (`physicsPaintStudioKeyboard.ts:31-37`), so typing in the Set Key Space input never triggers timeline shortcuts.

### Anti-Patterns to Avoid

- **Second toolbox state authority:** the popover must not mirror interpolation/spacing values into local state; it edits through the existing callbacks (`onRotoInterpolationEnabledChange`, force-spacing handlers). D-03 spec invariant.
- **Reimplementing clamp math in the view layer:** the ghost destination must come from the same exported pure clamp the resolver commits (43.3 D-05).
- **Copying `buildMoveGroupCandidate`'s collision rejection:** push clamps and commits; rejection only when zero valid movement exists (43.3 PATTERNS critical deviation, carried).
- **Copying the single-range `visibleRanges` rebuild:** every lifecycle field (`phaseOrigin`, `originalEndExclusive`, every `visibleRanges` entry, every `frameOverrides` appFrame) translates by the same delta (43.3 D-13; `buildMoveGroupNextLoopClips` L1862-1922 is the proven implementation).
- **Armed state in the document/history/persistence:** session-only Signals (D-19).
- **New logic in `PhysicsPaintStudio.tsx`:** focused sibling hook/module (43.4-02 precedent; CLAUDE.md state-boundary guidance).

## Common Pitfalls

### Pitfall 1: `role="dialog"` popover silently kills Delete/Backspace routing (D-02 violation)

**What goes wrong:** `isPhysicsPaintRotoDeleteTarget` (`physicsPaintStudioKeyboard.ts:42`) returns false when `target.ownerDocument.querySelector('[role="dialog"], [aria-modal="true"]')` finds any dialog. The toolbox popover is `role="dialog"` (UI-SPEC locked), so while it is open, Delete/Backspace stop deleting keys — violating D-02 ("Delete/Backspace and other shortcuts keep their normal routing while the popover is open").
**Why it happens:** the guard was written for modal dialogs (sole-occurrence delete confirmation) that genuinely suspend timeline shortcuts.
**How to avoid:** refine the guard to key off `aria-modal="true"` only (the popover is explicitly `aria-modal="false"`), or exclude the toolbox popover by a dedicated marker. Add a regression test: popover open + Delete on a selected key still routes.
**Warning signs:** native UAT step 3 (popover dismissal/shortcut routing) fails on Delete while popover open.

### Pitfall 2: Escape double-handling across layers

**What goes wrong:** the global dispatcher's bubble-phase Escape calls `collapseRotoSelection` (`physicsPaintStudioKeyboard.ts:139-155`); the drag session's capture-phase Escape uses `stopImmediatePropagation`; the popover needs its own dismiss. Without layering, one Escape could cancel a drag AND collapse selection, or close the popover AND disarm.
**Why it happens:** three Escape consumers with different registration phases.
**How to avoid:** follow the locked rule "one Escape handles at most one layer" (UI-SPEC keyboard contract): active push drag (capture, stopImmediatePropagation) > popover open > armed tool disarm > existing collapse. The drag-session capture idiom already wins during gestures; the popover/armed layer should be handled before `collapseRotoSelection` in the dispatcher (or via capture with suppression), with the armed disarm not also collapsing selection.
**Warning signs:** UAT step 5 (armed lifecycle) or 3 (dismissal) shows selection collapse on disarm-Escape.

### Pitfall 3: Break-unaware proposal version (stale-authority false pass)

**What goes wrong:** a prepare path that fingerprints the revision without the break collection accepts a commit whose breaks changed mid-gesture.
**Why it happens:** the pre-43.3 `buildProposalVersion` omitted the break collection (43.3 RESEARCH Pitfall 1).
**How to avoid:** copy `buildGroupDragProposalVersion(records, interpolation, loopClips, incomingInterpolationBreakKeyIds, launch)` (`useRotoTimelineActions.ts:1745`) — thread breaks into both the resolver input and the fingerprint.
**Warning signs:** commit-time stale rejection tests fail; a concurrent Scissor/break edit is invisible to the push commit guard.

### Pitfall 4: Straddle guard enforced at commit but not at hover (or vice versa)

**What goes wrong:** D-17 requires the straddle rejection to be preflight at hover with identical copy; two code paths diverge.
**Why it happens:** hover preflight derives the prospective set in the view layer while the resolver re-derives it at commit.
**How to avoid:** one shared pure derivation (anchor → directional set → straddle check, keyed on `sourceCycleId` shared between a moved-set source-attached Group and any fixed-side Group) consumed by both the hover preflight port and the resolver branch — same shape as the clamp authority pattern. Note: `getPhysicsPaintRotoSourceCycleId(sourceKeyIds)` exists in `physicsPaintRotoSpacingSelection.ts:42` and `PhysicPaintRotoLoopRange.sourceCycleId` is already derived (`physicsPaintRotoPhysicalResolver.ts:4064`).
**Warning signs:** guarded tooltip copy and rejection copy disagree; drag starts on a straddled anchor.

### Pitfall 5: Moved set containing only duplicated placements reports no-change

**What goes wrong:** placement-only moves leave the key mapping identity-equal; `computeChanged` on the mapping returns false and the commit rejects as "This move would not change the timeline."
**Why it happens:** 43.3 hit exactly this regression for duplicated placement drags; the fix made `changed` reflect the placement delta (`destination !== clip.placementStart`, resolver L3911 comment).
**How to avoid:** push `changed` must account for both key-mapping deltas and `nextLoopClips` placement deltas.
**Warning signs:** pushing a set whose only movable content is duplicated placements publishes nothing.

### Pitfall 6: Attachment/straddle decided from UI state instead of canonical facts

**What goes wrong:** the strip decides source-attachment from presentation props; stale presentation misclassifies.
**Why it happens:** attachment is presentation-derivable but authority must be canonical (43.3 Pitfall 4): `placementStart === first source key frame` (resolver L2053: `const attached = frameByKeyId.get(clip.sourceKeyIds[0]) === clip.placementStart;`).
**How to avoid:** resolver derives attachment and straddle from canonical records/clips only; the view passes anchor + delta, never attachment flags.

### Pitfall 7: Strip geometry regressions from the new buttons

**What goes wrong:** the ToolCase + Push pill add width/height and push the strip past 161px or cover cells/rails.
**Why it happens:** the interpolation pill lives in the **header** (`PhysicsPaintWorkflowStaticChromeImpl`, L494-561) while the Key Spacing form lives in the **bottom action row** (L2102-2141) — the freed space is in two different rows; the ToolCase button goes at the interpolation pill's header spot (before Close) and the Push pill in the freed bottom-row space per UI-SPEC T3/D-05.
**How to avoid:** reuse `physics-paint-roto-key-icon-button` (26px) exactly; CSS strictly additive; verify at 1280×720 (prompt acceptance 13).
**Warning signs:** strip height change, clipped toolbar, covered spacing-proxy cells while popover open.

### Pitfall 8: Test files that vitest never runs

**What goes wrong:** new tests named `*.test.tsx` are silently excluded — `app/vitest.config.ts:5` includes only `src/**/*.test.ts`.
**How to avoid:** name every new test file `*.test.ts` (the repo even uses `PhysicsPaintKeyRail.test.tsx.test.ts` companions for tsx-adjacent coverage).
**Warning signs:** `vitest run` count doesn't increase after adding tests.

### Pitfall 9: Optimistic paint before parent acknowledgement

**What goes wrong:** originals translate/dim during drag, or gap/break state appears before the accepted document.
**How to avoid:** all preview paint is session-only and `aria-hidden`, originals stay at 100% until commit; the strip consumes only the retained publication for paint (43.3 D-01/D-17 carried; UI-SPEC state precedence).

## Open Questions

1. **Exact push set boundary when the anchor is a generated frame inside a Group vs. a Key Rail cell**
   - What we know: D-07 — any non-empty cell resolves to the containing Rail; a frame inside a Group targets the complete Group; Key Rail anchor resolves to the derived segment.

   - What we know: UI-SPEC — readout updates at pointer-move cadence on the existing polite channel; never on hover.

   - What's unclear: whether the popover mounts inside the strip root (positioned) or via the `createPortal` idiom already imported in `PhysicsPaintStyledTooltip.tsx`.
