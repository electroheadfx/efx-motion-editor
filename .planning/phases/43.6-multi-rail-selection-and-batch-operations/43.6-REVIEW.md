## Warnings

### WR-01: Pending Loop Clip single-click timer is not cancelled when a batch rail-set drag begins — can collapse/mutate the set mid-drag

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:1610` (port contract: `app/src/components/physic-paint/hooks/usePhysicsPaintRailSetDrag.ts:236`)

**Issue:**
The batch rail-set drag hook calls `input.clearClickSequence()` inside `beginDrag()` (usePhysicsPaintRailSetDrag.ts:236) — the one place a pending click sequence is meant to be cancelled before the drag mutates selection. The strip wires that port as a stub: `clearClickSequence: () => {}` (PhysicsPaintWorkflowStrip.tsx:1610; the push-drag port at 1544 is a separate concern and benign). For a set-member Loop Clip rail, `PhysicsPaintLoopClipRail` routes pointerdown to the batch session (`if (props.isSetMember && props.onRailSetDragPointerDown) { props.onRailSetDragPointerDown(event); return; }`, PhysicsPaintLoopClipRail.tsx:260-262) and returns before the rail's own group-drag hook — so the rail's real `clearClickSequence` (which cancels `pendingSingleClickRef`, PhysicsPaintLoopClipRail.tsx:156-159) is never consulted. The batch session's no-op is the only cancellation point, and it does nothing.

Concrete failure: any click on a set-member Loop Clip (plain or modifier) arms the 250 ms single-click timer (PhysicsPaintLoopClipRail.tsx:216-220) that later dispatches `props.onSelectLoopClip(loopId, gesture)`. If the user presses and crosses the drag threshold within that window (typical after the final click that builds the set), the timer fires mid-drag:

- **plain** → Studio's plain branch sets `railSetSelection.value = null` (PhysicsPaintStudio.tsx:1333) → the set collapses under the live drag → the next `prepareAtDelta` reads the now-empty `railSetMoveMembersRef` and fails with `'Rail set move unavailable.'` (PhysicsPaintWorkflowStrip.tsx:1595-1596) → the drop is rejected and the ghost disappears mid-drag.
- **toggle (Cmd/Ctrl-click)** → the clicked member is toggled out of the set mid-drag → the drag silently continues with the reduced member set, violating the all-or-nothing composition contract: the user drags N rails and N-1 move.

This is exactly the interaction `clearClickSequence` exists to prevent; the wiring defeats it.

**Fix:** Wire a real `clearClickSequence` for the batch session. Because the pending timer is per-rail state inside `PhysicsPaintLoopClipRail`, expose a cancellation path from the strip, e.g. a strip-owned registry (ref of `() => void` cancellers) that each Loop Clip rail registers into on mount / de-registers on unmount, and pass a wrapper that invokes every registered canceller:

```ts
// in PhysicsPaintLoopClipRail, when routing to the batch session:
onPointerDown={(event) => {
  if (props.isSetMember && props.onRailSetDragPointerDown) {
    props.onRailSetDragPointerDown(event);
    return;
  }
  onPointerDown(event);
}}
// and have the batch session's clearClickSequence reach this rail's
// clearPendingSingleClick via the strip-level registry instead of a no-op.
```

Cancelling on `beginDrag` (threshold crossed), not on pointerdown, preserves the double-click-to-open-editor path for set members.

## Info

### IN-01: Render-phase signal write in the rail-set reconcile

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:541-542`

**Issue:** `railSetSelection.value = null` is written during render when the reconcile detects that the stored set no longer matches the canonical ordering (`effectiveRailSetSelection === null`). The write is guarded by `peek() !== null` so it is self-limiting (converges in one extra render) and is documented as mirroring the existing `effectiveSelectedRotoKeyRail` pattern. Still, a signal write during render is a Preact anti-pattern that makes the effective value and the stored value disagree for one frame and can cascade renders in subtler future edits.

**Fix:** Defer the write to a `useEffect` keyed on `effectiveRailSetSelection`, or keep the stored signal always in sync via the reducer call sites; at minimum document that the write is intentionally render-phase and why an effect would be worse here.

### IN-02: Drag-session handlers close over the pointerdown render's input closures

**File:** `app/src/components/physic-paint/hooks/usePhysicsPaintRailSetDrag.ts:189-248`

**Issue:** The session captures `projectDelta`, `clampDelta`, `prepareAtDelta`, and `onDropCommit` from the render in which `onPointerDown` fired. Those closures read `loopResolutionContext`, `frameCells.length`, `incomingInterpolationBreakKeyIds`, etc. from that render. The `railSetMoveMembersRef` ref pattern and the commit-time proposalVersion staleness fingerprint mitigate the risk (a stale commit is rejected), but the live clamp/preview can momentarily use pre-revision authority data if a document revision lands mid-drag.

**Fix:** Either document the staleness contract explicitly (preview is authoritative only for the render it was derived from; commit re-validates), or route the volatile inputs through refs so the session reads the latest data on every pointermove.

### IN-03: `railSetSnapshots` map grows without bound within a session

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRailSetSelection.ts:264`

**Issue:** `recordRailSetSnapshot` appends an entry for every accepted command — including every undo/redo command's own acceptance — keyed by unique operationIds, and the map is pruned only by `clearRailSetSnapshots()` on launch replacement. Long sessions accumulate entries that will never be looked up again (lookups always use the original replay provenance id).

**Fix:** Prune snapshots when the undo stack advances (e.g., a new mutation invalidates redo snapshots) or cap the map, so a session does not accumulate unbounded entries.
