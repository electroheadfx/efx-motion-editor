## Warnings

### WR-01: Plain Loop Rail click does not disarm an armed Solo — the only rail-selection change path that skips disarm

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:1415-1450` (contrast: `handleSelectRotoKeyRail` plain path at 1349-1363; invariant comment at 1296-1298)

**Issue:**
`clearRotoLoopSelection` (1295-1302) documents the locked contract: "every rail-selection setter routes through this clear — ANY rail-selection change/clear disarms an armed Solo." Every selection-change path honors it — launch replacement (185), Select All (386), mutation-lock entry (653), key-rail plain click (1351, via `clearRotoLoopSelection()`), key-rail modifier gestures (1333), loop modifier gestures (1399), loop clear (1370), spacing-proxy selection (2016), and the Escape set-collapse (1950).

The single exception is `handleSelectRotoLoopClip`'s **plain-click success branch** (1415-1450): it sets `railSetSelection.value = null` and writes `selectedLoopClipIds`/`selectedLoopClipId` directly, never calling `disarmSolo()` or `clearRotoLoopSelection()`. Concrete consequence: arm Solo on Loop A (single-rail set of one, D-15), then plain-click Loop B. The set collapses, the single-rail selection moves to B, and Solo **stays armed** — `getSoloWindow` (1154-1161) and the armed-solo capsule (PhysicsPaintWorkflowStrip.tsx:1983-1994) both fall back to the single-rail selection, so playback silently retargets to solo Loop B while the user never asked for that. The equivalent plain click on a Key Rail disarms Solo. The same gap is reachable via the double-click-to-open-editor path, which plain-selects first (PhysicsPaintLoopClipRail.tsx:234).

Whichever behavior is intended (disarm vs. follow), the two single-rail plain-click paths must agree, and the documented invariant says disarm.

**Fix:** Disarm in the plain branch before applying the new selection (do not call `clearRotoLoopSelection()` — it would clobber the selection being written):

```ts
// Plain click collapses the set into the single-rail path (D-04).
railSetSelection.value = null;
disarmSolo(); // 43.6-06 D-14: a rail-selection change disarms an armed Solo.
```

Add a Studio-level regression test: arm Solo with Loop A selected, plain-click Loop B, assert `isSoloArmed() === false`.

### IN-01: Render-phase signal write in the rail-set reconcile (carried forward, still present)

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:542-544`

**Issue:** `railSetSelection.value = null` is still written during render when reconcile detects a stale set. Guarded by `peek() !== null` so it converges in one extra render, and it mirrors the `effectiveSelectedRotoKeyRail` precedent — but it remains a render-phase signal write, with the effective and stored values disagreeing for one frame.

**Fix:** Defer to a `useEffect` keyed on `effectiveRailSetSelection`, or document why render-phase convergence is required here.

### IN-02: Drag-session handlers close over the pointerdown render's input closures (carried forward, still present)

**File:** `app/src/components/physic-paint/hooks/usePhysicsPaintRailSetDrag.ts:137-310`

**Issue:** The session captures `projectDelta`/`clampDelta`/`prepareAtDelta`/`onDropCommit` from the render in which `onPointerDown` fired. The strip's `clampDelta` reads `rotoKeyRecords`, `loopResolutionContext`, `props.rotoLoopClips`, and `incomingInterpolationBreakKeyIds` from that render's scope (PhysicsPaintWorkflowStrip.tsx:1567-1597). A document revision landing mid-drag leaves the live clamp/preview on pre-revision authority; only `railSetMoveMembersRef` is refreshed, and the commit-time `proposalVersion` fingerprint is the correctness backstop (the stale commit is rejected, but the ghost paint is stale meanwhile).

**Fix:** Route the volatile inputs through refs (as `railSetMoveMembersRef` already does for members), or document the staleness contract at the port declarations.

### IN-03: `railSetSnapshots` map grows without bound within a launch (carried forward, still present)

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRailSetSelection.ts:285-298`; recorder at `app/src/components/physic-paint/PhysicsPaintStudio.tsx:1869-1874`

**Issue:** `recordRailSetSnapshot` is called for **every** accepted command — including every undo/redo acceptance, whose own `operationId` is never looked up again (lookups always use the original replay-provenance command id, line 1877). Entries are pruned only by `clearRailSetSnapshots()` on launch replacement, so a long session accumulates dead entries.

**Fix:** Skip recording for `undo`/`redo` acceptances (their snapshots are unreachable), and consider pruning entries when a new ordinary command truncates the redo branch.

### IN-04: Loop Clip click-sequence canceller registers during render

**File:** `app/src/components/physic-paint/view/PhysicsPaintLoopClipRail.tsx:174-181`

**Issue:** The 43.6 WR-01 fix registers into the strip registry as a render-phase side effect (`if (registrationRef.current === null && props.registerClickSequenceCanceller) { registrationRef.current = props.registerClickSequenceCanceller(clearClickSequence); }`), with unregistration deferred to the mount effect's cleanup. If the target's first render throws after registration (e.g., inside `usePhysicsPaintGroupRailDrag`), the registry leaks a stale canceller that keeps a dead rail's refs alive and fires `clearTimeout` on a defunct timer for every subsequent batch drag. The comment acknowledges the choice, but an effect-only registration is strictly safer at equal cost.

**Fix:** Move registration into the existing mount effect:

```ts
useEffect(() => {
  clearClickSequence();
  registrationRef.current = props.registerClickSequenceCanceller?.() ?? null;
  return () => { registrationRef.current?.(); registrationRef.current = null; };
}, []);
```

### IN-05: Dead ternary in `cancelPhysicalEdit` — both branches identical

**File:** `app/src/components/physic-paint/hooks/useRotoPhysicalEditCoordinator.ts:1239`

**Issue:** `finalizeFailed(pending, before, reason === 'launch-replacement' ? 'settlement-mismatch' : 'settlement-mismatch', ...)` — the conditional is dead code; both arms are `'settlement-mismatch'`. Either a distinct failure reason for launch replacement was intended (improving the failure-output diagnostics), or the conditional should be collapsed.

**Fix:** Pass `'settlement-mismatch'` directly, or introduce a dedicated `'launch-replacement'` reason if the distinction matters for diagnostics.
