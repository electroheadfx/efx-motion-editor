## Warnings

### WR-01: Seed bridge only carries a same-type plain selection — a plain-selected rail of the other type is silently dropped on the first modifier gesture

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:1312-1316` and `1374-1378`
**Issue:** Each modifier handler seeds the rail set only from its own type's single-rail signal: `handleSelectRotoKeyRail` seeds from `selectedRotoKeyRail.value` and ignores `selectedLoopClipId.value`; `handleSelectRotoLoopClip` seeds from `selectedLoopClipId.value` and ignores `selectedRotoKeyRail.value`. Because plain-selecting one rail type clears the other type's signal (line 1346 via `clearRotoLoopSelection`, line 1426 directly), exactly one single-rail selection is ever live — but it can be of the opposite type from the modifier-clicked target. Concretely: plain-select Loop Rail A (`selectedLoopClipId = A`, `selectedRotoKeyRail = null`), then Cmd+click Key Rail B → `singleIdentity` is null → `seedRailSetSelection` returns null → the reducer's toggle creates a fresh one-member set `{B}` and line 1328 clears Loop A. The plain-selected rail is dropped, which is exactly the M1 defect ("carry a plain-selected rail into the rail set on first modifier gesture") this plan closed — but only for same-type gestures. The seeded helper itself is type-agnostic; the Studio wiring is what narrows it.
**Fix:** In both handlers, derive the seed identity from whichever single-rail signal is live, e.g. in `handleSelectRotoKeyRail`:

```ts
const singleIdentity: RailSetIdentity | null = selectedRotoKeyRail.value !== null
  ? { kind: 'key-rail', firstKeyId: selectedRotoKeyRail.value.firstKeyId }
  : selectedLoopClipId.value !== null
    ? { kind: 'loop', loopId: selectedLoopClipId.value }
    : null;
```

(and symmetrically in `handleSelectRotoLoopClip`). If the same-type restriction is deliberate, document it in the 43.6-08 comment, since the helper's contract ("bridges the two disconnected selection tracks") reads as cross-type.

### WR-02: A modifier click inside the double-click window still opens the Loop editor instead of committing set membership

**File:** `app/src/components/physic-paint/view/PhysicsPaintLoopClipRail.tsx:228-245`
**Issue:** The new synchronous-commit branch (241-245) sits *after* the double-click gate (228-234). The gate fires on `hasPendingSingleClick || elapsed <= LOOP_CLIP_FAST_DOUBLE_CLICK_MS (220ms)` without regard to gesture, so a modifier click that follows a plain click within the pending-timer window (250ms) or the fast-double-click window is still treated as open-editor intent: it calls `props.onSelectLoopClip(range.loopId, 'plain')` and `props.onOpenLoopEdit(...)`, discarding the toggle/range/union gesture and opening the Edit Group editor. This contradicts the new comment's own invariant ("a modifier click is never an open-editor double-click intent"), which only holds outside the double-click window. Realistic sequence: user plain-clicks a Loop Rail, then within ~250ms Cmd+clicks it to start a multi-selection → the editor opens unexpectedly and no set is created.
**Fix:** Compute `gesture` before the gate (it already is, at lines 212-218) and bypass the gate for non-plain gestures:

```ts
const hasPendingSingleClick = pendingSingleClickRef.current !== null;
if (gesture === 'plain'
  && (hasPendingSingleClick || (elapsed >= 0 && elapsed <= LOOP_CLIP_FAST_DOUBLE_CLICK_MS))) {
  // ...existing open-editor branch
}
clearPendingSingleClick();
if (gesture !== 'plain') { /* existing synchronous commit */ }
```

## Info

### IN-01: A stale plain-selected identity can be seeded into the set on range/union gestures

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:1316-1317` and `1378-1379` (with reducer behavior at `physicsPaintRotoRailSetSelection.ts:199-200`)
**Issue:** `seedRailSetSelection` validates the identity's shape but not its presence in `orderedRailSetIdentities`. If the single-rail signal points at a since-deleted rail, a `range`/`union` gesture hits the reducer's fail-closed path `if (current === null || current.anchor === null) return selection;` — which returns the *seeded* (stale) set unchanged, so `railSetSelection.value` briefly holds a member absent from the canonical ordering. The render-phase reconcile (PhysicsPaintStudio.tsx:538-544) clears it on the next render, so the window is one render and the gesture simply no-ops — acceptable, but the toggle path self-heals immediately (stale seed → fresh `{target}` set) while range/union do not, an asymmetry worth a comment or a presence check in `seedRailSetSelection`.
**Fix:** Either pass `orderedRailSetIdentities` to the seed helper and return null when the identity is absent, or add a comment noting the render-phase reconcile is the stale authority for seeded sets.

### IN-02: Two divergent `PhysicPaintRotoPhysicalEditOperationKind` unions exist; the 43.6-07 allowlist compiles only via the broad one

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalResolver.ts:172-189` vs `app/src/types/physicPaint.ts:820-849`
**Issue:** The resolver module declares its own narrower operation-kind union (no `'delete-rails'`, no group/play-script kinds) that duplicates the canonical union in `types/physicPaint.ts`. `useRotoPhysicalEditHistory.ts` imports the broad one (line 67), which is why `kind === 'delete-rails'` at line 219 type-checks — but a future edit that switches the import to the resolver's union would turn the new allowlist entries into ts(2367) no-overlap errors. Pre-existing duplication, not introduced by this diff, but 43.6-07 now depends on the distinction.
**Fix:** Re-export or alias the canonical union from `types/physicPaint.ts` in the resolver module (or delete the narrow duplicate) so there is one source of truth.
