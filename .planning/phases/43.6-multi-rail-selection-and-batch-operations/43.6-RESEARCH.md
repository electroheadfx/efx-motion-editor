## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Spec default gestures accepted. **Shift+click** selects the canonical range from the anchor rail to the clicked rail — the range is ordered by canonical first-key frame across all three rail types in one shared ordering. **Cmd/Ctrl+click** toggles one rail in/out of the set.
- **D-02:** The range anchor is the **last plain-clicked rail** (Finder/VS Code behavior). Shift+click replaces the set with the anchor→clicked range; the anchor stays put. Cmd/Ctrl+click toggle does not move the anchor.
- **D-03 (user-locked):** **Cmd+Shift+click ADDS** the anchor→clicked range to the current set (union — Finder behavior). Already-selected rails in the range stay selected; no toggling. The anchor does not move.
- **D-04:** Set collapse/clear: plain click on any rail collapses the multi-set to that single rail (existing single-rail selection takes over); plain click on empty strip/frame clears the set entirely; Escape collapses layers one at a time (43.5: one Escape handles at most one layer — solo exit, then selection collapse); selecting a physical frame or key clears the rail set (43.4 mutual exclusion).
- **D-05:** The multi-rail set **may be empty**. Cmd+click toggling off the last selected rail leaves an empty set (no rail selection scope active). This intentionally diverges from Phase 37's never-empty key multi-selection — rails have no always-current editing obligation.
- **D-06 (user-locked):** Selection across batch operations: after a batch Move commits, the whole set stays selected at the new positions and the anchor follows its rail's identity; Undo restores the set selection at the original positions; Redo re-applies at the destination. After Delete Rails commits, the selection is empty and the cursor stays on its current valid frame (43.4 delete precedent); one Undo restores the exact pre-delete selection set; Redo clears it again. The anchor follows rail identity across Undo/Redo.
- **D-07:** Spec default accepted: the whole set translates **rigidly by one delta** — relative offsets, internal gaps, and internal breaks preserved exactly. The set **clamps or rejects as one unit** at the first collision with any unselected key, Group occupancy, frame 0, or capacity. Unselected objects never move; movement-created gaps persist.
- **D-08:** Batch Move initiates by **dragging any selected rail** — the grabbed rail is not special; the set is the unit. Dragging an unselected rail collapses the set to that rail first (normal single-rail selection), then runs its own 43.3/43.4 drag.
- **D-09:** Drag preview: **per-rail translucent mode-colored ghosts** (purple/cyan/gray per rail type) at the proposed destination; originals stay visible until exact parent acceptance; **one live status-line set readout** (delta + resulting set range + opened gap if any); red blocked-edge treatment on the colliding rail's ghost.
- **D-10:** Shared-source Groups inside the set follow 43.3 algebra: source-attached rails move source keys with identity; duplicated placements move placement-only. Straddle reject: an unselected Group sharing a source with a selected source-attached rail rejects the move with a mapped reason (43.5 D-16 generalized); the family is never silently pulled in.
- **D-11 (user-locked):** Break/gap normalization: internal breaks and internal gaps travel rigidly with the set (43.4 D-19 identity travel). Movement-created gaps at the set edges follow 43.3 D-12 authority — a break lands on the first surviving successor only when a gap actually opens. Landing adjacent to a fixed-side neighbor never merges; breaks travel with the moved keys.
- **D-12 (user-locked copy):** Accepted Move status: `Moved {N} Rails by {D} frames — set now frames {A}–{B}. Gap left at frames {G1}–{G2}.` — the gap sentence appears only when a gap actually opened; one deterministic mapper; correct singular/plural.
- **D-13 (user-locked):** Zero-delta drop: no commit, no status, no history entry, the set stays selected (43.5 push-drop-noop precedent). Escape during the drag cancels: originals byte-untouched, no history entry, the set stays selected (43.3/43.4 cancel precedent).
- **D-14 (user-locked):** Solo means **hide others + restrict range**: during solo playback only the selected rails' content renders; the play range restricts to the selection's frame coverage and loops within it by default. Guards: session-only playback state — never persisted, never affects preview/export output or the canonical render; changing or clearing the rail selection ends solo immediately; audio preview keeps following the playhead unchanged (Main Editor authority), simply over the restricted range; a visible active indicator marks solo mode (same active-state orange language as armed tools); Escape or re-click exits.
- **D-15 (user-locked):** The Solo button lives in the **bottom workflow strip** and enables whenever **any rail selection** is active — a single selected Rail is a set of one (soloing one rail is a legitimate "watch just this Group" case). Disabled only when no rail selection exists (guarded tooltip: `Select a Rail to solo.`). Solo state never persists across save/reopen. Exact button placement in the action row goes to UI-SPEC.
- **D-16:** Solo interacts with transport as an **arm**: toggling solo only arms the filter/range — the user presses Play (or it keeps playing if already playing). Solo persists across stop/start while the selection is unchanged.
- **D-17:** Implementation mechanism: solo is a **pure presentation filter on cached playback frames only** — the canonical render source, preview stills, export, and the accepted document are never touched. Unselected rails keep all their state; they just don't paint during solo playback. Session-only signal, never crosses the bridge.
- **D-18 (user-locked):** Scrubbing while solo-armed but stopped is **unrestricted timeline navigation**: the filter applies ONLY to playing frames. The stopped canvas always renders everything, at any cursor position, inside or outside the solo range.
- **D-19 (user-locked):** The solo range derives from the selected rails' **effective boundaries** — first selected placement start to last selected effective end — so generated/linked occurrences of selected Groups are included in the range, and only unselected content is hidden during playback.
- **D-20 (user-locked copy):** While solo is armed, the status capsule carries `Solo — {N} Rails, frames {A}–{B}.` (one mapper, correct singular/plural); the Solo button shows the active orange state. Both clear on exit (toggle, Escape, or selection change).
- **D-21:** Affordances split across existing homes with dynamic scope — one home per operation, no duplicated controls: **Delete** keeps living on the existing Delete control with a dynamic scope label (`Delete Frame` / `Delete Key Rail — …` / `Delete {N} Rails`); **Solo** gets its own strip toggle (D-15); **Key Spacing** stays in the 43.5 ToolCase popover, applying to the active set when one exists.
- **D-22 (user-locked):** Delete/Backspace keyboard shortcuts route through the **same dynamic scope** as the visible Delete control: an active multi-rail set means both keys commit `Delete {N} Rails` as one atomic command. No separate shortcut path.
- **D-23:** Mixed-set Delete is **fully direct — no confirmation modal** at any set size or composition. Each rail deletes with its own type semantics: Key Rail deletion removes its real keys and derived projection; Motion/Static Rail deletion follows the 43.2 Delete Group semantics and **never deletes the referenced Action**. One atomic history command; one Undo restores every rail, key, break, and the exact pre-delete selection set; Redo re-applies. Vacated intervals remain intentional persistent gaps; break normalization follows the 43.4 rules per deleted rail; never touches unselected rails, keys, Actions, or shared sources still referenced by another Group.
- **D-24:** Key Spacing on a set: the spacing factor applies **per selected rail, each rail keeping its own first key as anchor**. No cross-set spacing mode this phase. One atomic command for the whole set.
- **D-25 (user-locked):** Key Spacing validates the **whole set before commit**: every selected rail's membership, anchors, capacity, and collisions are checked up front; if any rail fails, the entire command rejects with a mapped reason — no partial application. All-or-nothing.
- **D-26 (user-locked):** The ToolCase popover is **scope-aware**: with an active rail set, the Key Spacing section applies to the set (and its copy reflects the scope); without a set, behavior is exactly the 43.5 single-selection behavior. The popover never creates or modifies the selection set itself.
- **D-27:** Set copy (spec formula + type breakdown): `N Rails selected — frames {A}–{B}.` with correct singular/plural and a type breakdown when mixed (e.g. `3 Rails selected — frames 12–88 (1 Motion, 2 Key).`). Homogeneous sets name the type directly (`2 Key Rails selected — …`). **One deterministic mapper** owns all set copy: capsule, tooltips, accessibility names, Delete scope label, and solo status.

## Summary

Phase 43.6 is, like 43.3/43.4/43.5, an **additive composition over an already-closed architecture** — but it is the first 43.x phase that introduces a genuinely new *session-state scope* (the cross-type rail set) rather than only new operations. Every mechanism it needs exists and was read this session: the pure selection-reducer idiom (Phase 37 key-level `physicsPaintRotoMultiSelection.ts` and the Loop-Rail-level `physicsPaintRotoSpacingSelection.ts`), the closed resolver intent union with fail-closed candidate builders, the coordinator's specialized execute inputs, the parent-side recompute-and-exact-match validation for group lifecycle operations, the injectable pointer-session drag hook, the armed-tool session-signal module, and the playback `getFrames` enumeration seam.

Three findings shape the plan:

1. **The rail set already half-exists.** `selectedLoopClipIds` + `loopSelectionAnchorId` + `updatePhysicsPaintRotoLoopClipSelection` implement plain/toggle/range Loop-Rail multi-selection today (never-empty, Loop-only). Key Rail selection is single-only (`RotoKeyRailSelection`). Phase 43.6 generalizes both into one discriminated-identity set (`{ kind: 'loop', loopId } | { kind: 'key-rail', firstKeyId }`), adds the union gesture (D-03 — genuinely new; Cmd+Shift+click currently collapses to `'range'` in `PhysicsPaintLoopClipRail.tsx:159-163`), and permits the empty set (D-05 — the existing reducers return `null` on empty, which already means "no rail selection scope active," so the empty-set contract is a semantic relaxation, not a new representation).

2. **Batch Delete atomicity is the hard part.** Key Rail deletion flows through the resolver (`delete-key-rail` intent → child-computed proposal). Group deletion does NOT: it is a specialized coordinator execute input (`RotoGroupLifecycleDeleteExecuteInput`, no child proposal) whose semantic delta the **parent recomputes** via `proposePhysicPaintRotoDeleteGroup` and exact-matches against the child's complete proposed records/loopClips/breaks/revision. D-23 demands one atomic command for a mixed set. The expressiveness exists — the apply payload already carries complete proposed records, loopClips, and breaks — but the plan must choose where the composition lives (Open Question 1). Recommended: one new resolver intent producing the combined complete next state plus a new semantic-delta kind the parent recomputes by composing the existing per-group proposer with record removal.

3. **Solo is a frame-list filter, not a re-render — and that is sufficient.** Cached playback frames are flattened PNG data URLs (`PhysicPaintRenderedFrame`, types/physicPaint.ts:1509-1521: "Rendered PNG output only"). D-17's "pure presentation filter on cached playback frames only" therefore means frame-granular inclusion: enumerate only the solo range in the `getFrames` seam and yield `{ appFrame, frame: null }` (the existing "missing frames play transparent/background" treatment) for in-range frames not attributed to a selected rail. Per-frame attribution is single-owner by construction: the physical cell model assigns each frame exactly one kind (real/generated/empty — resolver L229-237) and exactly one render source (`'real' | 'generated' | 'loop-placeholder'`, physicalModel L139-172), so no frame can carry two rails' merged content — the plan should still verify this via `visibleRanges`/loop resolution for placement-overlap edge cases (Assumption A3). The stopped canvas path (`findCachedRotoDisplayFrame`) is a separate seam and stays untouched (D-18).

**Primary recommendation:** Build the phase as four vertical slices in dependency order — (1) rail-set session state + gestures + copy (RSET-*), (2) batch Move intent + set drag (BMOV-*), (3) batch Delete classifier + intent (BDEL-*), (4) ToolCase scope + Key Spacing on set (BSPC-*) and Solo (SOLO-*) — with the rail-set reducer module first, since every later slice consumes it.

### Anti-Patterns to Avoid

- **Re-rendering frames for solo:** the cache is flattened PNGs; any engine re-render for solo violates D-17 ("pure presentation filter on cached playback frames only") and risks diverging from the accepted render authority.
- **Sequential per-rail commands for batch ops:** composing batch Delete/Move as N existing single-rail commands breaks D-23/D-06 atomicity (one history command, one Undo/Redo) and double-publishes status. One new intent per batch operation.
- **Porting the Phase 37 never-empty contract:** `toggleRotoKeySelection` no-ops when removal would empty the set (multiSelection L85). D-05 explicitly reverses this for rails.
- **A second copy owner:** all set copy (capsule, tooltips, Delete scope, solo status, readouts) flows through the existing mapper family in `useRotoTimelineActions.ts` — no per-component string assembly (D-27).
- **Effect-mirrored selection state:** set/arm state lives in Signals computed at render or consumed via `peek()`; do not copy set state into `useState`/`useEffect` mirrors (CLAUDE.md Preact guidelines; 38.1 D-01 discipline for playback-adjacent signals).

## Common Pitfalls

### Pitfall 1: Cmd+Shift+click is already wired to the wrong gesture
**What goes wrong:** `PhysicsPaintLoopClipRail.tsx:159-163` [VERIFIED] routes modifiers as `event.shiftKey ? 'range' : event.metaKey || event.ctrlKey ? 'toggle' : 'plain'` — so Cmd+Shift+click currently produces `'range'` (replace), silently contradicting D-03's union.
**Why it happens:** Shift is checked first; the union gesture did not exist when the routing was written.
**How to avoid:** Add the `'union'` branch explicitly (`shiftKey && (metaKey || ctrlKey)`) BEFORE the plain-Shift branch in BOTH rail components (`PhysicsPaintKeyRail.tsx` needs the full modifier routing — it currently exposes only `shiftKey` in its `RailMouseEvent`-adjacent props surface at L90 [VERIFIED]).
**Warning signs:** UAT step 1 fails: Cmd+Shift+click replaces instead of unions.

### Pitfall 2: Key Rail identity goes stale under the set
**What goes wrong:** A Key Rail's identity is its `firstKeyId`; the segment set re-derives from accepted records (`deriveKeyRailSegments`), so any accepted edit that changes segment boundaries invalidates a stored `firstKeyId`. The existing single-rail path handles this via `reconcileRotoKeyRailSelection` (PhysicsPaintStudio.tsx:98-101 [VERIFIED via grep]) and the classifier's `'stale-key-rail'` branch (useRotoTimelineActions.ts:468, 544, 560 [VERIFIED]).
**Why it happens:** Segment identity is derived, not stored.
**How to avoid:** Reconcile the rail set against freshly derived segments + loop ranges on every accepted revision (43.4 stale-selection rule: clear the invalid set instead of inventing a fallback — UI-SPEC Interaction Contract). Batch Move keeps Key Rail identities stable by construction (rigid move preserves firstKeyId); Delete empties the set (D-06) — but Interpolation toggles and external edits must trigger reconcile.
**Warning signs:** Set copy shows rails that no longer exist; Delete scope announces a stale set.

### Pitfall 3: Solo filter leaking into the stopped canvas
**What goes wrong:** Applying the solo frame filter in `findCachedRotoDisplayFrame` (or any shared display lookup) instead of only in the playback `getFrames` enumeration makes the stopped canvas hide unselected content — a direct D-18 violation, and worse, it would alter what canvas reconciliation renders.
**Why it happens:** Both paths eventually produce "the frame to show for appFrame N."
**How to avoid:** The filter lives at the enumeration site only (Pattern 5). Add a regression test: solo armed + stopped → `findCachedRotoDisplayFrame` returns unfiltered frames.
**Warning signs:** UAT step 7 fails: stopped scrub renders partial content.

### Pitfall 4: Batch drag starts from a modifier click or an unselected rail
**What goes wrong:** Two failure modes — (a) the new set-drag session forgets the L140 modifier guard and Cmd+click starts a drag; (b) pointer-down on an unselected rail starts a batch drag instead of collapsing first (D-08).
**How to avoid:** Keep the modifier guard verbatim; route pointer-down through selection first — if the rail is not in the set, collapse (plain-click semantics) and hand off to the rail's own 43.3/43.4 drag session; only rails already in the set arm the batch session.
**Warning signs:** Selection toggles feel "sticky"; dragging an unselected rail moves the ghost set.

### Pitfall 5: Whole-set preflight skipped for Key Spacing
**What goes wrong:** Applying `force-spacing` per rail sequentially: rail 2 of 3 fails capacity, leaving rails 1 applied — D-25 forbids partial application.
**Why it happens:** The existing single/loop-scope spacing path applies immediately after its own scope check (`deriveForceSpacingScope`, useRotoTimelineActions.ts:1092+ [VERIFIED via grep]).
**How to avoid:** The `spacing-on-set` intent validates every selected rail's membership/anchor/capacity/collision inside the resolver before producing a proposal; the resolver's fail-closed contract gives all-or-nothing for free if the intent takes the whole set as input instead of looping intents outside.
**Warning signs:** Mixed-set spacing partially applies; one Undo restores only part.

### Pitfall 6: Undo/Redo loses the selection set
**What goes wrong:** D-06 requires Undo after Delete to restore the exact pre-delete set and Undo after Move to restore the set at original positions. The history replays complete document snapshots, but the rail set is session state — nothing automatically restores it.
**Why it happens:** `resolvePostAcceptanceRotoSelection` (multiSelection L147-171 [VERIFIED]) keys key-level selection aftermath on `operationKind`, but rail-set aftermath is new and the empty-after-delete/restore-on-undo asymmetry is easy to drop.
**How to avoid:** Carry the pre-command set snapshot as session metadata alongside the history command (never persisted — process boundary), and key set aftermath on the new operation kinds explicitly, including the `'undo'`/`'redo'` fall-through (the Phase 37 module collapses unknown kinds to single-selection — the rail set must NOT fall through to collapse).
**Warning signs:** UAT step 3 fails: Undo restores rails but not the selection set.

### Pitfall 7: Set playback status churn during playback
**What goes wrong:** Solo/Move readouts publishing per pointer-move or per tick create live-region churn and render storms. The playback hook queues status events while playing and flushes once on stop (useRotoCachedPlayback L86-96, L254-260 [VERIFIED]).
**How to avoid:** Live drag readouts publish through the same `setStatus` gate; never bypass it. The persistent solo capsule line (D-20) is a render-time projection, not a status event stream.
**Warning signs:** Screen reader repeats; capsule flicker during solo playback.
