# Phase 43.4: Derived Key Groups and Scissor Breaks - Research

**Researched:** 2026-08-15
**Domain:** Physics Paint Roto physical timeline — derived Key Rail segmentation, Scissor break action, selection-scoped Delete Key Rail, Key Rail direct drag (Preact + Signals, canonical physical document authority)
**Confidence:** HIGH (all load-bearing seams read this session; zero new external dependencies)

## Summary

Phase 43.4 adds a third derived rail kind — the mid-gray **Key Rail** — over ordinary real Roto keys not owned by a Motion/Static Group, segmented by the persistent Phase 43.1 stable-key-owned incoming breaks. Three operations ship on that derivation: **Scissor** (toolbar button creating one incoming break on a selected real ordinary key), **Delete Key Rail** (selection-scoped direct deletion of a derived segment's keys with persistent-gap normalization), and **Key Rail drag** (43.3 clamp-and-commit direct drag applied to whole ordinary-key segments).

The research's central finding: **every mechanism this phase needs already exists in the codebase and was verified by reading it.** The 43.1 break collection (`incomingInterpolationBreakKeyIds`) is canonical, parsed, revisioned, and persisted; the generated-cell projection already suppresses interpolation at break owners; the 43.3 clamp authority, drag session hook, ghost/blocked-edge/gap-preview paint, and prepare/commit publication idiom are directly generalizable from Loop Clips to key segments; and the 43.2 delete scope classifier is the exact host for the dynamic Delete scope. The phase is an **extension of proven seams, not new machinery** — the highest-risk work is (a) break normalization on Delete Key Rail (the existing `delete-key-group` resolver branch only *removes* deleted-key breaks; it does **not** add the vacated-interval successor break D-15 requires), and (b) Key Rail selection as a third mutually-exclusive session selection mode with stale-authority clearing.

**Primary recommendation:** Implement derivation as one pure function (ordered real keys + break set + Group ownership → Key Rail segments), three new closed-union intents (`scissor` / key-rail move / key-rail delete — exact names are Claude's discretion per CONTEXT), a sibling rail host + drag session modeled verbatim on `PhysicsPaintLoopClipRail` / `usePhysicsPaintGroupRailDrag`, and one product-reason mapper extension — with the D-01 terminology migration touching only the four surfaces the UI-SPEC lists.

### Pattern 1: Pure derived segmentation over canonical facts

**What:** One pure function computes Key Rail segments: order real keys by frame, exclude Group-owned keys (`loopClips` `sourceKeyIds` + `frameOverrides` keyIds), split segments at keys owning an incoming break, emit half-open `[firstKeyFrame, lastKeyFrame + 1)` spans.

**When to use:** This is THE phase foundation — rail paint, selection scope, delete scope, drag span, and copy counts all consume this one derivation.

**Verified inputs (all canonical, all read this session):**

- Break collection on the document: `readonly incomingInterpolationBreakKeyIds: readonly string[];` [VERIFIED: physicsPaintRotoPhysicalModel.ts:309]
- Strict parser rejecting malformed/duplicate/orphan entries: `parsePhysicPaintRotoIncomingInterpolationBreakKeyIds` throws on `orphan keyId` [VERIFIED: physicsPaintRotoPhysicalModel.ts:737-755]
- Revision participation: `...(incomingInterpolationBreakKeyIds.length > 0 ? [\`incoming-breaks:${encodeCanonicalIncomingInterpolationBreakKeyIds(incomingInterpolationBreakKeyIds)}\`] : [])` [VERIFIED: physicsPaintRotoPhysicalModel.ts:1018-1019]
- Break suppression in the generated-cell projection: `if (incomingBreakOwners.has(right[0])) continue;` [VERIFIED: physicsPaintRotoPhysicalResolver.ts:2530]
- 43.1 marker predicate (segment start = real + ordered predecessor + break owner): `const startsInterpolationSegment = kind === 'real' && keyId !== null && keyOrder > 0 && hasIncomingInterpolationBreak;` [VERIFIED: physicsPaintWorkflowPresentation.ts:328-331]

**Key insight:** a Key Rail segment boundary is exactly the existing `startsInterpolationSegment` predicate lifted from per-cell to per-segment. No new authority is invented; derivation cannot disagree with interpolation behavior because both read the same owner set.

### Pattern 2: 43.3 clamp-and-commit, generalized from clip to key set

The 43.3 pure clamp authority signature [VERIFIED: resolver:2010-2018]:

```typescript
export function clampPhysicPaintGroupDragDestination(
  input: PhysicPaintRotoGroupDragClampInput,
): PhysicPaintRotoGroupDragClampResult
```

Its collision algebra — frame 0 / capacity bounds, boundary key frames outside the dragged interval, other Group intervals overlap, nearest-free-position search in the drag direction only — maps onto Key Rails with two simplifications: no duplicated-placement branch (D-17: every Key Rail drag is source-attached whole-segment rigid translation) and no Infinity/zero-width interval cases (a Key Rail span is always ≥ 1 frame of real keys). The clamp must additionally treat **break-adjacency as free** (landing immediately before the next segment's first key is legal — the split is preserved by the successor's existing break) while treating key-occupancy as blocking.

Post-move break derivation semantics are already implemented and must be mirrored [VERIFIED: resolver:2110-2186, docstring quoted]:

```
 * (a) the next real key at or after the vacated interval's end owns (or reuses)
 * the incoming break when one exists — never when the interval ends content
 * (D-12); (b) a source-attached move opens a landing gap when the first source
 * key lands more than one frame after its new predecessor, giving that key a new
 * incoming break (D-10); (c) every existing break is carried unchanged (43.1
 * D-14). ... Reuse-never-duplicate: the output is a complete collection
 * replacement, never a delta.
```

## Common Pitfalls

### Pitfall 1: Reusing `delete-key-group` verbatim loses the persistent gap (D-15 violation)

**What goes wrong:** The existing resolver branch removes the requested keys and filters deleted break owners out of the collection [VERIFIED: resolver:3193-3203]:

```typescript
    const removedBreakOwners = new Set(intent.keyIds);
    const candidate = {
      ...buildDeleteGroupCandidate(
        identities,
        intent.keyIds,
        new Set(loopClips.flatMap((clip) => clip.sourceKeyIds)),
      ),
      nextIncomingInterpolationBreakKeyIds: Object.freeze(
        incomingInterpolationBreakKeyIds.filter((keyId) => !removedBreakOwners.has(keyId)),
      ),
    };
```

It never ADDS a break. After deleting a middle Key Rail, the left surviving key and the right surviving key become consecutive with no break on the right key — and the generated-cell projection (`if (incomingBreakOwners.has(right[0])) continue;` [VERIFIED: resolver:2530]) will interpolate across the vacated interval, silently bridging the "intentional gap" and merging the two surviving Key Rails. Direct violation of D-15 and prompt acceptance steps 6-7.

**Why it happens:** Manual multi-key delete (the existing arm's use case) never promised gap persistence; Delete Key Rail does.

**How to avoid:** The new key-rail delete intent applies 43.3 rule (a): the next real key at/after the vacated interval's end owns (or reuses) an incoming break — never when the interval ends content, never duplicated if already owned. Delete is complete-collection replacement, same as drag.

**Warning signs:** Interpolation On refilling a deleted rail's interval; two surviving rails rendering as one after deletion; acceptance step 7 failing.

### Pitfall 2: Break collection omitted from the prepare/commit fingerprint

**What goes wrong:** 43.3 Pitfall 1, carried: `buildPhysicPaintRotoPhysicalRevision`'s fourth parameter defaults to empty [VERIFIED: physicsPaintRotoPhysicalModel.ts:951-956, quoted in 43.3 RESEARCH], so a prepare/commit version built without the break collection passes stale checks when break authority changed between prepare and commit. Scissor changes break authority by definition; drag and delete re-derive it.

**How to avoid:** Every new prepare path passes `incomingInterpolationBreakKeyIds` into BOTH the resolver input and the proposal version (43.3's `buildGroupDragProposalVersion` already does [VERIFIED: useRotoTimelineActions.ts:1432]); do not modify existing call sites (regression boundary).

**Warning signs:** a commit accepted against a document whose breaks changed after prepare.

### Pitfall 3: Key Rail host gated on Loop Clip context

**What goes wrong:** The existing rail mount is conditional on Group infrastructure [VERIFIED: PhysicsPaintWorkflowStrip.tsx:1552-1556 — `loopResolutionContext !== null && loopResolutionContext.ranges.length > 0 && props.onSelectRotoLoopClip && props.onOpenRotoLoopEdit`]. Mounting Key Rails under the same condition hides every Key Rail on timelines with zero Motion/Static Groups — the most common case.

**How to avoid:** The Key Rail host has its own mount condition (any ordinary real key exists) and its own band-contained host; zero ordinary keys → absent from DOM (UI-SPEC empty state).

### Pitfall 4: Clamp semantics — rejecting instead of clamping, or clamping against the dragged segment's own keys

**What goes wrong:** 43.3 Pitfall 3 carried: `move-key-group`'s candidate builder rejects on collision (`duplicate-destination-frame`); copying it imports the wrong semantic. Additionally, a naive key-occupancy clamp treats the dragged segment's own current positions as blockers, making every drag reject.

**How to avoid:** New pure key-rail clamp: dragged segment's own keys are pass-through; boundaries are frame 0, capacity/parent end, every real key outside the segment, and every Group interval (including linked occurrences, via the derived ranges the strip already computes). Reject only on zero valid movement in the dragged direction (`No empty space in that direction.`, D-20). Preview is the commit: the ghost consumes the same pure clamp the resolver commits.

### Pitfall 5: Selection-mode mutual exclusion leaks

**What goes wrong:** Three selection modes (physical keys, Motion/Static Rails, Key Rails) must be mutually exclusive synchronously (UI-SPEC Selection ownership). `selectedLoopClipIds` clearing lives in `PhysicsPaintStudio.tsx` (signal declared at L113; cleared at L142 and L311 [VERIFIED via grep this session]); adding a Key Rail selection signal without routing ALL clearing paths through both directions leaves double-scope states, and `classifyRotoDeleteTarget` would see ambiguous input.

**How to avoid:** One clearing discipline: selecting any rail clears the other rail selection AND physical selection; physical-key selection clears all rail selection. Stale authority (membership/breaks/revision changed under a selection) clears the invalid Key Rail selection — derivation identity (e.g., first-key stable ID + member count or boundary pair) must be re-validated against the accepted document, not cached presentation state.

**Warning signs:** Delete announcing two scopes; orange paint on two rails; acceptance step 4 failure.

### Pitfall 6: Post-drop click re-fires Key Rail selection (43.3 Pitfall 2 carried)

**What goes wrong:** After pointer capture + drop, the browser dispatches `click` on the capture target; the rail click handler re-fires selection after an accepted drag. The Loop Clip rail solves it with `consumeClickSuppression` inside `usePhysicsPaintGroupRailDrag` [VERIFIED: PhysicsPaintLoopClipRail.tsx:127-145].

**How to avoid:** Fork the suppression idiom with the drag session; also cancel any pending click timer at threshold crossing.

### Pitfall 7: Scissor no-op must not even publish status

**What goes wrong:** Cutting at an existing break is an exact no-op — zero mutation, zero status, zero history (D-04, prompt-locked, UI-SPEC acceptance row 4 checks "unchanged history depth"). A resolver `fail(...)` path that publishes the mapped rejection copy would violate this: it is NOT a rejection, it is a silent no-op.

**How to avoid:** Preflight detects the already-broken target and short-circuits before `runPhysicalAction` (copy: `This key already starts a Key Rail segment.` appears in the guarded tooltip, not the status line). The resolver stays fail-closed for the racing case, but the UI no-op path produces no history attempt at all.

### Pitfall 8: Terminology migration forked vocabularies

**What goes wrong:** D-01's reversibility note: migrating some touched surfaces but not their copy tests (or missing one surface in the migration map) forks the UI into Group/Rail mixed vocabulary — UI-SPEC acceptance row 11 auto-rejects on "`Key Group` in any user-facing copy, or a mixed Group/Rail vocabulary on the touched rail surfaces."

**How to avoid:** One plan task owns the migration map end-to-end including tests; a copy-grep gate (`Motion Group` / `Static Group` / `Group Rail` / `Key Group` across user-facing strings in the touched modules) verifies no residue; untouched surfaces (dialog titles, Scripts panel, Actions inspector) are asserted unchanged.

### Key Rail segment derivation (shape — representation is Claude's discretion per CONTEXT)

```typescript
// Inputs: all canonical, all already available in the store/strip bundle.
// Source: derivation semantics verified at resolver:2525-2530 (break suppression)
// and physicsPaintWorkflowPresentation.ts:328-331 (segment-start predicate).
interface KeyRailSegment {
  readonly firstKeyId: string;        // stable identity — anchor for selection/break travel
  readonly keyIds: readonly string[]; // ordered member keys
  readonly firstKeyFrame: number;
  readonly lastKeyFrame: number;      // span geometry: [firstKeyFrame, lastKeyFrame + 1)
}

function deriveKeyRailSegments(input: {
  readonly orderedRealKeys: readonly { keyId: string; appFrame: number }[]; // ascending
  readonly incomingInterpolationBreakKeyIds: ReadonlySet<string>;
  readonly groupOwnedKeyIds: ReadonlySet<string>; // loopClips sourceKeyIds + frameOverrides keyIds
}): readonly KeyRailSegment[] {
  const segments: KeyRailSegment[] = [];
  let current: { keyIds: string[]; firstKeyFrame: number; lastKeyFrame: number } | null = null;
  for (const key of input.orderedRealKeys) {
    if (input.groupOwnedKeyIds.has(key.keyId)) { current = null; continue; }
    const startsNewSegment = current === null || input.incomingInterpolationBreakKeyIds.has(key.keyId);
    if (startsNewSegment) {
      current = { keyIds: [key.keyId], firstKeyFrame: key.appFrame, lastKeyFrame: key.appFrame };
      segments.push({
        firstKeyId: key.keyId, keyIds: Object.freeze(current.keyIds.slice()),
        firstKeyFrame: key.appFrame, lastKeyFrame: key.appFrame,
      });
    } else {
      current.keyIds.push(key.keyId);
      current.lastKeyFrame = key.appFrame;
      // NOTE: real implementation rebuilds frozen segment objects; mutation shown for brevity.
    }
  }
  return segments; // re-derive member arrays immutably in production code
}
```

Empty frames between member keys without a break stay inside one rail (they are simply absent from `orderedRealKeys`); a break splits immediately before its owner (43.1 semantics — the owner starts the right rail and keeps its blue left-edge cell marker).

## Open Questions (RESOLVED)

1. **Key Rail selection identity under derivation drift** — RESOLVED (pinned in plan 06, Task 3): identity = **firstKeyId + full member equality**.    - What we know: selection must clear on stale authority (UI-SPEC); segments are derived, so identity must come from canonical facts.
   - What's unclear: exact identity key — first-key stable ID alone, or (firstKeyId, memberKeyIds hash) to catch membership changes that keep the same first key.
   - Recommendation: anchor on firstKeyId + revalidate full membership equality against the accepted derivation at each authoritative change; clear on any mismatch. Planner specifies the exact comparison.

2. **Scissor target when a rail is selected but cursor sits elsewhere** — RESOLVED (pinned in plan 01, Task 2): the recommendation stands — a **cursor-frame ordinary key still arms Scissor** when a Key Rail is selected. The classifier resolves the selected real ordinary key first, else the real ordinary key at the cursor frame; rail selection alone neither arms nor disables Scissor.
   - What we know: D-03 resolves "the selected real ordinary key first, else the real ordinary key at the cursor frame"; rail selection is mutually exclusive with key selection (UI-SPEC).
   - What's unclear: with a Key Rail selected (no key selected), is Scissor enabled at all? D-10 says Scissor is never advertised on the rail — implying rail selection alone does not arm Scissor.
   - Recommendation: Scissor availability requires a real ordinary key target from key-selection/cursor only; a rail-selected state with the cursor on an ordinary key of that rail is a planner-level decision to confirm against the product prompt during planning (default: cursor-frame ordinary key still arms Scissor, matching "else the real ordinary key at the cursor frame").

3. **Does Delete Key Rail leave a break when the deleted rail was the FIRST content on the timeline?** — RESOLVED (pinned in plan 03, Task 3): **YES** — the successor owns the break whenever it exists. Deleting the first rail leaves the successor owning a dormant break (legal per 43.1: dormant while the owner has no predecessor); deleting the LAST rail adds no break (no successor exists).    - What we know: 43.3 rule (a) adds a break only when a successor exists; breaks are owned by keys, and a first-content deletion leaves no predecessor span to protect.
   - What's unclear: whether the successor of a deleted first rail should own a break even though no left neighbor exists (no interpolation span enters it until a new key appears before it — at which point the dormant break becomes effective and preserves the gap, matching the prompt's "later ordinary-key creation must still respect the accepted deletion gap").
   - Recommendation: YES — the successor owns the break whenever it exists (dormant breaks are legal per 43.1: "stays dormant while the owner has no predecessor", STATE.md decision). Planner pins this in the resolver spec and tests both cases.
