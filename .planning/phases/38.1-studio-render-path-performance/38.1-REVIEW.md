# Phase 38.1: Code Review Report

**Reviewed:** 2026-07-28T00:00:00Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

Reviewed the 38.1 render-path performance changes: the scheduled-flag rAF flush scheduler, the generation-token navigation pipeline, the playbackTick signal surfaces, the store structural read memo, the timeline-model persistent signal graph, and the engine FIFO decode cache. One correctness defect in the rAF coalescing loses the latest navigation frame and desyncs the Studio from the canvas — this is a Blocker. The store structural memo's identity-triple contract holds at every current mutation site (all replace the record map / frozen interpolation / capacity), but the cache is never pruned on layer teardown paths. The timeline-model memo is defeated at its only call site by a per-render fresh settings object. The decode cache and generation-token pipeline are otherwise sound: superseded image loads are rejected before cache insertion, and the begin-before-await ordering in `navigateToSyncedPhysicalFrame` is correct.

## Critical Issues

### CR-01: rAF flush scheduler runs the FIRST queued flush and discards the LATEST — Studio startFrame desyncs from canvas on click bursts

**File:** `app/src/components/physic-paint/hooks/rotoUiFlushScheduler.ts:19-25` (also `app/src/components/physic-paint/PhysicsPaintStudio.tsx:104-108`)
**Issue:** `schedule()` returns early when a flush is pending, so the callback that runs at fire time is the first-scheduled closure, not the latest. The scheduler's own doc comment claims "each flush reads the latest state at fire time," but the sole caller captures a per-call value in the closure:

```ts
const scheduleRotoStartFramePropagation = useCallback((frame: number) => {
  rotoUiFlushScheduler.schedule(() => {
    setLaunchContext((current) => current ? { ...current, startFrame: frame } : current);
  });
}, [rotoUiFlushScheduler, setLaunchContext]);
```

Trace: navigate to frame 5, then to frame 7 within the same animation frame. The frame-5 closure posts the rAF; the frame-7 call is dropped. The canvas was painted synchronously for frame 7 (D-03 canvas-first), the store cursor is 7, the frame-sync message sent 7 — but `launchContext.startFrame` becomes **5**. The Studio's `currentFrame`, the nav pill, the timeline current-cell highlight, selection reconciliation, and arrow-key navigation base all show/derive from the stale frame until the next navigation. This directly contradicts the stated design ("coalesces to at most one Studio render per animation frame showing the LATEST frame", PhysicsPaintStudio.tsx:812) and is a user-visible correctness bug under exactly the fast-clicking scenario the scheduler was built for.
**Fix:** Retain the latest flush callback instead of the first:

```ts
export function createRotoUiFlushScheduler(): RotoUiFlushScheduler {
  let pendingId: number | null = null;
  let pendingFlush: (() => void) | null = null;

  function schedule(flush: () => void): void {
    pendingFlush = flush; // latest wins
    if (pendingId !== null) return;
    pendingId = requestAnimationFrame(() => {
      pendingId = null;
      const run = pendingFlush;
      pendingFlush = null;
      run?.();
    });
  }

  function dispose(): void {
    if (pendingId !== null) cancelAnimationFrame(pendingId);
    pendingId = null;
    pendingFlush = null;
  }

  function isPending(): boolean {
    return pendingId !== null;
  }

  return { schedule, dispose, isPending };
}
```

This preserves the one-rAF-per-frame cap while making the fire-time flush the latest-scheduled one.

## Warnings

### WR-01: `start()` early-return on empty frame list leaves a previously running playback interval alive

**File:** `app/src/components/physic-paint/hooks/useRotoCachedPlayback.ts:128-134`
**Issue:** When `start()` is invoked while playback is already active and `getFrames()` now returns an empty array, it publishes "No cached Roto frames yet..." and returns **before** `clearTimer()`. The previous `setInterval` keeps ticking with the stale captured `cachedFrames` array, `isActive` stays true, and `setIsPlaying` stays true — the status line says playback is impossible while playback visibly continues. Reachable via `updateFps` (`if (isActive) start(nextFps)`, line 186) after frames are cleared mid-playback, or any external `start()` re-entry.
**Fix:** Move `clearTimer()` (and, on the empty path, `setIsActive(false)` / `inputRef.current.setIsPlaying(false)` / `playbackTick.value = null`) ahead of the empty-frames early return, or route the empty case through `finishPlayback()`.

### WR-02: Per-render fresh `interpolationSettings` object defeats the persistent signal-graph memo (38.1 D-07) at its only call site

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:239-247` (memo at `app/src/components/physic-paint/hooks/useRotoTimelineModel.ts:112-118`)
**Issue:** `useRotoTimelineModel`'s `useMemo` dependency array includes `input.interpolationSettings`, but the Studio passes `physicPaintStore.getRotoInterpolationSettings(launchContext.layerId)` inline — and that getter returns `_cloneRotoInterpolationSettings({...})`, a **new object identity on every call**. Every Studio render therefore produces a new `interpolationSettings` identity, the memo recomputes, and `createRotoTimelineModel` rebuilds the entire structural signal graph (all `computed`s, both structural selectors, the projection) on every render — exactly the per-render rebuild D-07 was designed to eliminate. Values stay correct (the rebuild is byte-identical), so this is not stale-cache behavior, but the phase's central memoization deliverable is silently void at runtime. Sibling inputs are correctly stabilized (`rotoKeyRecords`/`rotoInterpolationState` are memoized on `physicPaintVersion.value`); this one is not.
**Fix:** Memoize the settings read the same way as the records:

```ts
const rotoLegacyInterpolationSettings = useMemo(
  () => launchContext ? physicPaintStore.getRotoInterpolationSettings(launchContext.layerId) : undefined,
  [launchContext?.layerId, physicPaintVersion.value],
);
```

and pass `rotoLegacyInterpolationSettings` into the model input. Alternatively, drop `input.interpolationSettings` from the memo deps and sync it through a guarded write seam like `setCurrentFrame`.

### WR-03: WorkflowStrip per-cell derivation cache grows unboundedly as the timeline window slides

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:401-438`
**Issue:** `rotoCellDerivationCacheRef.current.entries` accumulates one `RotoCellDerivation` per rendered frame and is only ever pruned by (a) full invalidation on structural identity change, or (b) deletion of the previous/new current frame on a frame change. As the user navigates, `buildPhysicsPaintRotoFrameCells` slides the 120-cell window and `getRotoCellDerivation(frame)` inserts entries for every newly visible frame, but entries for frames that scrolled out of the window are never removed. A long session scrubbing across thousands of physical frames grows the Map without bound (each entry holds a view-model with aria/tooltip strings). Full invalidation rescues it only when the physical cells or cached frames change identity.
**Fix:** On a pure `currentFrame` change, drop entries outside the active window:

```ts
} else if (activeCellDerivationCache.currentFrame !== props.currentFrame) {
  const window = new Set(frameCells);
  for (const key of activeCellDerivationCache.entries.keys()) {
    if (!window.has(key)) activeCellDerivationCache.entries.delete(key);
  }
  activeCellDerivationCache.currentFrame = props.currentFrame;
}
```

(or cap `entries` size with an explicit eviction bound).

### WR-04: `_rotoPhysicalStructuralCache` is never pruned on layer teardown or store reset

**File:** `app/src/stores/physicPaintStore.ts:184-204` (`_clearLayerState`), `1110-1128` (`reset`), `1485-1495` (`clearRotoPhysicalRecords`), `826-849` (`loadFromMceOutputs`)
**Issue:** The 38.1-07 structural memo's cache map is keyed by layerId, but none of the four layer/state teardown paths delete its entries. Reads are self-healing (`_resolveRotoPhysicalStructural` deletes the entry when the record map is gone, and the identity triple prevents stale hits if a layerId is reused), so there is no stale-data bug — but layers that are cleared/reset and never read again leave their cached projection + content-revision entry (including sorted record references) resident for the life of the store. This undercuts the memory discipline the phase applied elsewhere (FIFO cap, alpha-canvas pruning).
**Fix:** Add `_rotoPhysicalStructuralCache.delete(layerId)` to `_clearLayerState` and `clearRotoPhysicalRecords`, and `_rotoPhysicalStructuralCache.clear()` to `reset()` and `loadFromMceOutputs` (next to the other map clears).

### IN-02: Redundant `!== undefined` guards after `Number.isInteger` checks

**File:** `app/src/components/physic-paint/roto/rotoTimelineSelectors.ts:207-210`
**Issue:** `Number.isInteger(inBetweenCount) && inBetweenCount !== undefined && inBetweenCount >= 1` — `Number.isInteger(undefined)` is already `false`, so the undefined check is dead (same pattern for `deform` and `position`).
**Fix:** Drop the redundant clauses: `Number.isInteger(inBetweenCount) && (inBetweenCount as number) >= 1` or restructure with a local narrowed variable.

### IN-03: `batch()` wrapping `useState` setters is a no-op and misleading

**File:** `app/src/components/physic-paint/hooks/useRotoCachedPlayback.ts:98-109`
**Issue:** `finishPlayback` wraps its whole stop path in `@preact/signals` `batch()`, but only `playbackTick.value = null` is a signal write; `setIsActive`, `setStatus`, and `setIsPlaying` are `useState` setters (or an external callback) that `batch()` does not defer. The comment claims the batch produces "exactly ONE catch-up render," which overstates what the primitive guarantees.
**Fix:** Either narrow `batch(() => { playbackTick.value = null; })` to the signal write, or adjust the comment to describe the actual (synchronous, single-call-stack) guarantee.

### IN-04: Decode cache retains up to 32 full-resolution decoded images with no hit-recency refresh

**File:** `packages/efx-physic-paint/src/engine/EfxPaintEngine.ts:187-188, 543-563`
**Issue:** `previewBaseImageCache` holds decoded `HTMLImageElement`s (canvas-width x height RGBA each — potentially ~8 MB at 1920x1080, ~250 MB at the 32-entry cap), bounded only by insertion-order FIFO. Cache hits do not refresh recency, so a hot frame revisiting between 32 cold ones can still be evicted; and the cache lives until `destroy()`. The correctness story is fine (superseded loads are rejected before insertion; cleared on destroy), but the footprint/recency policy is worth revisiting.
**Fix:** Consider a smaller cap, an LRU touch on hit (`delete` + `set`), or clearing the cache on `clear()`/launch replacement if frame dataUrls are known not to recur.

### IN-05: `resetBackground` skip memo keys `paperTextures` by Map identity, but the Map is mutated in place

**File:** `packages/efx-physic-paint/src/engine/EfxPaintEngine.ts:515-541` (mutation at `2060-2082`)
**Issue:** The skip memo's input tuple compares `inputs.paperTextures === this.paperTextures`, yet `loadPaperTextures` mutates that same Map instance via `this.paperTextures.set(...)`. Today this self-heals because `loadPaperTextures` also replaces `this.bgData`, failing the identity half of the guard — but the tuple half of the contract is silently dead for in-place texture changes, and any future texture mutation that does not replace `bgData` will be incorrectly skipped by the memo.
**Fix:** Track a texture revision counter (incremented in `loadPaperTextures`) in the memo inputs instead of the Map reference.
