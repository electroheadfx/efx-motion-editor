## User Constraints (from CONTEXT.md)

### Locked Decisions

### Empty-key and break contract

- **D-01:** Empty-frame Insert creates a genuinely empty real Paint key at the cursor frame and a persistent interpolation break owned by that key's stable identity. It must never duplicate, copy, or materialize the previous rendered drawing. Key plus break are accepted, rejected, undone, and redone as one atomic physical-document command. — **Reversibility:** one-way — once persisted and included in canonical revision/history snapshots, changing ownership away from stable key identity would require rewriting saved physical documents and replay semantics.
- **D-02:** The break suppresses only the incoming interpolation span from the preceding real-key segment. A later real key after the inserted key may interpolate normally from the inserted key, creating a new local segment.
- **D-03:** Interpolation Off does not delete, hide, or rewrite the break and Insert never toggles Interpolation. Turning Interpolation On again re-applies the stored boundary.
- **D-04:** When a break-bearing key temporarily has no preceding real key, the break remains attached but dormant. It is not drawn as a leading boundary while the key is first; it becomes visible and effective again if a predecessor later exists.

### Physical-strip marker

- **D-05:** Show the intentional break as a compact left-edge cut immediately before the owning real key inside the existing physical-row/cell geometry. Add no timeline row, track height, persistent badge, or separate marker lane.
- **D-06:** The cut stays visible when Interpolation is Off because the boundary remains durable. It follows normal key visibility and is drawn only when the owning key currently has a predecessor.
- **D-07:** Explain the cut by extending the existing real-key cell tooltip/accessibility copy with the exact fact `Starts a new interpolation segment`. The cut has no independent pointer target or tooltip lifecycle.

### Insert affordance and accepted feedback

- **D-08:** Keep the existing visible toolbar label `Insert` in both valid contexts. Do not add a second action, context-changing button name, persistent helper, or new toolbar surface.
- **D-09:** On a genuinely empty frame, the enabled action tooltip is `Insert an empty key and start a new interpolation segment.` Existing real-key Insert tooltip/status copy remains unchanged; the contextual tooltip alone distinguishes the two valid behaviors.
- **D-10:** After exact acceptance, publish `Inserted empty key at frame {N}. New interpolation segment started.` Keep the cursor at `{N}`, select the new real key, and show its empty Paint canvas ready for drawing.

### Break lifecycle across existing key operations

- **D-11:** Duplicate and Copy/Paste copy only Paint key payload/content. They never copy an intentional break to a fresh key identity; creating a new segment remains an explicit empty-frame Insert action.
- **D-12:** Deleting the real key that owns a break deletes that break in the same atomic delete transaction. The break is never transferred to the next key and never persists as an orphan frame-position boundary.
- **D-13:** Pasting/replacing Paint content onto an existing break-bearing key preserves the destination key identity and its break; only the Paint payload changes.
- **D-14:** Every accepted identity-preserving timing edit carries the break with the stable key identity, including direct drag, group drag, directional Push Left/Right, and partial Key Spacing. If ordering changes, the break applies to the owning key's new predecessor.

### Availability and rejection feedback

- **D-15:** Known-invalid empty-frame Insert targets are disabled before activation and expose the exact reason through the existing guarded tooltip. The physical resolver remains the fail-closed authority for stale/racing inputs and must reject before mutation.
- **D-16:** Product reasons are target-specific: generated render-only frame, resolved linked occurrence, unresolved linked frame, target occupied for the empty-frame operation, invalid destination, out-of-capacity destination, and edit already in flight. Do not expose raw resolver codes as user copy.
- **D-17:** A race rejected after activation publishes the same verbatim mapped product reason used by the disabled tooltip. One reason mapper owns both surfaces so preflight and rejection cannot disagree.
- **D-18:** Failure leaves records, breaks, Loop Clips, selection, cursor, and history unchanged. No modal, alert, automatic navigation, nearest-empty fallback, or partial optimistic marker is introduced.

### Locked regression boundaries

- **D-19:** Existing Insert/Open-and-Insert behavior on an occupied selected real key must not regress. The new empty-frame path is additive and context-dispatched.
- **D-20:** Generated/non-editable frames, resolved or unresolved linked frames, invalid/out-of-capacity destinations, and occupied targets for the new empty-frame intent cannot create a key or break.
- **D-21:** Existing physical-key selection, painting, deletion, Copy/Paste, drag, Key Spacing, Undo/Redo, Loop Clip, and interpolation workflows remain unchanged except where the decisions above explicitly describe break participation.

### Claude's Discretion

- Exact left-edge cut dimensions, color, and layering within the existing cell tokens, provided it stays compact, visible in all supported themes/states, adds zero geometry, and cannot be confused with the 3px Loop Rail's canonical white endpoint cuts.
- Exact target-specific failure sentences beyond the locked enabled tooltip and accepted success message, provided one mapper supplies both tooltip and status copy.
- Exact additive persistent field/type shape and resolver intent name, provided the break is stable-key-owned, fail-closed, revisioned, persisted, and included in complete accepted history snapshots.
- Exact test decomposition and UI-SPEC need assessment; native visual UAT remains required for the marker and contextual Insert behavior.

## Summary

Phase 43.1 should extend the existing parent-authoritative physical Roto document with one additive immutable collection of stable key identities representing incoming interpolation breaks. The durable fact belongs to the real key, not a frame number, generated cell, selection, toolbar state, or interpolation toggle. This directly satisfies the locked identity and lifecycle rules: mapping-only timing edits carry the break automatically, deleting the owner removes it, replacing the owner's payload preserves it, and fresh identities created by Duplicate or Paste do not inherit it. [VERIFIED: .planning/phases/43.1-intentional-gap-insert-use-specs-milestone-v0-9-0-new-phases/43.1-CONTEXT.md:20-25,39-45; quoted contract: `persistent interpolation break owned by that key's stable identity`, `Duplicate and Copy/Paste copy only Paint key payload/content`, `Deleting the real key that owns a break deletes that break`, `Pasting/replacing Paint content onto an existing break-bearing key preserves the destination key identity and its break`]

The smallest safe implementation is one complete-document path: strict model and revision support first; one new resolver intent and semantic delta; complete break-state threading through coordinator, bridge, store, persistence, history, and replay; then Signals-derived Insert context and integrated marker presentation. Generated frames remain runtime derivations. For each adjacent ordered pair `(left, right)`, skip only that pair's strict interior when `right.keyId` owns a break. This yields the required isolated incoming gap while permitting a later pair to interpolate outward from the inserted key. [VERIFIED: SPECS/milestone-v0.9.0-new-phases/phase-43.1-intentional-gap-insert-prompt.md:9-17,21-29; quoted example: `After:   [0]--[3]--[6]    [10]` and `[0]--[3]--[6]    [10]--[13]`]

No external package or new test configuration is needed. Extend the existing Preact Signals, physical resolver/coordinator, strict parser, persistence, bridge, Vitest, and native UAT patterns. [ASSUMED]

**Primary recommendation:** Add one stable-key-owned incoming-break collection to the canonical physical document and carry it as complete accepted state through the existing resolver → coordinator → bridge → store/history path; do not create a second command, interpolation engine, UI authority, or marker target. [ASSUMED]

### Pattern 1: Stable-Identity-Owned Additive State

**What:** Store incoming break ownership as a complete immutable collection of real-key IDs. The recommended field name is `incomingInterpolationBreakKeyIds`; the final name is discretionary. [ASSUMED]

**When to use:** Every canonical physical document, proposal, snapshot, transport payload, accepted ledger entry, and persistence record. [ASSUMED]

**Rules:**
- Strict parse rejects malformed, duplicate, and orphan owner IDs. [ASSUMED]
- Absent persisted field hydrates as a frozen empty collection, matching the established additive-field approach. [ASSUMED]
- Canonicalize deterministically, preferably by the real-key ordering or a documented stable key-ID sort. [ASSUMED]
- Never mutate the array in place; replace it wholesale so structural memoization can include collection identity. [ASSUMED]
- Do not store the predecessor or a frame-position boundary; derive the predecessor from current ordering. [VERIFIED: .planning/phases/43.1-intentional-gap-insert-use-specs-milestone-v0-9-0-new-phases/43.1-CONTEXT.md:24-25,45; quoted rules: `temporarily has no preceding real key`, `If ordering changes, the break applies to the owning key's new predecessor.`]

### Pattern 2: Right-Key Adjacency Rule

**What:** During generated-cell derivation for adjacent ordered real keys `(left, right)`, skip the strict interior only when the right key owns an incoming break. [ASSUMED]

**When to use:** Both read-only projection and proposal finalization must call the same projection function with the same break set. [ASSUMED]

**Example:**

```ts
// Recommended shape; exact field name is discretionary. [ASSUMED]
for (let index = 0; index < orderedPairs.length - 1; index += 1) {
  const left = orderedPairs[index];
  const right = orderedPairs[index + 1];

  if (incomingBreakKeyIds.has(right[0])) {
    continue;
  }

  for (let frame = left[1] + 1; frame <= right[1] - 1; frame += 1) {
    generatedCells.push({
      kind: 'generated',
      appFrame: frame,
      leftKeyId: left[0],
      rightKeyId: right[0],
    });
  }
}
```

### Pattern 3: One Complete Accepted Transaction

**What:** The new resolver proposal carries complete next records and complete next breaks. The coordinator snapshots and stages both, the bridge independently validates both, and history records both in one accepted before/after command. [ASSUMED]

**When to use:** Empty-segment Insert, rollback, Undo, and Redo. Existing mapping-only operations carry the break collection unchanged; deletes remove owner IDs as part of their complete proposal. [ASSUMED]

**Acceptance ordering:**
1. Compute target and blank payload without mutation. [ASSUMED]
2. Resolver rejects or returns one complete proposal. [ASSUMED]
3. Coordinator captures complete pre-state. [ASSUMED]
4. Bridge validates expected revision and semantic delta. [ASSUMED]
5. Store installs one complete physical document. [ASSUMED]
6. Only after exact acknowledgement: publish locked success copy, keep cursor at target, select new key, and reconcile the blank canvas. ### Pattern 4: One Typed Target Classifier and Reason Mapper

**What:** Derive a discriminated target result such as occupied-real, genuinely-empty, generated, resolved-linked, unresolved-linked, invalid, out-of-capacity, or busy. A single pure mapper converts invalid variants to product copy. [ASSUMED]

**When to use:**

### Pattern 5: Descriptive State on the Existing Cell Control

**What:** Project a boolean such as `startsInterpolationSegment` into the existing real-key cell view model. Render one non-interactive internal cut and append the exact descriptive fact to the cell's existing tooltip and accessible description. [ASSUMED]

**When to use:** Only when the owner currently has a predecessor, regardless of global interpolation enabled state. [VERIFIED: .planning/phases/43.1-intentional-gap-insert-use-specs-milestone-v0-9-0-new-phases/43.1-CONTEXT.md:25,29-31]

### Anti-Patterns to Avoid

- **Frame-number-owned breaks:** Timing edits would require manual rebasing and could leave orphan boundaries. Keep ownership on stable key identity. [ASSUMED]
- **Two accepted commands:** Adding the blank key and break separately violates atomic rejection, history, and persistence. [VERIFIED: .planning/phases/43.1-intentional-gap-insert-use-specs-milestone-v0-9-0-new-phases/43.1-CONTEXT.md:22]
- **Effect-mirrored availability:** It creates a second UI authority and possible stale tooltip/action states. Derive from Signals. [CITED: https://preactjs.com/guide/v10/signals/]
- **UI-only marker state:** The marker must derive from accepted canonical state; never show it optimistically. [VERIFIED: .planning/phases/43.1-intentional-gap-insert-use-specs-milestone-v0-9-0-new-phases/43.1-CONTEXT.md:47-51]
- **Raw resolver code as product copy:** Keep diagnostics internal and map to one product vocabulary. [VERIFIED: .planning/phases/43.1-intentional-gap-insert-use-specs-milestone-v0-9-0-new-phases/43.1-CONTEXT.md:49-50]

## Common Pitfalls

### Pitfall 1: Suppressing Both Sides of the Break-Bearing Key
**What goes wrong:** The inserted key remains isolated even after a later real key is added. [ASSUMED]
**Why it happens:** The implementation treats a break as a property of the key's entire segment rather than only its incoming adjacency. [ASSUMED]

### Canonical Break Collection Parsing

```ts
// Recommended implementation shape; identifiers are discretionary. [ASSUMED]
function parseIncomingInterpolationBreakKeyIds(
  value: unknown,
  records: readonly PhysicPaintRotoRealKeyRecord[],
): readonly string[] {
  if (value === undefined) return EMPTY_INCOMING_BREAK_KEY_IDS;
  if (!Array.isArray(value)) throw new Error('Invalid interpolation breaks.');

  const ownerIds = new Set(records.map((record) => record.keyId));
  const seen = new Set<string>();

  const parsed = value.map((item) => {
    if (typeof item !== 'string' || item.length === 0) {
      throw new Error('Invalid interpolation break owner.');
    }
    if (seen.has(item) || !ownerIds.has(item)) {
      throw new Error('Invalid interpolation break owner.');
    }
    seen.add(item);
    return item;
  });

  return Object.freeze(parsed);
}
```

// Recommended shape; final union names and product sentences are discretionary. [ASSUMED]
const insertTarget = computed(() => classifyInsertTarget(input));
const canInsertFrame = computed(() => insertTarget.value.kind === 'occupied-real'
  || insertTarget.value.kind === 'genuinely-empty');

async function insertRotoFrame(): Promise<boolean> {
  const target = classifyInsertTarget(input);

      intent: { kind: 'insert-slot', selectedKeyId: target.keyId },
      operationKind: 'insert-slot',
      requiredKeyId: target.keyId,

  return false;
