## Non-Blocking Deferred Findings

### DF-01: Cache publication is not transactional with project persistence

**Original technical severity:** Critical
**Phase 43.1 disposition:** `NEW_SCOPE_FROM_VERIFIER` — deferred, non-blocking

**Files:**
- `app/src/lib/physicPaintPersistence.ts:163-168,246-273`
- `app/src/stores/projectStore.ts:684-692,725-752`

`savePhysicPaintData()` publishes or removes the fixed-path cache before the corresponding `.mce` save completes. A project-save failure can therefore leave the prior durable project paired with changed sidecars.

This ordering predates Plans 07–12. Plan 07 intentionally preserved canonical `cache/physic-paint/...` metadata paths and direct empty-output removal while closing the accepted pre-publication cache-replacement gap. Cross-resource `.mce`/cache transactionality and immutable generation-qualified project paths were not part of the locked closure contract.

**Deferred remediation:** Design separately approved persistence work covering immutable generations, project-save failure rollback, and old-generation cleanup.

### DF-02: Native publication lacks containing-directory crash durability

**Original technical severity:** Critical
**Phase 43.1 disposition:** `NEW_SCOPE_FROM_VERIFIER` — deferred, non-blocking

**Files:**
- `app/src-tauri/src/services/physic_paint_cache.rs:45-69,88-120`
- `app/src-tauri/src/commands/physic_paint_cache.rs:23-52`

The Plan 07 native service synchronizes staged files and directories before rename/exchange but does not synchronize `cache_parent` after the namespace mutation.

Plan 07's locked contract required pre-publication recursive synchronization, one same-directory rename/exchange, old-cache survival on pre-publication failure, and process-time old-or-new reader visibility. Post-rename parent-directory synchronization, crash/power-loss durability, and post-mutation sync-failure semantics were not specified.

**Deferred remediation:** Add parent-directory synchronization and explicit post-mutation failure semantics in separately approved persistence hardening.

### DF-03: Provenance-only Loop Clip updates can be treated as no-ops

**Original technical severity:** Critical
**Phase 43.1 disposition:** `NEW_SCOPE_FROM_VERIFIER` — deferred, non-blocking

**Files:**
- `app/src/stores/physicPaintStore.ts:1495-1511`
- `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:878-897`

The store comparator omits `scriptId`, motion deformation/position, and `overrideColor`, while the canonical Loop Clip fingerprint includes them.

The comparator predates Plans 07–12, and the historical Phase 43.1 verification explicitly recorded this concern as non-blocking. Phase 43.1 also explicitly excluded changes to Loop Clip persistence; Plans 07–12 preserved existing Loop Clip behavior and did not introduce this defect.

**Deferred remediation:** Use one complete canonical Loop Clip equality helper and add provenance-only replacement tests in separately approved Loop Clip maintenance.

### DF-04: Browser frame-sync trusts unauthenticated `postMessage` senders

**Original technical severity:** Critical security
**Phase 43.1 disposition:** `NEW_SCOPE_FROM_VERIFIER` — deferred to separate security remediation, non-blocking for Phase 43.1

**Files:**
- `app/src/lib/physicPaintBridge.ts:1448-1467,1786-1797`
- `app/src/main.tsx:37-41`
- `app/src/lib/physicPaintBridge.test.ts:1994-2011`

The browser fallback validates payload shape but not `event.origin`, `event.source`, the active child window, or launch identity.

This behavior predates Plans 07–12. The historical Phase 43.1 verification explicitly recorded it as non-blocking, and Plan 10 explicitly excluded unrelated security findings from the gap closure implementation.

**Deferred remediation:** Preserve for a separate security remediation that authenticates origin, exact source window, and active launch operation. Do not use it to reopen Phase 43.1 retroactively.
