# Phase 43.1 Code Review

## Assessment

The Phase 43.1 user-facing contract and native UAT passed, but the standard source review found five blocking correctness/security risks and three warnings. The review is advisory in the execute-phase workflow; no source changes were applied. Group deletion and packed-boundary insertion remain explicitly deferred and must not expand Phase 43.1.

## Critical Findings

### CR-01: Cache replacement can destroy the previous valid sidecars

**File:** `app/src/lib/physicPaintPersistence.ts:214-224`

The save path removes the existing cache directory before the replacement directory and every PNG sidecar are durable. A directory creation or write failure can therefore leave persisted metadata referencing deleted files or an incomplete replacement.

**Remediation:** Write the complete replacement into a sibling temporary directory, atomically swap only after every write succeeds, and restore the previous directory if the final rename fails.

### CR-02: Parent authority does not semantically prove every physical edit

**File:** `app/src/lib/physicPaintBridge.ts:728-923`

The parent independently validates semantic deltas for `insert-empty-segment`, duplicate/paste operations, Play Script, and interpolation changes, but mapping operations such as insert-slot, delete, move, group move/delete, and Force Spacing can reach complete-document replacement after structural validation alone. A child holding the active launch tuple and revision can submit unrelated structurally valid state under one of those operation kinds.

**Remediation:** Transmit and validate a typed intent for every operation, rerun the canonical resolver on the parent, and compare its complete records/selection/Loop Clips/break result against the submitted document before mutation.

### CR-03: Undo/Redo command authorization is not authority-scoped

**File:** `app/src/lib/physicPaintBridge.ts:123-135,884-955`

Accepted commands are retrieved globally by original operation ID without binding the ledger entry to project context, layer, launch operation, or capacity. Documents with equal revisions can allow a replay command from one authority scope to authorize a transition in another.

**Remediation:** Store and verify `projectContextId`, `layerId`, `launchOperationId`, and capacity on every ledger entry; compare complete before/after snapshots and partition or clear the ledger when authority changes.

### CR-04: Browser frame synchronization trusts arbitrary message senders

**File:** `app/src/lib/physicPaintBridge.ts:1247-1265`

The browser `message` listener forwards data to frame synchronization without checking origin, source window, or active launch identity. A window with a reference to the editor can seek the main timeline and influence subsequent edit context.

**Remediation:** Require same origin, the active Physics Paint child window as `event.source`, and a matching active launch tuple before applying frame synchronization.

### CR-05: Loop Clip provenance-only updates can be discarded

**File:** `app/src/stores/physicPaintStore.ts:1495-1510`

The Loop Clip no-op comparison omits revision-bearing provenance members including `scriptId`, motion deformation/position, and `overrideColor`. A valid provenance-only update can return success without storing the new value, bumping revision, or notifying subscribers.

**Remediation:** Reuse one canonical Loop Clip equality/encoding seam that includes every persisted revision-bearing field and add independent provenance-field mutation tests.

## Warnings

### WR-01: Rollback/history snapshots may retain mutable references

**File:** `app/src/components/physic-paint/hooks/useRotoPhysicalEditCoordinator.ts:412-416,575-604`

Frame-map cloning copies only the Map container, while entry values, repaint-base objects, and engine snapshots may remain mutable. Later mutations could alter a previously captured rollback or history snapshot.

**Remediation:** Require immutable snapshot values or type-aware clone/serialization ports for frame entries, references, and engine state.

### WR-02: Loop resolution exposes a mutable Map through an immutable contract

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalResolver.ts:2059-2071,3265-3271`

The outer loop-resolution context is frozen but `keyIdByAppFrame` remains a native mutable Map. `set`, `delete`, or `clear` can corrupt later lazy resolution without a Signal update.

**Remediation:** Wrap the Map with the existing immutable-map helper and test that mutation methods throw without changing resolution.

### WR-03: Group operations are partially implemented but availability is inconsistent

**Files:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:210-240`, `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:669-719,1228-1264`, `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:700-740`

Select All intentionally clears the primary key while retaining the multi-selection set. Group execution branches exist, but toolbar delete and drag availability still require a primary key, creating inconsistent keyboard/toolbar behavior.

**Scope decision:** The user explicitly deferred group deletion, frame-from-group behavior, packed-boundary hole insertion, and any `Insert Gap` action to a later phase. Do not fix this by expanding Phase 43.1. Reassess the existing partial group machinery only when that later phase is explicitly scheduled.
