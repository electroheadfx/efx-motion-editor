**As a** stop-motion animator, **I want to** have every real Roto key, generated in-between, timeline edit, persisted frame, and rendered output use one deterministic physical-frame authority, followed by a polished timeline UI that exposes the approved behavior without duplicating business logic, **so that** editing, reopening, previewing, and exporting the same Roto work cannot disagree about frame identity.

<objective>

Purpose: Make every user-visible downstream Roto read agree with the accepted physical records and identity-owned cache state established by Plan 09. A moved key must play, onion, reference, preview, export, and extend the timeline at its current physical position without any source/display adapter or stale generated timing authority.

Output: Physical navigation and traversal, one shared physical Roto renderer used by preview and export, deterministic missing/background composition, and physical timeline-length derivation while Basic and FX paint remain unchanged.
</objective>

<assumptions>
- A Roto layer's standalone playback extent is physical frame `0` through the highest valid real-key `appFrame`, inclusive. Leading cells before the first real key are ordinary missing cells; the playback range has no trailing cell beyond the last real key. A layer with no valid real key has no Roto playback extent.
- Global preview/export may request a frame before the first or after the last Roto real key because another sequence or layer establishes the global duration. Those requests are missing Roto frames, never generated frames, and follow the same transparent or configured paper/background-only policy.
- A runtime generated render payload is usable only for a currently derived generated cell whose two adjacent stable real-key identities and accepted revisions match the current physical projection. If that payload is absent, malformed, stale, or unresolved, the cell follows missing-frame composition; it never duplicates or blends a neighboring payload inside the downstream consumer.
- Onion traversal considers ordered real physical keys only. From a real, generated, or empty current cell, previous and next mean the nearest strictly lower and strictly higher real-key `appFrame` values. Existing onion count, previous/next toggles, depth order, opacity math, cached-composite preference, and stroke-preview preference remain unchanged.
- Reference/display lookup may return the exact accepted real-key payload at a real cell or the exact accepted runtime-generated payload at a derived generated cell. Empty, leading, trailing, malformed, and unavailable generated cells return no paint payload and trigger the existing reference clear/reset behavior.
- Timeline extension is `highestValidRealKeyAppFrame + 1`. Runtime generated interiors cannot extend this value because they are strictly between adjacent real keys. Invalid physical projection returns no Roto-derived extension rather than using cache metadata as fallback.
- No external service, dependency, package-manager install, test configuration, build, or server process is required. Execution must stop and report an assumption delta rather than widening this plan if that changes.
</assumptions>
