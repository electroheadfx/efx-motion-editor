# Phase 43.2: Code Review Report (WR-01)

**Reviewed:** 2026-08-13T00:00:00Z
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

The WR-01 correction (commit 35c73b42) recomputes the canonical physical hash at both trust boundaries: the TypeScript guard `isPhysicPaintActionTransactionTarget` now requires `physicalHash === buildPhysicPaintRotoProjectEquality(parsedDocument)`, and the Rust `validate_prepare_request` recomputes `canonical_physical_hash` and rejects a caller-supplied hash that does not match, before any retained artifact is persisted.

I verified the core encoding by replicating the TypeScript `buildPhysicPaintRotoProjectEquality` in Node and confirmed the Rust parity vector `project-360-b521097e` is correct for the fixture. The TS guard change is correct and introduces no false rejections for valid ASCII documents. The mismatch-rejection tests on both sides are adequate for the basic tamper case.

However, the parity claim "byte-for-byte" does not hold for every value the canonical document can carry. There are four concrete defects:

1. **f64 formatting divergence** — JS `String(number)` switches to exponential notation below 1e-6 and at/above 1e21; Rust `format!("{}", f64)` always uses decimal notation. A valid document with `grainStrength` in `(0, 1e-6)` produces different hashes on the two sides, so the Rust boundary rejects a legitimate request.
2. **Non-ASCII string divergence** — `canonical_string` length prefixes differ (UTF-16 code units in TS vs UTF-8 bytes in Rust), the record/loop sort comparators differ (`localeCompare` vs byte-wise `cmp`), and the hash length prefix differs. `localeCompare` is also locale-dependent, so the TS hash is not stable across environments.
3. **One-directional parity pin** — the Rust test pins `project-360-b521097e` but the fixture's `revision` is non-canonical (`"physical-after"` vs canonical `"physical-292-ea77b953"`), so `buildPhysicPaintRotoProjectEquality` would throw on the exact fixture the comment claims it was computed from. No TS test pins the same vector, so TS drift breaks the cross-boundary flow silently.
4. **Rust trust boundary is more lenient than the TS guard** — `canonical_physical_hash` reads only the fields it needs and does not structurally validate the document (`kind: 'real-key'`, duplicate keyIds/appFrames, unknown members, `groupOverrideRecords: null`, width/height both-or-neither, capacity bounds, selectedKeyId existence, cursorAppFrame < capacity, loop lifecycle all-or-nothing, canonical revision).

No BLOCKER findings: the divergences cause false rejection of valid requests (failed transactions, no data loss or security exposure), and the common path (ASCII keyIds, grainStrength >= 1e-6) is correct.

## Warnings

### WR-01: f64 formatting divergence rejects valid documents with tiny grainStrength

**File:** `app/src-tauri/src/services/script_library.rs:1242-1244` (and `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:1244-1246`)
**Issue:** `canonical_number` uses Rust `format!("{}", f64)`, which always emits decimal notation. JS `String(number)` (used by `encodeCanonicalNumber`) switches to exponential notation for values `< 1e-6` and `>= 1e21`. Verified empirically:

| value | JS `String(v)` | Rust `format!("{}", v)` |
|---|---|---|
| `0.0000001` (1e-7) | `1e-7` | `0.0000001` |
| `0.000001` (1e-6) | `0.000001` | `0.000001` (match) |
| `1e21` | `1e+21` | `1000000000000000000000` |
| `0.1` / `0.30000000000000004` | `0.1` / `0.30000000000000004` | same (match) |

`grainStrength` is a finite float in `[0,1]` per `isPhysicPaintRotoBackground` (`physicPaint.ts:1734-1745`), so values in `(0, 1e-6)` are valid canonical-document content. For such a document the TS guard computes a hash containing `n1e-7;` while Rust recomputes `n0.0000001;` — the hashes differ and `validate_prepare_request` rejects a legitimate request with `"Target physical hash does not match the canonical physical document"`. The same divergence applies to `capacity >= 1e21` (unrealistic, but the model does not bound capacity above).

**Fix:** Make the two formatters agree. Options: (a) implement a JS-compatible `Number::toString` in Rust (shortest round-trip with the same exponent thresholds); (b) bound `grainStrength` to `>= 1e-6` in the shared validator so both formatters stay in decimal range; or (c) encode floats with an explicit fixed-precision scheme on both sides. Note that Rust `{:?}` is not a drop-in fix — it emits `24.0` for integers, which also diverges from JS `String(24)`.

### WR-02: Non-ASCII strings diverge in length prefix, sort order, and hash length

**File:** `app/src-tauri/src/services/script_library.rs:1238-1240, 1292-1298, 1338-1344, 1483-1490` vs `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:1240-1242, 996, 1058, 1053, 1266-1272`
**Issue:** Three independent divergences for any non-ASCII string the document can carry (`keyId`, `loopId`, `scriptId`, `paperGrain`, `overrideColor`):

1. `canonical_string` length prefix: TS uses `value.length` (UTF-16 code units), Rust uses `value.len()` (UTF-8 bytes). `"é"` encodes as `s1:é;` in TS but `s2:é;` in Rust.
2. Sort comparator: TS sorts records/loops/breaks with `localeCompare`; Rust sorts with byte-wise `cmp`. Verified: `"é".localeCompare("z")` is `-1` (é first) but byte-wise `"é" > "z"` is `true` (z first). Different order → different encoded string → different hash.
3. Hash length prefix: TS `source.length` (UTF-16) vs Rust `source.len()` (UTF-8 bytes) in the `project-<len>-<hex>` output.

Additionally, `localeCompare` without an explicit locale is environment-dependent (e.g., Swedish collation sorts `"ä"` after `"z"`), so the TS hash is not stable across user locales even for the same document. The validators (`isBoundedKeyId`, `isNonEmptyString`) do not restrict to ASCII, so these are reachable values.

**Fix:** Use a locale-independent, code-unit-based comparator in TS (e.g., `a.keyId < b.keyId ? -1 : a.keyId > b.keyId ? 1 : 0`), and make the Rust length prefixes count UTF-16 code units (or restrict canonical strings to ASCII and reject non-ASCII at validation).

### WR-03: Parity test is one-directional and its fixture is not a valid TS input

**File:** `app/src-tauri/tests/script_library_transaction_contract.rs:148-160` (fixture at 58-77)
**Issue:** The test pins `project-360-b521097e` on the Rust side only. I verified the vector is correct by replicating the TS encoding in Node, but two problems remain:

1. The fixture's `revision` is `"physical-after"`, which is not the canonical revision (computed canonical: `physical-292-ea77b953`). `buildPhysicPaintRotoProjectEquality` calls `parsePhysicPaintRotoPhysicalDocument`, which throws `"canonical revision mismatch"` on this exact fixture — so the comment's claim that the vector was "computed from `buildPhysicPaintRotoProjectEquality`" is inaccurate, and the test does not exercise the TS function on a document TS would accept.
2. No TS test pins the same vector. `physicPaint.test.ts` computes the hash dynamically via `buildPhysicPaintRotoProjectEquality`, so if the TS encoding changes, the TS tests still pass, the Rust test still passes (it pins the old vector), and the cross-boundary flow breaks silently.

**Fix:** Add a TS test asserting `buildPhysicPaintRotoProjectEquality` produces `project-360-b521097e` for the same document (with a canonical `revision`), or add a cross-language parity test that runs both implementations on one shared fixture.

### WR-04: Rust trust boundary does not structurally validate the physical document

**File:** `app/src-tauri/src/services/script_library.rs:1496-1596` (called from `validate_prepare_request` at 1218-1225)
**Issue:** `canonical_physical_hash` reads only the fields it needs and errors only when a required field is missing or of the wrong JSON type. It does not enforce the structural rules the TS guard enforces, so the Rust boundary accepts documents TS rejects whenever the caller-supplied hash matches the Rust encoding. Omitted checks include: `kind: 'real-key'` on records, duplicate `keyId`/`appFrame`, unknown members, `groupOverrideRecords: null` (treated as absent), payload `width`/`height` both-or-neither, `appFrame < capacity`, `selectedKeyId` existence, `cursorAppFrame < capacity`, loop lifecycle all-or-nothing, and canonical `revision`. A malformed document accepted here is persisted as the recovery anchor; the TS guard would then reject it at recovery time, turning a recoverable transaction into a failed recovery.

**Fix:** Run a full structural validation of `physical_document` in Rust (mirroring `parsePhysicPaintRotoPhysicalDocument`) before hashing, or at minimum validate the fields the hash reads (record `kind`, duplicate identities, capacity bounds, lifecycle completeness).

## Info

### IN-01: `authority.expectedPhysicalHash` remains advisory text

**File:** `app/src-tauri/src/services/script_library.rs:1167-1170`
**Issue:** The WR-01 fix enforces the *target* hash but leaves `authority.expected_physical_hash` validated as text only, never compared to anything. This is the same class of "advisory text" the fix was meant to eliminate, though the pre-transaction state is independently pinned by `expected_action_revision` via `require_revision`, so the impact is limited.

**Fix:** Either compare `expected_physical_hash` against the canonical hash of the current physical state, or document why it is intentionally advisory.

### IN-02: Rust integer types are narrower than the TS guard's safe-integer range

**File:** `app/src-tauri/src/services/script_library.rs:69-91`
**Issue:** `cursor_app_frame: u32` and `generation: u64` reject values above `u32::MAX`/`u64::MAX`, while the TS guard accepts any non-negative safe integer up to 2^53. Not reachable in practice (cursor is bounded by capacity, generation is a small counter), but a latent boundary divergence.

**Fix:** Use `u64` for `cursor_app_frame` or align both sides on the same bound.
