## User Constraints (from CONTEXT.md)

### Locked Decisions

### Product nomenclature and Group lifecycle

- **D-01:** Every EFX Paint/Roto user-facing surface uses the locked terminology: `Group`, `Motion`, `Motion Group`, `Static`, `Static Group`, future `Key Group`, `Group Rail`, `Edit Group`, `Action`, `Actions`, `Save Action`, `Create Group…`, `Group Type` with `Motion` and `Static`, and `Apply to Frame`. Visible labels, tooltips, inspector headings, dialogs, status/error copy, accessibility names, product-copy tests, and new planning artifacts follow this vocabulary.
- **D-02:** Internal TypeScript, Rust, transport, and persistence identifiers may retain `loopClip`, `progressive`, `static`, and `scriptId` where renaming has no product benefit. Existing saved documents receive no nomenclature-only migration.
- **D-03:** A Group has one stable logical identity, one Action provenance reference, committed real source keys, derived occurrences, one or more visible rail ranges, applied mode/Motion/color/repeat/placement/source-cycle settings, optional source sharing, and derived caches that never become a second authority. The persisted Action is provenance and the explicit Regenerate source, not a live dependency that silently changes accepted output.
- **D-04:** Synchronization state is a durable accepted lifecycle fact: green means Synchronized with Action; orange means Modified by accepted local Paint or Delete Frame work; neutral gray distinguishes Action detached from Source Action unavailable. Existing unresolved/error presentation has precedence and is never replaced by the synchronization dot. The dot remains visible while Interpolation is Off and is passive—no separate pointer target or added timeline height.
- **D-05:** Action-content editing, automatic Action mutation from Paint, `Update Action from Group Frame…`, and Relink are outside this phase. Deleting and recreating a Group is the current path after detachment.

### Exact-frame local Paint

- **D-06:** Painting on a repeated Group occurrence changes only that exact physical frame inside the selected logical Group. Other repeats in the same Group remain byte-equivalent, and other Groups remain unchanged. Copy-on-write authority occurs before mutation whenever source keys or caches are shared. — **Reversibility:** costly — changing later to cycle-phase-wide edits would require reinterpreting or migrating saved frame-local modifications and their history semantics.
- **D-07:** The persisted Action is never modified by local Paint. Local Paint preserves Group identity, Motion/Static mode, placement, repeat, relative timing, stored applied settings, Action provenance, and Regenerate capability.
- **D-08:** An exact-frame local Paint edit keeps the Group Rail continuous. It adds no fragment, split, or frame-level modification marker; the Group-level synchronization dot changes to orange and its tooltip/accessibility copy explains the Modified state.
- **D-09:** A Group returns from Modified to Synchronized only when Regenerate restores the Action result or Undo restores the accepted synchronized snapshot. Redo reapplies the Modified state. Manually repainting visually equivalent pixels does not silently change provenance state.
- **D-10:** Painting directly into a frame previously emptied by Delete Frame fills that exact Group frame, removes the locally owned deletion gap at that frame, visually reunites adjacent fragments when contiguous again, and leaves the Group Modified.
- **D-11:** Local Paint acceptance, copy-on-write source/cache changes, synchronization state, gap removal/reunion, canvas reconciliation, and Undo/Redo are one canonical accepted transaction. Rejection or cancellation changes nothing.

### Delete Frame, fragments, and Delete Group

- **D-12:** Delete, Backspace, and the visible Delete action open the same Studio-local choice dialog only when the active physical position is owned by a Motion Group or Static Group. The dialog offers exactly `Delete Group`, `Delete Frame`, and `Cancel`. Ordinary-key deletion remains unchanged and neither Group action deletes the referenced Action.
- **D-13:** The Delete dialog uses one compact choice-card surface. It identifies the Group and current frame once, then explains each action inline: Delete Group removes all fragments and uniquely owned source/cache/gap authority; Delete Frame removes one occurrence, creates or adjusts the intentional gap/range, and leaves the Group Modified. Do not add a second confirmation step.
- **D-14:** A middle Delete Frame produces explicit left and right visible ranges of the same stable logical Group, with the selected frame left as one intentional persistent empty gap. No invisible per-frame exclusion mask or second fragment authority is introduced. The right fragment resumes the exact source-cycle phase the original Group would have rendered after the deleted frame. — **Reversibility:** costly — treating fragments as independent Groups later would require identity, provenance, history, selection, and saved-document migration.
- **D-15:** Selecting any fragment selects the whole logical Group. Every fragment receives the selected treatment, the Actions inspector targets the one stable Group identity, and Delete Group / Regenerate apply to all fragments.
- **D-16:** Every visible fragment carries the same passive synchronization dot centered on that fragment. After Delete Frame, each fragment shows the shared orange Modified state so independently scrolled ranges remain understandable.
- **D-17:** Deleting the first or final occurrence shortens the visible Group range. Choosing Delete Frame on the only remaining occurrence keeps the required `Delete Frame` label but explicitly warns that this will remove the whole logical Group and its uniquely owned data.
- **D-18:** Delete Group removes the complete selected logical Group, every fragment, occurrences, uniquely owned source real keys, uniquely owned caches, and locally owned persistent gaps/fragment authority. It does not delete the Action, another Group sharing the same `scriptId`, or source/cache data still referenced by another Group. Cleanup and one-step Undo/Redo are atomic.

### Regenerate

- **D-19:** `Regenerate` in Edit Group is enabled only for an orange Modified Group whose attached Action is available. Synchronized, detached, and source-unavailable Groups expose clear disabled reasons rather than performing a no-op or failing after activation.
- **D-20:** Regenerate uses one structured confirmation rather than raster before/after thumbnails. The confirmation shows Group name/type, original/restored range, locally painted frame count, deleted-frame count and ranges, fragment reunion, locally owned gaps that will clear, resulting Synchronized state, and any source/cache effects.
- **D-21:** If accepted shared-source Regenerate affects multiple synchronized Groups, the confirmation shows the exact affected count plus a compact placement-ordered list of every affected Group name and range. The commit control states `Regenerate {N} Groups`.
- **D-22:** Accepted Regenerate reloads the referenced persisted Action, reconstructs the selected logical Group from the Action plus its stored applied settings, restores locally painted and deleted frames, reunites fragments, restores the complete original range and exact source-cycle phase, clears locally owned Delete Frame gaps, returns the dot to green, and preserves stable Group identity and placement in one atomic Undo/Redo transaction.
- **D-23:** After Regenerate succeeds, the initiating Group remains selected and the physical cursor remains on its current frame. The current Studio canvas reconciles immediately from the regenerated accepted result, including when that frame was a restored deletion gap. Shared affected Groups do not replace the initiating selection.
- **D-24:** Detached or unavailable Actions cannot Regenerate. If Action editing is introduced later, Regenerate uses the latest explicitly saved Action version; accepted Groups never update silently.

### Action deletion

- **D-25:** Deleting an unreferenced Action retains the existing simple Action-library flow. Deleting an Action referenced by one or more Groups opens one Actions-panel dialog with exactly `Keep Groups` (recommended), `Delete Action and Groups`, and `Cancel`.
- **D-26:** `Keep Groups` deletes the Action and detaches provenance while preserving every affected Group, fragment, key, timing value, placement, repeat, cache, rendered result, and occupied range. Affected Groups become neutral gray detached Groups and Regenerate is unavailable. Keeping Groups does not free timeline space.
- **D-27:** `Delete Action and Groups` deletes the Action and every logical Group referencing it, including every fragment and uniquely owned source/cache/gap authority, as one atomic destructive transaction. Shared data referenced outside the deleted set survives.
- **D-28:** Deleting a Group never deletes its Action. Action deletion dialogs disclose affected Group count/ranges, source/cache cleanup, resulting synchronization state, and occupied-space consequences before commit. Cancellation or stale rejection leaves Actions, Groups, keys, gaps, caches, selection, cursor, and history unchanged.

### Action and Group navigation

- **D-29:** Selecting a Group reveals and selects its reference Action in the Actions panel when available. Detached or unavailable Groups never auto-select an unrelated Action.
- **D-30:** Selecting an Action highlights every linked Group Rail without moving the timeline cursor. Linked rails retain their Motion purple or Static cyan and receive a brighter mode-colored halo/outline. Orange remains exclusive to the actually selected Group and operation scope.
- **D-31:** `Linked Groups — {current} of {total}` orders logical Groups by current timeline placement from left to right. A fragmented Group appears once under its stable identity.
- **D-32:** If a linked Group is already selected when its Action becomes active, preserve it as current. Otherwise choose the first linked Group at or after the current physical cursor, falling back to the last linked Group before the cursor. This initializes the current count without moving the cursor.
- **D-33:** `Previous` and `Next` select the corresponding logical Group and move the physical cursor to that Group’s start. Navigation stops at the first and last Group; controls disable at their respective ends and never wrap. One linked Group may expose `Go to Group` instead.

### Creation, authority, and regression boundaries

- **D-34:** The multi-frame Action-generated flow is named `Create Group…`; its Group Type choice is `Motion` or `Static`. The unlinked single-frame operation is `Apply to Frame`. Do not use `Create Motion` as the shared action name.
- **D-35:** Paint, Delete Frame, Delete Group, Regenerate, Keep Groups, and Delete Action and Groups all use the accepted canonical physical document, parent authority, strict stale guards, complete semantic comparison, exact settlement, and one-command history model. Reject stale Group identity, ambiguous sharing, invalid fragment boundaries, unresolved output, duplicate destinations, capacity violations, or stale Action authority before mutation.
- **D-36:** Preview, Studio playback, export, persistence, and save/reopen resolve the same accepted Group, fragment, status, and persistent-gap result. Derived caches never become document authority.
- **D-37:** Preserve the existing zero-added-height Group Rail, physical-cell behavior, Group/physical selection boundaries, source sharing, Interpolation Off/On behavior, Phase 43.1 incoming-break authority, and accepted Phase 43 preview/export semantics.
- **D-38:** Do not modify the Motion Editor timeline; add a second timeline/fragment/cache authority; implement Push Right/Push Left, direct Group drag, ordinary Key Group rails, Scissor, Action-content editing, Relink, multiple internal Paint tracks, or Phase 44 signing/release work.
- **D-39:** Native visual acceptance must run from a fully restarted frozen-code parent/child session. Prior Phase 43.1 evidence showed that mixed hot-reload state can falsely present hydration/lifecycle loss even when canonical data is correct.

## Summary

Phase 43.2 is an additive canonical-document expansion, not a UI rename and not a new subsystem. The current durable object already has stable `loopId`, `placementStart`, ordered `sourceKeyIds`, `repeat`, `mode`, and optional Action provenance; it is strictly parsed, included in canonical revision/equality, transported through the accepted physical-map envelope, persisted, hydrated, snapshotted, replayed, and consumed by preview/export. [VERIFIED: app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:256-291] [VERIFIED: app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:809-864] [VERIFIED: app/src/types/physicPaint.ts:425-470]

The planning-critical change is to make one logical Group own explicit visible ranges, a stable source-cycle phase origin, accepted synchronization/provenance facts, and exact-frame override authority while keeping real key payloads as the raster authority. [ASSUMED] Delete Frame must modify explicit ranges and Phase 43.1 break ownership, never an invisible exclusion mask; exact-frame Paint must materialize or reuse a Group-owned override key before pixel mutation; Regenerate and deletion must compute ownership/reference effects before staging one complete accepted document. [ASSUMED]

The most dangerous integration seam is current Paint persistence: it writes directly to the real source key found at the physical frame, which is correct for ordinary keys but would alter every repeated occurrence resolving to that source key. [VERIFIED: app/src/components/physic-paint/hooks/useRotoFramePersistenceCoordinator.ts:173-212] The phase should therefore cut over Group-owned Paint into the same physical coordinator/history transaction before building lifecycle UI. [ASSUMED]

**Primary recommendation:** Extend `PhysicPaintRotoLoopClip` additively, route every Group mutation through `replace-roto-physical-map`, and implement UI only as computed projections of exactly acknowledged document and library state. [ASSUMED]

### Pattern 1: Additive Canonical Group Record

**What:** Extend the existing record rather than renaming persisted fields or introducing a parallel fragment entity. [ASSUMED]

**Recommended internal shape:** preserve existing fields verbatim and add: `syncState`, `provenanceState`, `phaseOrigin`, `originalEndExclusive`, `visibleRanges`, and `frameOverrides`. These names and literal values are implementation recommendations, not existing schema values. [ASSUMED]

- `syncState`: proposed literals `'synchronized' | 'modified'`. [ASSUMED]
- `provenanceState`: proposed literals `'attached' | 'detached'`; attached plus missing library row projects “Source Action unavailable.” [ASSUMED]
- `phaseOrigin`: immutable source-cycle modulo origin; initially equals `placementStart` and does not move when outer fragments shorten. [ASSUMED]
- `originalEndExclusive`: complete accepted range end used by Regenerate. [ASSUMED]
- `visibleRanges`: sorted, non-overlapping, non-adjacent half-open ranges; adjacency must be merged. [ASSUMED]
- `frameOverrides`: sorted `{ appFrame, keyId }` entries pointing to canonical real-key payloads; never inline raster/cache data. [ASSUMED]

This keeps Delete Frame authority explicit in `visibleRanges`, keeps cycle phase based on `phaseOrigin`, and keeps local Paint raster authority in existing real records. [ASSUMED]

### Pattern 2: Complete Semantic Transaction

**What:** Every lifecycle operation proposes a complete next document slice and a semantic delta that the parent can independently recompute. [ASSUMED]

Use proposed specialized operation literals: `'paint-group-frame'`, `'delete-group-frame'`, `'delete-group'`, `'regenerate-group'`, `'detach-action-groups'`, and `'delete-action-groups'`. [ASSUMED]

Each delta should include stable Group identity, target frame where applicable, frozen affected Group IDs, ownership cleanup IDs, and expected Action revision for Action-backed operations. [ASSUMED] Do not trust UI-computed counts as authority; the parent recomputes and compares them before mutation. [ASSUMED]

### Pattern 3: Exact-Occurrence Copy-on-Write

**What:** Resolve whether the selected physical frame is a source frame, repeated occurrence, existing override, or deleted Group gap before accepting Paint. [ASSUMED]

1. Classify the frame under the selected stable Group identity. [ASSUMED]
2. If it is already a unique override real key, paint that key. [ASSUMED]
3. Otherwise allocate a fresh real key, initialize it from the exact resolved accepted pixels, and add one `frameOverrides` entry before pixel mutation. [ASSUMED]
4. If the frame is a deleted gap, extend/merge `visibleRanges`, remove the Group-owned break for that gap, and create the override in the same candidate. [ASSUMED]
5. Mark `syncState` modified regardless of later pixel equality. [ASSUMED]
6. Publish cache/canvas only after parent acknowledgement. [ASSUMED]

### Pattern 4: Prepared Action Deletion

## Common Pitfalls

### Pitfall 1: Painting the Shared Source Key
**What goes wrong:** Painting one repeated occurrence changes every occurrence resolving to the same source key. [ASSUMED]
**Why it happens:** The current persistence path resolves a real record and updates that key’s payload directly. [VERIFIED: app/src/components/physic-paint/hooks/useRotoFramePersistenceCoordinator.ts:173-212]
**How to avoid:** Classify Group ownership first and complete COW plus Group override insertion in the physical transaction before accepting pixels. [ASSUMED]
**Warning signs:** The parent payload remains `apply-canvas` for a repeated Group occurrence, or no new override identity appears in the accepted document. [ASSUMED]

### Pitfall 2: Losing Source-Cycle Phase After Fragmentation
**What goes wrong:** The right fragment restarts the cycle instead of rendering the phase the original Group would have used. [ASSUMED]
**Why it happens:** Modulo is computed from fragment start rather than immutable Group phase origin. [ASSUMED]
**How to avoid:** Preserve `phaseOrigin`; calculate cycle index from physical frame minus phase origin for every range. [ASSUMED]
**Warning signs:** Deleting one middle frame causes the next visible frame to display cycle index zero. [ASSUMED]

### Pitfall 3: Treating Incoming Breaks as the Whole Fragment Model
**What goes wrong:** A stable-key-owned incoming break suppresses interpolation but does not by itself describe explicit left/right Group ranges or Group ownership of the deleted occurrence. [ASSUMED]
**Why it happens:** Phase 43.1 breaks are keyed by real-key identity, while a deleted repeated occurrence may not be a unique real key. [VERIFIED: app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:267-291]
**How to avoid:** Persist explicit Group ranges and reuse incoming-break authority for interpolation semantics; do not introduce an exclusion mask. [ASSUMED]
**Warning signs:** Rail fragments are reconstructed by scanning breaks, or a deleted occurrence has no stable owning Group metadata. [ASSUMED]

### Pitfall 4: Omitting New Fields from One Equality Boundary
**What goes wrong:** Save cache, replay, bridge settlement, or UI can accept two semantically different Group states as equal. [ASSUMED]
**Why it happens:** Loop Clip equality is manually enumerated in revision encoding, history comparison, persistence, transport, and bridge snapshots. [VERIFIED: app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:878-897] [VERIFIED: app/src/components/physic-paint/hooks/useRotoPhysicalEditHistory.ts:162-205]
**How to avoid:** Land schema/parser/revision/equality/transport/persistence/history changes in the same wave, with a field-participation matrix test. [ASSUMED]
**Warning signs:** A lifecycle-only change leaves `revision` unchanged or Undo ignores status/range changes. [ASSUMED]

### Pitfall 5: Partial Action Deletion
**What goes wrong:** The Action file disappears but Groups are not detached/deleted, or the physical document changes while the file remains. [ASSUMED]
**Why it happens:** Current `confirmDelete()` performs one direct library delete request and closes confirmation. [VERIFIED: app/src/components/physic-paint/roto/physicsPaintRotoScriptLibrary.ts:253-262]
**How to avoid:** Use prepared file deletion with rollback around one accepted physical transaction, under frozen file and document revisions. [ASSUMED]
**Warning signs:** The dialog calls `library.confirmDelete()` directly for referenced Actions. [ASSUMED]

### Pitfall 6: Confusing Detached with Unavailable
**What goes wrong:** Recreating an Action with the same ID silently relinks a deliberately detached Group, or unavailable Actions are persisted as detached. [ASSUMED]
**Why it happens:** Both states render neutral colors but have different authority semantics. [ASSUMED]
**How to avoid:** Persist explicit detached provenance; derive unavailable only when provenance is attached and the Action lookup fails. [ASSUMED]
**Warning signs:** Status is derived only from whether a current library row exists. [ASSUMED]

### Pitfall 7: Fragment-Level Selection or Navigation
**What goes wrong:** One Group appears multiple times in linked counts, or Delete/Regenerate affects one fragment only. [ASSUMED]
**Why it happens:** Rail rendering maps ranges directly and currently keys each target by `range.loopId`; multiple ranges will require unique render keys while retaining one logical operation ID. [VERIFIED: app/src/components/physic-paint/view/PhysicsPaintLoopClipRail.tsx:152-186]
**How to avoid:** Render range-specific target keys but dispatch stable Group ID; deduplicate navigation by Group identity. [ASSUMED]
**Warning signs:** `Linked Groups` total equals fragment count. [ASSUMED]

### Pitfall 8: Optimistic Lifecycle UI
**What goes wrong:** Dots, fragments, Action rows, canvas, or occupied ranges change before parent settlement and must be repaired after rejection. [ASSUMED]
**Why it happens:** Dialog/controller state is mistaken for accepted document state. [ASSUMED]
**How to avoid:** Keep preparation/busy state separate; project accepted facts only from the acknowledged store document. [VERIFIED: .planning/phases/43.2-motion-and-static-group-stabilization-and-action-lifecycle-u/43.2-UI-SPEC.md:538-544]
**Warning signs:** Clicking Delete Frame immediately splits the rail before the apply result arrives. [ASSUMED]

### Pitfall 9: Stale Frozen-Session Evidence
**What goes wrong:** Mixed parent/child bundles falsely appear to lose lifecycle or hydration state. [VERIFIED: .planning/phases/43.2-motion-and-static-group-stabilization-and-action-lifecycle-u/43.2-UI-SPEC.md:704-704]
**How to avoid:** Fully restart the frozen-code parent/child session before native visual acceptance. [VERIFIED: .planning/phases/43.2-motion-and-static-group-stabilization-and-action-lifecycle-u/43.2-UI-SPEC.md:704-704]
