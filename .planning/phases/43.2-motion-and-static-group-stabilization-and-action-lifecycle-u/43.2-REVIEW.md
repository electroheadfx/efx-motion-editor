# Phase 43.2: Code Review Report

**Reviewed:** 2026-08-13T00:00:00Z
**Depth:** standard
**Files Reviewed:** 19
**Status:** issues_found

## Summary

Reviewed the Phase 43.2 group-stabilization and Action-lifecycle surface at standard depth: the physical resolver and model (loop/Group guards, revision fingerprinting), Group lifecycle proposals, the ordinary-key edit coordinator/history, timeline action routing, the parent bridge (canonical edit revalidation, referenced-Action deletion with retained artifacts), the durable transaction IPC/Rust contract, persistence, export preflight, and store/preview render-source selection.

The 43.2 delete guard landed in `2cd4c033` is present and correct: `delete-key` rejects loop-source-key deletion fail-closed (`loop-source-key-delete-rejected`) and suppresses the left ripple whenever any surviving key after the removed slot is Group-referenced. The durable lease/transaction lifecycle (prepare → commit → acknowledge → release) is internally consistent between client and Rust, and the retained-artifact identity checks in `applyCommittedReferencedActionDeletion` are sound.

One BLOCKER was found: the ripple-suppression invariant that 2cd4c033 established for delete is NOT applied to `insert-slot` or `duplicate-key`. Both ordinary edit paths still shift every key at/after a threshold frame right by one, including Group loop source keys, while the durable Loop Clip lifecycle metadata (`placementStart`/`phaseOrigin`/`originalEndExclusive`/`visibleRanges`) is left unchanged. The result is a silent desync between physical source positions and the Group lifecycle extent — the exact corruption the delete guard's own comment names. It is accepted end-to-end because the coordinator and the parent bridge re-run the same resolver and pass the loop clips through unchanged.

## Critical Issues

### CR-01: insert-slot and duplicate-key ripple Group loop source keys with no loop guard, desyncing durable Group lifecycle metadata

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalResolver.ts:1001-1034` (insert-slot), `:1214-1258` (duplicate-key), `:2599-2613` (insert-slot dispatch)
**Also:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:106-108`, `:842-856`, `:933-940`; `app/src/components/physic-paint/hooks/useRotoPhysicalEditCoordinator.ts:1828-1872`; `app/src/lib/physicPaintBridge.ts:723-764`

**Issue:**

`buildInsertCandidate` shifts every identity at `appFrame >= selectedFrame` right by exactly one physical slot:

```ts
for (const identity of identities.ordered) {
  if (identity.appFrame >= (selectedFrame as number)) {
    const next = identity.appFrame + 1;
    mapping.set(identity.keyId, next);
    ...
  }
}
```

The `insert-slot` dispatch (lines 2599-2613) performs no loop consultation whatsoever: unlike `delete-key` (lines 2693-2711, which rejects via `countLoopsReferencingSourceKey` and suppresses the ripple via `new Set(loopClips.flatMap((clip) => clip.sourceKeyIds))`), there is no `loopReferencedKeyIds` set and no rejection when any shifted key is Group-referenced. `buildDuplicateCandidate` (lines 1221-1237) has the identical defect: `record.appFrame >= destination ? record.appFrame + 1 : record.appFrame` shifts all later keys, including loop source keys, with no guard.

Both paths are reachable on Group source keys:
- `classifyRotoInsertTarget` (useRotoTimelineActions.ts:106-108) returns `'occupied-real'` for any real selected keyId with no Group-ownership or loop-reference check, and `canInsertFrame`/`insertDisabledReason` (lines 763-764) only gate on that classification — so `insertRotoFrame` (lines 842-856) routes to `insert-slot` whenever a real key is selected.
- `duplicateKey` (lines 933-940) routes straight to `runPhysicalAction` with `duplicate-key`.

The corrupted proposal is accepted end-to-end:
- The coordinator's `buildStagedRecords` (useRotoPhysicalEditCoordinator.ts:1828-1872) stages the shifted records without loop consultation.
- The parent bridge's `validateCanonicalOrdinaryPhysicalEdit` (physicPaintBridge.ts:723-764) re-runs the same resolver (`canonicalLoopClips = proposal.nextLoopClips ?? input.currentLoopClips`; `nextLoopClips` is `null` for insert/duplicate), so the Loop Clips pass through byte-identical while the physical source keys move. The desync is therefore validated as canonical.

Consequence: the durable Loop Clip fields `placementStart`, `phaseOrigin`, `originalEndExclusive`, and `visibleRanges` are persisted unchanged while their source keys shift. The Group lifecycle reads the stored extent for all frame classification — `proposePhysicPaintRotoDeleteGroupFrame` rejects frames outside `[phaseOrigin, originalEndExclusive)` and computes `repeatInstance`/`cycleOffset` against it (physicsPaintRotoGroupLifecycle.ts:99-100, 291-296, 551-560). After an insert, a source key physically sits inside a *different* occurrence than the stored extent says; paint/delete/Regenerate targets are misclassified and the Group Rail renders occurrences at stale positions. `validatePhysicPaintRotoGroupReferences` (physicsPaintRotoPhysicalModel.ts:1097-1144) does not cross-check the extent against source positions, so nothing fails closed — the corruption is silent and durable.

**Fix:** Apply the same invariant to `insert-slot` and `duplicate-key` that 2cd4c033 established for delete. In the `insert-slot` dispatch, compute `const loopReferencedKeyIds = new Set(loopClips.flatMap((clip) => clip.sourceKeyIds))`; when any identity at `appFrame >= selectedFrame` is loop-referenced, fail closed (mirror `loop-source-key-delete-rejected`, e.g. a new `insert-loop-source-shift-rejected` code) because insert necessarily shifts. For `duplicate-key`, reject duplication when the source key is loop-referenced or any shifted survivor at `appFrame >= destination` is loop-referenced. Alternatively, reanchor the Loop Clip extent (`placementStart`/`phaseOrigin`/`originalEndExclusive`/`visibleRanges`) by +1 alongside the physical shift, and persist `nextLoopClips` through the proposal — but the delete-guard precedent and the memory contract ("Roto keys keep absolute positions") favor fail-closed rejection. Add the same guard to the UI classification (`classifyRotoInsertTarget`) so the Insert/Duplicate controls are disabled with a reason when the selection would shift a loop-referenced key.

## Warnings

### WR-01: transaction physicalHash integrity anchor is never cross-checked against the embedded physicalDocument

**File:** `app/src/types/physicPaint.ts:221-235`; `app/src-tauri/src/services/script_library.rs:1145-1219` (physical_hash at line 1206)
**Also:** `app/src/components/physic-paint/hooks/useRotoScriptLibraryController.ts:455-456`

**Issue:**

`isPhysicPaintActionTransactionTarget` parses `value.physicalDocument` and verifies `physicalRevision === physicalDocument.revision`, but never verifies `physicalHash` — even though the document is embedded in the same record and the hash is computed by the exported `buildPhysicPaintRotoProjectEquality`. Similarly, the Rust `validate_prepare_request` validates `physical_hash` (and `expected_physical_hash`) as text only. The hash is the recovery settlement anchor (`recoverBeforeAvailability` at useRotoScriptLibraryController.ts:455-456 uses `buildPhysicPaintRotoProjectEquality(current) === discovered.target.physicalHash` to decide whether the committed deletion is already applied), yet it is persisted as advisory text. The client computes it fresh at prepare time and cross-checks it on the replay path (useRotoScriptLibraryController.ts:115), so normal operation is safe; the gap is that a corrupted or out-of-band prepare record carrying a stale `physicalHash` passes validation at the persistence boundary and can produce a wrong `alreadySettled` verdict during recovery (redundant settlement is idempotent, so this is not data loss — but the anchor is not enforced where it is stored).

**Fix:** In `isPhysicPaintActionTransactionTarget`, add `|| value.physicalHash !== buildPhysicPaintRotoProjectEquality(physicalDocument)` after parsing. In `validate_prepare_request`, recompute the FNV-1a of the canonical encoding of `physical_document` (the algorithm is documented and deterministic; the canonical serializer is mirrored in the retained-artifact flow) and reject on mismatch. This closes the loop at both the type guard and the durable boundary.

## Info

### IN-01: matchesTransactionIdentity treats 'released'/'retained' as correlation mismatches even though those states never reach it

**File:** `app/src/lib/ipc.ts:153`

**Issue:** `matchesTransactionIdentity` returns `false` for `result.state === 'released' || result.state === 'retained'`, which surfaces as `correlation-mismatch`. But `'released'` is only ever returned by `script_library_release_action_history`, which is correlated by `matchesReleaseIdentity` (ipc.ts:307), and `'retained'` is a metadata state on `retained-*.json` files that no transaction command returns. The branch is unreachable defensive code that misleads maintainers into thinking terminal `released` results can be correlated here.

**Fix:** Remove the branch (the token-matching fallthrough at line 155 already handles every reachable state) or add a comment documenting why these states are impossible for the commands using this matcher.

### IN-02: orphaned retained artifacts accumulate after a recovered-prepared rollback of a Forward prepare

**File:** `app/src-tauri/src/services/script_library.rs:974-1032`, `:1051-1143`

**Issue:** `restore_prepared_transaction` removes `active-*.json` on rollback (line 1028) but leaves the `retained-*.json`/`retained-*.bytes` written by the Forward prepare in place. `reconcile_retained_history_before_scan` only deletes retained artifacts when a `released-*` receipt exists (line 1090), so a Forward prepare that is rolled back via `recover` (crash before commit, or a commit that fails validation at line 628) leaves orphaned retained files. Repeated crash→recover cycles accumulate them; the next prepare with a different command_id/generation writes new files and never cleans the orphans. Bounded but unbounded over time.

**Fix:** In `restore_prepared_transaction`, after clearing `active-*.json`, delete `retained-*.json`/`retained-*.bytes` for the transaction's command_id/generation when no other active/committed/acknowledged record references them (reuse `reject_active_retained_reference` semantics).

### IN-03: discover_action_transaction silently treats acknowledged-path errors as "not acknowledged"

**File:** `app/src-tauri/src/services/script_library.rs:440`

**Issue:** `candidates.retain(|(_, token, _)| !acknowledged_transaction_path(&transactions, token).map(|path| path.exists()).unwrap_or(false))` — a failure computing the acknowledged path (e.g. malformed token derived from a filename) is swallowed by `unwrap_or(false)`, keeping the transaction as a recovery candidate and potentially returning an error later from `read_transaction_record`. Silent failure masking, inconsistent with the fail-closed style of the surrounding code.

**Fix:** Propagate the path error with `?` instead of `unwrap_or(false)`, or skip the malformed token explicitly with a comment.

### IN-04: recoverBeforeAvailability parses the lease generation from a colon-delimited token string

**File:** `app/src/components/physic-paint/hooks/useRotoScriptLibraryController.ts:428-431`

**Issue:** `const leaseParts = discovered.leaseToken.split(':'); const generation = Number(leaseParts[leaseParts.length - 2]);` assumes a fixed colon-delimited lease token with the generation in the penultimate segment. The token fields (`projectContextId`, `layerId`) are free-form transaction text, and `validate_transaction_text` permits colons; if a future project/context or layer ID contains a colon, the generation extraction silently shifts and recovery fails with "Recovery lease identity is malformed."

**Fix:** Carry the generation as an explicit field on the recovered/discovered result (or on the lease object) rather than re-parsing the opaque token string.
