# Phase 43.2: Motion and Static Group Stabilization and Action Lifecycle - Context

**Gathered:** 2026-08-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Stabilize the Action-created Loop Clips delivered by Phase 43 as durable Motion Groups and Static Groups. This phase applies the locked user-facing nomenclature, adds understandable Action provenance and synchronization state, permits safe exact-frame local Paint edits through copy-on-write authority, adds explicit Delete Group / Delete Frame behavior with persistent fragments and gaps, restores accepted Action output through Regenerate, defines reference-aware Action deletion, and connects Actions to their Groups through predictable highlighting and navigation.

The accepted canonical physical document, exact parent acknowledgement, source sharing, persistent interpolation-break authority, atomic Undo/Redo, playback, preview, export, and save/reopen remain authoritative. Existing saved projects reopen without a nomenclature-only migration. The Motion Editor timeline is unchanged.

Requirements are currently not assigned IDs in `.planning/REQUIREMENTS.md`; downstream research/planning must derive Phase 43.2 IDs and traceability from the activated product prompt without changing completed Phase 43 or Phase 43.1 requirements.

</domain>

<decisions>
## Implementation Decisions

### Product nomenclature and Group lifecycle

- **D-01:** Every EFX Paint/Roto user-facing surface uses the locked terminology: `Group`, `Motion`, `Motion Group`, `Static`, `Static Group`, future `Key Group`, `Group Rail`, `Edit Group`, `Action`, `Actions`, `Save Action`, `Create Group…`, `Group Type` with `Motion` and `Static`, and `Apply to Frame`. Visible labels, tooltips, inspector headings, dialogs, status/error copy, accessibility names, product-copy tests, and new planning artifacts follow this vocabulary.
- **D-02:** Internal TypeScript, Rust, transport, and persistence identifiers may retain `loopClip`, `progressive`, `static`, and `scriptId` where renaming has no product benefit. Existing saved documents receive no nomenclature-only migration.
- **D-03:** A Group has one stable logical identity, one Action provenance reference, committed real source keys, derived occurrences, one or more visible rail ranges, applied mode/Motion/color/repeat/placement/source-cycle settings, optional source sharing, and derived caches that never become a second authority. The persisted Action is provenance and the explicit Regenerate source, not a live dependency that silently changes accepted output.
- **D-04:** Synchronization state is a durable accepted lifecycle fact: green means Synchronized with Action; orange means Modified by accepted local Paint or Delete Frame work; neutral gray distinguishes Action detached from Source Action unavailable. Existing unresolved/error presentation has precedence and is never replaced by the synchronization dot. The dot remains visible while Interpolation is Off and is passive—no separate pointer target or added timeline height.
- **D-05:** Action-content editing, automatic Action mutation from Paint, `Update Action from Group Frame…`, and Relink are outside this phase. Deleting and recreating a Group is the current path after detachment.

### Exact-frame local Paint

- **D-06:** Painting on a repeated Group occurrence changes only that exact physical frame inside the selected logical Group. Other repeats in the same Group remain byte-equivalent, and other Groups remain unchanged. Copy-on-write authority occurs before mutation whenever source keys or caches are shared. — **Reversibility:** costly — changing later to cycle-phase-wide edits would require reinterpreting or migrating saved frame-local modifications and their history semantics.
- **D-07:** The persisted Action is never modified by local Paint. Local Paint preserves Group identity, Motion/Static mode, placement, repeat, relative timing, stored applied settings, Action provenance, and Regenerate capability.
- **D-08:** An exact-frame local Paint edit keeps the Group Rail continuous. It adds no fragment, split, or frame-level modification marker; the Group-level synchronization dot changes to orange and its tooltip/accessibility copy explains the Modified state.
- **D-09:** A Group returns from Modified to Synchronized only when Regenerate restores the Action result or Undo restores the accepted synchronized snapshot. Redo reapplies the Modified state. Manually repainting visually equivalent pixels does not silently change provenance state.
- **D-10:** Painting directly into a frame previously emptied by Delete Frame fills that exact Group frame, removes the locally owned deletion gap at that frame, visually reunites adjacent fragments when contiguous again, and leaves the Group Modified.
- **D-11:** Local Paint acceptance, copy-on-write source/cache changes, synchronization state, gap removal/reunion, canvas reconciliation, and Undo/Redo are one canonical accepted transaction. Rejection or cancellation changes nothing.

### Delete Frame, fragments, and Delete Group

- **D-12 (superseded 2026-08-11):** Delete scope follows accepted selection directly. With an individual Group-owned physical frame selected, Delete, Backspace, and the visible Delete action invoke Delete Frame. With the complete logical Group selected through any Group Rail fragment, the same routes invoke Delete Group. No routine Delete Group / Delete Frame scope-choice modal is shown. Ordinary-key deletion remains unchanged and neither Group action deletes the referenced Action.
- **D-13 (superseded 2026-08-11):** Frame-selected and Group-selected deletion remain separate canonical atomic commands. Delete Frame removes only the selected occurrence, creates or adjusts the intentional gap/range, and leaves surviving Group fragments Modified. Delete Group removes the complete logical Group and uniquely owned authority. Preserve only a focused destructive warning for deleting the sole remaining occurrence; do not use a routine scope-selection dialog or second confirmation.
- **D-14:** A middle Delete Frame produces explicit left and right visible ranges of the same stable logical Group, with the selected frame left as one intentional persistent empty gap. No invisible per-frame exclusion mask or second fragment authority is introduced. The right fragment resumes the exact source-cycle phase the original Group would have rendered after the deleted frame. — **Reversibility:** costly — treating fragments as independent Groups later would require identity, provenance, history, selection, and saved-document migration.
- **D-15:** Selecting any fragment selects the whole logical Group. Every fragment receives the selected treatment, the Actions inspector targets the one stable Group identity, and Delete Group / Regenerate apply to all fragments.
- **D-16:** Every visible fragment carries the same passive synchronization dot centered on that fragment. After Delete Frame, each fragment shows the shared orange Modified state so independently scrolled ranges remain understandable.
- **D-17:** Deleting the first or final occurrence shortens the visible Group range. Invoking Delete Frame on the only remaining occurrence presents the focused warning `This is the Group’s only frame. Delete Frame will remove the whole Group and its uniquely owned data.` before removing the logical Group; this edge warning does not reintroduce the retired scope-choice modal.
- **D-18:** Delete Group removes the complete selected logical Group, every fragment, occurrences, uniquely owned source real keys, uniquely owned caches, and locally owned persistent gaps/fragment authority. It does not delete the Action, another Group sharing the same `scriptId`, or source/cache data still referenced by another Group. Cleanup and one-step Undo/Redo are atomic.

### Regenerate

- **D-19:** `Regenerate` in Edit Group is enabled only for an orange Modified Group whose attached Action is available. Synchronized, detached, and source-unavailable Groups expose clear disabled reasons rather than performing a no-op or failing after activation.
- **D-20:** Regenerate uses one structured confirmation rather than raster before/after thumbnails. The confirmation shows Group name/type, original/restored range, locally painted frame count, deleted-frame count and ranges, fragment reunion, locally owned gaps that will clear, resulting Synchronized state, and any source/cache effects.
- **D-21:** If accepted shared-source Regenerate affects multiple synchronized Groups, the confirmation shows the exact affected count plus a compact placement-ordered list of every affected Group name and range. The commit control states `Regenerate {N} Groups`.
- **D-22:** Accepted Regenerate reloads the referenced persisted Action, reconstructs the selected logical Group from the Action plus its stored applied settings, restores locally painted and deleted frames, reunites fragments, restores the complete original range and exact source-cycle phase, clears locally owned Delete Frame gaps, returns the dot to green, and preserves stable Group identity and placement in one atomic Undo/Redo transaction.
- **D-23:** After Regenerate succeeds, the initiating Group remains selected and the physical cursor remains on its current frame. The current Studio canvas reconciles immediately from the regenerated accepted result, including when that frame was a restored deletion gap. Shared affected Groups do not replace the initiating selection.
- **D-24:** Detached or unavailable Actions cannot Regenerate. If Action editing is introduced later, Regenerate uses the latest explicitly saved Action version; accepted Groups never update silently.

### Action deletion

- **D-25:** Deleting an unreferenced Action retains the existing simple Action-library flow. Deleting an Action referenced by one or more Groups opens one Actions-panel dialog with exactly `Keep Groups` (recommended), `Delete Action and Groups`, and `Cancel`.
- **D-26:** `Keep Groups` deletes the Action and detaches provenance while preserving every affected Group, fragment, key, timing value, placement, repeat, cache, rendered result, and occupied range. Affected Groups become neutral gray detached Groups and Regenerate is unavailable. Keeping Groups does not free timeline space.
- **D-27:** `Delete Action and Groups` deletes the Action and every logical Group referencing it, including every fragment and uniquely owned source/cache/gap authority, as one atomic destructive transaction. Shared data referenced outside the deleted set survives.
- **D-28:** Deleting a Group never deletes its Action. Action deletion dialogs disclose affected Group count/ranges, source/cache cleanup, resulting synchronization state, and occupied-space consequences before commit. Cancellation or stale rejection leaves Actions, Groups, keys, gaps, caches, selection, cursor, and history unchanged.

### Action and Group navigation

- **D-29:** Selecting a Group reveals and selects its reference Action in the Actions panel when available. Detached or unavailable Groups never auto-select an unrelated Action.
- **D-30:** Selecting an Action highlights every linked Group Rail without moving the timeline cursor. Linked rails retain their Motion purple or Static cyan and receive a brighter mode-colored halo/outline. Orange remains exclusive to the actually selected Group and operation scope.
- **D-31:** `Linked Groups — {current} of {total}` orders logical Groups by current timeline placement from left to right. A fragmented Group appears once under its stable identity.
- **D-32:** If a linked Group is already selected when its Action becomes active, preserve it as current. Otherwise choose the first linked Group at or after the current physical cursor, falling back to the last linked Group before the cursor. This initializes the current count without moving the cursor.
- **D-33:** `Previous` and `Next` select the corresponding logical Group and move the physical cursor to that Group’s start. Navigation stops at the first and last Group; controls disable at their respective ends and never wrap. One linked Group may expose `Go to Group` instead.

### Creation, authority, and regression boundaries

- **D-34:** The multi-frame Action-generated flow is named `Create Group…`; its Group Type choice is `Motion` or `Static`. The unlinked single-frame operation is `Apply to Frame`. Do not use `Create Motion` as the shared action name.
- **D-35:** Paint, Delete Frame, Delete Group, Regenerate, Keep Groups, and Delete Action and Groups all use the accepted canonical physical document, parent authority, strict stale guards, complete semantic comparison, exact settlement, and one-command history model. Reject stale Group identity, ambiguous sharing, invalid fragment boundaries, unresolved output, duplicate destinations, capacity violations, or stale Action authority before mutation.
- **D-36:** Preview, Studio playback, export, persistence, and save/reopen resolve the same accepted Group, fragment, status, and persistent-gap result. Derived caches never become document authority.
- **D-37:** Preserve the existing zero-added-height Group Rail, physical-cell behavior, Group/physical selection boundaries, source sharing, Interpolation Off/On behavior, Phase 43.1 incoming-break authority, and accepted Phase 43 preview/export semantics.
- **D-38:** Do not modify the Motion Editor timeline; add a second timeline/fragment/cache authority; implement Push Right/Push Left, direct Group drag, ordinary Key Group rails, Scissor, Action-content editing, Relink, multiple internal Paint tracks, or Phase 44 signing/release work.
- **D-39:** Native visual acceptance must run from a fully restarted frozen-code parent/child session. Prior Phase 43.1 evidence showed that mixed hot-reload state can falsely present hydration/lifecycle loss even when canonical data is correct.

### Claude's Discretion

- Exact green/orange/neutral dot geometry and exact mode-colored linked halo tokens, provided they remain passive, accessible, visible without added rail height, and distinct from selected orange and unresolved/error presentation.
- Exact sole-occurrence Delete Frame warning markup, macOS-safe focus behavior, spacing, typography, and concise consequence copy, provided routine frame-selected and Group-selected deletion stays direct and modal-free.
- Exact additive model fields and copy-on-write representation for local frame overrides, fragment origin authority, synchronization lifecycle, and detached provenance, provided no second authority, invisible Delete Frame exclusion mask, or nomenclature-only migration is introduced.
- Exact disabled-reason wording beyond the locked status facts, exact range/list formatting, and exact component decomposition, provided one canonical mapper supplies consistent tooltip, dialog, status, and accessibility copy.
- Exact test decomposition and UI-SPEC structure. Native UAT remains required for nomenclature, dots, fragments, dialogs, Regenerate, linked navigation, save/reopen, playback, preview, and export.

</decisions>

<specifics>
## Specific Ideas

- Locked synchronization copy: `Synchronized with Action.`
- Locked modified copy: `Modified locally — Regenerate to restore from Action.`
- Neutral state distinguishes `Action detached` from `Source Action unavailable`.
- Local Paint changes one exact physical occurrence only and leaves the Group Rail continuous.
- Every visible fragment of a split Group carries the same centered synchronization dot and selects as one logical Group.
- Delete follows selection scope directly: an individual Group-owned physical frame invokes Delete Frame, while Group Rail selection invokes Delete Group. No routine scope-choice modal appears; only the sole-occurrence Delete Frame warning remains.
- Regenerate is Modified-only, uses a structured textual summary, and labels shared commits `Regenerate {N} Groups` after listing every affected Group and range.
- Action-linked rails use a brighter halo in their existing Motion purple or Static cyan; actual Group selection remains orange.
- Linked navigation is placement-ordered, cursor-relative on initial Action selection, and non-wrapping at the ends.
- Native acceptance must run after a full frozen-code restart of the parent and Physics Paint child surfaces.

</specifics>
