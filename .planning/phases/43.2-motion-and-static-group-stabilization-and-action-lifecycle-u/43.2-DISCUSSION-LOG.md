## Local Paint Scope

### Repeated-occurrence Paint scope

| Option | Description | Selected |
|--------|-------------|----------|
| Exact frame only | Only the painted physical occurrence changes; every other repeat in that Group stays byte-identical. This matches the prompt’s “locally painted frame” language and Delete Frame’s occurrence-local behavior. | ✓ |
| Same cycle phase | The corresponding source-cycle phase changes across every repeat of that selected Group, while copy-on-write protects all other Groups sharing the old source cycle. | |
| Source cycle only | Only edits made inside the original source-cycle range propagate across repeats; painting a derived occurrence first redirects to or materializes its source phase. | |

**User's choice:** Exact frame only
**Notes:** Copy-on-write must occur before mutation whenever source keys or caches are shared, protecting both other repeats and other Groups.

### Rail presentation after local Paint

| Option | Description | Selected |
|--------|-------------|----------|
| Continuous rail | Keep the Group’s full rail/range intact; only the centered synchronization dot turns orange and the rail tooltip explains that local changes exist. | ✓ |
| Add frame marker | Keep the rail continuous but add a small passive marker on each locally painted frame, in addition to the orange Group status dot. | |
| Split around edit | Render separate rail fragments around the painted frame, visually treating local Paint like a structural range break. | |

**User's choice:** Continuous rail
**Notes:** Local Paint changes lifecycle state but does not create fragment authority or a frame-level modification marker.

### Returning to Synchronized

| Option | Description | Selected |
|--------|-------------|----------|
| Regenerate or Undo | It stays Modified until Regenerate restores Action output or Undo returns to the prior synchronized snapshot; visually repainting similar pixels never silently changes provenance state. | ✓ |
| Exact-content match | It returns green automatically whenever the edited frame’s accepted result exactly equals the Action-generated baseline, including a manual repaint that happens to match. | |
| Regenerate only | Only explicit Regenerate returns green; even Undoing the local edit keeps the Group marked Modified. | |

**User's choice:** Regenerate or Undo
**Notes:** Synchronization is an accepted lifecycle fact, not a pixel-equivalence heuristic. Redo reapplies Modified state.

### Painting into a deleted Group frame

| Option | Description | Selected |
|--------|-------------|----------|
| Fill and reunite | The exact frame becomes locally painted Group content, its deletion gap is removed, adjacent fragments visually reunite, and the Group remains Modified. | ✓ |
| Keep fragments | Store the paint at that frame but keep the left/right fragment boundary and deletion-gap authority around it. | |
| Require Regenerate | Reject painting into a deleted Group frame; the user must Regenerate the full Group before painting there. | |

**User's choice:** Fill and reunite
**Notes:** The refill, gap removal, visual reunion, canvas reconciliation, and history settlement belong to one accepted transaction.

## Delete Fragments

### Fragment selection scope

| Option | Description | Selected |
|--------|-------------|----------|
| Whole Group | Both fragments highlight as one selected Group, the Actions inspector targets that single identity, and Delete Group/Regenerate clearly apply to all fragments. | ✓ |
| Clicked fragment | Only the clicked rail fragment highlights, while the other fragment remains visually unselected even though both still belong to one logical Group. | |
| Primary plus related | The clicked fragment gets the selected treatment and the other fragments get a lighter related treatment. | |

**User's choice:** Whole Group
**Notes:** Fragments remain visible ranges of one stable logical Group, not independently selectable Groups.

### Synchronization-dot placement on fragments

| Option | Description | Selected |
|--------|-------------|----------|
| One per fragment | Center the same orange status dot on every visible fragment so each rail remains understandable when scrolled independently; all dots represent the same logical Group state. | ✓ |
| One primary dot | Show a dot only on the earliest visible fragment; later fragments have no synchronization dot. | |
| One full-range dot | Keep a single dot centered across the Group’s original complete range, even if that center lands in the intentional empty gap. | |

**User's choice:** One per fragment
**Notes:** Every dot projects the shared logical Group lifecycle state and remains passive.

### Delete-dialog presentation

| Option | Description | Selected |
|--------|-------------|----------|
| Choice cards | Show the Group name and current frame once, then two compact action rows with consequences: all fragments/unique cleanup for Delete Group; one occurrence/new gap/Modified state for Delete Frame. | ✓ |
| Buttons plus summary | Use plain action buttons and one shared paragraph below them describing all possible consequences. | |
| Two-step confirm | First choose Delete Group or Delete Frame, then open a second confirmation dialog with detailed consequences for that choice. | |

**User's choice:** Choice cards
**Notes:** The dialog contains exactly Delete Group, Delete Frame, and Cancel, with no second confirmation step.

### Delete Frame on the only remaining occurrence

| Option | Description | Selected |
|--------|-------------|----------|
| Keep label, warn | Keep the required Delete Frame option, but state clearly that deleting this only frame will remove the whole Group and uniquely owned data. | ✓ |
| Disable Delete Frame | Leave the choice visible but disabled and require the user to choose Delete Group instead. | |
| Rename dynamically | Replace Delete Frame with Delete Group for this edge case, so the dialog no longer shows both actions. | |

**User's choice:** Keep label, warn
**Notes:** The product label remains stable while the destructive consequence is disclosed before commit.

## Regenerate Confirmation

### Regenerate availability

| Option | Description | Selected |
|--------|-------------|----------|
| Modified only | Enable it only for an orange Modified Group with an available attached Action; green synchronized and gray detached/unavailable Groups show a clear disabled reason. | ✓ |
| Green or Modified | Allow synchronized Groups to regenerate too; only detached or unavailable Groups are disabled. | |
| Always visible enabled | Allow every Group to attempt Regenerate and surface unavailable/detached failures only after activation. | |

**User's choice:** Modified only
**Notes:** Regenerate must not perform a no-op or defer a known unavailable-state failure until activation.

### Confirmation content

| Option | Description | Selected |
|--------|-------------|----------|
| Structured summary | Show Group name/type, restored range, locally painted frame count, deleted-frame count/ranges, fragment reunion, affected shared-Group count, and the resulting Synchronized state—without generating raster previews. | ✓ |
| Before/after thumbnails | Render representative visual previews of current versus regenerated Group output in the confirmation. | |
| Short warning only | Show only a concise sentence that local changes will be lost, with no counts or affected ranges. | |

**User's choice:** Structured summary
**Notes:** The accepted context also requires disclosure of locally owned gaps that clear and source/cache effects.

### Shared-source disclosure

| Option | Description | Selected |
|--------|-------------|----------|
| Count plus list | Show the exact affected count and a compact placement-ordered list of each Group name and range; the commit button states “Regenerate N Groups”. | ✓ |
| Count only | Show the exact affected count but no individual Group names or ranges. | |
| Expandable details | Show the count initially with a disclosure control that expands to the complete placement-ordered list. | |

**User's choice:** Count plus list
**Notes:** Merely sharing an Action identifier does not define shared-source Regenerate scope; the accepted shared source cycle does.

### Selection and cursor after Regenerate

| Option | Description | Selected |
|--------|-------------|----------|
| Stay in place | Keep the initiating Group selected and keep the current physical frame; immediately refresh that frame from the regenerated result, even if it was a restored deletion gap. | ✓ |
| Jump to Group start | Keep the initiating Group selected but move the cursor to its restored start frame. | |
| Select all affected | Select or highlight every Group changed by shared-source Regenerate and move to the earliest affected start. | |

**User's choice:** Stay in place
**Notes:** Shared affected Groups do not replace the initiating selection.

## Action Navigation

### Linked-rail highlight

| Option | Description | Selected |
|--------|-------------|----------|
| Mode-color halo | Keep each rail purple/cyan and add a brighter mode-colored halo or outline; orange remains exclusive to the actually selected Group. | ✓ |
| Shared Action accent | Give every linked rail one new common highlight color regardless of Motion/Static type. | |
| Dim unrelated rails | Leave linked rails unchanged and reduce the opacity of every unrelated Group Rail while the Action is selected. | |

**User's choice:** Mode-color halo
**Notes:** The linked state must remain distinguishable from actual Group selection and operation scope.

### Previous/Next ordering

| Option | Description | Selected |
|--------|-------------|----------|
| Timeline order | Order logical Groups by current placement start from left to right; fragments count once under their stable Group identity. | ✓ |
| Creation order | Navigate Groups in the order they were originally created, regardless of later placement changes. | |
| Nearest cursor | Recompute the next target by distance from the current cursor rather than maintaining a fixed ordered list. | |

**User's choice:** Timeline order
**Notes:** Navigation follows current placement, not historical creation order.

### Initial current linked Group

| Option | Description | Selected |
|--------|-------------|----------|
| Cursor-relative | Use the first linked Group at or after the current cursor, falling back to the last linked Group before it; highlight all rails but do not move the cursor yet. | ✓ |
| First Group | Always initialize current to the earliest linked Group in timeline order, without moving the cursor. | |
| No current yet | Show only the total until Previous, Next, Go to Group, or a rail click establishes a current Group. | |

**User's choice:** Cursor-relative
**Notes:** If a linked Group is already selected when its Action becomes active, preserve that Group as current instead.

### Navigation boundaries

| Option | Description | Selected |
|--------|-------------|----------|
| Stop at ends | Disable Previous on the first Group and Next on the last; navigation never wraps unexpectedly in an editing timeline. | ✓ |
| Wrap around | Previous from the first jumps to the last, and Next from the last jumps to the first. | |
| Stay enabled | Keep both controls enabled but leave selection and cursor unchanged when the user presses beyond an end. | |

**User's choice:** Stop at ends
**Notes:** Previous and Next move selection and the physical cursor to the target Group start only when an adjacent target exists.

## Late Amendments (2026-08-12)

### Edit scope on a repeated Group occurrence

| Option | Description | Selected |
|--------|-------------|----------|

**Decision:** Source-phase propagation (CONTEXT A-01). The earlier occurrence-local wording is superseded; other Groups and the persisted Action remain byte-untouched.
