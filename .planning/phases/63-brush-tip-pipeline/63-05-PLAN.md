<objective>
Make the import real across both realms: the Studio reads the file and derives the mask, the main realm — which owns the project — encodes it, registers it, adds the catalog entry and marks the project dirty.

Purpose: the import surface lives in the Studio webview while `projectStore` lives in the main window (D-01, D-15). The existing image-import request/result bridge is the proven pattern for "child asks, main realm performs the project mutation"; this plan reuses it rather than duplicating project state into the child.

This plan is also where the phase's REALM BOUNDARY is solved once, for plans 63-06, 63-07 and 63-08. The main window owns the catalog, the mask registry and the stored WebP bytes; the Studio is a separate JS context whose module instances (`aquarelleBrushCatalog`, `maskRegistry`, `efxPaintBrushAssets`) start empty and are re-created on every layer switch. `emitTo` alone cannot update them. So the catalog travels the same way the project context does: the main realm publishes a full snapshot, a named Studio-side receiver applies it to the child's own module instances, and the receiver PULLS on mount — which is exactly what makes it survive the Studio re-boot.

Output: a reshaped `importTip` with caps and the shared derivation (with every call site updated in the same plan), the main-realm import handler, the catalog payload producer and applier, the Studio-side receiver hook, and the four brush bridge events with their guards.

Scope note (accepted, not an oversight): this plan carries 15 `files_modified` entries — above the 10-file warning band — and is recorded as accepted rather than split. Three reasons. (1) The file count comes from the realm boundary being solved once: four event constants plus guards, a producer, an applier, a receiver hook, its mount point and the main-window install point are one contract, and splitting the transport into its own plan would half-define the boundary across two plans and move 63-06, 63-07 and 63-08 to waves 6, 7 and 8. (2) The boundary design is the one the checker confirmed holds; a split now re-opens it. (3) The calibrated projection is 78% of the 100,000-token budget across 3 tasks, and the plan's own `tsc --noEmit` gate at task 2 fails loudly on any half-migrated consumer, so an overflow degrades into a visible failure rather than a silent one. If execution still overflows, the natural cut is task 3's transport half into a follow-up plan — not a reduction of any contract above.
</objective>
