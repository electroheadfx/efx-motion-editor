# Phase 52.1: Modern frame runtime + native HD paint - Research

**Researched:** 2026-09-06
**Domain:** Frame runtime identity (base64 dataUrl → bytes/ImageBitmap), Rust WebP-lossless codec, byte-budgeted LRU, working-resolution cap raise
**Confidence:** HIGH

## Summary

Phase 52.1 replaces the base64-dataUrl frame runtime with a bytes/ImageBitmap runtime, moves PNG→WebP-lossless encode/decode into Rust, lazy-loads sidecars behind a byte-budgeted LRU, and raises the working-resolution cap 1000→1920. The CONTEXT.md already locks the big decisions (D-01..D-19); this research grounds the five "Claude's Discretion" items in the actual current code and crate sources.

**Primary recommendation:** Build the Rust codec as a codec-agnostic `FrameCodec` trait over the **already-present** `webp = "0.3.1"` crate (which wraps `libwebp-sys` 0.9.6 and already provides BOTH lossless encode and libwebp-backed decode — no new crate, no `image`-crate webp decode needed for the sidecar path). Use `Encoder::from_rgba` + `encode_advanced` with a custom `WebPConfig` setting `lossless=1, exact=1` (the `config_exact` alpha semantics D-01 requires — the crate's convenience `encode_lossless()` does NOT set `exact`). On the JS side, wrap decoded RGBA into `ImageData` and call `createImageBitmap(imageData, { premultiplyAlpha: 'none' })` to preserve straight alpha, with a mandatory WKWebView contract test because Safari/WebKit is documented to ignore `premultiplyAlpha: 'none'`.

The single most important architectural fact for the planner: **the child→main bridge currently transports frames as base64 `dataUrl` strings over Tauri `emitTo` (JSON events)** — `sendPhysicPaintApplyPayload` in `physicsPaintBridgeTransport.ts:152`. JSON events cannot carry raw bytes efficiently, so the D-05 "bridge transport" retarget must move byte transfer to a Tauri `invoke` command (which accepts `ArrayBuffer`/`Uint8Array` raw bodies) or a Rust sidecar-write + stable-ref pattern, not another base64 string.

## User Constraints (from CONTEXT.md)

### Locked Decisions
- **D-01:** Sidecars switch PNG → **WebP lossless** via Rust libwebp bindings (crate `webp`/`libwebp-sys`), `config_exact` alpha semantics (RGB preserved under transparent pixels). Browser codec support is IRRELEVANT: Rust owns encode AND decode; JS receives raw RGBA → ImageData/ImageBitmap. PNG survives only as import/export interchange. — **Reversibility:** one-way — the on-disk sidecar format changes; old projects fail to open (clean-break no-compat, Phase 45 contract).
- **D-02:** The Rust codec seam is **codec-agnostic** (trait over encode/decode), so swapping WebP → JPEG XL (libjxl) touches one module. JPEG XL is the documented re-evaluation point for v1.2.0.
- **D-03:** Encode never happens during the paint gesture. Encode moves to async Rust commands at frame commit/save/bake. The one remaining synchronous piece is the canvas readback (`getImageData`, ~10-30ms at HD) — acceptable at HD; escalate to `createImageBitmap(canvas)` + OffscreenCanvas worker if profiling shows jank. Scrub cold-miss = libwebp decode ~20-50ms at HD, covered by the LRU + neighbor prewarm riding the existing playback lookahead machinery.
- **D-04:** Tauri 2.10.x → **2.11.5** (`@tauri-apps/api`, cli, Cargo `tauri`/`tauri-build`, plugins fs/store/dialog/notification/shell). Preact 10.28.4 → **10.29.8** + `@preact/signals` + `@preact/preset-vite` to latest compatible. Do NOT touch Preact 11 (RC). Gates: `pnpm install` clean, `vitest run` green, `tsc` clean, app launches, native UAT smoke.
- **D-05:** Runtime frame identity is **bytes/ImageBitmap, not dataUrl string**. Retarget `RenderedFramePayload`, the dataUrl-keyed registries, content tokens (`resolveContentToken`), dedup, bridge transport, main-editor preview/export readers.
- **D-06:** **Base64 elimination covers ALL THREE dataUrl-keyed registries** — `_rotoAlphaCanvasRegistry` (paint frames), `_backgroundSourceImages` (imported background photos), `_referenceSourceImages` (imported photo references). **Keys become the existing stable `sourceRef`/library asset IDs; values become decoded handles in the same byte-budgeted LRU.** — **Reversibility:** one-way — the dataUrl-keyed registries are removed; no parallel registry survives.
- **D-07:** Rust encode/decode commands (WebP lossless, exact alpha) write/read the existing sidecar files from bytes — **no base64 in JS anywhere**. Retarget PNG signature probes / `isRotoPngDataUrl` validation to WebP RIFF/VP8L magic bytes.
- **D-08:** Lazy sidecar load: project open reads refs only; bytes fetched and decoded to ImageBitmap on demand; byte-budgeted LRU over decoded frames (budgets in BYTES, never frame counts).
- **D-09:** **LRU byte ceiling = fixed 512 MB.** At 1920×1080 RGBA one decoded frame ≈ 8.3 MB, so ~60 HD frames stay hot. — **Reversibility:** reversible — a tuning constant.
- **D-10:** **Neighbor prewarm shares the 512 MB budget** — one budget, one eviction policy. The "lookahead evicts the current frame" scenario is impossible under proper LRU ordering.
- **D-11:** **Pinning correctness rule:** frames referenced by an in-flight composite/draw are PINNED (unevictable) until the draw releases them. Pinning is a correctness rule (you cannot `close()` a bitmap mid-`drawImage`), NOT a second budget. Eviction of an unpinned handle owns the explicit `bitmap.close()` call.
- **D-12:** **ONE decoded-frame cache authority after this phase.** The decode-once content-keyed caches shipped by G-52-7/G-52-8 are absorbed into the new byte-budgeted LRU — no parallel registry keyed by the dying dataUrl string survives.
- **D-13:** **ImageBitmap is the canonical decoded handle.** Rust decodes WebP → raw RGBA bytes → JS wraps into ImageData → `createImageBitmap(ImageData)` → GPU-backed ImageBitmap held in the LRU. Lifecycle: LRU eviction owns `bitmap.close()` explicitly; frames referenced by an in-flight draw are pinned. **ImageData exists only as the transient IPC→bitmap bridge, never stored.** The compositor draws via `drawImage(bitmap)`. — **Reversibility:** costly.
- **D-14:** **Watch items (correctness):** the `premultiplyAlpha` convention (straight alpha per Phase 48 D-02 — `createImageBitmap(ImageData)` must preserve straight alpha, not premultiply) and a **Safari `createImageBitmap(ImageData)` contract test** (WKWebView behavior may differ from Chrome).
- **D-15:** Raise the working-resolution cap **1000 → 1920** (native HD 1080p). Rescale pixel-relative physics/brush defaults proportionally (~1.9x) — minimal calibration, no physics redesign. Legacy projects: old keys keep their recorded size, `drawCanvasAtSize` scales them. — **Reversibility:** one-way.
- **D-16:** 2K/4K activation must be a **single-constant change + gates**. Nothing in the LRU, IPC, or cache code may hard-code resolution assumptions.
- **D-17:** The scope lands in **strict dependency order**: (1) runtime frame identity, (2) Rust codec, (3) lazy load + LRU, (4) cap raise 1000→1920 **LAST**, (5) the 2K/4K single-constant contract woven through all of them. The ~1.9x physics/brush defaults rescale ships in the **SAME plan as the cap raise (D-15), never deferred**.
- **D-18:** After the async Rust encode at frame commit, JS holds the **compact WebP bytes** (`Uint8Array`, typically 0.1-2 MB) on the runtime frame object until save stages them to sidecars. **Raw RGBA (8.3 MB/frame at HD) must never be held per-frame in the JS heap**; decoded ImageBitmaps exist only inside the byte-budgeted LRU.
- **D-19:** Hundreds of tests assert on dataUrl strings and PNG signatures — expect a **large test retarget**. Distribution floor: WKWebView WebP DECODE needs macOS 11+; the runtime never relies on it, but any direct file display (asset protocol) does.

### Pattern 1: Codec-agnostic Rust trait (D-02)
**What:** A `FrameCodec` trait over `encode_rgba`/`decode_rgba` so swapping WebP → JPEG XL touches one module.
**When to use:** The single seam every encode/decode command calls; never call `webp::` directly from commands.
**Example:**
```rust
// app/src-tauri/src/services/frame_codec.rs
pub trait FrameCodec: Send + Sync {
    fn encode_rgba(&self, rgba: &[u8], width: u32, height: u32) -> Result<Vec<u8>, String>;
    fn decode_rgba(&self, bytes: &[u8]) -> Result<(u32, u32, Vec<u8>), String>;
}

pub struct WebPLosslessCodec;

impl FrameCodec for WebPLosslessCodec {
    fn encode_rgba(&self, rgba: &[u8], width: u32, height: u32) -> Result<Vec<u8>, String> {
        let mut config = webp::WebPConfig::new().map_err(|_| "webp config init failed".to_string())?;
        config.lossless = 1;
        config.exact = 1;              // config_exact: preserve RGB under transparent pixels (D-01)
        config.alpha_compression = 0;  // lossless alpha
        config.quality = 75.0;
        webp::Encoder::from_rgba(rgba, width, height)
            .encode_advanced(&config)
            .map(|mem| mem.to_vec())
            .map_err(|e| format!("webp encode failed: {e:?}"))
    }

    fn decode_rgba(&self, bytes: &[u8]) -> Result<(u32, u32, Vec<u8>), String> {
        let img = webp::Decoder::new(bytes).decode().ok_or("webp decode failed".to_string())?;
        let (w, h) = (img.width(), img.height());
        let rgba = if img.is_alpha() {
            img.to_vec() // already RGBA (4 bytes/px)
        } else {
            let rgb = img.to_vec();
            let mut out = Vec::with_capacity(rgb.len() / 3 * 4);
            for px in rgb.chunks_exact(3) { out.extend_from_slice(&[px[0], px[1], px[2], 255]); }
            out
        };
        Ok((w, h, rgba))
    }
}
```
Source: read from `~/.cargo/registry/src/.../webp-0.3.1/src/{lib.rs,encoder.rs,decoder.rs,shared.rs}` and `libwebp-sys-0.9.6/src/ffi.rs:104-134` this session.

### Pattern 2: Byte-budgeted LRU with pinning (D-08..D-12)
**What:** A single decoded-frame cache authority keyed by stable frame ID, budgeted in bytes, with a pin count for in-flight draws.
**When to use:** Every decoded ImageBitmap (paint frames, background photos, reference photos) lives here; no parallel registry.
**Example:**
```typescript
// app/src/lib/frameLru.ts (shape — Claude's discretion)
interface DecodedFrameEntry {
  readonly key: string;        // stable frame ID: cachePath / sourceRef / library asset ID
  bitmap: ImageBitmap;
  readonly byteSize: number;   // width * height * 4 (decoded RGBA)
  pinCount: number;            // >0 = pinned (in-flight draw), unevictable
  lastUsed: number;            // monotonic LRU clock
}
// Eviction: while (totalBytes > 512MB) evict least-recently-used entry with pinCount === 0,
// calling entry.bitmap.close() explicitly (D-11). Pinned entries are skipped.
```

### Pattern 3: Transient ImageData → ImageBitmap bridge (D-13/D-14)
**What:** Rust returns raw RGBA bytes; JS wraps into `ImageData`, then `createImageBitmap` with `premultiplyAlpha: 'none'`.
**When to use:** Every decode; ImageData is never stored.
**Example:**
```typescript
const { width, height, rgba } = await invoke('decode_webp_frame', { bytes });
const imageData = new ImageData(new Uint8ClampedArray(rgba), width, height);
const bitmap = await createImageBitmap(imageData, { premultiplyAlpha: 'none' });
```

### Anti-Patterns to Avoid
- **Calling `webp::Encoder::encode_lossless()` directly:** it does NOT set `config.exact`, so transparent-pixel RGB is not preserved — violates D-01. Use `encode_advanced` with `exact=1`.
- **Keying the LRU by dataUrl string:** the exact pattern this phase eliminates (D-06). Key by stable `sourceRef`/library asset ID / `cachePath`.
- **Holding raw RGBA per-frame in the JS heap:** D-18 forbids it; only compact WebP `Uint8Array` rides the runtime frame object.
- **A second budget for prewarm:** D-10 — one 512 MB budget, one eviction policy.
- **Transporting bytes over `emitTo` (JSON):** JSON events base64-encode; use `invoke` (raw `ArrayBuffer`/`Uint8Array`) or a Rust sidecar-write + ref.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| WebP lossless encode/decode | A custom WebP codec | `webp` crate (`Encoder::from_rgba` + `encode_advanced`, `Decoder`) | libwebp is the reference implementation; hand-rolling lossless WebP is a multi-year effort. |
| `config_exact` alpha semantics | Post-processing transparent-pixel RGB | `WebPConfig.exact = 1` | libwebp's `exact` flag preserves RGB under transparent pixels natively (D-01). |
| base64 encode/decode in JS | `atob`/`btoa` loops over frame bytes | Eliminate entirely (D-07); Rust owns bytes | The current `encodePngDataUrl`/`decodePngDataUrl` (`efxPaintPersistence.ts:111-131`) and `bytesToBase64`/`base64ToBytes` (`physicsPaintBridgeTransport.ts:169-180`) are the multi-MB-string-as-Map-key pattern this phase removes. |
| Frame-count cache budget | `Map` capped by frame count | Byte-budgeted LRU (width×height×4) | Frame counts are resolution-dependent; D-08/D-16 require resolution-agnostic budgets. |
| Bitmap lifecycle tracking | Ad-hoc `close()` calls scattered in draw code | LRU owns `bitmap.close()`; pinning for in-flight draws | D-11: you cannot `close()` a bitmap mid-`drawImage`; centralizing lifecycle prevents use-after-close. |

**Key insight:** The codec and the cache are both "deceptively complex" — libwebp's lossless encoder has subtle alpha semantics (`exact`, `alpha_compression`, `near_lossless`) that a hand-rolled encoder would get wrong, and a naive frame-count cache silently breaks at 2K/4K (D-16). Both are solved by existing, already-present primitives.

## Common Pitfalls

### Pitfall 1: `encode_lossless()` silently drops transparent-pixel RGB
**What goes wrong:** The `webp` crate's convenience `encode_lossless()` sets `lossless=1, alpha_compression=0` but NOT `exact=1`. libwebp then rewrites RGB values under fully-transparent pixels for better compression — corrupting the straight-alpha RGB that Phase 48 D-02 depends on.
**Why it happens:** The crate's own test (`lib.rs:108-123`) documents this: "To achieve better compression, the webp library changes the rgb values in transparent regions."
**How to avoid:** Use `encode_advanced` with a custom `WebPConfig` setting `exact=1` (see Code Examples).
**Warning signs:** Semi-transparent stroke edges show color fringing after a save/reopen round-trip.

### Pitfall 2: Safari/WebKit ignores `premultiplyAlpha: 'none'`
**What goes wrong:** `createImageBitmap(imageData, { premultiplyAlpha: 'none' })` preserves straight alpha in Chrome, but Safari/WebKit ignores the option (WHATWG html#10142), so the bitmap may be premultiplied — breaking the straight-alpha compositing convention.
**Why it happens:** Documented WebKit interop gap; the only portable straight-alpha readback today is WebGL `UNPACK_PREMULTIPLY_ALPHA_WEBGL=false`.
**How to avoid:** Ship the D-14 contract test that asserts WKWebView behavior; if Safari premultiplies, the compositor's `drawImage(bitmap)` path must be validated against the straight-alpha flattened raster (Phase 48 D-02) and a fallback (e.g., draw through a straight-alpha canvas) considered.
**Warning signs:** Semi-transparent edges render brighter/darker in the packaged WKWebView build vs Chrome dev.

### Pitfall 3: Transporting frame bytes over `emitTo` (JSON) re-introduces base64
**What goes wrong:** The current `sendPhysicPaintApplyPayload` uses `emitTo('main', PHYSIC_PAINT_APPLY_EVENT, payload)` where `payload.renderedFrame.dataUrl` is a base64 string. If the retarget keeps `emitTo` and just swaps the string for a `Uint8Array`, Tauri's JSON event serialization base64-encodes it — violating D-07 ("no base64 in JS anywhere").
**Why it happens:** Tauri events are JSON-serialized; `invoke` commands accept raw `ArrayBuffer`/`Uint8Array` bodies.
**How to avoid:** Move byte transfer to a Tauri `invoke` command (or a Rust sidecar-write + stable-ref), not `emitTo`.
**Warning signs:** A `Uint8Array` in an event payload arrives as a base64 string or `{0:..,1:..}` object on the main side.

### Pitfall 4: The `background-only-support` frame is a fake PNG dataUrl
**What goes wrong:** `_makeBackgroundOnlySupportFrame` (`physicPaintStore.ts:1594`) fabricates `data:image/png;base64,${btoa('background-only-support:...')}` — a string that is NOT a valid PNG. The D-07 WebP magic-byte retarget must not blindly reject it, or the background-only support path breaks.
**Why it happens:** This is the exact "base64 mislabeled as PNG" bug class from Phase 36.14 (the known landmine).
**How to avoid:** Treat `background-only-support` frames as a distinct non-raster marker (they are never decoded), not as a WebP/PNG payload to validate.
**Warning signs:** `isRotoPngDataUrl`/WebP probe rejects the fabricated string and background-only cells render as missing.

### Pitfall 5: The `_compositorImageCache` is a second decode authority
**What goes wrong:** `_compositorDecode` (`physicPaintStore.ts:1097`) maintains a `dataUrl → HTMLImageElement` cache alongside `_rotoAlphaCanvasRegistry`. D-12 requires ONE decoded-frame cache authority; leaving `_compositorImageCache` keyed by dataUrl keeps a parallel registry.
**Why it happens:** The G-52-7/G-52-8 fixes shipped decode-once caches keyed by the dying dataUrl string.
**How to avoid:** Absorb `_compositorImageCache` and `_rotoAlphaCanvasRegistry` into the byte-budgeted LRU; the compositor's `_preResolveTrackContent` (`:1196`) resolves the LRU handle instead of `_compositorDecode(dataUrl)`.
**Warning signs:** Two caches hold the same frame; evicting one leaves a stale handle in the other.

## Open Questions

1. **Does Tauri v2 `invoke` accept `Uint8Array`/`ArrayBuffer` command arguments with raw (non-base64) bodies, and is there a practical size ceiling for a 0.1-2 MB frame?**
   - What we know: Tauri v2 `invoke` supports `ArrayBuffer`/`Uint8Array` as command args (serialized as raw bytes in the IPC body); `emitTo` events are JSON-serialized (base64). The existing thumbnail encoder already round-trips `rgbaBase64` over events.
   - What's unclear: the exact byte-transfer ceiling and whether the apply path can switch from event to command without breaking the child→main request/response flow.
   - Recommendation: Verify with a spike in the first plan; fall back to a Rust sidecar-write + stable-ref pattern if `invoke` byte transfer is unsuitable.

2. **Does Safari/WKWebView actually premultiply `createImageBitmap(ImageData, { premultiplyAlpha: 'none' })`, and does the compositor's `drawImage(bitmap)` still produce correct straight-alpha output?**
   - What we know: WHATWG html#10142 documents Safari ignoring `premultiplyAlpha: 'none'`; Safari 15+ supports `createImageBitmap(ImageData)` (WebKit r265360).
   - What's unclear: whether the premultiply mismatch is observable through `drawImage` (which converts to premultiplied internally) or only through readback.
   - Recommendation: Ship the D-14 contract test as a Wave 0 test; validate against the Phase 48 D-02 straight-alpha flattened raster in native UAT.

3. **Which physics constants are genuinely pixel-relative vs per-pixel-normalized?**
   - What we know: `brushRenderRadius = size/2` (pixel-relative); `DENSITY_NORM`/`LUT_SIZE` are per-pixel density normalization; `BLOW_STRENGTH` is a per-cell fluid force.
   - What's unclear: whether the fluid solver grid scales with resolution (making `BLOW_STRENGTH` pixel-relative) or is fixed.
   - Recommendation: A calibration UAT at 1920 (dense Physics strokes) determines the exact rescale values; keep the rescale in the SAME plan as the cap raise (D-17).
