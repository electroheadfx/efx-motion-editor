# Phase 52.1: Modern frame runtime + native HD paint - Context

**Gathered:** 2026-09-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the base64-dataUrl frame runtime with a bytes/ImageBitmap runtime, move PNG→WebP-lossless encode/decode into Rust, lazy-load sidecars behind a byte-budgeted LRU, and raise the working-resolution cap 1000→1920 — so HD projects paint at native resolution without main-thread jank or heap blowup. This is urgent work inserted before the Phase 53 lock/release.

**Verified current state (do not re-litigate):** Disk persistence is already file-based — the `.mce` holds `cachePath` refs only; frames are binary PNG sidecars under `cache/efx-paint/` with UUID staging + path guards (`efxPaintPersistence.ts`, DOC-05). The problems are runtime + codec:
- (a) every frame lives as a base64 dataUrl string in the JS heap — registries key Maps BY the dataUrl string (`physicPaintStore.ts:339`);
- (b) capture runs `toDataURL` SYNCHRONOUSLY on the main thread;
- (c) project open EAGERLY `readFiles` every sidecar of every track and re-encodes each to base64 (`loadEfxPaintDocuments`, `efxPaintPersistence.ts:370-401`);
- (d) the working-resolution cap (`PHYSICS_PAINT_WORKING_LONG_EDGE=1000`, `physicsPaintCanvasSizing.ts:3`) makes paint resolution a permanent quality ceiling — strokes are never persisted, transport is raster-only (`physicPaint.ts:1779`). A 1920x1080 project paints at ~52%.

**Naming contract (carried from Phases 45/46/47/48/49/50/52):** "EFX Paint" = the inline main-editor Basic/FX layer (out of scope, unchanged). "EFX Physic Paint" = the independent module + Studio window — the sole target of v1.0.0 and this phase. All user-facing copy is English.

</domain>

<decisions>
## Implementation Decisions

### Codec (locked — researched)
- **D-01:** Sidecars switch PNG → **WebP lossless** via Rust libwebp bindings (crate `webp`/`libwebp-sys`), `config_exact` alpha semantics (RGB preserved under transparent pixels). Evidence: op111.net lossless benchmarks (Oct 2025) — PNG collapses to ~0% reduction on photo content (our Phase-52 reveal-baked photo keys) while WebP lossless reaches ~88%, and wins 40-73% on stroke/sparse frames at ~15-90ms encode for 1-1.5MP frames. AVIF/HEIC eliminated (negative ratios on this content class). Browser codec support is IRRELEVANT: Rust owns encode AND decode; JS receives raw RGBA → ImageData/ImageBitmap. PNG survives only as import/export interchange. (WKWebView cannot encode WebP and Tauri v2 uses the system WebKit — this is why the codec work lives in Rust.) — **Reversibility:** one-way — the on-disk sidecar format changes; old projects fail to open (clean-break no-compat, Phase 45 contract).
- **D-02:** The Rust codec seam is **codec-agnostic** (trait over encode/decode), so swapping WebP → JPEG XL (libjxl) touches one module. JPEG XL is the documented re-evaluation point for v1.2.0 when the 2K/4K cap activates (JXL encodes ~4x faster than WebP at 4K with equal-or-better ratios; effort levels e1-e3 offer sub-second 4K encodes).

### Fluidity (locked — researched)
- **D-03:** Encode never happens during the paint gesture (gesture = engine canvas redraw, GPU). Encode moves to async Rust commands at frame commit/save/bake — the current main-thread `toDataURL` jank disappears. The one remaining synchronous piece is the canvas readback (`getImageData`, ~10-30ms at HD) — acceptable at HD; if profiling shows jank, escalate to `createImageBitmap(canvas)` transferred to a worker doing the readback on OffscreenCanvas. Scrub cold-miss = libwebp decode ~20-50ms at HD, covered by the LRU + neighbor prewarm riding the existing playback lookahead machinery.

### Step 0 — dependency bumps (locked, folded into this phase, no separate quick)
- **D-04:** Tauri 2.10.x → **2.11.5** (`@tauri-apps/api`, cli, Cargo `tauri`/`tauri-build`, plugins fs/store/dialog/notification/shell) — 2.11.1 fixed IPC ACL security issues. Preact 10.28.4 → **10.29.8** + `@preact/signals` + `@preact/preset-vite` to latest compatible — CVE-2026-22028 already patched at our floor, ship the signed release on latest patch. Do NOT touch Preact 11 (RC, breaking changes). Gates: `pnpm install` clean, `vitest run` green, `tsc` clean, app launches, native UAT smoke (open/paint/playback/save).

### Runtime frame identity (locked + discussed)
- **D-05:** Runtime frame identity is **bytes/ImageBitmap, not dataUrl string**. Retarget `RenderedFramePayload`, the dataUrl-keyed registries, content tokens (`resolveContentToken`), dedup, bridge transport, main-editor preview/export readers.
- **D-06:** **Base64 elimination covers ALL THREE dataUrl-keyed registries** — `_rotoAlphaCanvasRegistry` (paint frames), `_backgroundSourceImages` (imported background photos), `_referenceSourceImages` (imported photo references). The imported background/reference photos are the same multi-MB-string-as-Map-key pattern (a 12 MP photo reference outweighs most paint frames); excluding them keeps two known-hot instances of the exact pattern this phase exists to eliminate, and v1.2.0's 2K assets would compound it. **Keys become the existing stable `sourceRef`/library asset IDs; values become decoded handles in the same byte-budgeted LRU.** Accepted cost: the Phase 49/50 import+composite paths join the retarget, re-validated inside the phase's full native roto UAT. — **Reversibility:** one-way — the dataUrl-keyed registries are removed; no parallel registry survives.

### Rust encode/decode (locked)
- **D-07:** Rust encode/decode commands (WebP lossless, exact alpha) write/read the existing sidecar files from bytes — **no base64 in JS anywhere**. Retarget PNG signature probes / `isRotoPngDataUrl` validation to WebP RIFF/VP8L magic bytes.

### Lazy load + LRU (locked + discussed)
- **D-08:** Lazy sidecar load: project open reads refs only; bytes fetched and decoded to ImageBitmap on demand; byte-budgeted LRU over decoded frames (budgets in BYTES, never frame counts — resolution-agnostic by design).
- **D-09:** **LRU byte ceiling = fixed 512 MB.** At 1920×1080 RGBA one decoded frame ≈ 8.3 MB, so ~60 HD frames stay hot. — **Reversibility:** reversible — a tuning constant.
- **D-10:** **Neighbor prewarm shares the 512 MB budget** — one budget, one eviction policy. The "lookahead evicts the current frame" scenario is impossible under proper LRU ordering (the just-drawn frame is most-recently-used; prewarm only evicts the distant tail behind the playhead — the desired scrub-forward behavior).
- **D-11:** **Pinning correctness rule:** frames referenced by an in-flight composite/draw are PINNED (unevictable) until the draw releases them. Pinning is a correctness rule (you cannot `close()` a bitmap mid-`drawImage`), NOT a second budget. Eviction of an unpinned handle owns the explicit `bitmap.close()` call.
- **D-12:** **ONE decoded-frame cache authority after this phase.** The decode-once content-keyed caches shipped by the G-52-7/G-52-8 fixes (roto PNG decode off-main-thread, reveal-rail decode/encode storms) are absorbed into the new byte-budgeted LRU — no parallel registry keyed by the dying dataUrl string survives. Their off-main-thread decode behavior is preserved by construction (Rust decode + `createImageBitmap`).

### Decoded frame handle (discussed)
- **D-13:** **ImageBitmap is the canonical decoded handle.** Rust decodes WebP → raw RGBA bytes → JS wraps into ImageData → `createImageBitmap(ImageData)` → GPU-backed ImageBitmap held in the LRU. Lifecycle: LRU eviction owns `bitmap.close()` explicitly; frames referenced by an in-flight draw are pinned (unevictable) until released. **ImageData exists only as the transient IPC→bitmap bridge, never stored.** The compositor draws via `drawImage(bitmap)`. — **Reversibility:** costly — touches the compositor draw path and the frame lifecycle.
- **D-14:** **Watch items (correctness):** the `premultiplyAlpha` convention (straight alpha per Phase 48 D-02 — `createImageBitmap(ImageData)` must preserve straight alpha, not premultiply) and a **Safari `createImageBitmap(ImageData)` contract test** (WKWebView behavior may differ from Chrome).

### Working-resolution cap (locked)
- **D-15:** Raise the working-resolution cap **1000 → 1920** (native HD 1080p). Rescale pixel-relative physics/brush defaults proportionally (~1.9x) — minimal calibration, no physics redesign. Legacy projects: old keys keep their recorded size, `drawCanvasAtSize` scales them (clean break accepted per policy). — **Reversibility:** one-way — legacy keys keep their recorded size; no re-paint affordance.

### Architecture contract (locked)
- **D-16:** 2K/4K activation must be a **single-constant change + gates**. Nothing in the LRU, IPC, or cache code may hard-code resolution assumptions. (4K will still need measured capture-readback and encode budgets; GPU compositing stays out of scope.)

### Dependency order (locked)
- **D-17:** The scope lands in **strict dependency order**: (1) runtime frame identity, (2) Rust codec, (3) lazy load + LRU, (4) cap raise 1000→1920 **LAST**, (5) the 2K/4K single-constant contract woven through all of them. The cap raise comes after the runtime is proven so a UAT regression can be bisected between runtime and resolution. The ~1.9x physics/brush defaults rescale ships in the **SAME plan as the cap raise (D-15), never deferred**.

### At-rest frame form (locked)
- **D-18:** After the async Rust encode at frame commit, JS holds the **compact WebP bytes** (`Uint8Array`, typically 0.1-2 MB) on the runtime frame object until save stages them to sidecars. **Raw RGBA (8.3 MB/frame at HD) must never be held per-frame in the JS heap**; decoded ImageBitmaps exist only inside the byte-budgeted LRU.

### Known blast radius (locked)
- **D-19:** Hundreds of tests assert on dataUrl strings and PNG signatures — expect a **large test retarget**. Distribution floor: WKWebView WebP DECODE needs macOS 11+; the runtime never relies on it, but any direct file display (asset protocol) does.

### Claude's Discretion
- The exact Rust codec trait shape (encode/decode over bytes) and where it lives relative to the existing `webp`/`image` crates already in `app/src-tauri/Cargo.toml`.
- The exact LRU accounting (decoded RGBA bytes = width × height × 4) and eviction granularity (per-frame).
- The exact `createImageBitmap(ImageData)` invocation (premultiplyAlpha option) and the transient ImageData bridge shape.
- Which pixel-relative physics/brush defaults are rescaled (~1.9x) and the exact calibration values.
- The exact retarget of `resolveContentToken`, dedup, and bridge transport to bytes/ImageBitmap.
