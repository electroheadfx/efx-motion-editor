# 52.5 Multi-Audio Concept (input for a future quick)

Status: **concept only — not implemented.** Sourced from the 52.5 UAT round 3
feedback (2026-10-07), extended by UAT round 6 (2026-10-07): the user wants
several document audios per Studio document, each with its own settings,
selectable from a list in the modal, and the ability to place several clips
that share one imported audio file. The implementation is intended for a
separate `gsd-quick --full` inside a named milestone. Nothing in this file is a
commitment of the quick's scope — it is the design the 52.5 singleton work was
reshaped to leave room for.

## Goal

Import and manage **several** document audios in one Studio document. Each
audio is a timeline clip with its own geometry and its own playback settings.
Clicking a list entry in the Document sound modal selects and reveals that clip
on the timeline.

### Two ways in (UAT round 6)

The two entry points must open **the same dialog** but land on different
targets:

| Entry | Opens | Lands on |
|---|---|---|
| Double-click a clip on the timeline | the Document sound modal | **that** clip's editor (list pre-selected) |
| The `Document sound` header launcher | the Document sound modal | the **list**, so the user can choose which clip to edit |

The launcher is therefore a *chooser* when several clips exist, not an editor
of an arbitrary clip. Double-click stays the fast path straight into the clip
you are looking at. With a single clip both entries land on the same place (the
one clip is already selected).

## Identity (the UAT's "add an ID to audio imported")

Two distinct identities already exist in the 52.5 model. **Keep both — do not
overload them:**

| Field | Identity | Stable across | Used for |
|---|---|---|---|
| `DocumentSoundClip.id` | the **placed clip** (timeline instance) | edits, moves, trims, save/reopen | modal list selection, timeline selection, `documentAudio` transport key, `preparedTrackIds` buffer key |
| `DocumentSoundClip.sourceId` | the **imported file** (shared-gallery asset) | re-imports of the same file AND alt+drag duplication | peaks cache key (`audioPeaksCache.get(sourceId)`), dedupe in the gallery |

`sourceRevision` already bumps on re-import and stays the asset-freshness
token. A future quick should NOT introduce a third id — `id` is the list key.

**`id` is unique per clip, `sourceId` is NOT** (UAT round 6): alt+drag creates
a second clip with a fresh `id` and the **same** `sourceId`, so one imported
file can be used several times without duplicating the bytes. Every code path
must be explicit about which key it wants — buffers/transport by `id`, peaks
and gallery by `sourceId`.

## Data model

Replace the top-level singleton with an ordered array:

```ts
interface EfxPaintDocument {
  // ...
  readonly audios: readonly DocumentSoundClip[]; // 0..n, replaces `sound`
}
```

- `DocumentSoundClip` keeps its current per-clip shape unchanged:
  `id`, `sourceId`, `relativePath`, `sourceRevision`,
  `startFrame`, `inFrame`, `outFrame`,
  `gain`, `fadeInFrames`, `fadeOutFrames`, `fadeInCurve`, `fadeOutCurve`,
  `enabled`.
- **Every clip owns its own settings** (the UAT requirement). There is no
  shared/global volume, fade, or on/off — `enabled` is per clip.
- Overlaps are allowed and MIX (the 52.5-02 export mixer sums clips). Ordering
  in `audios[]` is the list order; it has no timing meaning. **UAT round 4
  note: overlapping clips are expected and must mix, never clip or reject.**
  See "Overlaps MIX" below for the per-clip gain/fade-then-sum law.
- `sourceId` is shared freely: the array may hold several clips with the same
  `sourceId` (alt+drag). Nothing in the parser may assume `sourceId` is unique
  across `audios[]`.
- Fail-closed parse: `SOUND_KEYS` per entry (unchanged allowlist), plus a
  fail-closed `AUDIO_LIST_KEYS` on the container. Unknown members throw.

**No backward compatibility** (v1.0.0 is the project-breaker version): the
`singular sound` member is simply gone. Old projects fail to parse and are
rebuilt fresh.

## Modal (`PhysicsPaintAudioModalView`)

Becomes a list + a per-selection editor. The list is the **chooser** the
launcher opens; the editor below it is what double-click jumps straight into.

1. Header: `AudioWaveform` + `Document sounds` + close X.
2. **List** — one row per clip: filename, `enabled` state, `in..out` range,
   and a `selected` marker. Click a row → select that clip
   (`selectedSoundId` → `clip.id`) and reveal it on the timeline.
   Several clips may name the **same** filename — the row must show the clip's
   own `in..out` (and its start frame) so two uses of one file stay
   distinguishable.
3. **Per-selection editor** (below the list) — the current field set, editing
   ONLY the selected clip: File + `Replace…`, `Remove` + `On`/`Off`, Volume,
   `Fade in | Fade out` (frames), `In | Out` (frames).
4. `Import sound` — ADDS a new entry (does not replace). `Replace…` swaps the
   selected entry's source, preserving its position/in-out (the
   `buildReplacedSoundClip` clamp law).
5. **Show in timeline** (per list row or on the editor) — scrolls the timeline
   to the clip and selects it, the mirror of "click a row → reveal". This is
   the answer to "make show in timeline" from the UAT.
6. Empty state (`No sound yet`) only when `audios.length === 0`.

## Timeline (the current rendering is already per-clip geometry)

Generalize the single `props.documentSound` read to a map over `audios[]`:

- One stain + one pair of trim handles + one fade/volume overlay per clip
  (the UAT round 3 rendering is already driven by one clip's fields — repeat
  it per entry).
- `selectedSoundId` drives the `is-selected` visual on exactly one clip.
- Click a clip → select it (never scrubs — the UAT round 3 truth table). Click
  the band outside every clip → deselect.
- Double-click a clip → open the modal on **that** clip (see "Two ways in").
- The playhead scrub handle and the ruler stay the ONLY scrub targets.

### Overlaps MIX (UAT round 6)

Two clips may occupy the same frames. The audible result is a **sum**, never a
winner and never a rejection:

- Each clip's own `gain`, `fadeInFrames`/`fadeInCurve` and
  `fadeOutFrames`/`fadeOutCurve` apply to that clip alone before the sum.
- The mixer adds the resulting signals (the 52.5-02 export mixer is the same
  law as the Studio preview). No limiter is promised in the quick; a later
  master-lane idea is out of scope here.
- `enabled: false` removes that clip's contribution entirely (it does not
  duck or mute the others).

### Alt+drag duplicates a clip onto the same source (UAT round 6)

`Alt`+drag a clip to create a **second placed clip that shares the source**:

- The new clip gets a fresh `DocumentSoundClip.id` (it is a new timeline
  instance) and **the same `sourceId`** as the original — one imported file,
  several uses. No second copy of the bytes, no second gallery entry, no
  second `audio/` path in the package.
- The duplicate starts as a copy of the geometry (start/in/out + settings) so
  the user can immediately slide it and trim it to "another portion of audio".
- Peaks stay keyed by `sourceId`, so both clips render the same waveform from
  one cached decode — the peaks cache must be source-keyed, never clip-keyed
  (it already is).
- `documentAudio` transport and `preparedTrackIds` stay clip-keyed (`id`),
  because the two clips may play at different offsets simultaneously.

## Transport + persistence

- `documentAudio` on the launch/bridge channel: carry
  `clips: [{ id, sourceId, sourceRevision, relativePath, ... }]` under the same
  monotonic revision + null-clear law (one revisioned section for the whole
  list keeps the strict newer-than funnel intact). Per-clip events would break
  the watermark.
- **PITFALL (UAT round 6 root cause):** the native launch path deserializes
  the context into the Rust `PhysicsPaintLaunchContext` struct and serde
  **silently drops members the struct does not declare**. A section that
  exists in JS and vanishes on the native path is this bug — the child then
  never runs `prepareClip` and playback is dead while the band still draws.
  Whatever shape `documentAudio` takes for the list, the Rust struct field
  must grow with it (and a round-trip test must pin it).
- `.mce`: `audios/` package-relative references, one path per clip. The
  existing `isSafePackageRelativePath` + `audio/`-prefix guards extend to the
  list (the path law itself is unchanged).
- `prepare()` / `prepareClip()` decode every listed clip; `preparedTrackIds`
  already keys on `sound.id`, which is the per-clip key we need. Note it must
  be keyed per PLACED clip (`id`), never per `sourceId` — two clips sharing a
  source may play at different offsets at the same time.

## Playback (relates to 52.5-02)

- Studio: every `enabled` clip mixes (the Q3 clip leg loops over `audios[]`).
- Main editor + export: every `enabled` clip is gated by D-12/D-13 (hide/solo)
  and summed in the mixer. Per-clip `enabled` is the per-clip mute.

## Out of scope for the quick (keep it tight)

- No per-clip automation lanes (volume/fade envelopes over time).
- No cross-fade automation between clips.
- No waveform reordering / grouping in the list.
- No master/limiter lane over the mixed sum.
- No dedupe-by-content of two separately imported copies of the same file
  (alt+drag is the supported way to reuse one source; importing the file twice
  still makes two gallery assets).
