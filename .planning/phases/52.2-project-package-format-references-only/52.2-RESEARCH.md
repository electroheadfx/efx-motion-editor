### Package shape & layout (discussed — amends spec §4/§5)

Rationale (scout, spec §4's mapping ask): no existing folder fits — `paint/<layerId>/frame-NNN.json` holds main-editor INLINE paint frames (still live via `savePaintData`, different subsystem, out of scope), `images/` holds imported source originals + thumbs, `cache/efx-paint/` holds regenerable derived frames, `scripts/` holds the Roto library. - **D-03:** **Full macOS package treatment in this phase.** The project folder becomes `Name.mce/` (document package), the app declares the document type (Info.plist CFBundleDocumentTypes + package flag) so Finder shows ONE icon and double-click opens the project; open/save dialogs target packages; Windows/Linux keep a plain folder. Matches spec §4 and the "icon clicks" native-UAT line (§13.4). — **Reversibility:** costly — a published open/save surface users build habits on.
- **D-04:** **Manifest = pure index; the layer sub-file holds the COMPLETE document.** `project.mce` carries the main-editor project content + a per-physic-paint-layer index (layer file path + document/composite revisions) + `formatVersion`. One authority per fact; the Studio writes exactly one sub-file, so spec §6 ("Studio saves only its layer's sub-file + that layer's changed media") holds structurally. Supersedes the spec §5 draft split (which spread per-track fields across manifest and layer file — hide/solo edits in the Studio would have dirtied the manifest and broken §6). — **Reversibility:** costly — the file partition defines every save/read path.
- **D-05:** **`cache/` moves OUT of the package** — machine-local disposable cache keyed by project identity, the package carries authoritative content only. The plan must: recompute `cachePath` references to the machine-local location on load; and re-derive on cache miss (a moved package opens on a cold machine with an empty cache). Consequence: the package must contain NO machine-local paths — any derived-frame reference inside `layers/*.json` must be recomputable from project identity or re-derivable; the exact scheme is planning's to design. — **Reversibility:** costly — reversing means packages carry regenerable weight again and the ref scheme changes twice.

### Persistence laws (locked — carried from the spec; do not re-litigate)
- **D-07:** References only — images are files on disk; JSON holds relative paths + content digests, never payloads. No embedded database; the user must open the folder and SEE the `.webp` files (spec §2.1).
- **D-08:** Clean break — pre-52.2 projects are refused by shipped code; no migration shims. The refusal mirrors the Phase 45 no-recourse dialog pattern. A **dev-only rescue converter** (outside app sources, not shipped) converts the user's current 37 MB project; the user's test material survives (spec §2.2, §9). — **Reversibility:** one-way — shipped readers only speak the new format; a migration would need a new reader.
- **D-09:** Granularity: per paint layer, never per key — key metadata lives in the layer's sub-file; key bytes live as `frames/` media files (spec §2.3).
- **D-10:** Extend, don't replace — the shipped transactional save machinery (staging → hardlink unchanged → fsync → atomic rename-swap → digest-bound commit/rollback) is extended to the new file set, not rewritten (spec §2.4).
- **D-11:** Save = write only CHANGED files (per-file change tokens extend the existing `savedFrameTokens` model) + atomic multi-file commit. **No full-document serialize anywhere** — the measured ~4.6 s `persist.serialize` term dies. Studio saves only its layer's sub-file + that layer's changed media (spec §6). The cancelled autosave quick is absorbed: its per-key dirty-tracking becomes per-file change tracking.
- **D-12:** Bridge (Studio↔main) sync passes references + metadata, not base64 payloads; bytes cross only when a frame actually changed (digest-keyed). Kills the ~4.5 s `docSync` term (spec §7).
- **D-13:** Read-back leg — the genuinely new construction (spec §8): open = read manifest + layer sub-files + lazily decode media files through the 52.1 bytes/ImageBitmap + LRU path. Missing media file → locked slate behavior (Phase 49 law); corrupt digest → refuse, no silent fallback. **Note for planning:** the loader comment at `efxPaintPersistence.ts:430-433` claims an existing "fetch the WebP sidecar on demand" — no such fetch exists anywhere in the codebase (verified 2026-09-12); this leg must be BUILT, not wired.
- **D-14:** Derived frames re-derive in memory — nothing reads `cache/*.webp` today (verified; see Verified Facts). Cache files are write-only artifacts (staged/hardlinked/deleted by the save transaction) until the read-back leg ships, and remain re-derivable after.

## Summary

This phase replaces the single-JSON persistence model with a **file-referenced package**: a light `project.mce` manifest, one `layers/<layerId>.json` sub-file per paint layer, and real `frames/<layerId>/<keyId>.webp` rasters on disk. Research confirms all four construction legs are green-field but mechanically supported by existing in-repo machinery: the transactional save (staging → hardlink → fsync → atomic swap → digest-bound commit) in `efxPaintPersistence.ts` + `physic_paint_cache.rs`; the fail-closed document parser; the 52.1 bytes/ImageBitmap LRU decode path; and SHA-256 already available in Rust (`sha2`).

The highest-risk discovery is the **Tauri bundler's limitation on macOS document packages**: `bundle.fileAssociations` generates `CFBundleDocumentTypes` + `UTExportedTypeDeclarations` but **never emits `LSTypeIsPackage`** (verified against downloaded tauri-utils/tauri-bundler source), and the user-supplied `Info.plist` merge is a **shallow top-level key overwrite** — so a merge plist containing `CFBundleDocumentTypes` silently replaces the generated one. The plan must hand-author the complete document-type declaration in one place, never split across both mechanisms.

The second-highest risk is the **chunk budget (D-19)**: the frozen 1320 kB budget has only ~14.9 kB of headroom (main chunk measured 1305.11 kB), while a minimal Effect bundle measures ~164 kB and XState ~84 kB. `PhysicsPaintStudio` is already a lazy chunk, but three of the four pilot files reach the **main chunk** through `physicPaintFlush.ts`. The pilot's implementation modules must sit behind the Studio lazy boundary or the budget gate fails.

**Primary recommendation:** Build the format legs in this order — (1) Rust media write/read commands + digest, (2) package read-write plumbing with the extended transaction, (3) Info.plist package declaration via a single merge plist, (4) refusal gate + rescue converter — and defer the two async pilot waves behind the Gate-2 conventions doc with a pilot-start re-verification of the pinned alpha/RC versions.

## Executor-Facing Takeaways

1. **The packager exists; the package reader does not.** `commands/physic_paint_cache.rs` has exactly three commands (publish/settle/hardlink). There is **no read command** anywhere. D-13's "read-back leg" is new Rust + new TS, not a wire-up.
2. **`frames/*.webp` are not servable through `efxasset://`** — the MIME allowlist at `lib.rs:399-418` has no `webp` entry. Bytes must cross via IPC (plugin-fs `readFile`, or a new Rust read command).
3. **Tauri will not produce a document package by itself.** `fileAssociations` alone yields a document type that Finder treats as a *folder* or a *plain file* — never as a single-icon package. `LSTypeIsPackage` must be added through the `Info.plist` merge, and the merge replaces, not augments, `CFBundleDocumentTypes`.
4. **Dev-mode cannot verify any of the Finder behaviour.** `tauri dev` runs the raw binary; Info.plist only exists inside a bundled `.app` (`target/{debug,release}/bundle/macos/EFX Motion Editor.app`). The D-03 "icon clicks" UAT must run on a bundled build.
5. **Budget math is tight:** 1320 kB frozen − 1305.11 kB measured = **14.89 kB headroom**; a minimal Effect import alone is ~164 kB minified. The pilot must be confined to the Studio lazy chunk.

### System Architecture Diagram — save path (write direction)

### Pattern 1: Extend the transaction to a file SET (D-10)
**What:** the shipped transaction binds exactly one project file. Verbatim from `physic_paint_cache.rs`:
```rust
struct CacheTransactionMarker {
    version: u32,
    transaction_id: String,
    staging_basename: String,
    replaced_existing: bool,
    phase: CacheTransactionPhase,
    project_file_path: Option<String>,
    expected_project_digest: Option<String>,
}
```
`bind_cache_transaction_to_project_write(project_dir, project_file_path, project_bytes, transaction_id)` binds ONE file with ONE expected digest. The package has N authoritative files (manifest + k layer sub-files + m media files). **Two designs are viable:**
- **(a) Aggregate digest:** keep one marker; compute the expected digest over a canonical concatenation (path-sorted `path\0sha256` list) of every file the transaction will touch. Minimal surface change; the marker's `expected_project_digest` semantics change from "the file" to "the set".
- **(b) Per-file digest list:** change `project_file_path: Option<String>` → `project_files: Vec<(String, String)>`. More faithful to per-file rollback, more code.

Recommendation: **(a)** — the rollback granularity that matters is "the whole commit or nothing"; per-file rollback has no current consumer. Preserve the existing 64-hex validation, extended to each entry of the set.

### Pattern 2: Per-file change tokens extending `savedFrameTokens`
**What:** today's map, verbatim (`efxPaintPersistence.ts:82-88`):
```ts
/**
 * Last-saved per-frame byte tokens, keyed `layerId:trackId:appFrame` (52.1 a2).
 * Populated only after a successful commit; the changed set on the next save is
 * every frame whose current token differs from this map. Empty after a restart
 * (or a first save), which forces a full re-stage — the fail-closed default.
 */
const savedFrameTokens = new Map<string, string>();
```
Extend to a key space covering the three file classes: `frame:<layerId>:<keyId>`, `layer:<layerId>`, `manifest`. Media entries store the **persisted SHA-256** (so the same map answers "is the on-disk file current?" on open, feeding the read-back leg's cache-miss logic). Keep `buildFrameBytesToken` for the in-memory O(1) comparison. Do NOT key by `appFrame` — `frames/<layerId>/<keyId>.webp` is keyed by **keyId** (D-02/D-09), and one keyId can be referenced by multiple placements.

### Pattern 3: Prefix-locked Rust read command (ASVS V12, mirrors existing guards)
**What:** the in-repo precedent, verbatim (`efxPaintPersistence.ts:134-143`):
```ts
/**
 * Prefix-locked sidecar path guard (T-45-11, ASVS V12): the path must live
 * under `cache/efx-paint/`, contain no backslash, no absolute prefix, no NUL,
 * and no empty/dot segments.
 */
export function isSafeEfxPaintCachePath(cachePath: unknown): cachePath is string {
  if (typeof cachePath !== 'string' || !cachePath.startsWith(`${EFX_PAINT_CACHE_DIR}/`)) return false;
  if (cachePath.includes('\\') || cachePath.startsWith('/') || cachePath.includes('\0')) return false;
  return cachePath.split('/').every((segment) => segment.length > 0 && segment !== '.' && segment !== '..');
}
```
A media-path guard must do the same for `frames/` (and `images/` for Law-1 references), and the Rust reader must additionally canonicalize + `starts_with(project_root)` the same way `resolve_efxasset_path` does (`lib.rs:434-450`):
```rust
let canonical = std::fs::canonicalize(decoded_path).map_err(|_| EfxassetRejection::NotFound)?;
...
if !allowed_roots.iter().any(|root| canonical.starts_with(root)) {
    return Err(EfxassetRejection::OutOfScope);
}
```

### Pattern 4: Media-body law — bytes never enter JSON (D-07, Law-1)
Every image-bearing field becomes `{ relativePath, digest, width, height }`. The in-repo payload shape to convert is (`PhysicPaintRotoRealKeyPayload`):
```ts
export interface PhysicPaintRotoRealKeyPayload {
    frameIndex: number;
    appFrame: number;
    bytes: Uint8Array;      // <-- this field is what dies
    width?: number;
    height?: number;
}
```
The parser key set `PHYSIC_PAINT_ROTO_REAL_KEY_PAYLOAD_KEYS = new Set(['frameIndex','appFrame','bytes','width','height'])` must be updated in lockstep, or the fail-closed parser will reject the new documents.

### Anti-Patterns to Avoid
- **Splitting the document-type declaration** between `bundle.fileAssociations` and the merge `Info.plist` — the merge is a shallow overwrite; only one mechanism may own `CFBundleDocumentTypes`.
- **Widening the `fs:scope` capability to `**/frames/**`** when a prefix-locked Rust command already fits the codebase's guard pattern.
- **Importing Effect/XState from `physicPaintFlush.ts` or anything reachable from `projectStore.ts`** — see Pitfall 1.
- **Storing an absolute cache path in any package file** — D-05 forbids machine-local paths in the package.
- **Silent fallback on digest mismatch** — D-13 says refuse.
- **Per-key files in `layers/`** — D-09 is per paint layer, never per key.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Atomic multi-file commit + crash recovery | A new journal/manifest-pair scheme | Extend the shipped staging→hardlink→fsync→rename transaction (D-10) | It is already digest-bound, phased, and tested; a second mechanism doubles the failure surface |
| Content hashing | A JS hash or `crypto.subtle` wrapper | Rust `sha2` (`digest_bytes`, `physic_paint_cache.rs`) | Already present, validated (64 hex), and hashes the exact persisted bytes |
| Path safety for media references | A new bespoke validator | Mirror `isSafeEfxPaintCachePath` + `resolve_efxasset_path` canonicalize/prefix rules | Established project law (T-45-11, T-46-04, ASVS V12); one guard shape, not two |
| JSON schema validation on open | Ad-hoc field checks | Extend `parseEfxPaintDocument` (`efxPaintDocumentParsers.ts`) | Fail-closed parser is the boundary contract (T-45-13) |
| macOS document type | Custom LaunchServices calls at runtime | `Info.plist` declaration in the bundle | LaunchServices reads the bundle's plist; runtime registration is not how macOS resolves document types |
| App-data directory resolution | String-concatenating `$HOME/Library/...` | `app.path().app_data_dir()` (Rust) / `appDataDir()` (JS) | Tauri owns the platform mapping; the existing `efxasset_allowed_roots` already uses `app_data_dir()` |
| Bounded queue / interruption semantics | Hand-rolled promise queue with abort flags | Effect `Queue.bounded` + `Fiber.interrupt` (pilot only, per D-16) | The pilot's stated success criterion is that these semantics become *testable* — re-implementing them defeats the purpose |
| Hold-to-repeat button timing | A bespoke timer loop per input | One shared stepper component with a single delay/interval constant | D-23 requires one shared treatment everywhere |

## Common Pitfalls

### Pitfall 1: The chunk budget is 14.89 kB, and Effect alone is ~164 kB
**What goes wrong:** importing `effect` (or `xstate`) from any module reachable from the main chunk blows the frozen 1320 kB budget and fails `viteBuild.test.ts`.
**Why it happens:** the frozen budget, verbatim:
```ts
it(
  'resolved chunkSizeWarningLimit is exactly the documented 1320 desktop budget',
  { timeout: 180_000 },
  () => {
    expect(captured.chunkLimit, 'chunkSizeWarningLimit must resolve to the documented 1320 desktop budget').toBe(1320);
  },
);
```
and the measurement trail in the same file:
```
//   = current main chunk                      1305.11 kB
// Budget raised 1300 → 1320 (measured value + ~14.9 kB headroom).
```
`PhysicsPaintStudio` **is** a lazy chunk (`src/main.tsx` dynamic import) and `viteBuild.test.ts` already pins that separation:
```
it(
  'PhysicsPaintStudio lazy chunk remains a separate bundle',
```
— but `physicPaintFlush.ts` is imported by the main chunk: confirmed at `src/stores/projectStore.ts:31` (`import {requestPhysicPaintFlush} from '../lib/physicPaintFlush';`) and `src/lib/exportEngine.ts:3` (`import { requestPhysicPaintFlush } from './physicPaintFlush';`).
**How to avoid:** keep `physicPaintFlush.ts` a thin main-chunk façade (plain function signatures, no library imports) and put the machine/queue implementation in a module imported **only** from inside the Studio lazy chunk (e.g. `components/physic-paint/**`). Re-measure with the real Vite build; if the pilot genuinely needs main-chunk presence, raise the budget as an explicit signed decision (D-19, `6325e2e8` pattern).
**Warning signs:** `viteBuild.test.ts` chunk-size warning assertion fails; `PhysicsPaintStudio-[hash].js` disappears from the emitted bundle list.

### Pitfall 2: `bundle.fileAssociations` cannot produce a document package
**What goes wrong:** the plan declares `fileAssociations` in `tauri.conf.json`, ships, and `.mce` folders are still plain folders in Finder (no single icon, no double-click).
**Why it happens:** verified against the downloaded tauri-utils source this session — the generated plist contains `UTExportedTypeDeclarations` (`UTTypeIdentifier`, `UTTypeDescription`, `UTTypeConformsTo`, `UTTypeTagSpecification` with `public.filename-extension` / `public.mime-type`) and `CFBundleDocumentTypes` (`CFBundleTypeExtensions`, `LSItemContentTypes`, `CFBundleTypeName`, `CFBundleTypeRole`, `LSHandlerRank`). It **does not emit `LSTypeIsPackage`**, and it **does not emit `CFBundleTypeIconFile`**.
**How to avoid:** declare the complete `CFBundleDocumentTypes` array by hand in a merge plist (`app/src-tauri/Info.plist` — confirmed **absent today**), including `LSTypeIsPackage: true` and (for a distinct document icon) `CFBundleTypeIconFile`. Keep `fileAssociations` out of `tauri.conf.json` entirely, or accept that its array will be replaced.
**Warning signs:** Finder shows the folder icon; double-click opens Finder instead of the app.

### Pitfall 3: the Info.plist merge is a SHALLOW top-level overwrite
**What goes wrong:** the plan puts *half* the document-type declaration in `fileAssociations` and half in the merge plist; the merged plist silently wins on the whole `CFBundleDocumentTypes` key and the other half vanishes.
**Why it happens:** verbatim from the downloaded tauri-bundler macOS source:
```rust
if let Some(user_plist) = &settings.macos().info_plist {
    let user_plist = match user_plist {
      PlistKind::Path(path) => plist::Value::from_file(path)?,
      PlistKind::Plist(value) => value.clone(),
    };
    if let Some(dict) = user_plist.into_dictionary() {
      for (key, value) in dict { plist.insert(key, value); }
    }
}
```
Top-level keys are inserted wholesale — no deep merge.
**How to avoid:** one owner per top-level plist key. If `CFBundleDocumentTypes` is hand-written, it must be complete (both document types if two exist) and `fileAssociations` must be empty.
**Warning signs:** a document type works in one build and disappears in the next after unrelated plist edits.

### Pitfall 4: no Preact binding for XState v6
**What goes wrong:** the plan assumes `@xstate/preact` or `@xstate/react`-style hooks for wiring the machine into components.
**Why it happens:** the official bindings are React, Vue, Svelte, Solid only. `@xstate/react` publishes `7.0.0-alpha.2` for v6 — and it is React.
**How to avoid:** use the framework-agnostic core: `createActor(machine)` → `actor.subscribe()` (change-only snapshot stream) / `actor.select(selector)` returning `Readable<T>` → bridge into `@preact/signals` manually (one signal write per emission, outside render). This is exactly the D-17 "signals bridge pattern" the conventions doc must specify per flow. The core is documented as framework-agnostic — "an actor is a plain object you can subscribe to".
**Warning signs:** a dependency on `useActor`/`useSelector` appears in a plan task.

### Pitfall 5: v6 removed the entire v5 action-creator surface
**What goes wrong:** implementation copies v5 examples from Context7 `/statelyai/docs` (which covers **v5 only**) and nothing compiles.
**Why it happens:** v6 unexports every action creator: `assign`, `raise`, `sendTo`, `emit`, `log`, `cancel`, `enqueueActions`, `spawnChild`, `stopChild`; `interpret` → `createActor`; `fromPromise` → `createAsyncLogic({ run })`; `fromCallback` → `createCallbackLogic`, `fromObservable` → `createObservableLogic`, `fromTransition` → `createLogic`; guards `and/or/not/stateIn` are plain JS; context is per-state (`setup().states`); `setup().types` → `schemas`; `@xstate/immer` and `@xstate/inspect` are removed. Verification probe this session: `createActor`/`createMachine` work; `actor.select(s => s.value).subscribe(...)` emitted `["active","draining","idle"]` (change-only); `actor.trigger.INC()` exists.
**How to avoid:** source the v6 API from the repo (README/CHANGELOG/examples) and Stately announcements only. Context7 `/statelyai/docs` and `/juststeve/xstate-skill` are **actor-model concepts only** (D-15).
**Warning signs:** `import { assign } from 'xstate'` appears anywhere.

### Pitfall 6: `LSTypeIsPackage` alone is often not enough; LaunchServices caches
**What goes wrong:** the plist is correct, the build is installed, and Finder still shows a folder.
**Why it happens:** the type must also be exported as a UTI conforming to `com.apple.package` in `UTExportedTypeDeclarations`, and LaunchServices may hold a stale registration for the same bundle identifier (`com.efxlab.motion-editor` has shipped before at this identifier).
**How to avoid:** declare `UTExportedTypeDeclarations` with `UTTypeConformsTo: ["com.apple.package"]` **and** `CFBundleDocumentTypes` → `LSItemContentTypes` referencing that identifier, with `LSTypeIsPackage: true`; bump `CFBundleVersion` (Tauri derives it from `tauri.conf.json` `version` — currently `0.9.0`) to force re-registration. Verification requires a rebuilt bundle (`target/{debug,release}/bundle/macos/EFX Motion Editor.app`); `lsregister -f <app>` can force the refresh during iteration.
**Warning signs:** icon changes after a version bump but not after a plist-only edit.

### Pitfall 7: `tauri dev` cannot verify any D-03 behaviour
**What goes wrong:** the native UAT runs against `tauri dev` and reports "icon clicks" as failing/passing without evidence.
**Why it happens:** `tauri dev` runs the compiled binary directly; the `.app` bundle (and therefore `Info.plist`) only exists in a bundled build. The project already has this knowledge in packaged-vs-dev CSP divergence. [ASSUMED — verify at plan time]
**How to avoid:** make the D-03 UAT step explicitly a **bundled-build** step (`tauri build --debug` at minimum), mirroring the existing practice of judging bundle freshness from `bundle/macos/*.app`.
**Warning signs:** UAT notes contain "in dev it works".

### Pitfall 8: rfd dialog — packages vs directories
**What goes wrong:** the open dialog shows `Name.mce` greyed out or navigates into it.
**Why it happens (verified against the rfd macOS panel source this session):** `build_pick_file` sets `setCanChooseDirectories(false)` + `setCanChooseFiles(true)` and applies extension filters via the **deprecated** `setAllowedFileTypes`; it **never sets `treatsFilePackagesAsDirectories`** (default false → packages are treated as single files and ARE selectable). The deprecated filter API respects package semantics; the modern `allowedContentTypes` API is reported to ignore `treatsFilePackagesAsDirectories`. rfd uses the safe one — a file dialog filtered to `mce` should show `MyProject.mce` as one selectable file, provided LaunchServices knows it is a package.
**How to avoid:** keep the current `filters: [{name, extensions:['mce']}]` shape on macOS. On Windows/Linux the same path is a plain folder → the flow must branch to `openDialog({directory: true})` there (platform-conditional; D-03 already states Windows/Linux keep a plain folder).
**Warning signs:** a directory-open dialog is used on macOS for `.mce` (users then open the folder's *parent*, or the package's contents).

### Pitfall 9: double-click delivery is not automatic in Tauri
**What goes wrong:** the document type is registered, double-click opens the app, and the project never loads.
**Why it happens:** Tauri's default `.run(generate_context!())` does not surface macOS document-open events. Delivery requires `.build(...)` + `app.run(|app, event| ...)` matching `RunEvent::Opened { urls }`; on cold start the event can fire before the webview is ready (needs the buffered-URLs + `invoke('opened_urls')` handshake pattern plus a live `listen('opened')` for the warm case).
**How to avoid:** plan the cold-start and warm-start paths as two explicit tasks with a shared handler. No single-instance plugin is installed today; on macOS, LaunchServices delivers `odoc` to a running instance, so the plugin is not required for this feature — but flag it as an assumption to verify on the bundled UAT. [ASSUMED]
**Warning signs:** a task says only "handle RunEvent::Opened".

### Pitfall 10: the refusal gate must run BEFORE any sidecar read or store mutation
**What goes wrong:** a pre-52.2 project is opened, the EFX Paint map is read, mutation begins, then the refusal fires — partial mutation, which DOC-03 forbids.
**Why it happens:** the existing order in `projectStore.openProject` is `ipcProjectOpen` → gate → early return with zero mutation. The new gate keys on `formatVersion` in the manifest instead of the legacy `physic_paint_outputs` carrier scan, and must keep the same position and the same no-recourse dialog pattern.
**How to avoid:** the gate reads the manifest it already has in hand; no additional IO, no parser invocation, no store write before the verdict.
**Warning signs:** the new gate is implemented inside `loadEfxPaintDocuments` or the parser.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Path traversal in a media reference inside a hostile package (`"../../../etc/..."`) | Tampering | Reject at parse (segment check) **and** at read (canonicalize + prefix-check against the package root) — defense in depth, matching T-45-11/T-46-04 |
| Symlink escape from the package root to an arbitrary file | Tampering / Information disclosure | Canonicalize before the prefix check (existing `resolve_efxasset_path` order: canonicalize → regular file → extension → root membership) |
| Malicious package with a digest that does not match the bytes (silent corruption) | Tampering / Repudiation | D-13: refuse — no silent fallback, no auto-repair |
| Oversized media file causing memory pressure (a hostile `frames/*.webp` of 2 GB) | DoS | Validate dimensions before decode where available; the 512 MB LRU budget already bounds decoded memory, but the *read* must be size-checked before loading into JS |
| UTI collision — another app claiming `.mce` | Spoofing | Declare `UTExportedTypeDeclarations` with a reverse-DNS identifier tied to `com.efxlab.motion-editor` |
| Widening the webview fs scope unintentionally | Elevation of privilege | Prefer the prefix-locked Rust command; if plugin-fs is chosen, the scope narrowing must be an explicit reviewed decision |
| Writing outside the package (a ref path escaping the staging root) | Tampering | Same prefix-lock law applied on the write side, not only on read |

## Open Questions (RESOLVED)

1. **Does the atomic transaction re-point at `frames/` (authoritative) or stay on the manifest?**
   - What we know: today the transaction binds exactly one project file (`project_file_path: Option<String>`, `expected_project_digest: Option<String>`) and the shipped cache path uses it to publish derived frames.
   - What's unclear: with `cache/` leaving the package (D-05), the derived frames it used to guard no longer live in the package — while `frames/*.webp` (authoritative, irreplaceable) now do. Guarding the disposables and not the originals inverts the risk.
   - Recommendation: retarget the transaction at the authoritative set (manifest + layer sub-files + changed media) and write the machine-local cache best-effort (a lost cache entry is re-derivable per D-14). Record the marker change from one digest to an aggregate/path-sorted digest set (Pattern 1).
   - RESOLVED: the transaction binds the authoritative set — `BoundFile { path, sha256, had_original }` with a path-sorted aggregate digest — and the cache generation becomes a separate disposable leg with no project binding (plan 05); the save funnel stages every authoritative file and drives bind → publish → settle (plan 07).

2. **Which read seam wins for `frames/*.webp`?**
   - What we know: `efxasset://` cannot serve webp; plugin-fs `readFile` works but "permissions alone do not grant a scope" and would require a `**/frames/**` scope entry plus the package root; a Rust command mirrors the existing guard pattern with no scope widening.
   - What's unclear: the IPC cost difference for the lazy-read path (a combined read+decode command would halve round trips but must not disturb the two-format law that keeps PNG in JS).
   - Recommendation: new Rust read command, prefix-locked to the package root, `frames/` + `layers/` + `images/` only. Optional second command `read_and_decode_frame` only if telemetry shows the read hop is hot; keep the PNG branch in JS.
   - RESOLVED: a Rust read command prefix-locked to the package root (`resolve_package_media_path` for `frames/`, `resolve_package_bound_path` for the transaction's set) with its TS ipc wrapper (plan 01), consumed by the lazy decode leg built on the existing bytes/ImageBitmap + LRU path (plan 09). No scope widening.

3. **Windows/Linux dialog branch.**
   - What we know: D-03 states Windows/Linux keep a plain folder; macOS gets the package.
   - What's unclear: whether v1.0.0 ships Windows/Linux at all, and if so which platform detection to use for the dialog branch.
   - Recommendation: gate the dialog shape on `platform()` from the Tauri API, and treat the Windows/Linux path as the pre-existing behaviour (directory open) unless the plan deliberately extends it.
   - RESOLVED: the macOS package treatment (Info.plist document type, double-click open, package-shaped dialogs) is planned in plan 11, which keeps the Windows/Linux path on the ordinary-folder branch and gates the dialog shape on the Tauri `platform()` API.

4. **`projectId` minting and existing projects.**
   - What we know: D-05 requires the package to contain no machine-local paths; a project identity is the natural key.
   - What's unclear: whether `projectId` also becomes the cache key for the inline (non-physic-paint) subsystems.
   - Recommendation: scope `projectId` to the EFX Physic Paint frame cache only in this phase; do not refactor unrelated cache keys.
   - RESOLVED: `projectId` is minted in the TS package contract and carried on the persisted shape (plan 02), and is used only as the EFX Physic Paint frame-cache key (`<app_data_dir>/frame-cache/<projectId>/`, plan 05). No unrelated cache key is refactored.
