<objective>
Retarget the Studio↔main bridge to references (D-12, spec §7): sync passes layer documents as references + metadata, bytes cross only for frames the receiver does not already have (digest-keyed), killing the measured ~4.5 s `docSync` term.

Purpose: the bridge is the second half of the same problem the file format solves — the document currently travels as base64 between two windows on every sync. With layer sub-files now reference-shaped, the bridge can carry exactly what the file carries.

Output: reference-shaped transfer entries, a digest-keyed byte channel, and a receiver that asks only for what it is missing.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Studio window → main window | Two webview contexts exchange document payloads |
| Bridge payload → applied runtime state | A payload from the other window is untrusted input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-52.2-33 | Tampering | a bridge entry applying corrupted pixels | high | mitigate | Every arriving byte entry is verified against the digest that identified it before being installed; a mismatch is refused and recorded, never applied (same law as the disk read path). |
| T-52.2-34 | Spoofing | a digest claimed for content it does not describe | high | mitigate | The digest is the identity AND the verification: the receiver recomputes it from the received bytes, so a mislabelled entry cannot displace correct content. |
| T-52.2-35 | Denial of Service | repeated full-document retries | medium | mitigate | Retries are per digest entry; content the receiver already holds is never re-requested, so a retry storm cannot re-send the whole document. |
| T-52.2-36 | Information Disclosure | reference payloads leaking machine-local paths | low | mitigate | References are exactly the package-relative ones produced by the plan-02 builders, validated by the same guard on both ends. |
</threat_model>
