# Phase 43.6: Multi-Rail Selection and Batch Operations - Context

**Gathered:** 2026-08-18
**Status:** Ready for planning

<domain>
## Phase Boundary

Deliver a **multi-rail selection scope** for the Physics Paint Studio bottom workflow strip: the user can select multiple Rails of any type — Key Rail, Motion Rail, Static Rail — in one shared session-only selection set ordered by canonical first-key frame, then apply four batch operations to the whole set:

1. **Delete Rails** — remove every selected rail as one atomic command, each rail with its own type semantics (Key Rail removes its real keys; Motion/Static Rail follows 43.2 Delete Group semantics and never deletes the referenced Action).
2. **Move Rails** — rigid one-delta translation of the whole set, dragging from any selected rail, clamping/rejecting as one unit.
3. **Key Spacing** — existing Force Spacing semantics applied per selected rail, each rail keeping its own first key as anchor, validated all-or-nothing before commit.
4. **Solo playback** — session-only playback filter hiding unselected rails' content and restricting the loop range to the selected rails' effective coverage.

Multi-selection is a new explicit selection scope alongside the existing single-rail and physical-frame selections; the 43.4 mutual-exclusion and selection-authority rules extend to the set. All invariants from Phases 43.3/43.4/43.5 remain binding: persistent intentional gaps, break ownership by stable key identity, capacity as the single end authority, atomic Undo/Redo through the canonical physical history, replay snapshots read from the accepted document authority, and one shared rail behavior (focus capsule, click-to-focus, roving Tab/arrows, Delete/Backspace, Cmd+Z/Cmd+Shift+Z) with no per-type forks.

The accepted canonical physical document, exact parent acknowledgement, stable-key-owned break authority, Motion/Static Group lifecycle (`visibleRanges`, `phaseOrigin`, `frameOverrides`, synchronization), Key Rail derivation, 43.5 Push semantics (Push derives from its drag anchor only — never from the selection set), Key Spacing/Interpolation state authority, preview/export parity, and Paint brush history remain authoritative and unchanged. The Motion Editor timeline is unchanged.

Requirements are not yet assigned IDs in `.planning/REQUIREMENTS.md`; downstream research/planning must derive Phase 43.6 IDs and traceability from the activated product prompt without reopening completed Phase 43/43.1–43.5 requirements.

**43.2 carryover caution (restated):** frozen `69d07703` still has open native red loops for project-local save staging, Paint into a deleted Group gap, and original-extent Regenerate. Multi-rail work must build on the accepted Group lifecycle authority without reopening those repair paths, and its own native UAT runs from a fully restarted frozen-code session (43.2 D-39).

<decisions>
## Implementation Decisions

### Multi-select gestures and set lifecycle

- **D-01:** Spec default gestures accepted. **Shift+click** selects the canonical range from the anchor rail to the clicked rail — the range is ordered by canonical first-key frame across all three rail types in one shared ordering. **Cmd/Ctrl+click** toggles one rail in/out of the set.
- **D-02:** The range anchor is the **last plain-clicked rail** (Finder/VS Code behavior). Shift+click replaces the set with the anchor→clicked range; the anchor stays put. Cmd/Ctrl+click toggle does not move the anchor.
- **D-03 (user-locked):** **Cmd+Shift+click ADDS** the anchor→clicked range to the current set (union — Finder behavior). Already-selected rails in the range stay selected; no toggling. The anchor does not move.
- **D-04:** Set collapse/clear: plain click on any rail collapses the multi-set to that single rail (existing single-rail selection takes over); plain click on empty strip/frame clears the set entirely; Escape collapses layers one at a time (43.5: one Escape handles at most one layer — solo exit, then selection collapse); selecting a physical frame or key clears the rail set (43.4 mutual exclusion).
- **D-05:** The multi-rail set **may be empty**. Cmd+click toggling off the last selected rail leaves an empty set (no rail selection scope active). This intentionally diverges from Phase 37's never-empty key multi-selection — rails have no always-current editing obligation. — **Reversibility:** costly — the empty-set contract shapes reducer semantics, copy, focus behavior, and UAT; switching to never-empty later would fork every set-consuming surface.
- **D-06 (user-locked):** Selection across batch operations: after a batch Move commits, the whole set stays selected at the new positions and the anchor follows its rail's identity (43.3/43.4 stay-selected precedent extended to the set); Undo restores the set selection at the original positions; Redo re-applies at the destination. After Delete Rails commits, the selection is empty and the cursor stays on its current valid frame (43.4 delete precedent); one Undo restores the exact pre-delete selection set; Redo clears it again. The anchor follows rail identity across Undo/Redo.

### Move Rails

- **D-07:** Spec default accepted: the whole set translates **rigidly by one delta** — relative offsets, internal gaps, and internal breaks preserved exactly. The set **clamps or rejects as one unit** at the first collision with any unselected key, Group occupancy, frame 0, or capacity. Unselected objects never move; movement-created gaps persist.
- **D-08:** Batch Move initiates by **dragging any selected rail** — the grabbed rail is not special; the set is the unit. Dragging an unselected rail collapses the set to that rail first (normal single-rail selection), then runs its own 43.3/43.4 drag.
- **D-09:** Drag preview: **per-rail translucent mode-colored ghosts** (purple/cyan/gray per rail type) at the proposed destination; originals stay visible until exact parent acceptance; **one live status-line set readout** (delta + resulting set range + opened gap if any); red blocked-edge treatment on the colliding rail's ghost. Extends 43.3/43.4 ghost language to the set with zero new visual concepts.
- **D-10:** Shared-source Groups inside the set follow 43.3 algebra: source-attached rails move source keys with identity; duplicated placements move placement-only. Straddle reject: an unselected Group sharing a source with a selected source-attached rail rejects the move with a mapped reason (43.5 D-16 generalized); the family is never silently pulled in. — **Reversibility:** one-way — rejection semantics join the product-reason mapper, resolver guard vocabulary, and UAT; silent set-expansion later would contradict explicit-scope semantics users will have learned.
- **D-11 (user-locked):** Break/gap normalization: internal breaks and internal gaps travel rigidly with the set (43.4 D-19 identity travel). Movement-created gaps at the set edges follow 43.3 D-12 authority — a break lands on the first surviving successor only when a gap actually opens. Landing adjacent to a fixed-side neighbor never merges; breaks travel with the moved keys.
- **D-12 (user-locked copy):** Accepted Move status: `Moved {N} Rails by {D} frames — set now frames {A}–{B}. Gap left at frames {G1}–{G2}.` — the gap sentence appears only when a gap actually opened; one deterministic mapper; correct singular/plural.
- **D-13 (user-locked):** Zero-delta drop: no commit, no status, no history entry, the set stays selected (43.5 push-drop-noop precedent — internal sentinels never surface). Escape during the drag cancels: originals byte-untouched, no history entry, the set stays selected (43.3/43.4 cancel precedent).

### Solo playback

- **D-14 (user-locked):** Solo means **hide others + restrict range**: during solo playback only the selected rails' content renders; the play range restricts to the selection's frame coverage and loops within it by default. Guards: session-only playback state — never persisted, never affects preview/export output or the canonical render; changing or clearing the rail selection ends solo immediately; audio preview keeps following the playhead unchanged (Main Editor authority), simply over the restricted range; a visible active indicator marks solo mode (same active-state orange language as armed tools); Escape or re-click exits.
- **D-15 (user-locked):** The Solo button lives in the **bottom workflow strip** and enables whenever **any rail selection** is active — a single selected Rail is a set of one (soloing one rail is a legitimate "watch just this Group" case). Disabled only when no rail selection exists (guarded tooltip: `Select a Rail to solo.`). Solo state never persists across save/reopen. Exact button placement in the action row goes to UI-SPEC.
- **D-16:** Solo interacts with transport as an **arm**: toggling solo only arms the filter/range — the user presses Play (or it keeps playing if already playing). Solo persists across stop/start while the selection is unchanged.
- **D-17:** Implementation mechanism: solo is a **pure presentation filter on cached playback frames only** — the canonical render source, preview stills, export, and the accepted document are never touched. Unselected rails keep all their state; they just don't paint during solo playback. Session-only signal, never crosses the bridge. — **Reversibility:** one-way — the spec forbids any document/history touch for solo; a document hide/restore mechanism would break the locked 'never affects preview/export authority' contract.
- **D-18 (user-locked):** Scrubbing while solo-armed but stopped is **unrestricted timeline navigation**: the filter applies ONLY to playing frames. The stopped canvas always renders everything, at any cursor position, inside or outside the solo range.
- **D-19 (user-locked):** The solo range derives from the selected rails' **effective boundaries** — first selected placement start to last selected effective end — so generated/linked occurrences of selected Groups are included in the range, and only unselected content is hidden during playback.
- **D-20 (user-locked copy):** While solo is armed, the status capsule carries `Solo — {N} Rails, frames {A}–{B}.` (one mapper, correct singular/plural); the Solo button shows the active orange state. Both clear on exit (toggle, Escape, or selection change).

### Batch affordance placement, Delete, Key Spacing

- **D-21:** Affordances split across existing homes with dynamic scope — one home per operation, no duplicated controls: **Delete** keeps living on the existing Delete control with a dynamic scope label (`Delete Frame` / `Delete Key Rail — …` / `Delete {N} Rails`); **Solo** gets its own strip toggle (D-15); **Key Spacing** stays in the 43.5 ToolCase popover, applying to the active set when one exists.
- **D-22 (user-locked):** Delete/Backspace keyboard shortcuts route through the **same dynamic scope** as the visible Delete control: an active multi-rail set means both keys commit `Delete {N} Rails` as one atomic command. No separate shortcut path.
- **D-23:** Mixed-set Delete is **fully direct — no confirmation modal** at any set size or composition. The multi-selection itself is the explicit scope. Each rail deletes with its own type semantics: Key Rail deletion removes its real keys and derived projection; Motion/Static Rail deletion follows the 43.2 Delete Group semantics and **never deletes the referenced Action**. One atomic history command; one Undo restores every rail, key, break, and the exact pre-delete selection set; Redo re-applies. Vacated intervals remain intentional persistent gaps; break normalization follows the 43.4 rules per deleted rail; never touches unselected rails, keys, Actions, or shared sources still referenced by another Group. — **Reversibility:** one-way — the direct no-modal contract is a learned product behavior (43.4 D-13 precedent); introducing a modal later would fork the deletion UX.
- **D-24:** Key Spacing on a set: the spacing factor applies **per selected rail, each rail keeping its own first key as anchor**. No cross-set spacing mode this phase. One atomic command for the whole set. — **Reversibility:** reversible — a cross-set mode could be added later as a new capability without invalidating per-rail semantics.
- **D-25 (user-locked):** Key Spacing validates the **whole set before commit**: every selected rail's membership, anchors, capacity, and collisions are checked up front; if any rail fails, the entire command rejects with a mapped reason — no partial application. All-or-nothing.
- **D-26 (user-locked):** The ToolCase popover is **scope-aware**: with an active rail set, the Key Spacing section applies to the set (and its copy reflects the scope); without a set, behavior is exactly the 43.5 single-selection behavior. The popover never creates or modifies the selection set itself.
- **D-27:** Set copy (spec formula + type breakdown): `N Rails selected — frames {A}–{B}.` with correct singular/plural and a type breakdown when mixed (e.g. `3 Rails selected — frames 12–88 (1 Motion, 2 Key).`). Homogeneous sets name the type directly (`2 Key Rails selected — …`). **One deterministic mapper** owns all set copy: capsule, tooltips, accessibility names, Delete scope label, and solo status.

### Process boundaries (carried, restated for downstream agents)

- Multi-selection is **session state only** — no new persisted record collection, nothing saved into the document (spec boundary).
- The 43.5 Push tools never consume the multi-rail set — Push derives strictly from its drag anchor (43.5 D-20, binding).
- No keyboard shortcuts for the new Solo button this phase (43.4 D-05 / 43.5 D-10 precedent); Delete/Backspace and Cmd+Z/Cmd+Shift+Z parity on the set comes through the existing shared rail modules (spec).
- This phase produces a **UI-SPEC** via `/gsd-ui-phase 43.6` after context (43.4 D-22 precedent; the prompt explicitly requests UI-SPEC for the multi-set visual language, Solo button placement, and set copy).
- Native visual UAT is the final oracle from a fully restarted frozen-code parent/child session (43.2 D-39), covering the prompt's 7-step acceptance list.
- Scope boundaries (spec-locked): no change to single-rail behavior, 43.5 Push semantics, or ToolCase layout beyond scope-awareness; no multiple internal Paint tracks; no Motion Editor timeline changes; no Action editing; no release work; solo never becomes an export or render mode.

### Claude's Discretion

- Exact multi-set visual distinction from single selection within the locked palette (orange selection language extended to every rail in the set; no new colors) — UI-SPEC decision.
- Exact Solo button placement and icon in the strip action row — UI-SPEC decision.
- Exact per-rail ghost translucency and blocked-edge rendering on sets, provided no confusion with selection orange, unresolved red, gap gray, or white endpoint cuts.
- Exact intent names and payload shapes for the batch resolver intents (delete-rails, move-rails, spacing-on-set), provided they join the closed union with strict parsing, canonical revision participation, and fail-closed validation (43.3 D-14 precedent).
- Exact reducer/derivation representation for the rail-level selection set (ordered identity list + anchor), provided it stays pure, session-only, and never becomes a second membership authority.
- Exact test decomposition. Native visual UAT remains required for gestures, batch operations, solo, Undo/Redo, Interpolation Off/On, and save/reopen.
