## Warnings

### WR-02: Residual G-43.6-2-class silent undo no-op for `delete-group` / `delete-action-groups` when the pre-op selection is inside the cleanup set

**File:** `app/src/lib/physicPaintBridge.ts:1636-1657` (guard); mechanism: `app/src/components/physic-paint/roto/physicsPaintRotoGroupLifecycle.ts:510-539` (`buildLifecycleProposal`)

**Issue:**
The new guard excludes only `'delete-rails'` from payload-derived before-snapshot selection. Every other cleanup-capable lifecycle kind keeps payload authority, and the new comment codifies this as "their proposal preserves the pre-op selection **in the common case**". The uncommon case is real: `buildLifecycleProposal` (520-522) sets `selectedKeyId = null` whenever the pre-op selected key is in `cleanupKeyIds`. For `delete-group` and `delete-action-groups`, cleanup includes group **sourceKeyIds** — real, selectable keys (unlike `delete-group-frame`/`regenerate-group`, whose cleanup is override-only).

Concretely reachable: Play Script accepts and selects the affected range start (a group source key) — the parent document and the child's `lastAcceptedSelectionRef` both hold that key. The user then deletes the group from the Group Rail (a child-local click that nulls only the child store's selection; the parent retains the last-accepted key). The forward payload ships the proposal's nulled selection; the parent ledger records `before.selectedKeyId = null` while the child history records `before.selectedKeyId = <deleted key>`. Undo resubmits the child's pre-op selection, `sameAcceptedPhysicalCommandSnapshot` (physicPaintBridge.ts:1590-1603) rejects, and undo silently no-ops — the exact G-43.6-2 mechanism, one kind over.

**Fix:** Prefer document authority for the before-snapshot selection of every lifecycle kind whose proposal can rewrite the selection, not just `delete-rails`:

```ts
const beforeSelectionFromPayload = payload.operationKind === 'move-group'
  || payload.operationKind === 'paint-group-frame'; // selection-preserving kinds only
```

or keep the kind list but add a mismatch tripwire so the silent case is at least observable:

```ts
if (beforeSelectionFromPayload
  && (payload.selectedKeyId !== (currentDocument?.selectedKeyId ?? null))) {
  // log diagnostic: lifecycle proposal rewrote the pre-op selection — before snapshot authority diverges
}
```

Add a bridge round-trip test mirroring the 43.6-12 one: seed `selectedKeyId` = a source key of group G, apply `delete-group` for G, undo, assert the restored document equals the seeded one.

### WR-03: Recovery-lease self-heal cannot see leases orphaned by Studio unmount — the G-43.6-2 dead-end survives a window close

**File:** `app/src/components/physic-paint/hooks/useRotoPhysicalEditCoordinator.ts:1260-1265` (self-heal), `1936-1946` (unmount effect)

**Issue:**
The self-heal releases only the token in the CURRENT hook instance's `recoveryLeaseSignal`. The unmount effect transfers a settled lease to recovery but never releases an already-held `recoveryLeaseSignal` token — so if the Studio window closes while a recovery lease is held (the plausible user reaction to the "Apply failed" state that created it), the store's `_rotoPhysicalOperationLeases` scope keeps the orphaned recovery token. On remount, the fresh coordinator's `recoveryLeaseSignal` starts null, the self-heal no-ops, the serialize guard passes, and `lease.acquire` (1450) returns null forever — every edit reports "A Roto physical edit is already in flight." until a full project reset (physicPaintStore.ts:1339-1341). That is the same session-permanent block G-43.6-2 set out to eliminate, one unmount later.

**Fix:** Release the recovery token in the unmount effect alongside the settled-lease transfer:

```ts
useEffect(() => () => {
  // ...existing pending/settled handling...
  const recovery = recoveryLeaseSignal.peek();
  if (recovery) {
    portsRef.current.lease.release(recovery);
    recoveryLeaseSignal.value = null;
  }
}, [clearPendingOnce, restoreSnapshot]);
```

Alternatively, make the self-heal probe the store scope (e.g., an `isRotoPhysicalOperationAvailable`-based recovery acquire/release) so a fresh instance can reclaim an orphaned lease.

### IN-06: `delete-rails` before-snapshot cursor fallback silently reintroduces payload authority when `currentDocument` is null

**File:** `app/src/lib/physicPaintBridge.ts:1655-1657`

**Issue:** For `delete-rails` the guard reads `selectedKeyId: currentDocument?.selectedKeyId ?? null` but `cursorAppFrame: currentDocument?.cursorAppFrame ?? payload.cursorAppFrame` — if `currentDocument` were ever null, the before snapshot would mix a null selection with the POST-delete payload cursor, exactly the authority mixing the guard exists to exclude. Practically unreachable (record/revision validation precedes the block), and the fallback shape predates this diff for ordinary kinds, but a fail-closed reject (or `?? 0`-style neutral value plus diagnostic) would keep the invariant total.

**Fix:** When `beforeSelectionFromPayload` is false and `currentDocument` is null, reject the apply rather than falling back to `payload.cursorAppFrame`.

The `beforeSelectionFromPayload` guard (physicPaintBridge.ts:1659) still excludes only `delete-rails`; `delete-group`/`delete-action-groups` keep payload authority. A correct fix requires the child to communicate its true pre-op selection (e.g., a new payload field), which is an architectural change with regression risk — deferred. The delete-rails fix (G-43.6-2) has the same limitation in the divergent case.
