# Phase 43.3: Code Review Report

**Reviewed:** 2026-08-13T19:41:01Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

Reviewed the Phase 43.3 Group Rail drag implementation at standard depth: the pure clamp authority (`clampPhysicPaintGroupDragDestination`), the move-group resolution arms (source-attached rigid translation and D-11 duplicated placement), the break derivation (`deriveMoveGroupIncomingInterpolationBreakKeyIds`), the prepare/commit publication pair, the acknowledged physical-edit coordinator integration, the rail drag session state machine, the ghost/blocked-edge rendering, the gap preview, and the status copy.

The architecture is coherent: the clamp is the single pure authority shared by the preview and the resolver (D-05 holds in the normal path — the strip's `getRotoGroupDragClampInput` and the resolver both derive from `derivePhysicPaintRotoLoopRanges` with the same inputs), the commit path is protected by the coordinator's acknowledged transaction with revision revalidation at commit time, and the post-drop click suppression (Pitfall 2) is correctly wired through `consumeClickSuppression`. The D-13 constant-width ghost fix and the D-06/D-07 status copy are consistent with the documented contracts.

No BLOCKER findings. Five WARNINGs and four INFOs. The most notable issues: the Escape cancel path ignores an armed-but-not-started session (WR-01), the break-aware `proposalVersion` is computed and stored but never consumed (WR-02), the vacated interval is derived by a second `derivePhysicPaintRotoLoopRanges` call duplicating the resolver's work (WR-03), the pointer-cancel handler is missing the session-identity guard the other handlers have (WR-04), and the pre-existing Infinity-repeat derivation debt is referenced by this phase's own UAT (WR-05).

## Warnings

### WR-01: Escape does not cancel an armed-but-not-started drag session

**File:** `app/src/components/physic-paint/hooks/usePhysicsPaintGroupRailDrag.ts:356`
**Issue:** `handleEscape` returns early when `!session.started`. The session is armed on pointer-down and only becomes `started` after more than 4px of horizontal travel. If the user presses Escape while holding the button before crossing the threshold, the session stays armed. If they then move past the threshold and release, the drag commits — the user explicitly pressed Escape to cancel, yet the move still lands. Every other cancel path (`handlePointerUp` for a not-started session, `handlePointerCancel`, `handleLostPointerCapture`) tears the session down regardless of `started`; only Escape is gated on it.
**Fix:** Remove the `!session.started` condition so Escape cancels the armed session unconditionally (the `sessionRef.current !== session` guard already prevents stale-session cancellation):
```ts
const handleEscape = (keyEvent: KeyboardEvent) => {
  if (keyEvent.key !== 'Escape' || sessionRef.current !== session) return;
  keyEvent.preventDefault();
  keyEvent.stopImmediatePropagation();
  cleanup();
  clearSuppressionSoon();
  restoreSourceFocus();
};
```

### WR-02: `proposalVersion` in the publication is dead data

**File:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:1423,1429`
**Issue:** `prepareRotoGroupDrag` computes the break-aware fingerprint via `buildGroupDragProposalVersion` (GDRAG-07 / Pitfall 1) and stores it in the publication, but nothing ever consumes it. The coordinator recomputes `expectedRevision` from current state at commit time (`useRotoPhysicalEditCoordinator.ts:1397`), and the strip, rail, and drag hook never read `publication.proposalVersion`. The only consumer is the test asserting the fingerprint. The field is dead data that also misleads readers into believing the commit path validates it — the commit path does not.
**Fix:** Either consume it in `commitRotoGroupDrag` (compare against a freshly computed revision and reject on mismatch, making the break-aware fingerprint load-bearing) or remove it from `RotoGroupDragPublication` and the `buildGroupDragProposalVersion` call site. If the coordinator's own revision revalidation is the intended authority, delete the dead field.

### WR-03: `prepareRotoGroupDrag` re-derives loop ranges the resolver already computed

**File:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:1409-1421`
**Issue:** To compute the D-07 `vacatedInterval`, `prepareRotoGroupDrag` calls `derivePhysicPaintRotoLoopRanges` a second time with the same inputs the resolver already used internally (`physicsPaintRotoPhysicalResolver.ts:3368-3379` derives the dragged interval and clamps against it). This is duplicate computation, and it is a drift risk: the vacated interval is derived from a fresh projection rather than the resolver's own derived interval, so any future divergence between the two call sites (e.g., a different `parentEndExclusive`) would silently corrupt the gap preview and the status copy while the resolver commits a different interval.
**Fix:** Expose the resolver's derived dragged interval on the proposal (or a dedicated field on the resolution result) and reuse it in `prepareRotoGroupDrag` instead of re-deriving:
```ts
// resolver: include the derived interval in the move-group resolution result
return Object.freeze({
  ok: true as const,
  proposal: finalized.proposal,
  draggedInterval: { phaseOrigin, effectiveEnd: resolvedEffectiveEnd },
});
// prepareRotoGroupDrag: read it instead of calling derivePhysicPaintRotoLoopRanges again
const vacatedInterval = attached && clip && resolution.draggedInterval
  ? resolution.draggedInterval
  : null;
```

### WR-04: `handlePointerCancel` is missing the session-identity guard

**File:** `app/src/components/physic-paint/hooks/usePhysicsPaintGroupRailDrag.ts:343-348`
**Issue:** `handlePointerCancel` checks only `cancelEvent.pointerId !== session.pointerId`, while `handlePointerUp` (line 320) and `handleLostPointerCapture` (line 350) also check `sessionRef.current !== session`. The single-session invariant (`onPointerDown` returns early when `sessionRef.current` is set) and pointerId uniqueness make the practical risk low today, but the inconsistency is a latent defect: if the invariant is ever relaxed, a stale cancel would run `cleanup()` and `clearSuppressionSoon()` against a newer session, clearing its click-suppression flag. It also calls `restoreSourceFocus()` for a not-started session, focusing the rail target on a cancel that never began a drag.
**Fix:** Mirror the other handlers:
```ts
const handlePointerCancel = (cancelEvent: PointerEvent) => {
  if (cancelEvent.pointerId !== session.pointerId || sessionRef.current !== session) return;
  cleanup();
  clearSuppressionSoon();
  restoreSourceFocus();
};
```

### WR-05: Infinity-repeat derivation debt affects the drag preview/commit for infinity Groups

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalResolver.ts:3718-3728`
**Issue:** For lifecycle-available clips, `requestedEnd` and `naturalEnd` are both taken from the stale `clip.originalEndExclusive!` regardless of `repeat`. A Group whose Repeat is set to `'infinity'` therefore derives its interval from the stale source-cycle end instead of the parent end, so the D-19 rightward-drag behavior (right edge pinned at the resolved effectiveEnd) and the ghost width are computed against the wrong extent. This is documented as pre-existing (proven on the 38cf2448 baseline; the regression anchor is the skipped test at `physicsPaintRotoPhysicalResolver.test.ts:1353-1405`), and it is not a 43.3 regression — but the phase's own UAT references it, and it directly affects the correctness of the drag preview and commit for infinity Groups shipped by this phase.
**Fix:** In the dedicated debug, honor `repeat === 'infinity'` for lifecycle-available clips by deriving `requestedEnd`/`naturalEnd` from the parent end (and rebuild lifecycle for infinity in `updateLoop`), then un-skip the baseline anchor test.

## Info

### IN-01: Single-frame gap produces "Gap left at frames 5–5."

**File:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:191`
**Issue:** When the vacated interval is a single frame, the D-07 copy reads "Gap left at frames 5–5." — a plural range for one frame.
**Fix:** Use a singular form when `start === end`:
```ts
const range = start === end ? `frame ${start}` : `frames ${start}–${end}`;
return `${moved} Gap left at ${range}.`;
```

### IN-02: Unmount cleanup calls `setGhost` during unmount

**File:** `app/src/components/physic-paint/hooks/usePhysicsPaintGroupRailDrag.ts:372-374`
**Issue:** The unmount effect calls `sessionRef.current?.cleanup()`, which runs `setGhost(GHOST_INACTIVE)` on a component that is being removed — dead work. The `input.onPreviewChange?.(null)` call is correct (it clears the parent's preview), but the `setGhost` call has no effect.
**Fix:** Accept as harmless, or split the cleanup so the unmount path skips the state write (e.g., a `notifyPreview` flag on the session).

### IN-03: Commit rejection path publishes no status

**File:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:1462-1469`
**Issue:** `commitRotoGroupDrag` publishes the accepted status only when `accepted` is true. When the coordinator rejects the commit (barrier failure, revision mismatch, lease timeout), the rail hook restores focus but the user receives no feedback — the prepare path validated the destination, so a commit rejection is rare, but it is silent.
**Fix:** Publish a rejection status on the `!accepted` path, e.g. `input.publishStatus?.('The Group move could not be applied.')`.

### IN-04: `originY`/`latestY` are dead data in the session

**File:** `app/src/components/physic-paint/hooks/usePhysicsPaintGroupRailDrag.ts:147,203,205,310,322`
**Issue:** The session tracks `originY` and `latestY`, but the rail drag is horizontal-only (`GROUP_RAIL_DRAG_THRESHOLD_PX` uses `latestX - originX` only) and neither field is ever read.
**Fix:** Remove the Y fields, or document them as reserved for a future diagonal gesture.
