# Phase 43.4: Derived Key Groups and Scissor Breaks - Context

**Gathered:** 2026-08-15
**Status:** Ready for planning

<domain>
## Phase Boundary

Represent ordinary real Roto keys not owned by a Motion Group or Static Group as **derived Key Groups**: computed from ordered real keys plus persistent Phase 43.1 interpolation breaks, never persisted as Group records and never a second membership authority. Every continuous ordinary-key segment — including a single isolated key — displays a thin mid-gray integrated Key Rail in the existing 3px physical-frame rail band; a 43.1 break divides one segment into two Key Rails.

Three operations ship on this derivation: **Scissor** (a new toolbar action that creates a persistent incoming break on a selected real ordinary key, splitting one Key Rail into two), **Delete Key Rail** (selection-scoped direct deletion of every real key in the derived group with persistent-gap normalization), and **Key Rail drag** (whole-group movement inside free space under the Phase 43.3 collision-limited direct-drag contract). Each operation is exactly one atomic physical-document history command with one Undo/Redo, surviving save/reopen and Interpolation Off/On.

The accepted canonical physical document, exact parent acknowledgement, stable-key-owned break authority, Motion/Static Group lifecycle (`visibleRanges`, `phaseOrigin`, `frameOverrides`, synchronization), existing physical-key operations, Key Spacing, preview/export parity, and Paint brush history remain authoritative and unchanged. Push Right/Push Left multi-object movement is Phase 43.5; the Motion Editor timeline is unchanged.

Requirements are not yet assigned IDs in `.planning/REQUIREMENTS.md`; downstream research/planning must derive Phase 43.4 IDs and traceability from the activated product prompt without reopening completed Phase 43/43.1/43.2/43.3 requirements.

**43.2 carryover caution (restated from 43.3):** frozen `69d07703` still has open native red loops for project-local save staging, Paint into a deleted Group gap, and original-extent Regenerate. Key Rail work must build on the accepted Group lifecycle authority without reopening those repair paths, and its own native UAT runs from a fully restarted frozen-code session (43.2 D-39).

<decisions>
## Implementation Decisions

### Terminology override (binding, user-locked 2026-08-15)

- **D-01:** One user-facing Rail family: **Motion Rail**, **Static Rail**, and **Key Rail**. Do not introduce `Key Group` / `Key Group Rail` in new user-facing copy. Where this phase touches the shared Rail surface, replace existing `Motion Group` / `Static Group` / `Group Rail` user-facing terminology so the three rail types stay coherent. — **Reversibility:** costly — 43.2 D-01 locked the Group vocabulary across labels, tooltips, dialogs, status/error copy, accessibility names, and product-copy tests; every touched surface and its copy tests must migrate together or the UI forks into two vocabularies.
- **D-02:** Internal TypeScript, transport, persistence, and historical planning identifiers keep `Group`, `loopClip`, and related names. No document migration or data-model rename. Scissor splits a Key Rail; rail selection selects, drags, and deletes the complete Key Rail; the user-facing destructive action is **Delete Key Rail**.

### Scissor action surface

- **D-03:** Scissor creates a break only when the cursor/selection is on a real ordinary key belonging to a Key Rail. The new persistent incoming break is owned by that key's stable identity and splits the Key Rail immediately before it. Every other target (generated frame, empty frame, Motion/Static Group frame, linked frame) is disabled before activation with a mapped product reason; the resolver remains fail-closed for stale/racing inputs.
- **D-04:** Scissor is a new dedicated toolbar button labeled `Scissor` in the bottom key toolbar, placed after Cut, with a distinct icon — the Scissors glyph stays exclusive to the existing Cut key tool. The locked toolbar order (`+ Key | Insert | Duplicate | …`, 43.2 A-04) is otherwise untouched. Guarded tooltip follows the 43.1 mapper pattern; enabled copy: `Split the Key Rail before this key.` Cutting at an existing break is an exact no-op with no history entry (prompt-locked).
- **D-05:** No keyboard shortcut for Scissor this phase — toolbar button plus guarded tooltip only.
- **D-06:** An accepted cut publishes `Split Key Rail before frame {N}.`; the owning key shows its 43.1 left-edge cut marker; the one gray rail re-derives into two adjacent gray rails; the cursor stays at `{N}` and the key stays selected (43.1 Insert precedent).

### Key Rail presentation

- **D-07:** The Key Rail uses a distinct mid-gray tone, clearly different from the neutral-gray intentional-gap cells (43.2/43.3 gap language) and from Motion purple / Static cyan. It must never read as empty space or unresolved.
- **D-08:** One shared selection language: a selected Motion Rail, Static Rail, or Key Rail uses the existing orange selection treatment. Hover only brightens the rail's base color and must remain distinct from selection; focus remains visibly distinct.
- **D-09:** A single isolated ordinary key is a one-key Key Rail occupying exactly one cell width — selectable, draggable, and deletable like any other Key Rail.
- **D-10:** Locked Key Rail copy family (user-facing term is `Key Rail`; correct singular/plural via the shared mapper):
  - Base, multiple: `Key Rail — frames {A}–{B}, {N} keys.`
  - Base, single: `Key Rail — frame {A}, 1 key.`
  - Selected, multiple: `Selected Key Rail — frames {A}–{B}, {N} keys. Drag to move. Delete removes all keys in this rail.`
  - Selected, single: `Selected Key Rail — frame {A}, 1 key. Drag to move. Delete removes this rail.`
  - Only currently-available actions are announced; unavailable drag/delete exposes the exact guarded reason instead. Scissor is never advertised on the rail — it acts on a selected real key, not rail selection.
- **D-11 (batch lock):** All rails use the existing integrated 3px rail band with zero added timeline height. Key Rail boundaries use the same clear white endpoint-cut language so Scissor breaks and adjacent rails stay visually separable. Adjacent Motion/Static/Key Rails never overlap or visually merge; every canonical boundary stays visible. The interactive hit target stays inside the dedicated rail band — it may be larger than the painted 3px line but must never cover or steal pointer interaction from the physical cell/key body. Rails never cover key markers, gap cells, linked indicators, synchronization dots, ruler labels, drag previews, or toolbar controls.

### Delete Key Rail

- **D-12:** The user-facing operation is `Delete Key Rail`. The existing Delete control dynamically exposes its live scope: `Delete Frame` when a physical frame is selected, `Delete Key Rail — frames {A}–{B}, {N} keys.` when a Key Rail is selected. Delete/Backspace follow the same scope. Frame selection and rail selection remain mutually exclusive at deletion time; no scope is inferred from cursor position alone (prompt-locked).
- **D-13:** Deletion is fully direct — no confirmation modal at any key count. One Undo restores every key, break, and selection; one Redo removes the same Key Rail again as one command.
- **D-14:** Accepted status: `Deleted Key Rail — frames {A}–{B}, {N} keys. The interval stays an intentional gap.` (single-key form: `Deleted Key Rail — frame {A}, 1 key. The interval stays an intentional gap.`).
- **D-15:** Complete Key Rail deletion plus persistent-gap normalization is one atomic command: every real key, the generated projection that depended on those keys, boundary-break normalization (no surviving Key Rails merge, no break references a deleted key identity, no dangling/duplicate break), selection clearing, cursor on the same valid frame, and canvas reconciliation commit together; partial cleanup is forbidden (prompt-locked). Stale, ambiguous, rejected, or no-op deletion produces no mutation, success status, or history entry.

### Key Rail drag

- **D-16:** Key Rail drag carries the 43.3 contract verbatim: translucent mode-colored (gray) ghost rail following the cursor, original rail visible until commit, clamp at every collision boundary (frame 0, capacity/parent end, every previous/next real key, every Group interval), red blocked-edge treatment at the clamp, neutral-gray gap preview for vacated/newly opened intervals, ~4px drag threshold, Escape cancels with zero state change and no history entry. Drag never pushes, pulls, reorders, stretches, splits, or retimes anything.
- **D-17:** The dragged Key Rail's first key keeps its incoming break — the break travels with the key's stable identity (43.1 D-14 / 43.3 D-10 semantics). Landing immediately adjacent to a predecessor keeps the split; a landing gap adds a break only when a gap actually opens. A vacated interval is preserved through stable-key-owned break authority exactly as in 43.3 D-09/D-12: the next real key after the vacated interval owns/reuses the incoming break; no break is created when no real key would interpolate across the gap. Key Rails have no duplicated-placement branch — every Key Rail drag is source-attached whole-segment rigid translation.
- **D-18:** Accepted drag status: `Moved Key Rail to frame {N}.` plus `Gap left at frames {A}–{B}.` when a gap opened (43.3 D-07 adapted).
- **D-19:** After an accepted drag the moved Key Rail stays selected, the physical cursor stays on its current frame, and the Studio canvas reconciles from the accepted document only when the current frame's content changed (43.3 D-17 verbatim — no automatic navigation).
- **D-20:** No-free-space rejection reuses 43.3 D-06 verbatim through the same product-reason mapper: `No empty space in that direction.` — one no-space sentence across all rail kinds.

### Process and regression boundaries

- **D-21:** One deterministic mapper owns all Key Rail tooltip, accessibility, status, disabled-preflight, and rejection copy, with correct singular/plural wording — preflight and rejection can never disagree (43.1 D-17 pattern).
- **D-22:** This phase produces a UI-SPEC via `/gsd-ui-phase 43.4` after context: the Key Rail presentation, Scissor button, dynamic Delete scope label, drag ghost/clamp/gap preview, and locked copy set are a new visual/interaction surface (43-UI-SPEC / 43.3 D-16 precedent).
- **D-23:** Native visual UAT is the final oracle and runs from a fully restarted frozen-code parent/child session (43.2 D-39), covering the prompt's 15-step acceptance list.
- **D-24:** Scissor, Key Rail drag, and Delete Key Rail each commit as exactly one atomic physical-timeline history command through the existing coordinator/history authority; no phase-local history stack, no brush/timeline history merge, and a new accepted edit after Undo truncates the Redo branch normally (prompt-locked). Save/reopen reconstructs the same keys, gaps, breaks, and derived Key Rails without history replay.
- **D-25 (scope boundaries, prompt-locked):** No persisted Key Group record collection; no tombstones; no Delete scope-choice modal; no Motion/Static Group lifecycle, source sharing, Action, Regenerate, or synchronization changes; no Action provenance/sync dots/Regenerate on Key Rails; no multiple internal Paint tracks; no Motion Editor timeline changes; no Key Spacing/Interpolation control moves or directional Push tools (Phase 43.5).

### Claude's Discretion

- Exact mid-gray token, hover brightening amount, and white endpoint-cut geometry on the Key Rail, provided they stay inside the locked presentation rules (D-07, D-08, D-11) and cannot be confused with gap gray, unresolved red, selection orange, or the mode colors.
- Exact Scissor icon choice, provided it is visually distinct from the Scissors glyph used by Cut key.
- Exact intent names and additive payload shapes for the scissor/drag/delete resolver intents, provided they join the closed union with strict parsing, canonical revision participation, and fail-closed validation (43.3 D-14 precedent).
- Exact derived-Key-Group computation/caching representation, provided derivation stays pure from ordered real keys plus persistent breaks and never becomes a second persisted authority.
- Exact test decomposition. Native visual UAT remains required for rail derivation/presentation, Scissor split/no-op, selection-scoped deletion, drag clamp/gap persistence, Undo/Redo, Interpolation Off/On, and save/reopen.

- The parent-authoritative physical document is accepted truth: ghost/preview/derivation state is presentation-only; nothing presents as cut, moved, or deleted before exact correlated acknowledgement.
- Additive persistent outcomes (new breaks, moved keys, normalized boundary breaks) participate together in strict parsing, canonical revision fingerprints, bridge equality, persistence, and complete history snapshots.
- Preact Signals/computed projections carry derived Key Rail state and drag preview; no effect-driven mirrored state or prop-drilling sprawl; keep new logic out of `PhysicsPaintStudio.tsx` where a focused module suffices.
