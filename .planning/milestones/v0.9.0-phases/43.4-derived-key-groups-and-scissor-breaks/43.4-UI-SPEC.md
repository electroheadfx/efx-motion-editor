Dialog titles (`Edit Group`), the Scripts panel (`Create Group…`), and the Actions inspector are not shared Rail surfaces touched by this phase and remain unchanged. Internal TypeScript, transport, persistence, and planning identifiers keep `Group` / `loopClip` names (D-02).

## Derivation Contract

Key Rail boundaries are pure derivation. They never become persisted state and never depend on Interpolation On/Off.

- A **Key Rail segment** is a maximal run of ordinary real keys — keys not owned by any Motion Group or Static Group — with no persistent incoming interpolation break between consecutive members. Group-owned keys, generated cells, linked frames, unresolved frames, and background-only cells never join a Key Rail.
- A persistent Phase 43.1 incoming break owned by key `K` splits the segment immediately before `K`: the left rail ends at `K`'s frame and the right rail starts at `K`. `K` retains its existing 43.1 blue left-edge cut marker inside its cell.
- Rail span geometry is half-open `[firstKeyFrame, lastKeyFrame + 1)` over physical cells. A single isolated ordinary key produces a one-cell-wide Key Rail (D-09).
- Empty frames between member keys without a break remain inside one continuous rail.
- Adding a new ordinary key extends the applicable Key Rail unless an explicit break separates it; deleting/moving keys re-derives rails from the accepted document only.
- Key Rails, Motion Rails, and Static Rails tile the same band and never overlap: Group-owned spans render Motion/Static Rails, ordinary segments render Key Rails, intentional gaps render no rail.

## Geometry and Layering Contract

### Existing geometry is immutable

The workflow strip remains exactly **161px**; the physical-frame row remains **38px**; the visible rail remains exactly **3px** high at `y: 0`; each rail target remains **12px** high at `top: 0`; frame pitch remains **18px/frame**. Key Rails, the Scissor button, the dynamic Delete scope, and the drag previews add zero row, track, lane, or height (D-11).

### K1 Key Rail geometry

- Key Rail segments render inside the same integrated rail band and containing block as Motion/Static Rails, sharing the 2160px content width, 18px/frame pitch, and 4px scroll-leading offset.
- Segment geometry: `left = firstKeyFrame × 18px`; `width = max(1px, (lastKeyFrame + 1 - firstKeyFrame) × 18px)`, visible-window clipped exactly like existing rails. A one-key Key Rail is exactly one cell (18px) wide.
- The transparent pointer/focus target is exactly **12px** high at `top: 0`, spanning the segment width; `cursor: pointer`. During an active drag session the cursor is `grabbing`; `grab` is never used at rest (43 contract carried).
- Every actual segment start and end receives the existing white endpoint-cut language: a **2px `#F8FAFC`** vertical cut on the rail plus matching white left/right boundary-cell borders (43 contract). Two rails adjacent across a break therefore show a double divider at the split; viewport-clipped edges receive no false cut. Every canonical boundary stays visible; adjacent rails never overlap or visually merge (D-11).
- The rail band stays inside its dedicated top band: the 12px target never covers or steals pointer interaction from the physical cell/key body below `y: 12px`, and rails never cover key markers, gap cells, linked indicators, synchronization dots, ruler labels, drag previews, or toolbar controls (D-11).
- Key Rails are absent from the DOM when no ordinary real keys exist. No empty placeholder, label, reserved space, or hidden focus target remains.

### K2 Scissor button geometry

- The Scissor button reuses the existing key-toolbar icon-button geometry (`physics-paint-roto-key-icon-button`, 18px icon, compact text label under the icon) and slots into the existing toolbar flow immediately after Cut: `… Copy | Cut | Scissor | Paste | Delete …`. The locked toolbar order (`+ Key | Insert | Duplicate | …`, 43.2 A-04) is otherwise untouched.
- The guarded tooltip and screen-reader disabled-reason span follow the exact Cut/Copy/Delete idiom (`buildGuardedActionTooltipCopy`, `aria-describedby` reason span, `PhysicsPaintStyledTooltip` region `bottom`).

### K4 drag preview geometry (43.3 carried verbatim)

- Ghost: paint-only 3px rail at the clamped proposed destination with the dragged segment's exact geometry; original rail stays fully visible at 100% opacity until commit.
- Blocked edge: **2px wide × 12px high** `#FF6B6B` vertical bar on the ghost's blocked side when clamped (frame 0, capacity/parent end, any previous/next real key, any Motion/Static Group interval including linked occurrences).
- Gap preview: vacated and newly opened destination intervals preview as ordinary empty cells (`roto-fill-empty`: border `#3D454D`, background `#4D535A`) — byte-identical to the 43.2 deleted-Group-gap treatment. No distinct drag-gap visual.
- All preview paint is `aria-hidden="true"`, `pointer-events: none`, and removed on commit, cancel, or rejection.

### Layer order

Unchanged from 43-UI-SPEC: physical cells 0; existing cell overlays 1–5; transparent rail targets 6; visible 3px rail paint 7 (`pointer-events: none`); ghost and blocked edge between 7 and 8; rail focus ring 8; styled tooltip 60. Key Rail targets and paint share layers 6/7 with Motion/Static Rails; segments of different kinds never occupy the same x-range.

### State precedence

Highest visible state wins (accepted rail layer):

1. Keyboard focus ring `#F2F5F7`
2. Selected `#F59E0B`
3. Hover brightened base
4. Normal base color (Key Rail gray / Motion purple / Static cyan)

During a drag: the clamped blocked-edge bar outranks ghost paint on the ghost layer only; the accepted rail never inherits ghost, clamp, or gap state. Key Rails have no truncated-amber or unresolved-red variants — derived rails cannot be truncated or unresolved. State changes alter paint only, never geometry.

### Responsive contract at 1280×720 minimum

Unchanged from 43-UI-SPEC: existing three-column Studio layout, 161px strip, shared horizontal scroller; Key Rail segments clip at the shared viewport and reappear on scroll; no vertical scrolling, canvas-height, or sidebar change.

- A Scissor split is cued by the double white cut plus the owning key's existing blue left-edge segment marker — shape/position cues, not a new hue.

## Interaction Contract

### Selection ownership

- Key Rail selection, Motion/Static Rail selection, and physical real-key selection are mutually exclusive session modes; neither selection nor any anchor is persisted. Selecting any rail clears the other modes synchronously; plain/Cmd/Shift physical-key selection retains its accepted behavior and clears all rail selection.
- Plain click on a Key Rail target selects exactly that one derived Key Rail, paints only its 3px line orange, updates the tooltip/accessible name to the Selected copy form, and does not move the physical cursor, navigate the playhead, or mark member key cells.
- Key Rail selection is always single-rail: Shift-click and Cmd/Ctrl-click on a Key Rail resolve as plain selection. Key Rails never join Motion/Static Rail range or toggle selections, and Group-rail Shift/Cmd semantics among Group rails remain unchanged.
- Stale authority (membership, breaks, or document revision changed under a selection) clears the invalid rail selection instead of inventing a fallback scope.

### K2 Scissor behavior

- Target resolution: the selected real ordinary key first, else the real ordinary key at the cursor frame. Every other target (generated, empty, Motion/Static Group, linked frame) disables the button before activation with the mapped reason; the resolver remains fail-closed for stale/racing inputs (D-03).
- Activation creates exactly one persistent incoming break owned by that key's stable identity, splitting its Key Rail immediately before it. Scissor never creates a real key, duplicates pixels, alters Paint content, or materializes generated frames.
- Cutting at an existing break is an exact no-op: no mutation, no status, no history entry, unchanged history depth (D-04).
- On acceptance: status publishes `Split Key Rail before frame {N}.`; the owning key shows its 43.1 left-edge cut marker; the one gray rail re-derives into two adjacent gray rails separated by the double white cut; the cursor stays at `{N}` and the key stays selected (D-06).
- No keyboard shortcut this phase (D-05). The button guards follow the paint-mode shortcut/adjacency rules already in force for the key toolbar.

### K3 Delete routing

- Delete, Backspace, and the visible Delete control share one activation-time scope classifier: physical-frame selection routes to existing Delete Frame; Key Rail selection routes to Delete Key Rail; Motion/Static Rail selection routes to existing Group deletion. No routine choice modal exists at any key count (D-12, D-13).
- Delete Key Rail removes every real key in the derived segment, the generated projection that depended on those keys, and normalizes boundary breaks — no surviving Key Rails merge, no break references a deleted key identity, no dangling or duplicate break remains — as one atomic command with selection clearing, cursor on the same valid frame, and canvas reconciliation (D-15).
- The vacated interval remains a persistent intentional gap: Interpolation On must not refill or bridge it, Interpolation Off/On preserves it exactly, and later ordinary-key creation respects the accepted gap.
- One Undo restores every key, break, selection, and cursor; one Redo removes the same Key Rail again as one command. A stale, ambiguous, rejected, or no-op deletion produces no mutation, success status, or history entry.

### K4 Key Rail drag (43.3 carried verbatim)

| Input | Result |
|-------|--------|
| Pointer down on Key Rail target | begin tracking; no paint change, no navigation, no drag session yet |
| Pointer moves ≤ 4px and releases | plain click selection behavior |
| Pointer moves > 4px horizontally | drag session starts; pointer capture on the rail target; cursor `grabbing`; gray ghost appears at the clamped proposed destination; vacated interval previews as `roto-fill-empty` cells |
| Pointer moves during session | ghost recomputes the clamped destination; blocked-edge bar appears/disappears with clamp state; gap preview updates |
| Escape during session | cancel: zero state change, zero history, all preview paint removed; selection and focus unchanged |
| Release (drop) | commit request at the currently shown (possibly clamped) position — the preview is the commit |
| Release with zero valid movement in the dragged direction | rejection: preview removed, nothing mutates, status publishes `No empty space in that direction.` |

- Drag never pushes, pulls, reorders, stretches, splits, or retimes anything; neighbors remain fixed at every collision boundary (D-16).
- The dragged rail's first key keeps its incoming break — the break travels with stable key identity; adjacent landing keeps the split; a landing gap adds a break only when a gap actually opens; the vacated interval follows 43.3 D-09/D-12 successor-ownership exactly (D-17). Key Rails have no duplicated-placement branch: every Key Rail drag is source-attached whole-segment rigid translation.
- After an accepted drag the moved Key Rail stays selected, the physical cursor stays on its current frame, no automatic navigation occurs, and the canvas reconciles from the accepted document only when the current frame's content changed (D-19).
- Ghost, blocked edge, and gap preview are presentation-only; nothing presents as moved before exact correlated parent acknowledgement. An accepted move is one atomic history command with one Undo/Redo.

### Keyboard and focus

- Each visible Key Rail segment exposes exactly one tab stop (`role="button"`, `tabIndex=0`); tab order follows canonical first-key frame order, then existing strip controls.
- **Space** plain-selects the Key Rail (prevents page scroll). **Enter** performs no action — Key Rails have no Edit dialog and no Action/Regenerate/synchronization surface (D-25). **Escape** hides the tooltip without changing selection or focus.
- **Delete/Backspace** with a Key Rail selected invokes Delete Key Rail directly through the shared scope classifier (D-12).
- Arrow-key physical-frame navigation remains unchanged when focus is not on a rail target; no Key Rail movement shortcut exists.
- Focus ring: 2px `#F2F5F7` with 1px offset around the 12px target, visible at viewport edges, never clipped by the timeline container.

### Busy and rejected-operation behavior

- During controller preparation/commit, the accepted rail remains visible in place at 55% opacity with `aria-busy="true"`; Scissor and Delete expose `aria-disabled="true"` with the current controller reason. A second drag session cannot start while a physical mutation is in flight.
- No optimistic rail split, movement, deletion, width, or status change. Update only from accepted canonical authority state.
- On rejection, preserve prior geometry, selection, focus, and cursor; announce the reason through the existing status channel.

### Accessibility

- Rail band group: `role="group"`, `aria-label="Rails"` (migrated from `Groups` per D-01); rendered only when any rail exists.
- Key Rail target accessible name: the exact D-10 copy form for its state; selected target `aria-pressed="true"`, unselected `aria-pressed="false"`, busy `aria-busy="true"`.
- Tooltip: existing `role="tooltip"` connected with `aria-describedby`; Scissor follows the guarded `aria-describedby` reason-span idiom exactly like Cut/Copy/Delete.
- Status updates publish through the existing `aria-live="polite"` status line; rejections additionally use `role="alert"`.
- The 12px rail target is the established compact-editor exception; tooltip, keyboard access, and the toolbar provide equivalent larger action access.
- Reduced motion: rail derivation, split, hover, selection, ghost, clamp, and gap-preview changes are immediate paint changes with no slide, tween, spring, shimmer, or pulse. Under `prefers-reduced-motion: reduce`, no transition is added to any touched element.
- No state relies on color alone (see Non-color cues).

## Implementation Boundaries

- Key Rail derivation is a pure Signals `computed` projection over ordered real keys, persistent breaks, and Group ownership from the canonical store; it never persists, never enters revision fingerprints as new state, and never becomes a second membership authority.
- Render Key Rail segments inside the existing integrated rail band (extend `PhysicsPaintLoopClipRail.tsx` or a sibling band-contained host sharing its geometry); keep new logic out of `PhysicsPaintStudio.tsx` where a focused module/hook suffices.
- The Scissor button and dynamic Delete scope extend the existing `computeInsertAvailability` / `buildGuardedActionTooltipCopy` / `runPhysicalAction` pattern in `useRotoTimelineActions.ts`; one product-reason mapper owns all new copy (D-21).
- Scissor, Key Rail drag, and Delete Key Rail join the resolver's closed intent union with strict parsing, canonical revision participation, and fail-closed validation (43.3 D-14 precedent); each commits as exactly one atomic coordinator/history command through the existing authority — no phase-local history stack (D-24).
- Key Rail drag reuses the 43.3 rail-drag stack (threshold, capture, Escape, ghost, clamp authority, gap preview) with the gray palette; `move-key-group` and Group-rail drag remain locked regression boundaries.
- No new row, lane, popover, dialog, modal, keyboard shortcut, persisted field, or Motion Editor timeline change (D-25).
- The D-01 terminology migration touches only the rail presentation module, the shared product-reason mapper's rail copy, the rail band accessible name, and the Delete scope labels — with their copy tests migrating together; dialog titles, Scripts panel, and Actions inspector copy remain unchanged this phase.
