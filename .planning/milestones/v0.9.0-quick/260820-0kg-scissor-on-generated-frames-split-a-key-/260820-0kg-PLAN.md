# 260820-0kg — Scissor on generated frames: split a Key Rail mid-interpolation

**Type:** quick · **Status:** planned
**Source:** SPECS/milestone-v0.9.0-new-phases/quick-scissor-generated-frame-split-prompt.md — revises the locked 43.4 decision "Scissor targets real keys only". Scissor now ALSO accepts a generated/interpolated frame inside a Key Rail. Everything else about Scissor is unchanged.

## Contract (locked, from the spec)

- Cursor on a **generated frame inside a Key Rail** → Scissor enabled. The cut resolves to the **next real key after the cursor within the same derived Key Rail segment**: that key owns the new persistent incoming break. The interpolated span between the surrounding real keys becomes an intentional persistent gap.
- User example: keys at 0/2/6/8 with interpolation; cursor on generated frame 4 → Scissor → rails `[0–2]` + `[6–8]`; frames 3–5 become a persistent gap (break blocks generation across it).
- Resolver intent UNCHANGED: `scissor-key-rail` with `breakOwnerKeyId` = the next real key. The whole feature lives in target classification + availability + copy. Resolver (`physicsPaintRotoPhysicalResolver.ts:4997`), history, bridge, and settlement paths must NOT change.
- Break ownership resolves ONLY within the same derived Key Rail segment (`deriveKeyRailSegments` authority). Generated frame with no following real key inside its own segment (edge of segment) → Scissor disabled with a mapped reason.
- Unchanged guards: first real key of a rail → disabled; frame already at an existing break → exact no-op, no history entry; empty/gap frames, Motion/Static Group-owned frames, linked/background/unresolved cells → disabled with the existing mapped reasons.
- Interpolation Off: no generated frames exist → nothing changes (real-key-only availability).
- Copy (mapper owns all variants):
  - Tooltip, real-key target: `Split the Key Rail before this key.` (locked 43.4)
  - Tooltip, generated-frame target: `Split the Key Rail at this point.`
  - Status on accept, real-key target: `Split Key Rail before frame {N}.` (locked 43.4; {N} = real-key frame)
  - Status on accept, generated-frame target: `Split Key Rail at frame {N}.` ({N} = cursor frame)
  - New edge-of-segment disabled reason (not spec-locked): `Scissor is unavailable at the edge of a Key Rail segment.`
- Cursor stays on frame {N} after commit; no key selection is created or moved; one atomic history command; Undo merges rails back, Redo re-splits. Save/reopen, Interpolation Off/On, drag, delete, spacing unchanged.
