# 260820-hq9 — addEmptyKey inside an interpolated segment: force the empty payload to own the display

**Type:** quick · **Status:** planned
**Source:** user-reported native bug. With Frame Blending ON, `addEmptyKey` on a frame strictly inside a derived Key Rail segment keeps the stale **interpolated** image on canvas. Native evidence: status line shows `Real Roto key · Frame 139` while the canvas still shows the interpolated render; the user paints over it and on refresh the paint is gone (the key is real and EMPTY — interpolation was never its content).

## Contract (locked)

- When `addEmptyKey` commits, the destination frame becomes a REAL EMPTY key and the **display authority is the empty payload** — the empty render replaces the cached interpolated image immediately on commit (per the project bump-and-subscribe `paintVersion` rule).
- Interpolation OFF: behavior is already correct — keep it byte-identical (no visible, no wiring change beyond the additive reconcile).
- Minimal change, single concern. The empty payload is the newest content revision and must win over the cached interpolated image via the existing content-token ordering.
- RED test desired (user): keys 0/4/8 interpolation ON, `addEmptyKey` at 6 → after commit frame-6 display authority is the empty payload; Undo restores interpolated display; Redo clears again.

## Root cause (verified)

`addEmptyKey` (`useRotoTimelineActions.ts:2259`) resolves `startsNewSegment` via `deriveKeyRailSegments` and runs:

```
runPhysicalAction({ intent: createPhysicPaintRotoPasteKeyIntent(destinationAppFrame, emptyPayload, null, startsNewSegment), operationKind: 'paste-key', ... })
```

`runPhysicalAction` (line 1837) → `executePhysicalEdit`. In the coordinator, `finalizeAccepted` (`useRotoPhysicalEditCoordinator.ts:1196`) decides whether to repaint the retained frame after acceptance. The reconcile list at lines **1225-1238** is:

```
'undo' | 'redo' | 'play-script' | 'regenerate-group' | 'insert-empty-segment'
| 'paint-group-frame' | 'delete-group-frame' | 'delete-group' | 'delete-rails' | 'paste'
```

**`'paste-key'` is missing.** `insert-empty-segment` is present, but `addEmptyKey` uses `paste-key`, not `insert-empty-segment`. So for `addEmptyKey` acceptance, `reconcileCurrentFrame(after.currentAppFrame)` is never invoked.

The only remaining refresh is the Studio `createdSelectedDestination` path (`PhysicsPaintStudio.tsx:2182-2197`), which calls `loadCachedRotoReferenceFrame(acceptedSelectedAppFrame, engine)` as a **PLAIN** refresh (no explicit generation, no explicit dataUrl). Since `regression-refresh-multi-paint`, the loader's plain-refresh guard **no-ops** when the engine holds an explicit settled base for the same appFrame with a non-null dataUrl (the prior interpolated settle) — so the canvas keeps the interpolated image while the accepted document says the key is real and EMPTY.

Adding `'paste-key'` to the reconcile list routes acceptance through the strong path (`PhysicsPaintStudio.tsx:1028-1068`): it loads the accepted render source for `after.currentAppFrame` (= the destination — `publishCompleteDocument` at line 1136 sets `lastAcceptedSelectionRef.current.cursorAppFrame = document.cursorAppFrame`, and `captureSnapshot` line 1089 reads it) with an explicit generation `max(acceptedToken, applied)`, so the engine's preview-base seam drops any stale interpolated settle (content-token ordering) and the empty payload — the newest revision — wins. It also arms the completion paint guard for the decode window. `physicPaintVersion` bumps via `_notifyVisualChange()` during `replaceRotoPhysicalDocument` (`physicPaintStore.ts:1572`).

Ordering is safe: `finalizeAccepted` (inside `consumePhysicalEditResult`) paints first via reconcile; the later Studio `createdSelectedDestination` plain call then no-ops against the explicit settled base (guard) — additive, no flicker, no double paint.
