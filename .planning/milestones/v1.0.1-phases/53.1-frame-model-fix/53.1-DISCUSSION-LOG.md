## I-4 fps timebase (where)

| Option | Description | Selected |
|--------|-------------|----------|
| Derived — project fps only | All time math reads `projectStore.fps`; delete dead `setSequenceFps`; drop `seq.fps` from the model (clean break) | ✓ |
| Derived read, keep serialized field | Time math reads project fps; `seq.fps` stays in .mce as an ignored leftover | |
| Sync-on-change — `seq.fps` mirrors project fps | Keep `seq.fps` as the read field; write-through from project fps on create and on fps change | |

**User's choice:** Derived — project fps only, with placement spelled out.
**Notes:** WHY (locked): `sequence.fps` is born at 24 and `setSequenceFps` has 0 callers — the bug is a single stale field, not a real dual timebase. Keeping the field keeps the seed of the bug. A per-sequence fps field contradicts the one-document-timebase model law. No-backward-compat: dropping a dead field is the debt fix itself. WHERE: call sites `exportRenderer.ts:315,329,367`; `previewRenderer.ts:832` (video seek `targetTime = frame / fps`) and `:977`; `SequenceList.tsx:96`. Delete `sequenceStore.setSequenceFps` (`sequenceStore.ts:448`). Drop `seq.fps` from the Sequence type, the three factories (`sequenceStore.ts:148,280,312`), and the .mce serializer/parser — no shim, no ignored leftover. Video seek and export MUST go through the same reader so frame N = N / projectFps seconds in both paths. U-01 fps law: 15fps project + 24fps-era .mov must show frame 15 = 1.0s in BOTH preview seek and export time mapping (not 0.625s).

## I-1/I-2 tail policy owner + attach points

### Q1 — Which function owns the tail policy?

| Option | Description | Selected |
|--------|-------------|----------|
| One resolver in `frameMap.ts` | New `resolveOverlaySample(clip, globalFrame, N)` mapping sample/skip/hold-last/loop; export + preview both call it | ✓ |
| Extend the outFrame fn + sibling mapper | Keep `getTimelineOverlaySequenceOutFrame` as boundary fn; add sibling for hold/loop mapping | |
| Per-path policy (today's shape) | `exportRenderer` gate and `previewRenderer` each implement tail policy locally | |

**User's choice:** One resolver in `frameMap.ts`, with placement.
**Notes:** Rough signature: `resolveOverlaySample(clip, globalFrame, N) → {kind:'sample', localFrame} | {kind:'skip'} | {kind:'hold-last'} | {kind:'loop', localFrame}`. Both paths call it — `exportRenderer.ts:339-340` past-out gate → resolver (skip = draw nothing); `previewRenderer.ts:831-836` modulo-loop → resolver (hold-last / loop). I-5 HOLD/LOOP is an INPUT to this resolver (per-clip extrapolation property), never a second policy site — that is what kills the I-1 vs I-5 divergence class. Unit-testable: one describe in `frameMap.test.ts` covering the truth table (inside range / past out / past source HOLD / past source LOOP).

### Q2 — How is "untrimmed follows N" represented (I-2)?

| Option | Description | Selected |
|--------|-------------|----------|
| `outFrame` absent = untrimmed | Absent = follows N; present = authoritative; written only on user resize | ✓ |
| Explicit `trimmed` flag | `outFrame` stays always-present + a boolean meaning "out is authoritative" | |
| Sentinel `outFrame` value | One field, untrimmed encoded as e.g. `-1` | |

**User's choice:** `outFrame` absent = untrimmed, with placement.
**Notes:** Absent `outFrame` = untrimmed = follows N (base layer). Present `outFrame` = AUTHORITATIVE — past out = nothing (Law 1). One field, two states, no flag, no sentinel. `createContentOverlaySequence` STOPS freezing `outFrame` at import (`sequenceStore.ts:317`) — that freeze is the I-1 root (overlay skipped the moment the sequence grows past the import-time out). `outFrame` is written ONLY when the user resizes. Timeline bar width and SequenceList duration treat absent `outFrame` as N. `getTimelineOverlaySequenceOutFrame` already does `seq.outFrame ?? fallback` — the fallback becomes the live N (base span), not a frozen import value. Law 3 attaches here: once trimmed, if N grows past out, the visible layer does not cover N → timeline gap marker (out .. N) + export diagnostic naming the clip. Untrimmed never gaps (it follows N). Clean break: no migration, no shim.

### Q3 — Where does the timeline gap marker attach?

| Option | Description | Selected |
|--------|-------------|----------|
| Hatched tail on the clip bar | Per-clip `(out .. N)` range on the clip's own timeline row, after the bar's right edge | ✓ |
| Timeline-wide gap lane | Per-frame marker lane aggregated across clips | |
| Export diagnostic only | No timeline marker | |

**User's choice:** Hatched tail on the clip bar, with placement.
**Notes:** The gap is the per-clip range `(out .. N)` on the clip's OWN timeline row — the same surface as the range bar the user just resized. Reads as "this clip ends here, composition continues". Derived from the resolver's skip region — one source, no second gap computation. Drawn alongside the clip bar in `TimelineRenderer` / `fxTrackLayouts`, AFTER the bar's right edge. `barW` stays `(out-in)*frameWidth` (exclusive) and the fade stays flush against the bar — the hatched tail sits outside both. Fires only for VISIBLE layers with an authoritative out. Untrimmed follows N and never gaps. Multiple clips can each carry their own tail. No new timeline lane — the marker lives on the surface the user already manipulates (avoids noisy extra UI).

### Q4 — How does the export diagnostic attach?

| Option | Description | Selected |
|--------|-------------|----------|
| Non-blocking named warning | Export runs and writes 0..N-1; progress/report carries a named warning per uncovered clip | ✓ |
| Blocking named error (SND-02 shape) | Export stops with a named errorMessage until the gap is fixed | |
| Sidecar file only | Sidecar JSON diagnostic, no in-app surfacing | |

**User's choice:** Non-blocking named warning, with placement.
**Notes:** Deliberately NOT the SND-02 fail-closed shape. SND-02 throws because an undecodable clip is broken data that would be silently dropped from the mix. A gap is a valid compositional state the user may intentionally want (clip ends, paper / other layers continue) — blocking would withhold a deliverable by design. The law says "export diagnostic", not "export abort". Export still runs and writes 0..N-1 (export length law unchanged). The export progress / completed report carries a named warning per uncovered visible clip, e.g. `video "nebula.mov" does not cover frames 16..17` — clip name and exact range always in the message. Channel: a `warnings` array on the export progress/result, NOT the `exportStore` error status (that one aborts). Surfaced in the existing export UI — no new notification system. Same coverage source as the timeline marker: the resolver's skip region. Timeline and export can never disagree about what a gap is.

## I-5 per-clip extrapolation property

### Q1 — Where does the HOLD/LOOP property live?

| Option | Description | Selected |
|--------|-------------|----------|
| On the Sequence (clip) | `extrapolation: 'hold' \| 'loop'` beside `inFrame`/`outFrame` | ✓ |
| On the Layer | Property on the Layer inside the sequence | |
| Project-level global | One project setting applying to every clip | |

**User's choice:** On the Sequence (clip).
**Notes:** The clip is what the user resizes and what Law 1 names ("per-clip extrapolation choice"). `resolveOverlaySample(clip, globalFrame, N)` reads `clip.extrapolation` as its I-5 input; `exportRenderer` and `previewRenderer` never branch on HOLD/LOOP themselves (I-1 single-resolver law — one policy site, zero forks). Content-overlay sequences carry one primary layer today, so clip grain is the correct grain: no per-layer policy, no per-layer gap ranges. Factories default `'hold'`. Loader maps an absent field to `'hold'`. One store setter writes the user's explicit choice (undo action + `markDirty`, same shape as `setInOut`). Layer-level would fork the resolver for a multi-layer future that does not exist yet; project-global violates Law 1 and forbids a held clip coexisting with a looped one on the same timeline. UAT: one timeline with a HOLD clip and a LOOP clip side by side, both behaving per-clip in preview AND export.

### Q2 — How is the choice surfaced?

| Option | Description | Selected |
|--------|-------------|----------|
| Two-state control in inspector | "Hold last frame" / "Loop" in `SidebarProperties` next to the clip range | ✓ |
| Clip context menu only | Right-click the clip bar → Hold / Loop | |
| Both surfaces | Inspector control AND timeline context menu | |

**User's choice:** Two-state control in the content-overlay inspector (`SidebarProperties`), next to the clip range (in/out).
**Notes:** Labels follow the physics-paint left-sidebar naming style: "Hold last frame" / "Loop", default Hold. No new panel, no timeline context menu (a Law-1 property must not hide behind right-click), no dual surface to keep in sync. One store setter for the toggle (undo/redo + `markDirty`, same shape as `setInOut`). Gap-tail interaction pinned: a LOOP clip never shows the hatched tail inside its own source repeat — the tail exists only past an authoritative out (Law 3), independent of extrapolation. Untrimmed clips (absent `outFrame`) never gap, HOLD or LOOP. UAT: toggling the control changes preview and export behavior on the next frame; undo restores the previous choice.

### Q3 — Default on create and on load of an existing .mce?

| Option | Description | Selected |
|--------|-------------|----------|
| HOLD everywhere, explicit LOOP write | Every clip is HOLD unless the user explicitly sets LOOP | ✓ |
| Legacy files keep looping | New clips HOLD; loaded .mce with no property keeps modulo-loop | |

**User's choice:** HOLD everywhere, explicit LOOP write.
**Notes:** Every clip — newly created, newly imported, and loaded from an existing .mce — is HOLD unless the user explicitly sets LOOP on that clip. In-memory the field is required and the factories default `'hold'`; the loader fills `'hold'` when an old .mce has no field (no legacy branch, no implicit-LOOP shim — clean break per no-backward-compat). Accepted consequence: a pre-53.1 project that relied on the silent modulo-loop (the nebula workaround) opens as HOLD; the user re-chooses LOOP once, and that choice must persist across save → close → reopen. Option 2 "legacy files keep looping" is exactly the silent default Law 1 was written to kill, and it needs a version branch — rejected. UAT: open a pre-53.1 .mce whose clip relied on the modulo-loop → it HOLDS; set LOOP; save; close; reopen → still LOOP.

## I-3 playhead clamp + tick-N presentation + inspector

### Q1 — Where does the playhead N-clamp live, and who maps N → END STATE?

| Option | Description | Selected |
|--------|-------------|----------|
| Clamp 0..N at store; preview maps N→N-1 | Store boundary only; one END-STATE line at the preview render boundary | ✓ |
| Store holds N; each consumer maps | Each consumer (preview, audio, export) special-cases N→N-1 | |
| Separate `atEnd` flag | `currentFrame` stays 0..N-1; a flag signals the boundary | |

**User's choice:** Clamp 0..N at the store; preview maps N→N-1 (END STATE).
**Notes:** The clamp ceiling becomes N inclusive at the STORE BOUNDARY ONLY: `timelineStore.seek`/`stepForward` `upper = max` (`timelineStore.ts:86-103` — not `max-1`); `frameFromX`'s `maxFrame` default becomes `totalFrames` (`TimelineRenderer.ts:1552-1560` — not `totalFrames-1`) so scrub can land on tick N. `resolveTimelinePointerFrame` floor math stays byte-untouched (260918-s52 law). END STATE mapping is exactly one line at the preview render boundary (`previewRenderer`): `renderFrame = playhead >= N ? N-1 : playhead`. Export still writes 0..N-1 and never sees N. Audio needs no N branch — playhead N is simply the end of the timeline (offsetSeconds at N = sequence end, nothing starts). No `atEnd` flag (option 3 forces every read site to check it); no per-consumer N fork (option 2 is the I-1 divergence class again). Edge pinned: if N shrinks below the current playhead, clamp down to the new N; if N grows while the playhead sits on N, the playhead stays on the end limit. Empty timeline (N=0) keeps today's empty render. UAT: scrub/step onto tick N → preview shows the last frame's result (END STATE), not black and not a phantom frame; export still writes 0..N-1; play from N does not crash.

### Q2 — How does the ruler present tick N?

| Option | Description | Selected |
|--------|-------------|----------|
| End marker, no number at N | Taller tick stroke + small horizontal cap, NO numeric label | ✓ |
| Styled number at N | Number at N, dimmed/italic | |
| Time label at N | Time value (e.g. `1.13s`) instead of a frame number | |

**User's choice:** End marker, no number at N.
**Notes:** Ruler ticks 0..N-1 keep their frame numbers exactly as today. Tick N draws a distinct END LIMIT: a taller tick stroke with a small horizontal cap (end-of-timeline shape), NO numeric label and NO time glyph. `drawRuler` gets a single `isEndLimit` branch on the last tick (`f === N`) — the only behavioral change in the ruler loop; every other tick is byte-unchanged. Tick N still exists as a legal playhead position (I-3 clamp) — the marker is display-only. "End limit, not a frame number" literally: a styled number at N (option 2) still asserts "frame N exists", which is the bug being fixed; a time label at N (option 3) mixes units on a frame ruler where every other tick is a frame index. UAT: ruler reads 0,1,…,N-1 as frame numbers and N as a capped end marker only; the playhead can sit on that marker; no numeric N label survives anywhere on the ruler.

### Q3 — How does the inspector "show the law"?

| Option | Description | Selected |
|--------|-------------|----------|
| Coverage law text in the overlay inspector | Range line + tail-state line in `SidebarProperties`, derived from the resolver | ✓ |
| Sequence-end readout only | Read-only line showing N and playhead position in END-STATE terms | |
| No inspector change | Hatched tail + ruler end marker are the law's display | |

**User's choice:** Coverage law text in the content-overlay inspector (`SidebarProperties`), same panel as the new Hold/Loop control.
**Notes:** One compact per-clip readout, derived from the I-1 resolver state (never a second computation): range line `0 → 16 (exclusive)` — restates the unchanged `outFrame` law; tail state line `Follows sequence end` when `outFrame` is absent (untrimmed), OR `Ends at 16 · sequence runs to 17` when trimmed — and when N > out, the gap is NAMED in that same line, matching the hatched tail range and the export warning text (same coverage source as the resolver skip region, so the three surfaces cannot diverge). No separate playhead/end readout (option 2): the playhead is transient state, not clip law — Law 4 is already legible on the canvas and the ruler end marker. No "no inspector change" (option 3): the stated goal is that the inspector shows the law, and this is where the user edits the clip. UAT: untrimmed clip reads "Follows sequence end"; trimmed clip with N past out reads "Ends at 16 · sequence runs to 17" and names the gap — identical range to the hatched tail and the export warning.
