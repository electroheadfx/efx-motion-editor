# Phase 38.1: Code Review Report

**Reviewed:** 2026-07-28T20:08:49Z  
**Depth:** standard  
**Files Reviewed:** 29  
**Status:** issues_found

## Summary

The current Phase 38.1 review found three blocker-level correctness defects and two warnings. Cached playback can render the wrong Roto background, `stopPhysics()` can finalize the wrong physics mode, and capacity-only physical timeline replacements can be silently ignored. Optional profiling storage access can abort Studio rendering in restricted environments, and the central persistent-canvas contracts are protected primarily by source-text assertions rather than runtime behavior tests.

No exploitable security vulnerability was identified. No source or test files were modified during review.

## Blocker Issues

### BL-01: Cached playback violates the Roto background contract

**File:** `app/src/components/physic-paint/view/PhysicsPaintStudioView.tsx:47-60`

**Evidence:** The playback background subscribes using `props.background.background` as the paper texture, unconditionally fills the canvas with `props.background.color ?? '#ffffff'`, and never applies `paperGrain` or `grainStrength`.

Consequently:

- `background: 'transparent'` renders white instead of remaining transparent.
- `paperGrain` can differ from the background mode but is not rendered.
- `grainStrength` appears in the effect dependencies but has no effect on pixels.

This conflicts with the canonical metadata contract in `app/src/types/physicPaint.ts:401-408` and the background resolver/compositor in `app/src/lib/rotoFrameDraw.ts:54-75,93-124`, which treats transparency, paper texture, paper grain, and grain strength as distinct inputs.

**Impact:** Cached playback can display a visibly different composite from the live canvas, preview, or exported Roto result. Transparent projects are especially affected because playback inserts an opaque white background.

**Fix:** Route cached playback through the shared Roto background instruction/compositing seam instead of duplicating it in the view. At minimum, leave transparent canvases cleared, resolve the intended paper source from the complete metadata, and apply `paperGrain` and `grainStrength` consistently.

Add behavior coverage for both:

```ts
{ background: "transparent", paperGrain: "canvas1", grainStrength: 0 }
{ background: "canvas2", paperGrain: "canvas3", grainStrength: 0.65 }
```

### BL-02: `stopPhysics()` restores the mode before finalizing the session

**File:** `packages/efx-physic-paint/src/engine/EfxPaintEngine.ts:708-750`

**Evidence:** `startPhysics()` records the prior mode and installs the requested session mode at lines 613-618. However, `stopPhysics()` restores `savedPhysicsMode` at line 717 before:

- Testing for the session's `last` mode at line 720.
- Recording `physicsMode` in the replay action at line 750.

A normal `startPhysics("last")` session therefore reaches the mode test with the restored prior mode, usually `local` or `null`. The selective last-stroke synchronization branch is skipped, and the replay action records the restored mode rather than the mode that actually ran.

**Impact:** Last-stroke physics can overwrite the complete saved wet layer instead of updating only the affected stroke, and deterministic replay metadata no longer describes the completed physics session.

**Fix:** Capture the completed session mode before restoring state, then use that captured value for finalization and action recording:

```ts
const completedMode = this.state.physicsMode;

// Finalize using completedMode.

this.state.physicsMode = this.savedPhysicsMode;
```

Add a test for `startPhysics("last")` followed by `stopPhysics()` proving unrelated `savedWet` pixels remain unchanged and the recorded action uses the completed mode.

### BL-03: Capacity-only physical replacements are incorrectly discarded as no-ops

**File:** `app/src/stores/physicPaintStore.ts:1202-1225`

**Evidence:** The no-op test at line 1207 compares revisions produced only from records and interpolation. Capacity is not included. When records and interpolation are unchanged but capacity differs, the method returns success before:

- Clamping the physical cursor at line 1221.
- Updating `_rotoPhysicalCapacity` at line 1222.
- Incrementing `rotoPhysicalRevision` at line 1224.
- Publishing the visible change at line 1225.

The structural cache explicitly treats capacity as part of its identity contract in `app/src/stores/physicPaintStore.ts:105-123`, confirming that capacity is structural state rather than incidental metadata.

**Impact:** The caller receives `{ ok: true }`, but the requested capacity and derived projection are not installed. A cursor can remain outside the requested smaller capacity, and subscribers receive no structural revision or visual notification.

**Fix:** Include the previous capacity in the no-op condition:

```ts
const previousCapacity = this.getRotoPhysicalCapacity(layerId);

if (
  _rotoRealKeyRecords.has(layerId)
  && previousRevision === nextRevision
  && previousCapacity === capacity
) {
  return { ok: true };
}
```

Add a regression test that replaces identical records and interpolation with a different valid capacity and verifies capacity, cursor clamping, projection, and revision publication.

## Warning Issues

### WR-01: Profiling storage access can abort Studio rendering

**File:** `app/src/components/physic-paint/performance/physicsPaintPerformanceTrace.ts:82-85`

**Evidence:** `profilingEnabled()` directly accesses `window.localStorage` and calls `getItem()`. Either operation can throw a `SecurityError`, including in restricted, sandboxed, or storage-disabled contexts. Optional chaining does not catch exceptions from the property getter or method call.

Performance counters are invoked directly during Studio and child-component rendering, including `app/src/components/physic-paint/view/PhysicsPaintStudioView.tsx:155-157`. A storage exception can therefore abort the render path even though profiling is optional.

**Fix:** Fail closed:

```ts
function profilingEnabled(): boolean {
  if (typeof window === "undefined" || !import.meta.env.DEV) return false;

  try {
    return window.localStorage.getItem(PROFILE_STORAGE_KEY) === "1";
  } catch {
    return false;
  }
}
```

Add tests for both a throwing `localStorage` getter and a throwing `getItem()` implementation.

### WR-02: Persistent-canvas tests verify source spelling rather than runtime behavior

**Files:**

- `app/src/components/physic-paint/engine/PhysicsPaintCanvasMount.test.ts:23-144`
- `app/src/components/physic-paint/PhysicsPaintStudio.test.ts:215-239`

**Evidence:** The tests load implementation files with `readFileSync` and assert string fragments or regular expressions. They do not mount the Preact components or verify that:

- Parent rerenders preserve the mounted engine/canvas instance.
- Navigation-only changes do not rerender or remount the canvas.
- Updated callback props reach stable forwarders.
- Structural dimensions or `canvasKey` changes cause the intended lifecycle transition.
- Lifecycle and observer cleanup occurs exactly once at runtime.

The current tests can pass after behavior is broken by a semantically significant refactor, or fail after a behavior-preserving formatting change.

**Impact:** The phase's central persistent-boundary and callback-freshness guarantees are weakly protected, increasing regression risk around engine ownership and canvas remounting.

**Fix:** Retain a small source-level architecture check only where an exact source constraint is intentional, but add runtime Preact tests using a mocked `EfxPaintCanvas`. Assert mount/unmount counts, instance identity across rerenders, callback freshness, and keyed remount behavior.
