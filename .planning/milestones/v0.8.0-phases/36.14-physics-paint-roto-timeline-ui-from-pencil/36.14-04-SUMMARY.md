## Decisions Made
- Coordinator owns snapshot/stage/send/match/restore; Studio no longer captures local move snapshots or applies local ownership
- Bridge result routing: apply result controller delegates `replace-roto-physical-map` to `coordinator.consumeBridgeApplyResult`; other kinds use existing `matchApplyResult`
- `useRotoApplyLifecycle` retains non-physical apply handling and routes physical results to `ignore` so the coordinator owns them exclusively
- History consumer fed via effect on `coordinator.acceptedOutput`, translating `RotoPhysicalEditSnapshot` (records) to `RotoKeyMoveSnapshot` (cache frames); Plan 05 replaces with generic accepted-only history
- Pragmatic replay lookup: snapshot stores real-key cache frames without keyId; replay re-derives keyId from current store records by appFrame. Plan 05 will replace this consumer with generic history keyed by stable identity
- Buffer port uses `unknown` value types for `frameStates`/`previewFrames`/`capturedFrames` since the coordinator does not interpret map values (only captures and restores them)

## Issues Encountered
- The existing `RotoKeyMoveSnapshot` stores `realKeyFrames: PhysicPaintRotoCacheFrame[]` (which has no `keyId` field), while the coordinator's `RotoPhysicalEditSnapshot` uses `records: PhysicPaintRotoRealKeyRecord[]` (which carries `keyId`). The history effect translates records → cache frames via `physicPaintStore.getRotoCacheFrames(layerId)` after the store replacement. The replay callback re-derives `keyId` from current store records by `appFrame`. This is a pragmatic compromise documented inline; Plan 05 will replace the history consumer with generic accepted-only history keyed by stable identity.
