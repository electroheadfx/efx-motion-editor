## Phase Goal

**As a** stop-motion animator, **I want to** have every real Roto key, generated in-between, timeline edit, persisted frame, and rendered output use one deterministic physical-frame authority, followed by a polished timeline UI that exposes the approved behavior without duplicating business logic, **so that** editing, reopening, previewing, and exporting the same Roto work cannot disagree about frame identity.

<objective>
Implement the pure physical timeline resolver that orders stable identities, derives exact interior generated cells, resolves complete Insert/Delete/Drag/Force Spacing proposals, validates uniqueness/range/capacity, and returns deterministic selection and presentation metadata from one authority used by preview and commit.

Purpose: Concentrate all physical edit semantics behind one small deterministic interface so later store, coordinator, action, persistence, rendering, and view plans consume validated complete proposals instead of reproducing timing rules.

Output: One dependency-free production module containing the closed edit intent/result contracts and the immutable resolver implementation for all approved single-key physical operations.
</objective>

<assumptions>
- `capacity` is the number of legal physical slots, must be an integer from `1` through `PHYSIC_PAINT_MAX_APPLY_FRAMES`, and therefore defines the inclusive physical range `0..capacity - 1`. This makes range and capacity validation explicit instead of relying on caller convention.
- The resolver receives identity placement only (`keyId`, `appFrame`), not rendered payload. Payload ownership therefore cannot be transferred or mutated by this module; later plans reconstruct payload-bearing snapshots by matching `keyId` against the complete proposal.
- Delete of the only real key is valid and yields an empty complete mapping with null selection. Otherwise Delete selects the original successor that ripples into the removed slot, or the previous surviving identity when no successor exists.
- A Drag physical-cell target denotes the desired final `appFrame`. It is accepted for an originally empty/generated cell and for the moved key's own current cell; another real key must be addressed by `before-key` or `after-key`. If closing the source slot causes a remaining key to occupy the requested final cell, opening that final slot shifts that key and every later key right rather than overwriting it.
- Dragging to the moved key's own physical cell or Force Spacing an already exact sequence is a valid immutable no-change proposal with `changed: false`; targeting the moved identity through an occupied before/after boundary is invalid because that boundary disappears during the cut.
- Force Spacing requires at least one real key because the first identity is the anchor. Its intent carries the current selected identity or null so the resolver can preserve selection without reading store state.
- No new dependency, external integration, package-manager install, server process, or source file beyond the declared resolver is required. If execution disproves this, stop and record an assumption delta rather than widening the plan.
</assumptions>

## Trust Boundaries

| Boundary | Description |
|---|---|
| Caller identity placement → resolver | Store/controller-provided IDs, frames, interpolation flag, and capacity enter the physical authority and may be malformed or stale. |
| Pointer/action intent → resolver | Direct cells, occupied boundaries, spacing values, and affected IDs can request invalid, forged, or over-capacity edits. |
| Resolver proposal → preview/commit callers | Downstream code relies on one complete immutable result; a partial or internally inconsistent proposal would corrupt multiple consumers. |

## Abuse Cases — OWASP ASVS L1

| Abuse case | Expected disposition |
|---|---|
| Duplicate or forged identity/frame input attempts to make two payloads share one physical slot. | Reject before operation resolution and return no proposal. |
