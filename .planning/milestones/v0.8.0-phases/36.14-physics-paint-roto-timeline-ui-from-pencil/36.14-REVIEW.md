# Phase 36.14: Code Review Report

**Reviewed:** 2026-07-25
**Depth:** standard

## Summary

Reviewed the complete physical-frame Roto contract: canonical model/validators, resolver, acknowledged coordinator, history, timeline actions, Studio composition, bridge/parent authority, persistence, preview/export render paths, and workflow views. The physical contract itself (validators, resolver, coordinator settlement matching, replay provenance) is thorough and consistently fail-closed. The defects found are at the edges: a broken export-resume path, an alpha-canvas registry poisoning in the Play Script renderer, a silently bypassed mutation-lock guard, an unguarded throwing action reachable from the keyboard, and a stuck-busy edge in the script clipboard navigation lock. Deliberately retired contracts (source/display projection, launch-level `rotoBackground`, `initialFps`, live in-between count authority) and dormant approval-gated modules (`useRotoPersistenceIntegration.ts`, legacy throws in `rotoLaunchHydration.ts`) were not flagged, per phase context.

## Critical Issues

### CR-01: Export resume wipes `outputPath` before the reuse check, splitting resumed exports into a new directory

**File:** `app/src/lib/exportEngine.ts:89-110`
**Issue:** `startExport(startFromFrame)` calls `exportStore.resetProgress()` at line 89, which (per `app/src/stores/exportStore.ts:94-99`) resets `resumeFromFrame: null, outputPath: null`. Only afterwards does the resume branch at lines 100-101 test `startFromFrame > 0 && exportStore.progress.peek().outputPath` — which can now never be non-null. The resume-with-existing-directory path is dead code: every resumed export creates a fresh timestamped directory, so frames `0..resumeFromFrame-1` stay in the old directory while resumed frames land in the new one. For video formats, the FFmpeg glob encode at lines 324-334 then runs in a directory missing the earlier frames, producing a truncated video or an encode failure. Resume is effectively broken as designed.
**Fix:** Capture the previous output path before resetting, or make `resetProgress()` preserve `outputPath`/`resumeFromFrame`:
```ts
const priorOutputPath = startFromFrame > 0 ? exportStore.progress.peek().outputPath : null;
exportStore.resetProgress();
...
let exportDir: string;
if (startFromFrame > 0 && priorOutputPath) {
  exportDir = priorOutputPath;
} else {
  const dirResult = await exportCreateDir(settings.outputFolder);
  ...
}
```

### CR-02: Play Script renderer zeroes the merged canvas after registering it in the shared alpha-canvas registry

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptRenderer.ts:73-80` (via `app/src/components/physic-paint/roto/rotoCanvasFrames.ts:121-126,166-174`)
**Issue:** Each staged frame is encoded with `encodeRotoFrameFromCanvas(merged, destination, input.size)`. Because `mergeRotoAlphaCanvases` (`physicsPaintRotoAlphaMerge.ts:20-38`) returns a canvas already sized `input.size`, `drawCanvasAtSize` returns the same `merged` canvas, and `registerRotoAlphaCanvasFrame(dataUrl, outputCanvas)` stores that exact canvas in the persistent `_rotoAlphaCanvasRegistry` (`physicPaintStore.ts:55-60`). The renderer's `finally` block then calls `releaseCanvas(merged)`, setting `width = height = 0` and wiping its pixels. The registry is left mapping every staged frame's dataUrl to a blank 0x0 canvas in the standalone (child) window. `physicPaintStore.getRotoPhysicalRenderSource` in `blend` mode reads exactly this registry (`_blendRegisteredAlphaCanvasDataUrl`, physicPaintStore.ts:447-466), so generated in-between frames render blank after a Play Script commit in blend mode until the layer is rehydrated. (`registerRotoAlphaCanvasFrameFromDataUrl` with an expected size would re-register because the zeroed canvas fails the size check, but no such re-preparation runs in the child after commit.) Releasing `scriptAlpha` has the same hazard if the engine reuses its progressive-alpha canvas across loop iterations.
**Fix:** Do not release a canvas that has been registered. Either release only when the canvas was not registered, or register a copy:
```ts
const encoded = await encodeRotoFrameFromCanvas(merged, destination, input.size);
staged.push({ ...encoded, frameIndex, appFrame: destination, source: 'real-key' });
...
finally {
  if (scriptAlpha) releaseCanvas(scriptAlpha);
  // Do NOT releaseCanvas(merged): it is registered in the alpha-canvas registry.
}
```
Alternatively have `encodeRotoFrameFromCanvas`/`buildRotoFrameFromCanvas` register an internally owned copy and document that the caller retains release ownership.

## Warnings

### WR-01: Unbound `mutationLocked.peek` silently disables the mutation-lock guard in engine actions

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:305`
**Issue:** `usePhysicsPaintEngineActions` receives `isMutationLocked: rotoScript.mutationLocked.peek` — the unbound `Signal.prototype.peek` method. The consumer invokes it as `input.isMutationLocked?.()` (`usePhysicsPaintEngineActions.ts:14,126`), so `this` inside `peek` is the `input` object, not the signal; `this.value` is `undefined`. In signals-core 1.13 (`d.prototype.peek = function(){ ... return this.value ... }`) this returns `undefined` rather than throwing, so `canMutate` always evaluates the lock as false. Tool selection, brush parameter changes, and physics start/stop therefore ignore the script-operation mutation lock at the hook layer (the engine's own `setInputLocked` still guards strokes, which limits blast radius but makes this failure silent). Every other call site in this file correctly wraps the call (`() => rotoScript.mutationLocked.peek()`, e.g. lines 619, 669, 851).
**Fix:** Wrap the call like the other sites:
```ts
} = usePhysicsPaintEngineActions({ engine, settings, setSettings, isMutationLocked: () => rotoScript.mutationLocked.peek() });
```

### WR-02: Keyboard Delete (and any unguarded Insert/Delete caller) throws an uncaught exception when no real key is selected

**File:** `app/src/components/physic-paint/hooks/useRotoTimelineActions.ts:545-551,280-298`; reachable via `app/src/components/physic-paint/PhysicsPaintStudio.tsx:821` and `app/src/components/physic-paint/view/physicsPaintStudioKeyboard.ts:98-101`
**Issue:** `insertRotoFrame`/`deleteRotoFrame` call `ensureSelectedKeyId(input)`, which throws `'No selected Roto key.'` synchronously when `selectedKeyId` is null. UI buttons are guarded by `canInsertFrame`/`canDeleteFrame`, but the keyboard dispatcher is not: `isPhysicsPaintRotoDeleteTarget` returns true for a focused `.physics-paint-roto-cell.current` regardless of whether that cell is empty or generated, and `actions.deleteRotoKey()` is invoked unconditionally. Pressing Backspace/Delete on an empty or generated current cell therefore throws an uncaught exception inside the keydown handler — no status message, console noise, and inconsistent with every other action in this bundle, which publish a status and return `false`.
**Fix:** Return `false` with a published status instead of throwing:
```ts
const insertRotoFrame = useCallback((): Promise<boolean> => {
  const selectedKeyId = input.getSelectedKeyId?.() ?? null;
  if (!selectedKeyId) {
    input.publishStatus?.('Select a real Roto key to insert.');
    return Promise.resolve(false);
  }
  return runPhysicalAction({ intent: { kind: 'insert-slot', selectedKeyId }, ... });
}, [runPhysicalAction, input]);
```
(same for `deleteRotoFrame`), or guard at the keyboard dispatcher with `rotoPhysicalActions.canDeleteFrame.value`.

### WR-03: `completeNavigation` leaks the pending-operation count when the engine is gone, permanently wedging the script controller busy

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoScriptClipboard.ts:743-758`
**Issue:** `prepareNavigation` increments `pendingOperationCount` and sets `busy` via `beginOperation(engine)`. `completeNavigation` only calls `endOperation(engine)` when `engineState.peek()` is non-null:
```ts
function completeNavigation(): void {
  if (!navigationLockHeld) return;
  navigationLockHeld = false;
  const engine = engineState.peek();
  if (engine) endOperation(engine);
}
```
If the engine was replaced or torn down between prepare and complete (`updateEngine(null)` / engine lifecycle teardown), `endOperation` never runs: `pendingOperationCount` stays >= 1, `busy` stays true, `mutationLocked` stays true, the old engine stays in `lockedEngines` with input locked, and `setNavigationLocked(true)` is never released. Every subsequent copy/apply/navigation is rejected by the busy guard with no recovery short of controller disposal.
**Fix:** Track the engine captured in `prepareNavigation` and always end that operation:
```ts
let navigationLockEngine: RotoScriptEnginePort | null = null;
// prepareNavigation: navigationLockEngine = engine; beginOperation(engine);
function completeNavigation(): void {
  if (!navigationLockHeld) return;
  navigationLockHeld = false;
  const engine = navigationLockEngine ?? engineState.peek();
  navigationLockEngine = null;
  if (engine) endOperation(engine);
}
```

### WR-04: Browser-fallback launch serializes the full physical document (including every PNG dataUrl) into the window URL

**File:** `app/src/lib/physicPaintBridge.ts:1207-1213`
**Issue:** `buildPhysicsPaintUrl` sets `context` as a URL search param containing `JSON.stringify(context)`. The canonical launch context embeds `rotoPhysical.records[*].payload.dataUrl` — one base64 PNG per real key — so the URL grows by megabytes as soon as a layer has a handful of Roto keys (payloads up to the 64 MB validator limit each). Browsers and `window.open` impose practical URL length limits (roughly 2 MB in Chromium, less elsewhere); beyond that the fallback launch fails or truncates silently, and `openBrowserFallback` reports only "window was blocked or could not be opened". `parsePhysicsPaintLaunchContext` on the other side then cannot reconstruct the context.
**Fix:** Do not place payloads in the URL. Hand off the context out-of-band — e.g. `sessionStorage`/`localStorage` keyed by `operationId`, an opener `postMessage` exchange (the channel already exists), or the Tauri-native command path exclusively — and keep only the operation ID in the URL.

### IN-02: Render-phase side effects in the Studio composition

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:238-244,706-726,788-814`
**Issue:** `rotoScript.updateEngine(...)`, `rotoScript.updateSource(...)`, `rotoNavigation.configureRuntimePort(...)`, `rotoNavigation.configureDisplayPort(...)`, and `physicalEditCoordinatorRouteRef.current = {...}` all execute during render. They are guarded/idempotent today, but `updateEngine`/`updateSource` can invalidate prepared load-and-apply state and toggle input locks — observable mutations that React/Preact double-render or concurrent rendering could interleave. Port wiring belongs in an effect.
**Fix:** Move these calls into `useEffect` keyed on the relevant identities (engine instance, source snapshot, coordinator handle).

### IN-04: Unbounded growth of operation ledgers in the bridge

**File:** `app/src/lib/physicPaintBridge.ts:90-111,208,705`
**Issue:** `deliveredOperations` and `acceptedPhysicalCommands` are module-level Maps that only ever gain entries (one per apply operation and per accepted history-bearing physical command). Over a long session with heavy Roto editing (each entry carries complete before/after record sets with dataUrl strings) these grow without bound.
**Fix:** Cap with an LRU/eviction (e.g. keep the most recent N entries per layer), or clear per-launch entries when `activeLaunchOperationByLayer` is replaced.

### IN-05: Scrollbar thumb can exceed the track width and produce negative offsets

**File:** `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:406-413`
**Issue:** `thumbWidth = Math.max(120, (clientWidth / scrollWidth) * clientWidth)`. When `clientWidth < 120`, `thumbRange = clientWidth - thumbWidth` is negative, so `left = (scrollLeft / scrollRange) * thumbRange` goes negative as the user scrolls, pushing the thumb off-track.
**Fix:** `const thumbWidth = Math.min(clientWidth, Math.max(120, ...))` (and guard `thumbRange > 0`).

### IN-06: `dispatchAndWaitForAccepted*` polling helper duplicated in two modules

**File:** `app/src/components/physic-paint/PhysicsPaintStudio.tsx:1031-1057` and `app/src/components/physic-paint/hooks/useRotoPlayScriptController.ts:142-165`
**Issue:** Two near-identical implementations of the same pending/accepted polling wait (subscribe, dispatch, 5.5 s deadline loop). They can drift independently; the Play Script one is already exercised by tests.
**Fix:** Export one shared helper (e.g. from `useRotoPlayScriptController.ts` or a small bridge-await module) and use it in both places.

### IN-07: Physical selector failure branch returns a non-empty "empty view"

**File:** `app/src/components/physic-paint/roto/rotoTimelineSelectors.ts:242-259`
**Issue:** When the projection fails, `selectRotoPhysicalTimelineView` returns `orderedRealKeyRecords: realKeyRecords` (the full unvalidated input) while every other field claims an empty, selection-less view. Callers reading `orderedRealKeyRecords` alone would see keys the view simultaneously reports as absent from cells/ordered IDs — an internally inconsistent fail-closed state.
**Fix:** Return `orderedRealKeyRecords: []` in the failure branch (or document why the raw records are intentionally retained).
