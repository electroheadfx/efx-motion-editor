# Phase 36.14 Plan 05: Accepted-only physical history, Undo/Redo through shared coordinator

**Generic accepted-only physical command ledger with coordinator-backed Undo/Redo, identity-changing replay provenance, and deleted move/apply wrappers — one stable ports/listener/coordinator settlement path**

## Performance

- **Duration:** ~90 min
- **Started:** 2026-07-21T13:08Z
- **Completed:** 2026-07-21T17:28Z
- **Tasks:** 3
- **Files modified:** 8 (created 1, modified 7, deleted 3 + 1 stale test)

## Accomplishments
- Replaced the move-only command ledger with `useRotoPhysicalEditHistory` — the single generic accepted-only physical-edit command ledger that records one immutable complete command per matching accepted ordinary edit, preserves existing paint barriers, duplicate suppression, ten-level per-brush reconciliation, and one availability Signal publication.
- Routed Undo/Redo through the same coordinator execute seam with new `undo`/`redo` operation kinds; peek without mutating stacks, require no pending coordinator operation, validate current revision against the command's expected side, then move the command between applied/redo only on matching acceptance.
- Added `PhysicPaintRotoPhysicalEditReplayProvenance` (historyCommandId, historyDirection, sourceRevision, targetRevision) and required it on undo/redo payloads/results while forbidding it on ordinary kinds; parent canonical accepted-operation ledger validates replay provenance against the original command before any mutation.
- Finalized `rotoCoordinatorPorts.ts` as the stable complete publication/parent/rollback/result/selection/status/source-revision interface.
- Moved the retained bridge-result intake and lifecycle responsibilities from `rotoApplyTransactions.ts` and `useRotoApplyLifecycle.ts` into `usePhysicsPaintApplyResultController.ts` (sole external bridge subscription, exact active-tuple matching for non-physical kinds) plus `useRotoPhysicalEditCoordinator.ts` (inline physical-edit result transition and pending-record constructor).
- Deleted `useRotoKeyMoveHistory.ts` (Task 1), `rotoApplyTransactions.ts`, `useRotoApplyLifecycle.ts`, and the stale `rotoApplyTransactions.test.ts` wrapper test after every importer consumes the final owners directly. No forwarding export, alias, second subscription, or operation-specific settlement function remains.
