## Summary

The core of the phase — the 37x fillFlat layering deletion, the R7-amended `drawBristleFootprint` capsule-sweep deposit (one fill per fibre at `STREAK_ALPHA`), the seeded tier-independent lane layout in `footprintLanes.ts`, the single-pipeline pickup path (261002-fpi), and the deferred-finalization phase machine in `EfxPaintEngine.ts` — is internally consistent and heavily pinned by source-shape gates, measure-first substrates, and contract tests. No security issues were found: no secrets, no eval/injection surfaces, the DEV capture hook is `import.meta.env.DEV`-gated with a whitelisted label, and all test globals are restored in `finally`.

The one critical finding is in the phase's own acceptance harness: the D-08 tier-parity capture (`runTierParityCapture`) no longer observes two distinct tier passes — since 260930-wm6 the engine runs a single `tier='final'` continuation, so the "live plane" and the "final plane" it compares are two reads of the same final-tier offscreen taken after the transfer. `tierParityPasses` therefore returns `true` unconditionally; the D-08 acceptance row cannot fail regardless of footprint behavior. Secondary findings: a non-idempotent monkey-patch in the seam probes (latent ordering hazard, currently masked by the post-raster dedup guard), and a cluster of dead code left behind by the one-pipeline refactor (unused private method, ignored parameters, three dead exports, a truncated comment).

## Critical Issues

### CR-01: D-08 tier-parity capture compares the final-tier plane against itself — `pass` is unconditional

**File:** `app/src/components/physic-paint/performance/depositSpeckleCapture.ts:1692-1729` (comparison), `:1663-1675` (live-promise wiring), `:1342-1355` (publication listener); root cause spans `packages/efx-physic-paint/src/engine/EfxPaintEngine.ts:2673-2688` and `packages/efx-physic-paint/src/brush/paint.ts:38-50, 601, 655-657`

**Issue:** `runTierParityCapture` documents its evidence as "the live-tier plane at stroke-first-raster-publication, the final-tier plane at the finalize transfer's post-raster read" (depositSpeckleCapture.ts:1588-1599, 1184). Neither of those stages exists as a distinct event anymore:

1. Since 260930-wm6 (ONE PIPELINE), `stepInteractivePaintFinalization` creates exactly ONE continuation with `tier: 'final'` (EfxPaintEngine.ts:2673-2679). The engine never requests `tier='live'` — pinned deliberately by `lookLawDigest.test.ts:137-144` ("the engine must not request tier='live'"). The live-tier display pass the capture was written for was deleted.
2. The generator yields once between footprint and transfer (paint.ts:601), and `step()` returns `true` only when the generator completes (paint.ts:41-45). `'stroke-first-raster-publication'` is recorded only after `active.raster!.step()` returns `true` (EfxPaintEngine.ts:2684-2688) — i.e. **after** `transferToWetLayerClipped` has already read the offscreen via the wrapped `getImageData` (paint.ts:655-657 → wet-layer.ts:452), which is what records the `post-raster` seam field (depositSpeckleCapture.ts:1289-1301).
3. The publication listener then re-reads `state.lastRasterCanvas` — the same final-tier offscreen that was just transferred — and stores it as `state.livePlane` (depositSpeckleCapture.ts:1342-1355).

Consequence: `finalField` (found by tag + seam `'post-raster'` at line 1694) and `livePlane` (line 1695) are two reads of the same buffer with no intervening writes, cropped onto the same rect (both origins come from the same `oc.translate` hook). `computeTierParityMetrics` receives byte-identical inputs → `gapMismatch = 0`, `silhouetteDriftPx = 0`, `newHoleCount = 0`, `centroidDriftPx = 0` → `tierParityPasses` is `true` **by construction**. The row cannot fail even if the footprint deposited garbage — both planes would be identically garbage. The manifest presents fabricated provenance (two "tier passes" that are one pass), and the phase's D-08 acceptance evidence (`tierParity.pass`) is a false green.

The metrics unit tests (depositSpeckleCapture.metrics.test.ts:258-399) exercise the pure comparison functions on synthetic planes and are sound; they do not, and cannot, catch this wiring defect — only the runtime capture is vacuous.

**Fix:** Do not compare two reads of the same buffer. Either:

- **Retire the tier-parity row** for post-260930-wm6 builds and replace it with an explicit attestation that preview == settled == persisted by construction (one pipeline), removing `livePlane`/`finalField`/`tierParityPasses` from the runner; or
- **Capture two genuinely distinct surfaces** if D-08 evidence is still required — e.g. the display composite at the reveal (`completeActiveStrokeFinalization`) vs. the wet alpha after settle — and update the provenance comments, which currently describe tier passes the engine no longer runs.

Either way, the `stroke-first-raster-publication` hook must stop being labeled a "live tier" capture: it fires after the final transfer.

## Warnings

### WR-01: `installSeamProbes` re-wraps every canvas context on each `getContext` call — non-idempotent monkey-patch stacking with order-dependent branch semantics

**File:** `app/src/components/physic-paint/performance/depositSpeckleCapture.ts:1260-1307` (wrap installed per `getContext` call), `:1346` (second `getContext` on the same canvas)

**Issue:** `wrappedCreate` replaces `canvas.getContext` with a closure that, on **every** invocation, captures the ctx's *current* `getImageData`/`translate` as `original*` and installs new wrappers over them (lines 1261-1305). A second `getContext('2d')` on the same canvas therefore stacks wrapper W2 over W1 over the native method, unboundedly. The live-plane read at line 1346 deliberately performs a second `getContext` on `state.lastRasterCanvas`, so at that moment the chain is depth ≥ 2.

With a stacked chain the inner wrapper runs first: it consumes `state.capturingLive` (sets it false, resolves the promise), then the **outer** wrapper's `post-raster` branch (lines 1289-1301) executes — the branch the comments claim must never run for a live read. Today it is saved only by the `capturedRasterForTag` dedup inside `recordSeamField` (line 1203). If the stage order ever shifts (which the stale comments at 1340-1341 suggest the author believed it already had — "before the finalize phase can touch anything"), the outer wrapper would record the wrong plane as `post-raster` and the dedup would then **block the true transfer read**. The correctness of the seam chain currently depends on an accident of ordering plus a dedup guard, not on the patch itself.

**Fix:** Make the wrap idempotent — track patched contexts and skip re-wrapping:

```ts
const wrappedCtx = new WeakSet<CanvasRenderingContext2D>();
canvas.getContext = ((type: string, ...args: unknown[]) => {
  const ctx = originalGetContext(type as '2d', ...(args as []));
  if (!ctx || type !== '2d' || wrappedCtx.has(ctx as CanvasRenderingContext2D)) return ctx;
  wrappedCtx.add(ctx as CanvasRenderingContext2D);
  // ... install translate/getImageData wrappers once ...
  return ctx;
}) as typeof canvas.getContext;
```

### IN-07: Hole definition differs between the defect metrics and the tier-parity scan

**File:** `app/src/components/physic-paint/performance/depositSpeckleCapture.ts:356` (`computeDefectMetrics`: holes only at `a === 0`) vs `:557-565` (`scanTierPlane`: any `a < DH1_INK_FLOOR` interior pixel with 8 ink neighbours)
**Issue:** An interior pixel with alpha 1-3 (sub-floor AA) surrounded by ink counts as an enclosed hole in tier parity but as nothing (mass only) in the defect metrics. The two acceptance metrics therefore disagree on what a "hole" is, and tier parity can report `newHoleCount` for pixels the defect metrics deliberately ignore.
**Fix:** Align the guards (use `a === 0` in `scanTierPlane`, or document why parity treats sub-floor interior pixels as holes and mirror it in `computeDefectMetrics`).

### IN-08: Failed capture runs are cached as resolved `null` — no retry within the engine session

**File:** `app/src/components/physic-paint/performance/depositSpeckleCapture.ts:1753, 1767-1775`
**Issue:** The `.catch(...)` returns `null` and that promise is stored in `dh1Runs`, so a transient failure (e.g. the thrown `'heavy-slow variant missing'` or any unexpected engine error) permanently maps that label to `null` until the engine remounts (`dh1Runs.clear()` only runs from `installDh1CaptureHook`). The documented one-shot rule applies to successful runs; silently caching failures means a user re-invoking `__EFX_DH1_CAPTURE__('green')` after an error gets no data and no second attempt.
**Fix:** Remove the entry on failure so the label is retryable:

```ts
const run = (...).catch((error) => {
  console.error('[dh1] capture failed', error);
  dh1Runs.delete(label);
  return null;
});
```
