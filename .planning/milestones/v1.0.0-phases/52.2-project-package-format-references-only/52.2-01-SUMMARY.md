# Phase 52.2 Plan 01: Package frame-media write/read leg Summary

**Rust-atomic `frames/<layerId>/<keyId>.webp` writes (canonical or staged under the Rust-derived package staging root) with in-Rust SHA-256 digests, a symlink-hardened read-back that distinguishes missing from refused, and the save transaction's separate bound-path guard — exposed through two raw-body Tauri commands and typed TS wrappers.**

## Accomplishments

- A key's raster bytes now land as a real `.webp` file at `<package>/frames/<layerId>/<keyId>.webp`, written atomically (sibling temp + `rename` + directory fsync) and returning the canonical relative path, the SHA-256 of the written bytes, and the byte length.
- Staged mode writes into `<package>/<staging-basename>/frames/...` while the canonical tree stays untouched and the returned path stays canonical — the save path plan 05/07 depends on; the staging root is always derived in Rust from a validated basename.
- The read-back leg (genuinely new — nothing reads a webp sidecar today) returns byte-identical bytes plus the digest computed from disk, and closes the T-52.2-02 hole: RED evidence showed the Task 1 read *following an escaping symlink and returning the outside file's bytes*; the hardened read canonicalizes the leaf, re-checks `starts_with(package_root)`, requires `is_file()`, and re-checks `.webp`.
- Two guards that stay separate by construction: the media lock accepts exactly `frames/` + `.webp`, while `resolve_package_bound_path` carries the transaction's file set (`project.mce`, `layers/<id>.json`, `frames/*.webp`) and delegates every `frames/` entry back to the media code path — asserted on both the accept and the reject side.
- `ipcEfxPaintWriteFrameMedia` / `ipcEfxPaintReadFrameMedia` give later plans a typed boundary: `{ kind: 'missing' }` (Phase 49 slate) vs `{ kind: 'refused', rejection }` (fail closed) vs `{ kind: 'io' }`, with bytes crossing as `Uint8Array` on both legs.

## Decisions Made

- The media/bound guard split is enforced by delegation, not duplication: the bound-path guard is existence-agnostic (a save binds paths that may not exist yet), while the read leg alone canonicalizes the leaf — which is what keeps symlink refusal in one place.
- Rejection labels are the only thing serialized on failure (`pathEscape`, `unsafeId`, `wrongExtension`, `notARegularFile`, `unsupportedPackagePath`, `missing`, `io`), per T-52.2-03's accepted disposition.
- Task 3's test set named the plan's five read behaviors; two of them (Missing, digest-from-disk) already held in the Task 1 slice and are kept as regression pins, so Task 3's RED is carried by the two genuinely new security behaviors.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `tauri::ipc::Response` has no header support — read leg returns a base64 envelope**
- **Found during:** Task 1 (implementation of `efx_paint_read_frame_media`)
- **Issue:** The plan's Task 1 and Task 3 instructions both require returning the bytes through `tauri::ipc::Response::new(bytes)` with `digest` and `relative_path` as response headers. In tauri 2.11.5 (`src/ipc/mod.rs`), `Response` exposes only `pub fn new(body: impl Into<InvokeResponseBody>)` — there is no headers API, and `Response::new` does not even accept a `Vec<u8>` directly. The instruction is unimplementable.
- **Fix:** Both commands return JSON envelopes: the write command `{ relativePath, digest, byteLength }`; the read command `{ relativePath, digest, byteLength, bytesBase64 }`, reusing the existing hand-rolled `encode_base64` (made `pub(crate)` in `frame_codec.rs`). This mirrors `DecodedWebpFrame.rgba_base64`'s documented rationale (on macOS a raw response degrades to a ~33 MB JSON number array for a 1080p frame), keeps the plan's truth "frame bytes never cross the IPC boundary as a JSON number array" true, and still hands plan 09 the returned digest it compares against `reference.digest`.
- **Files modified:** `app/src-tauri/src/commands/efx_paint_media.rs`, `app/src-tauri/src/commands/frame_codec.rs`, `app/src/lib/ipc.ts`
- **Verification:** `cargo test --test efx_paint_package` (`write_command_consumes_raw_request_bytes`, all read cases), `cargo build`, and `vitest run src/lib/ipc.efxPaintMedia.test.ts` (9 passed).
- **Committed in:** `9fd950ab` (Task 1 GREEN); routed to human review as coverage item D6.

**2. [Rule 3 - Blocking] Commands are not invocable from integration tests — wiring proven by source scans**
- **Found during:** Task 1 (RED test authoring)
- **Issue:** `tauri::ipc::Request<'a>` has private fields, so a command function cannot be called from an integration test with a constructed request. A command-level test would have to be a unit test that fabricates IPC internals.
- **Fix:** Command wiring is asserted by `include_str!` source-scan tests over `src/lib.rs` (both command names registered) and `src/commands/efx_paint_media.rs` (`InvokeBody::Raw(bytes)`), matching the existing repo pattern for Tauri command modules; the behavior behind the commands is exercised directly through the service functions.
- **Files modified:** `app/src-tauri/tests/efx_paint_package.rs`
- **Verification:** the two source-scan cases pass and the full 20-case target is green.
- **Committed in:** `551534f4` (Task 1 RED)
