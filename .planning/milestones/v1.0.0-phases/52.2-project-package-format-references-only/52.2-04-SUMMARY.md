# Phase 52.2 Plan 04: Solo content start + loop-wrap anchor Summary

**Any solo now starts playback at the beginning of the isolated content — the session pill at its window's first frame, a persisted row-S track solo at the first painted key of the soloed tracks (else project frame 0) — and every loop wrap returns there, through one pure resolver pair while the no-solo Phase 51 play-from-cursor path stays byte-for-byte unchanged**

## Accomplishments

- `deriveSoloContentStart` (pure, total, T-52.2-12) resolves one rule for two solo systems: the session pill's window start (its `start` IS the content start by construction) wins, then the first painted key of the persisted row-S soloed tracks, then project frame 0 when those tracks carry none — clamped into `[0, capacity - 1]` with a degenerate capacity collapsing to 0.
- `resolvePlaybackStartIndex` reproduces the Phase 51 play-from-cursor law when no solo is active and, when one is, returns the first cached frame at or after the content start — always an index **into `cachedFrames`**, so no document or session value can move the playhead outside the frame list (T-52.2-11).
- `useRotoCachedPlayback.start()` sets `frameIndexRef` **and** `loopStartIndexRef` from that single index (the key link the plan called out): iteration 2+ returns to the solo content start, never to the pre-solo cursor (D-22).
- `getSoloContentStart` is a lazy getter read at Play press time, so arming the pill — which does not re-render the Studio — still affects the next Play; `null` (no pill, no row-S) means the D-01 cursor branch runs unchanged.
- The Studio keeps the change call-site only: the pre-existing `getSoloWindow` body moved verbatim into a shared `resolveSessionSoloWindow()` closure that `getSoloContentStart` reuses, so the filter seam and the start seam can never drift; no new signal, no new store field.

## Decisions Made

- **Getter, not captured values** for the solo input (see key-decisions): the pill arms without a Studio re-render, so a plain value read at render time would be stale exactly when it matters.
- **`null` = no solo** rather than a `soloActive: false` pair, so the no-solo path is a single branch the Phase 51 tests already cover end-to-end.
- **One assignment, both refs**: assigning `startIndex` to `frameIndexRef` and `loopStartIndexRef` in the same block is the entire D-22 mechanism; the wrap branch's existing `loopStartIndexRef` read needed no change.
- **Row-S reads stay at the call site**: `getEfxPaintDocument(layerId)?.tracks.filter(t => t.solo)` plus `physicPaintStore.getRotoRealKeyRecords(layerId, trackId)`, filtered to the soloed track ids before the resolver call (the resolver expects pre-filtered input, per the plan). The resolver itself never touches the document/persistence/bridge.
- **Test read at the first tick inside the `onFrame` spy** rather than on the refs directly: `start()` runs one synchronous `showNextFrame()` that increments `frameIndexRef`, so the pre-increment values are the anchor evidence for `frameIndexRef.current === loopStartIndexRef.current`.
