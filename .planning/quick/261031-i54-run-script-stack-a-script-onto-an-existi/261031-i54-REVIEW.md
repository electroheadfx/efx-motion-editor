# Phase 261031-i54: Code Review Report — Run Script stacking (Quick A)

**Reviewed:** 2026-10-31
**Depth:** quick
**Files Reviewed:** 10
**Status:** issues_found

## Summary

Quick A adds a second Run Script destination: when the playhead sits inside an existing Paint rail, the dialog stacks the run onto that rail instead of creating a Loop Clip (new pure helpers in `physicsPaintRotoRunScriptStacking.ts`, a stack surface in the controller, a collision card in the dialog, and the Keep-script union re-bake in the Studio). Scope was read end-to-end beyond the pattern scan configured for `quick` because the stack path is new decision logic (boundary ranking, lifecycle extension, victim removal).

The core architecture is sound where it is testable: the run writes at a canonical source-cycle start, the lifecycle plan is extend-only and never silently capacity-capped, Overwrite removes the victim in the same single `ports.commit`, `keyScriptEdits` is never flipped, the Keep-script switch is OFF+disabled+reason on a flag-off rail, and record mode matches the visible switch. However, the collision/override layer has several ways to write where the user was never asked, and two locked decisions are simply not implemented in the shipped UI.

No security findings: the pattern scan (`eval`, `innerHTML`, secrets, empty catch, debug artifacts) is clean across the changed files.

## Narrative Findings (AI reviewer)

### Critical Issues (BLOCKER)

#### CR-01: The frame-override refusal is unreachable — override frames are looked up through the real-key index

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:149-156,180-184,346-348`
**Issue:** `buildAppFrameByKeyId` builds its map from `context.identities` (real keys) and `keyIdByAppFrame` (also real keys only, resolver 5507-5519). A frame override's key id is a dedicated override identity: the physical model rejects an override that reuses an ordinary key id (`physicsPaintRotoPhysicalModel.ts:1556-1561`) and group lifecycle creation rejects a duplicate override id (`physicsPaintRotoGroupLifecycle.ts:118`). Therefore `appFrameByKeyId.get(override.keyId)` is always `undefined`, `frameOverrideAppFrames` is always empty, and both the `overrideInSpan` refusal and the lifecycle override carry-forward check silently never fire. A run can write a real key onto a frame owned by a group frame override, producing two records at the same frame, with the intended refusal never shown. The controller test masks this by seeding `frameOverrides: [{ appFrame: 11, keyId: 'S2' }]` where `S2` is a real identity (`physicsPaintRotoPlayScriptController.test.ts:4560`), a state production cannot create.
**Fix:** The override already carries its frame — do not resolve it through real keys:
```ts
const overrideFrames = (clip.frameOverrides ?? [])
  .map((override) => override.appFrame)
  .sort((left, right) => left - right)
  .filter((frame, index, frames) => index === 0 || frames[index - 1] !== frame);
```
Delete `buildAppFrameByKeyId` or stop using it for overrides. Retarget the controller test to a real override identity (for example `{ appFrame: 11, keyId: 'override:L1:11' }`) and assert the refusal fires.

#### CR-02: The Overwrite explanation required by the locked decision is dead code — the collision card never says the other rail is removed

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:133`; `app/src/components/physic-paint/view/PhysicsPaintPlayScriptDialog.tsx:733-735`
**Issue:** `RUN_SCRIPT_OVERWRITE_COPY` ("Removes the other rail; its keys stay as ordinary keys.") is exported but never imported by the dialog; the only references are its own definition and the string test at `physicsPaintRotoRunScriptStacking.test.ts:624-627`. The shipped collision card renders a generic sentence that never mentions Overwrite, rail removal, or ordinary-key survival — the exact copy law in `261031-i54-CONTEXT.md` ("REMOVED", never "shortened"). A user pressing Overwrite destroys a rail with no on-screen explanation.
**Fix:** Render the constant in the collision card whenever overwrite is offered, and assert it in the dialog test (not only against the constant):
```tsx
{collisionOffers.includes('overwrite') ? (
  <span class="physics-paint-play-script-collision-copy">{RUN_SCRIPT_OVERWRITE_COPY}</span>
) : null}
```
Add a `PhysicsPaintPlayScriptDialog.test.ts` assertion that the rendered card text contains "Removes the other rail" and does not contain "shorten".

#### CR-03: Fragment collapsing treats a visible-range gap as inside the rail, and hides later fragments from boundary detection

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:163-202,213-215`
**Issue:** `toRunScriptRailViews` groups every canonical range of a clip into one view using the first fragment's `placementStart` and the maximum `effectiveEnd`. Visible-range gaps are real: deleting a group frame splits the clip's ranges (`physicsPaintRotoGroupLifecycle.ts:513-527`), and the resolver emits one range per fragment (`physicsPaintRotoPhysicalResolver.ts:5602-5638`). Consequences: (a) a playhead inside a gap is classified as `stack` (213-215) even though no rail exists there, so the run writes into deleted frames; (b) the collapsed view used for other rails only exposes the first fragment's `placementStart`, so later fragments are invisible to `resolveRunScriptStackBoundary` and the ranking can miss the true nearest boundary; (c) `truncated`/`effectiveEnd` are merged across fragments and no longer describe what the target actually covers. No test covers a gapped `visibleRanges` (`physicsPaintRotoRunScriptStacking.test.ts` has no gap case).
**Fix:** Carry fragments, don't collapse them:
```ts
readonly placementFragments: readonly { readonly start: number; readonly endExclusive: number }[];
```
Membership becomes `rail.placementFragments.some((f) => f.start <= appFrame && appFrame < f.endExclusive)`; other-rail boundaries iterate every fragment start (and treat a fragment covering `runStart` like a collision at `runStart`); the target's own fragments may stay grouped only for display. Add a test built from `visibleRanges: [{ start: 10, endExclusive: 13 }, { start: 14, endExclusive: 18 }]` asserting that a playhead at 13 resolves to `create` and that a later fragment at 14 still bounds another rail's run.

#### CR-04: A stale `collisionChoice === 'overwrite'` survives failures and can remove a rail the UI never offered

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:987,2091-2137,918-926`
**Issue:** `collisionChoice` is cleared only on success (2267), explicit Cancel (2100), the rerun override refusal, and the zero-free-span path. It is not cleared in the `catch` of `confirmStack` (2282-2286) nor when the boundary/context changes. The Overwrite branch (2104-2119) gates only on `boundary.blocker === 'other-rail' && victimClipId !== null`; it ignores `collisionOffers`, `boundary.collision`, and `runCollision`. `collisionOffers` deliberately filters Overwrite out of a lifecycle-only overflow (925). So: click Overwrite once, let the bake/commit fail (or scrub during the bake), then reach a lifecycle-only overflow scenario that still reports `blocker: 'other-rail'` at an unrelated rail further down — for example parent end 24, repeat 5, cycle 4, run frames 10-11, another rail at 20 (`collision` false because 14 > 20 is false, `lifecycleOverflow` true). The primary Run button is not disabled while the card is open (dialog 932-937), so clicking it re-enters `confirmStack` with the stale choice and silently removes the rail at F20, which was never offered. The Enter route is safe (dialog 443-449), which makes the mouse path an easy trap.
**Fix:** Gate the destructive branch on what is actually offered and invalidate the choice aggressively:
```ts
if (choice === 'overwrite'
  && boundary.collision
  && boundary.blocker === 'other-rail'
  && boundary.victimClipId !== null
  && boundary.offers.includes('overwrite')) { ... }
else if (choice === 'overwrite') {
  error.value = 'Overwrite is not available for this boundary. Choose Truncate or Cancel.';
  return false;
}
```
Reset `collisionChoice.value = null` in `fail()`/the catch path and whenever `stackBoundary`, `stackRailStart`, or the parsed count changes. Add a controller test: fail once with overwrite selected, then confirm a lifecycle-only overflow with a downstream rail and assert `commit` was never called.

#### CR-05: Overwriting a victim that owns frame overrides leaves unreferenced override records, so the atomic commit is rejected

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:2223-2225`; `app/src/components/physic-paint/hooks/useRotoPhysicalEditCoordinator.ts:2329-2377`; `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:1554-1561`
**Issue:** Overwrite removes the victim clip from `nextClips`, but the play-script publication carries no `groupOverrideRecords` (the type at controller 205-220 has none; `RotoPlayScriptExecuteInput` likewise), so the coordinator stages `currentGroupOverrideRecords` unchanged (2337). The victim's `frameOverrides[].keyId` records now reference nothing; `parsePhysicPaintRotoPhysicalDocument` throws `unreferenced Group override` and the whole edit is refused with the generic barrier message after a full bake. This is exactly the state Overwrite is advertised to support (a group-edited rail being removed). There is no test with a victim carrying `frameOverrides` (the existing victim test at ~4490 uses a plain clip).
**Fix (minimal, fail closed):** after CR-01 makes `victim.frameOverrideAppFrames` trustworthy, refuse the Overwrite choice when the victim has any frame override, with an actionable message, instead of letting the commit fail. **Full fix:** extend the play-script publication/execute input with `groupOverrideRecords` (filter out the victim's override key ids), stage them in the coordinator the same way `regenerate-group` already does (2331), and add a test asserting the victim's overrides are dropped in the same commit.

#### CR-06: A rail that covers the run start but began earlier is never a blocker, so the run writes into it with no prompt

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:329-333`; `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:790-797`
**Issue:** Destination resolution only checks the playhead frame (213-215), while the run start is normalized to the rail's source cycle (`runStartAppFrame`). Boundary detection skips every other rail with `placementStart < runStart`. These two rules do not meet when the playhead is in a later occurrence: another rail can cover `runStart` yet not the playhead, so no `ambiguous-rail` refusal happens, and its `placementStart` is skipped. Its source keys are usually before `runStart` too, so the `real-key` check (334-339) does not catch it either — and for a linked rail with an identical cycle they are `owned` and skipped explicitly. The run then writes real keys inside the other rail's span with no prompt and no Overwrite/Truncate choice.
**Fix:** Only ignore rails that end before the run:
```ts
for (const rail of input.rails) {
  if (rail.clipId === input.targetClipId) continue;
  if (rail.effectiveEnd <= input.runStartAppFrame) continue;
  const frame = rail.placementStart < input.runStartAppFrame
    ? input.runStartAppFrame   // covers the run start → zero free span, refuse
    : rail.placementStart;
  consider({ frame, kind: 'other-rail', victimClipId: rail.clipId });
}
```
With `freeCount === 0` this lands on the existing "No free span remains before the next boundary. Nothing changed." path. Add a controller test with an overlapping earlier rail and a playhead in a later occurrence.

### Warnings

#### WR-01: The dialog flips between stack and create surfaces on scrub, and the create confirm silently no-ops

**File:** `app/src/components/physic-paint/view/PhysicsPaintPlayScriptDialog.tsx:122-127,248-262,932-937`; `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:2298,2306-2334`
**Issue:** `stacking`, `stackReadout`, and `stackCollision` all read the live `runDestination`, while the controller keeps `canonicalStart` pinned from open. Scrubbing outside every rail while the confirmation is open swaps the stack readout and collision card for the creation surface (and re-enables Infinity/Repeat); the primary button then calls `confirmGeneration`, whose guard `startingSelection.appFrame !== start` (2334) returns `false` with no message, no phase change, and no error. The user sees a fully enabled dialog that does nothing.
**Fix:** While `confirmationOpen` is true, render from the pinned destination snapshot (or force-close/refuse when the live destination no longer matches the pinned rail and start). At minimum surface an error instead of the silent `return false` when the playhead left the pinned rail, and disable the primary button in that state.

#### WR-02: Pinned start and live destination are mixed, so a scrub within the rail shows one plan and aborts another after the bake

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:809-814,929-944,1012-1018,2173-2177`
**Issue:** `stackRailStart` pins the write start while `stackContext.destination` stays live. Scrubbing to another occurrence of the same rail keeps the pinned start for the boundary/readout but re-targets `context.destination.rail`; the boundary uses the pinned start against a live rail that may have different cycle geometry. `stackDestinationStillCurrent` then rejects at 2175 with "Play Script destination changed before commit" after the whole render, while the dialog had continued to show the pinned readout. The collision card can therefore display a boundary computed from a mix of two destinations.
**Fix:** Build the stack surface from one destination snapshot per confirmation: resolve the rail once in `openConfirmation`, store `{ clipId, phaseOrigin, cycleLength, repeat, start }`, and use it for boundary, readout, and commit. On scrub, either explicitly re-pin all of it or close the confirmation with a visible message before rendering starts.

#### WR-03: Lifecycle-only overflow is described as run truncation in both the card and the readout

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:905-914,929-943`; `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:438-445`; `app/src/components/physic-paint/view/PhysicsPaintPlayScriptDialog.tsx:733-735`
**Issue:** `stackReadout` passes `truncated: stackCollision.value !== null` (941), so a lifecycle-only overflow (run fits, the repeat-extended span crosses the parent end) reports "Truncated at the next boundary." The card copy always says "The run reaches past ... Truncate writes only the free span", which is false in that case: Truncate writes the full requested count and only clamps the rail lifecycle (2125-2128). The dialog ignores `runCollision`/`lifecycleOverflow` entirely (730-765), so the two distinct collision laws render identically.
**Fix:** Pass `truncated: stackCollision.value?.runCollision === true`; branch the readout and card copy on `lifecycleOverflow` (for example "The rail's repeat span crosses the parent end at Fx. Truncate clamps the rail to Fx and still writes the whole run."). Add a dialog test for `{ runCollision: false, lifecycleOverflow: true }`.

#### WR-04: Creation-only controls remain live on a stack destination — Key Script Editing and Color are inert

**File:** `app/src/components/physic-paint/view/PhysicsPaintPlayScriptDialog.tsx:713-725,793-839`
**Issue:** Both cards render whenever `dialogMode === 'apply'` and the tab is not Reveal, including on a stack destination (Key Script Editing at 714, Color at 793). `confirmStack` never reads `keyScriptEdits` or `overrideEnabled`: it always records through `recordRailKeyScripts` with the Keep-script-derived mode and only uses `currentTarget.overrideColor` for the summary line. The user can toggle "Save script on each key" and pick a color and neither has any effect — the locked decision explicitly forbids creation-only controls misleading on a stack destination.
**Fix:** Gate both cards on `!stacking` (the Source cycle card already is, 262), or wire them into `confirmStack` if they are meant to apply there.

#### WR-05: Any truncated target rail raises a collision even when the run fits, and Truncate can silently regrow the truncated span

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:340-344,356`; `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:2085-2128`
**Issue:** `targetEnd` is `effectiveEnd` whenever the target is truncated, and `collision` is `newCycleEndExclusive > winner.frame`, where `newCycleEndExclusive` always includes the full cycle (`phaseOrigin + max(cycleLength, cycleOffset + count)`). A rail truncated mid-first-cycle (deleted frames, another rail boundary, capacity) therefore prompts on every run, even a 1-frame run that fits entirely inside the free span, with `blocker: 'target-end'`. Truncate then writes the same count but the lifecycle plan grows `originalEndExclusive` back to the full cycle end (stacking 383-404), re-exposing frames the user had hidden. The existing own-repeat test uses an untruncated target, so this is uncovered.
**Fix:** Only treat `target-end` as a collision when the *written span or lifecycle growth* would actually cross it:
```ts
const requestedEndExclusive = input.runStartAppFrame + input.requestedCount;
collision: input.newCycleEndExclusive > Math.min(winner.frame, ...)
```
or compare `Math.max(requestedEndExclusive, targetEnd) > targetEnd` for the target candidate. Do not extend `visibleRanges` past `effectiveEnd` on a `target-end` Truncate. Add a test with `visibleRanges: [{ start: 10, endExclusive: 14 }]`, `repeat: 3`, count 2 asserting no collision.

#### WR-06: The Reveal tab is reachable on a stack destination and `confirm()` routes to the creation path before the stack path

**File:** `app/src/components/physic-paint/view/PhysicsPaintPlayScriptDialog.tsx:117-118`; `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:1792-1796,1208,1230-1244`
**Issue:** `tabsVisible` ignores `stacking`, so a stack confirmation still shows the "Reveal Photo Rail" tab. Switching to it sets `railTab = 'reveal'`, which turns `stacking` off, hides the stack readout/Keep switch, and makes `confirm()` take the `confirmReveal()` branch before `confirmGeneration()`. The result is a brand-new reveal rail created at the pinned stack start while the user believed they were stacking. The same state is reachable at open when the caller passes `{ railTab: 'reveal' }` (the track rail-creation flow, 1205-1208): `openConfirmation` still pins the stack start and seeds the stack branch, but never resets the tab.
**Fix:** Hide the tab strip while the destination is a stack (creation-only surface), and force `railTab.value = 'paint'` in the stack branch of `openConfirmation`. Route `confirm()` through `confirmStack` when the live/pinned destination is a stack before the reveal check.

#### WR-07: `sameLoopClipCollections` is not field-exact — it ignores every lifecycle field it is meant to verify

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:3326-3351` (used at 2725-2734)
**Issue:** The commit acknowledgement compares `loopId`, `placementStart`, `sourceKeyIds`, `repeat`, `mode`, `scriptId`, `motion`, and the creation flags, but omits `phaseOrigin`, `originalEndExclusive`, `visibleRanges`, `frameOverrides`, `syncState`, `provenanceState`, `railKind`, and `sourceOffsets`. Quick A's whole persistable effect is exactly the lifecycle extension and the merged source cycle; an ack that dropped or mis-ordered them would pass. `sourceOffsets` is not compared at all, so a reordered/truncated offset list is accepted.
**Fix:** Deep-compare the lifecycle members (ordered ranges and overrides), `sourceOffsets`, `syncState`, `provenanceState`, and `railKind`, or rename the helper and document the narrower contract.

#### WR-08: Extending a rail that shares its source cycle with a linked rail fails validation at commit

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:1579-1591`; `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:2196-2225`
**Issue:** Two rails may legally share an identical ordered source cycle (`identicalOrderedCycle` exemption). A stack run extends only the target's `sourceKeyIds` (2201-2220), so the two cycles become non-identical and the staged document throws "ambiguous source sharing between Groups". The run has already baked by then, and the failure is reported as the generic commit barrier. There is no test with a linked rail plus an extension.
**Fix:** Update every clip that shares the identical ordered cycle in the same publication (the rails module already treats linked rails as one cycle), or preflight the staged collection before baking and refuse with an actionable message. Add a controller test with two clips sharing `['k10','k12']` and a run that grows the cycle.

#### WR-09: `availabilityRevision` does not track loop-clip/document changes, so the stack context and boundary can be stale

**File:** `app/src/components/physic-paint/hooks/useRotoPlayScriptController.ts:38-45`; `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:765-801,2062-2098,2194-2225`
**Issue:** The hook bumps availability only for `operationLocked`, `projectSaved`, `selectionKind`, `keyId`, and `appFrame`. `stackContext` reads `getRotoLoopClips()` and the physical document as plain ports, so editing rails (delete, relink, move, another run) without moving the playhead does not invalidate the computed. `confirmStack` then bounds and picks a victim from stale `rails` while reading the target clip live (`stackTargetClip`), mixing two revisions — a deleted victim goes unnoticed until the coordinator rejects, a resized/moved rail can produce a wrong boundary, and a stale target view can write a lifecycle computed from old geometry.
**Fix:** Include a loop-clip/document revision in the availability signal (the Studio already has one for the physical document), or rebuild the rails from `getPhysicalDocument()` inside `confirmStack` and re-derive the boundary before baking. Add a test where the clips change without a selection change.

#### WR-10: `confirmStack`/`confirmStackCollision` are re-entrant during the commit phase

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:2062-2070,2290-2293`; `app/src/components/physic-paint/view/PhysicsPaintPlayScriptDialog.tsx:730-765,932-937`
**Issue:** `confirmStack` starts by bumping `generation` and setting `phase = 'preparing'` but never checks `isBusyPhase`/`canCancel`. The collision buttons are not disabled by `busy`, and the primary Run button stays enabled during `committing` (`busy` is `canCancel`, which is only preparing/rendering). A second Overwrite/Run click while the first commit is in flight aborts the first generation after its bridge commit resolves, so the first commit's `recordRailKeyScripts` is skipped and the dialog reports "cancelled", while the second flow re-bakes and commits again. The guard helpers exist for the edit paths (`loopOpGuard`) but not here.
**Fix:** `if (disposed || isBusyPhase(phase.peek())) return false;` at the top of `confirmStack` (and keep `confirmStackCollision` delegating to it), plus `disabled={busy}` on the collision buttons. Add a double-submit test.

#### WR-11: Tests miss the cases that would have caught CR-01, CR-03, CR-04, CR-05, and the copy violation

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.test.ts:110-130,325-335,624-627`; `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.test.ts:4490-4576`; `app/src/components/physic-paint/view/PhysicsPaintPlayScriptDialog.test.ts:1601-1643`
**Issue:** (a) The frame-override path is exercised only with a real key id (4560), which cannot exist in production, so CR-01 stays green. (b) No test feeds a gapped `visibleRanges`, so CR-03 is uncovered. (c) No test leaves a stale `collisionChoice` across a failure, so CR-04 is uncovered. (d) The Overwrite victim test uses a clip without `frameOverrides`, so CR-05 is uncovered. (e) The overwrite copy is asserted against the constant, never against the rendered dialog, so CR-02 is uncovered. (f) The collision card test uses a seed without `runCollision`/`lifecycleOverflow`, so the lifecycle-only copy is never rendered.
**Fix:** Add the targeted tests described in the corresponding findings, and change the copy test to render the dialog and inspect `physics-play-script-collision`'s text.

### Info

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:438,447`

#### IN-02: `repeatInstance` and `appendedSlots` are computed but never consumed

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoRunScriptStacking.ts:235,252-259`
**Issue:** Both fields are only asserted by unit tests; the controller never reads `destination.repeatInstance` or `extension.appendedSlots`. They suggest behavior (append slots) that the implementation performs through `mergeStackedSourceKeyIds` instead.
**Fix:** Remove them or use them in the readout/extension implementation so the public shape and the executed law agree.

#### IN-03: The pinned start has two authorities (`canonicalStart` vs `stackRailStart`)

**File:** `app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:605-609,809-814`
**Issue:** `destinationRange` (the dialog header span) is computed from `canonicalStart`, while every stack computation uses `stackRailStart`. **Fix:** Compute `destinationRange` from the same `stackRailStart`-aware source for a stack destination.
