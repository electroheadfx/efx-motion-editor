<decisions>
## Implementation Decisions

### Rename (Requirement 1)
- Already completed in commit `0266a199d` and UAT-approved (`7cd1ecbf0`):
  Scripts panel button, Tools popover, Workflow strip labels/tooltips all read
  "Run Script"; the dialog title/button already read "Run Script".
- This task only verifies no user-visible "Create Rail" label remains. Internal code
  comments/types may retain historical naming; they are not user-visible.
- Load + Apply, Save/Delete script, and the script library format are untouched.

### Destination resolution
- **Playhead membership only.** If the playhead sits inside exactly one rail's effective
  span — real key, generated frame, empty frame, or repeated occurrence — that rail is
  the target and the playhead maps to its source-cycle offset.
- Playhead outside every rail → today's create path, byte-identical to current Create
  Rail.
- Overlapping/ambiguous membership fails closed with a clear refusal reason.
- No "add to existing rail" option is added to the modal; the existing target selector
  is not extended.

### Position and role of the run
- The playhead's cycle offset is the script's first output frame. A repeated occurrence
  maps through the resolver to the source cycle; the run writes source-cycle keys at
  their canonical physical frames, never into virtual occurrences.
- Keys before/after the touched span keep exact pixels and identities.
- Generated/interpolated frames become valid run starts **only when inside a rail**;
  outside a rail the existing `generated-interpolation` refusal stays.

### Extend only
- If the run reaches beyond the rail's current cycle end, append new source-cycle keys
  and grow the cycle to the new length. Never shrink.
- Repeat count does not change; the rail re-resolves from the new cycle/cache, so a
  repeated rail's effective span grows by (repeat × cycle growth). Repeated occurrences
  are never materialized.
- Rail lifecycle must be updated (`originalEndExclusive`, `visibleRanges`, and any
  phase-relative extent) so the extended cycle belongs to the rail and repeats resolve.
  Infinity clips stay lifecycle-less per the existing parser contract.

### Keep script
- New switch shown only when the destination is an existing rail.
- **Quick A scope (user-authorized split): flag-on rails only.** The plan estimate
  exceeded the quick budget (165k vs 100k), so flag-off union stacking + the base-authority
  change are deferred to Quick B.
- Default ON for a flag-on stack destination. **ON (Quick A):** append the new run's
  strokes per touched key to that key's existing recorded script and re-bake the raw union
  over the key's known-empty base (a flag-on rail's base is known-empty). The switch is
  never ON on a flag-off target.
- **Flag-off stack destination (Quick A):** the switch is seeded OFF and disabled, with a
  reason stating that this rail cannot record per-key scripts and that this run replaces
  the touched span. The executed recording mode always matches the visible switch state;
  a checked-ON control never runs the destructive replace path.
- **OFF:** replace the touched span's pixels and purge then replace the touched keys'
  recorded scripts with THIS run's slices only. Keys before/after keep their records.
  This is the explicit opt-out; never silently erase.
- **The rail's persisted `keyScriptEdits` flag is never implicitly flipped.** Flipping it
  would make the base "known empty" and discard the original paint.
- Stacking is repeatable: running again appends/overlays again with no drift.
- "Save script on each key" remains the creation-time switch for new rails and is
  unchanged.
- **Quick B law (do not implement in Quick A).** Add one base seam for every target kind
  (ordinary/raster, source occurrence, override, reopened, flag-on, flag-off):
  1. persisted SNAP v5 durable base of the resolution key (`null` = known-empty);
  2. session durable-base map;
  3. resolution key has no recorded aquarelle events → its current payload IS the
     pre-script cache; pin it;
  4. else fail closed (`durable-base-unknown`), no write.
  For source occurrences and overrides the RESOLUTION key is the SOURCE key, never the
  occurrence's composite. Never use a payload as a base when that key has events.
  Persist freshly pinned bases; recovered bases stay session-only. Required regression:
  ordinary/raster, source occurrence, override, reopened, flag-on, flag-off, plus the
  raster-key edit UAT. This requires changing the current `durableBaseKeyId`
  payload-only path. Never ship flag-off Keep ON without this fix.

### Collision on extension
- Collision check applies when the new cycle end would cross another rail's start or
  the parent end.
- **Other rail:** confirmation dialog with Cancel, Truncate (default), Overwrite.
  - Cancel: no writes.
  - Truncate: clip the run at the boundary; the target rail extends only to it; the
    other rail is untouched.
  - Overwrite: **removes the other rail's Loop Clip** in the same atomic commit. Its
    source keys survive as ordinary keys; frames outside the run keep their pixels.
    This is the only representable semantics — a start-crossed rail cannot be shortened
    (parser forbids `originalEndExclusive <= phaseOrigin`) and its keys cannot be
    deleted in the same commit.
  - Overwrite copy says "removes the rail; its keys stay as ordinary keys" and, when
    the other rail started before the run, that its earlier frames stop being a rail.
    Never say "shortens".
  - One undo restores the removed rail exactly (identity, sourceKeyIds, lifecycle,
    repeat). Truncate remains the default.
- **Parent end:** Truncate / Cancel only. Overwrite is not offered; extending the parent
  layer is out of scope.
- The whole operation is one atomic undo entry, including any other-rail change.

### Dialog readout
- Before confirm the dialog shows the resolved span, the start offset (source cycle
  position), and the resulting extension/truncation.
- Max resolves to the free span before the collision boundary, not the whole capacity.
- Frames count defaults to the selected script's natural duration for EXISTING-rail
  targets only; new-rail creation keeps today's 3. Fallback 3 when duration is unknown.
  No silent clamp — capacity/collision validation still applies.
- Additional UAT: stack on an unscripted raster key, then edit the new strokes — the
  original raster must remain under them after re-bake, save/reopen and repeat.
  Reopen + repeat a rail whose key was stacked: no doubling. Unprovable base → refusal,
  no erase.

### Deferred to Quick B
- **Keep script ON for flag-off (unscripted) Paint rails**, together with the one base
  seam above (`aquarelleScriptBaseAuthority`), the `prepareRotoScriptTarget` rewrite,
  removal of `durableBaseKeyId`, and the extended base regression matrix + raster-key
  edit UAT. Quick A seeds the switch OFF and disabled for these rails with a reason and
  keeps the replace path explicit.
- Reveal rail stacking. User decision: Reveal rails will stack like Paint rails and
  Keep script will record the new strokes, which changes today's contract that Reveal
  keys are script-incapable. Extension of a Reveal rail must bake the new tail through
  the currently placed photo reference (same photo, new wash) and refuse with a clear
  reason when no reference is placed. Plain-paper keys must never be mixed into a Reveal
  rail.
- Frame-override bases: Quick A refuses a `frame-override` inside the written span with
  zero writes; Quick B owns the override base semantics.

  must extend the slice result rather than replace it.

  `keyScriptEdits === true` known-empty special case.

  STOP and report — do not improvise a schema.

  task. Read the current tests for these paths; they pin today's laws.
