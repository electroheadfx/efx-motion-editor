<objective>
Make Phase 59 motion-channel keys draggable through time on the rail, using the existing rail drag machinery.

Purpose: quick bug report against the shipped v2.1.0 motion surface on branch `gsd/phase-59-rail-motion-channels-v7-interface`. `TimelineMotionChannelLane` renders every motion key as a click-only `<button>` (onClick -> select). There is no pointer-down or drag wiring anywhere on the lane, so the key dots cannot be moved through time even though the other rails (Key Rail, Loop Clip, Background clip) all drag. The user must be able to grab a motion key and move it to another frame, exactly like the other rail keys.

Constraint (load-bearing): the fix MUST reuse `usePhysicsPaintKeyRailDrag` — the shared pointer session with the 4px threshold, pointer capture, Escape/pointercancel handling, preview state and post-drop click suppression — rather than adding a second gesture system. The reuse points are its ports: `projectDestination`, `clampDestination`, `prepareAtDestination`, `onDropCommit`, `onCancel`, `onRejected`, `clearClickSequence`.

Scope note: the write path is a single drag transaction, not a remove+set composition. `applyRemoveKeyEdit` cascades key -> channel -> record (D-15), so a naive remove-then-set would destroy a single-key channel; the plan adds a dedicated `move-key` edit. The persisted record shape, serializer, evaluator, compositor, CSS and the non-active rows' click-only lanes are unchanged. Only the active track's expanded block receives drag ports. `workflow.tdd_mode` is on: Tasks 1-2 are RED-first (`tdd="true"` with `<behavior>`); Task 3 is view wiring gated by the existing lane suite and typecheck.
</objective>
