<objective>
Fix WR-01 from the 52.3 review: a scrub onto a gap entry deselects the active sequence.

Root cause (pinned at planning time by reading, not speculation):

1. 52.3's dense enumeration (`app/src/lib/frameMap.ts:58-71`) emits one entry per frame in content-empty projects: a `paint` entry for frames inside an fx sequence's span, and a `gap` entry with `sequenceId: ''` for every other frame (`frameMap.ts:68`, type `GapFrameEntry` at `app/src/types/timeline.ts:54-58`).
2. `syncActiveSequence` (`app/src/lib/playbackEngine.ts:187-199`) reads `frameMap.peek()[cf]` and, when `entry.sequenceId !== activeId`, calls `sequenceStore.setActive(entry.sequenceId)` plus `uiStore.selectSequence(...)` and `timelineStore.ensureTrackVisible(...)`. With a gap entry that sequenceId is `''`, so the playhead landing on a leading gap (paint-only project with fx `inFrame > 0`) or an inter-fx gap calls `setActive('')`.
3. `setActive` (`app/src/stores/sequenceStore.ts:1091-1094`) sets `activeSequenceId` AND clears `selectedKeyPhotoId` in the same call. Downstream: the sidebar loses the fx properties and the export dialog's selected sequence silently becomes none until the playhead re-enters a paint span.
4. Pre-52.3, positions outside any sequence produced no entry at all, so the outer `if (entry)` skipped the whole block and the active sequence was preserved. D-08 documents gap entries as "ownerless" — not as deselection signals.

Fix (user-locked direction, smallest seam): guard the outer condition in `syncActiveSequence` so the block runs only for entries that own a sequence — `if (entry && entry.sequenceId !== '')`. This restores exact pre-52.3 semantics for unowned positions while keeping the 52.3 improvement (paint frames still activate their owning fx sequence).

Deliberately synthetic note for the test: gap entries exist ONLY in content-empty projects, so a paint-only document cannot carry a real key-photo selection. The two new cases still pin `selectedKeyPhotoId` because that signal is the observable side-effect of `setActive` — if the key photo survives a gap scrub, `setActive` provably was not invoked. That is exactly the assertion WR-01's fix text asks for.

Out of scope (do not touch, per the task's scope lock): every other 52.3 review item — WR-02 (D-06 clear / cold-decode anti-flicker), WR-03 (single-owner enumeration vs composite-all rendering), WR-04 (preload-clamp export cases), WR-05's overlapping-fx enumeration test, and IN-01..IN-05. Also out: `frameMap.ts` enumeration, `sequenceStore.setActive` semantics, `uiStore`, the tick loop's `ensureTrackVisible(entry.sequenceId)` read (`playbackEngine.ts:394-398` — `ensureTrackVisible` is a documented no-op at `app/src/stores/timelineStore.ts:149-151`, verified at planning time, so `''` there is inert), and any redesign of `syncActiveSequence` beyond the one condition.

Purpose: the active sequence and its selection must survive a scrub across ownerless frames — the pre-52.3 contract the 52.3 enumeration accidentally broke.
Output: a RED-pinned gap-scrub contract + the one-line guard + green playback/frameMap/timeline suites.
</objective>
