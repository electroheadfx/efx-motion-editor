<objective>
Add a rail-scoped mode to the Physic Paint header Raster action: when a key rail is selected (no frame key selected), Raster converts every scripted key of that rail to raster-only — each key keeps its painted pixels and loses its Brush/Water color script — instead of only the current key.

Purpose: the artist already rastered keys one at a time; a rail is the natural batch scope, and the Memory tab already offers a rail-wide script purge. The rail Raster must be exactly as safe as the per-key Raster: pixels captured and verified before any script is removed, and nothing removed when the retained raster is missing.

Output: a pure rail presentation/copy contract, a rail target computed, a shared per-key raster core reused by both the frame and the rail paths, a bounded rail handler with skip accounting and a single status summary, the strip/leaf rail mode (copy, aria, dispatch), and updated structural/unit tests.

Locked decisions (do not revisit):
- D-01 Mode trigger: a selected key rail (`effectiveSelectedRotoKeyRail !== null`) makes the action target the whole rail. The existing behavior that selecting a key clears the rail selection keeps the two modes mutually exclusive. With no rail selected the frame-only path is unchanged.
- D-02 Frame resolution: map the rail's `keyIds` through `physicPaintStore.getRotoPhysicalProjection(layerId, studioActiveTrackId())?.framesByKeyId`, dedupe and sort ascending. Never resolve rail frames through the display source.
- D-03 Enablement order (rail): ready -> cached playback -> mutation lock -> empty rail -> no rail script. Reasons: `The engine is not ready yet.`, `Stop cached playback before rastering the rail.`, `A timeline edit is in progress.`, `This rail has no keys to raster.`, `No key on this rail has a script to raster.` (key-mode reasons unchanged).
- D-04 Scope: only a `RotoKeyRailSelection` enables rail mode. Loop Clip rails and rail-set selections never do — they carry no own key scripts, and no new menu/picker is introduced.
- D-05 Per-key safety order (shared core): resolve ownership -> flush/capture pixels -> re-check key identity -> verify the retained raster exists -> clear and reload the preview base ONLY when this key is the live frame -> purge the script -> drop the pinned durable base. A failure before the purge leaves the stores untouched.
- D-06 Degraded keys: scriptless keys are not targeted; scripted keys without cached pixels (or whose key identity changed mid-run) are skipped and counted. Stop the run only on a session guard break; no retry, one pass, sequential awaits.
- D-07 Persistence: `purgeAquarelleFrameScript` per key, then ONE `applyFrameModuleState(liveFrame)` (only if the live frame was rastered) and ONE `studioScriptSnapshot.persistAfterPurge()` for the whole run — the Memory-tab rail-purge contract.
- D-08 Copy: multi-key rail dialog title `Raster rail keys {first}-{last}?`, body `Every scripted key on this rail loses its Brush and Water color script and keeps its painted pixels. Keys without cached pixels are skipped. Move, Select and replay are lost for those keys.`, confirm `Raster rail keys`, aria `Raster rail keys {first}-{last}`; a one-key rail reuses the exact key copy with that frame; button aria `Raster the rail` in rail mode; tooltip `Raster the rail — remove every key's script and keep the painted pixels.` The visible label stays `Raster` in both modes (no header layout shift).
- D-09 Concurrency: one ref boolean (`rasterInFlightRef`) guards both paths; a second request during a run is ignored. In-flight use is the keyed `firstKeyId`, never a captured frame list.

- Rationale: the frame action remains the primary single-key behavior and is required unchanged. This is accepted: the leaf branches on one nullable target, so a future scope (rail set, Loop Clip rail) would extend the same union rather than contradict the key path.
