<objective>
Fix the Physics Paint Studio Key Rail bug reported for quick 261108-o9d: with one key at frame 0, Create Cycle with Cycle = 10 fails with "Group update was not dispatched." in the dialog and the timeline status, while Cycle = 9 applies and a later re-edit of the created rail to 10 also applies.

The supplied parent-versus-child capacity hypothesis is REFUTED at HEAD e48b27331. The create path is repeat-independent: `confirmKeyRailCycle` clamps with `authority.physicalCapacity` and publishes `expectedLayerCapacity`/`expectedLayerEndExclusive` from the same fixed authority (`app/src/components/physic-paint/roto/physicsPaintRotoPlayScriptController.ts:2101`, `:2412-2422`); the coordinator compares those fixed values to the child capacity in `validatePlayScriptInput` (`app/src/components/physic-paint/hooks/useRotoPhysicalEditCoordinator.ts:1020-1028`); and `reconcilePhysicPaintRotoGroupFrames` (`app/src/components/physic-paint/roto/physicsPaintRotoPhysicalModel.ts:1082-1132`) trims any stored clip end above the child capacity before the document parse, so the `originalEndExclusive > capacity` rule (`:1846`) cannot fire for a create. No capacity configuration can accept repeat 9 and refuse repeat 10: if the capacities disagree both repeats are refused, and if they agree both are accepted up to the same clamped end. The 9-versus-10 correlation is timing, not arithmetic.

The reported copy is narrower than that: `formatPhysicalCommitFailure` emits "`{action}` was not dispatched." only for a settlement with no failure and no timeout (`app/src/components/physic-paint/hooks/useRotoPlayScriptController.ts:330-348`, fallback at `:337`), which `dispatchAndWaitForPlayScriptSettlement` produces when `executePhysicalEdit` returned false before minting `pendingOperationIdSignal` (`:296-303`). Parent rejection, transport failure, timeout and settlement mismatch all carry different copy, so the create never reached the parent. The pre-dispatch gates that produce exactly this are: the serialize guard (`useRotoPhysicalEditCoordinator.ts:1717-1725`, message `PHYSICAL_EDIT_SERIALIZE_MESSAGE` at `:142`), the store-side lease acquire refusal (`:1957-1961`, same message), the launch mismatch (`:1726-1729`, no message and no diagnostic), and the barrier paths (`:1995-1997`, `:2295-2305`, `:2562-2567`). A pending slot survives for the whole settlement budget (5.5 s in `useRotoPlayScriptController.ts:323`), so a confirm issued while the previous edit is still settling is dropped even though the cycle fits — and the request succeeds on a retry seconds later, exactly as reported. The project's own async contract forbids that drop: a submit past the turn limit WAITS on a slot and must not drop silently (`efx-async-orchestration` section 4).

Chosen law: a Key Rail cycle confirm that fits is serialized behind the open physical-edit slot, not refused — the wait is bounded by the settlement budget, honours cancellation, and authority is requested AFTER the slot clears so the publication revision is fresh. The clamp law and every validator stay exactly as shipped. Every remaining pre-dispatch false is named in the diagnostic channel.

Purpose: the reported gesture (one key at frame 0, Cycle 10) must apply on the first confirm, and the shorten law must still clamp genuinely oversized repeats.
Output: the pin at the real controller->coordinator seam, the bounded slot wait, its wiring, and a live UAT checklist.
