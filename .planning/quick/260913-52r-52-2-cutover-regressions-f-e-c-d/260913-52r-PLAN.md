## Defect F — P0: save dead again, deterministic bind refusal on a missing staged frame — FIXED (automated)

**Live:** both autosave and manual save ended in the blocking modal:

> package transaction bind refused "frames/4cf9d4ec-…/095fb9d8-….webp": the
> staged file is unreadable (No such file or directory (os error 2))

Same file across both attempts. Earlier saves in the session succeeded.

**F1/F3 answered from the package on disk** (`~/Desktop/efx-motion-editor-project-test/v1.0.0.mce`):

- F1: the failing key **exists canonically** (`frames/4cf9d4ec-…/095fb9d8-….webp`,
  35 KB, mtime 09:51); 16 canonical frames in the layer dir.
- F3: **no `.efx-paint-package-staging-*` leftovers**; no partial package.
- F2 (mechanism, code-level): deterministic, and it is not the key — it is the
  **first key whose payload carries a `media` reference** in the save's
  iteration order.

**Root cause:** `writeKeyMedia` early-returns the existing reference for a
payload that already carries `payload.media` (the open leg's runtime
projection, D-13 — a reopened document's keys are reference-only until the
compositor re-derives). The save's media loop pushed that reference into
`stagedPaths` **unconditionally**, so the transaction bound a file that no
write ever staged into the generation → the Rust bind refuses ("the staged
file is unreadable"). Deterministic: the same first reference-only key every
attempt.

Why the change set contained those keys at all: `packageFileTokens` /
`packageBaselineRoot` are only advanced by `savePackage` — an open never
seeds them, and a reference-only payload's content token differs from the
bytes-era token — so the first save after an open classifies every
reference-only key as changed. That is also why **earlier saves succeeded**
(they preceded the open) and why the failure looked like "the key appeared
later".

Why CI stayed green: the round-trip suite never re-saves after a load, and
its publish mock *skips* missing staged files; the persistence suite's bind
mock accepted any path. Third instance of the mocked-boundary class.

**Fix (commits):**

| Commit | Content |
|--------|---------|
| `a924fef1` | test: RED — bind mock enforces the live law (refuse missing staged file); the F test reproduces the live error verbatim |
| `63e5306d` | fix: GREEN — `writeKeyMedia` returns `{ reference, staged }`; only staged paths enter the bound set |

**Pinned law:** a reference-only key is referenced (its sub-file carries the
reference) and **never bound**; the canonical file already exists.

**UAT re-run (F):** reopen the §7 project, paint/apply, save (manual +
autosave) → must commit; then the 6 rows of 260913-05k.

**Trace round 2 (2026-09-13, read-only + instrumented):**

Cleared suspects (each read in full):

- The render (`renderRotoPlayScriptFrames`) is pure — no store writes.
- The 52.2-10 sync apply (`applyDocumentSyncFrameMedia`, the
  `PHYSIC_PAINT_EFX_PAINT_DOCUMENT_EVENT` listener) is PARENT-side; the sync
  is child→parent only — the Studio never receives sync applies, so it cannot
  mutate the Studio's stores mid-operation.
- The save path does not rewrite runtimes (it projects the DOCUMENT, never
  the `physicPaintStore` records).
- The coordinator's five gate terms all come from the Studio's OWN runtime
  (`physicPaintStore.*` via the Studio ports — no document-store lag;
  `getDocument` is the runtime-composed `getRotoPhysicalDocument`).
- The parent apply (`applyPhysicPaintRotoPhysicalMap`) threads all five terms
  (loopClips / breaks / overrides included) — not a missing-term apply bug.

New structural findings:

- **The fingerprint's per-record raster term is CARRIER-SHAPED** (52.2-02
  D-07, `encodeCanonicalRecordPayloadTerm`): `m{relativePath}{digest};` for a
  media reference, the byte content token for a runtime record. Equal content
  under different carriers fingerprints DIFFERENTLY — so the gate's revision
  equality also demands cross-realm carrier equality.
- Each realm can hold per-record carriers independently: an install
  normalizes media records to media-only (`toRuntimeRotoRecords`), bridge
  applies write the publication's payloads, and content-token refs (52.1
  Part 2) resolve to the RECEIVER's current payload — i.e. each realm keeps
  its own shape per untouched key.
- **Hard constraint proven by the authority path**: `getPhysicPaintRotoAuthority`
  throws on any media-only record (`requirePhysicPaintRotoInlineBytes`, the
  frames projection), and a throw yields no result (Studio request times
  out). The user's live failure came from the STAGING gate with a valid
  commit-check — therefore at that moment the parent's runtime was
  ALL-BYTES, and the Studio's staging-revision input must have differed
  (≥1 media-only record with equal content, or a content-side term diff).
- Diagnostic pins added:
  `physicsPaintRotoPhysicalTermDigests.test.ts` — per-term digest stability,
  per-term isolation, and the carrier-shape hazard (equal content, different
  carrier, different revision) pinned as a test.

**Instrumentation (this round):** the gate now logs a both-sides diff on a
revision mismatch — `Play Script stale-revision diff: parent={revision,
termDigests, recordShapes} studio={...}` — with the parent's per-term digests
and carrier census transported via the authority result
(`physicalTermDigests` / `physicalRecordShapes` → publication
`expectedTermDigests` / `expectedRecordShapes` → execute input). The next
live run of the static case names the divergent term/carrier directly.

**Presumed resorbed by `16d02fb6` (G fix):** the cross-realm carrier split is
removed at source (both realms all-bytes post-open); the instrumented diff
line stays as a safety net. Verdict owed once H unblocks paint.

**Trace so far (2026-09-13, read-only — no code changed):**

- The message lives at `useRotoPhysicalEditCoordinator.ts:1962`: the staging
  gate is `generatedPublicationInput.expectedRevision !== expectedRevision`.
- `generatedPublicationInput.expectedRevision` is the **parent's** revision:
  `useRotoPlayScriptController` builds the publication from the
  `commit-check` authority result (`physicsPaintRotoPlayScriptController.ts`
  1372-1378: the commit-check must equal the confirm authority's
  `physicalRevision`), and the coordinator input carries
  `publication.expectedRevision` verbatim.
- The bare `expectedRevision` at the gate is **rebuilt at staging time from
  the Studio's OWN store** (`records.getRecords/getInterpolation/
  getLoopClips/getIncomingInterpolationBreakKeyIds` +
  `getDocument(...).groupOverrideRecords`, lines 1754-1777).
- So the gate is a **cross-realm equality**: the parent's physical revision
  must equal the revision computed over the Studio's stores at staging
  moment. It fails when the two realms drift between the commit-check and
  the staging — the prime suspect is a Studio-side store mutation in that
  window (e.g. a 52.2-10 document-sync apply replacing records/terms, or a
  pending settlement's `captureSnapshot`), which would also explain why the
  failure is intermittent (a motion rail worked earlier in the same
  session).
- The revision formula itself takes five terms (records, interpolation,
  loopClips, incoming breaks, group overrides) — a targeted term-diff log at
  the gate (per-side digests of the five terms) is the surgical next step if
  the static read doesn't land the divergence; the sync apply path
  (`physicPaintBridge.ts` ~3035 `applyDocumentSyncFrameMedia`, ~3118 the
  incoming document apply) is the first place to inspect for a store
  mutation that runs mid-operation.

## Defect D — per-track frame-blending toggle not persisted across Studio close — OPEN (root-caused + fix shipped; native verdict owed)

**Live (build 16d02fb6, confirmed still broken):** Studio → track
frame-blending toggle ON → close Studio → the main app shows NO inter-frames
(behaves as OFF in-session — the parent document never reflects enabled=true
even immediately after Studio close) → reopen Studio → the toggle is back to
OFF.

**Root cause (traced 2026-09-13):** the per-row toggle
(`PhysicsPaintStudio.handleToggleBlend`) writes the Studio's physicPaint store
directly (`setRotoPhysicalInterpolationState`) and relied on "the push path
serializes it" — but the push pipeline (52.1 Part 1, this file's own comment)
triggers ONLY on `efxPaintVersion` (document-structure) changes. The
physicPaint-store write bumps no `efxPaintVersion`, so the toggle reached
NEITHER the parent runtime (the in-session main-app composite stayed blind)
NOR the save (the parent's runtime projection wrote enabled=false) — the
comment's premise was stale since the 52.1 physicPaintVersion debounce was
retired. The original suspect (a coordinator/update-roto-interpolation
-settings path) was checked first: the toolbox-era coordinator op
(`set-interpolation-enabled`) is active-track-scoped only, so a per-row
toggle cannot route through it; the missing link is the sync trigger.

**Fix (this quick):** `handleToggleBlend` now marks the ONE document-sync
pipeline dirty (`markDocumentSyncDirtyRef`, following the file's existing
pubref pattern) after a successful write — the idle-gated/debounced push then
serializes the child runtime (interpolation included), and the parent
listener's doc-revision guard passes (the track roto term joins the document
revision), the mirror installs the new interpolation into the parent runtime,
and the save + reopen keep it. Pinned by a source-contract test
(`PhysicsPaintStudio.test.ts`).

**UAT re-run (D):** Studio → toggle ON → the main app must show inter-frames
immediately after Studio close (in-session, no reopen needed) → save → reopen
→ the toggle stays ON AND `layers/<layerId>.json` holds
`"interpolation":{"enabled":true}`. If still OFF in-session, check the
Studio console for a sync push line and the main console for the receiver
rejection (the docSync emit is loud on failure).

## Defect G — reopen hydrates structure but ZERO pixels, everywhere, silently — FIXED (automated)

**Live (round 3):** fresh project → save → close → reopen: the disk document is
complete (media blocks with digests), the launch context transports it whole,
yet the main canvas is blank (paper gone), the Studio canvas is black, the
engine never becomes ready, the tracks strip shows 0, a bootstrap-time capsule
never resolves — and ZERO log lines anywhere.

**Root cause (two compounding 52.2 integration gaps):**

1. **The read-back leg's runtime materialization was never built.** The 52.2-09
   plan shipped the LAZY compositor seam (`resolveFrameMediaBitmap` +
   `_setPhysicPaintPackageDirProvider`) and wired the provider **only in tests**
   — production never installed it, so every reference answered `missing`
   silently (verdict map, no log). And three consumers structurally require
   INLINE BYTES with no lazy path: the parent authority's frames projection
   (`requirePhysicPaintRotoInlineBytes` throws on a media-only record), the
   launch pack, and the engine's real-key preparation
   (`prepareRotoPhysicalRealKeyFrames` throws "does not contain a valid WebP
   payload"). The open leg (`hydrateFromMce` → `hydrateRuntimeFromDocument`)
   installed the loader's reference-only records as-is — "lazily decode" in
   the spec covered the composite seam, not these three.
2. **The Studio's launch hydration failed silently** — for the reference-only
   records above, `hydrateRotoPhysicalLaunchContext` threw inside the alpha
   preparation (before the track install loop), the caller
   (`usePhysicsPaintLaunchIntegration`) stored the error in state WITHOUT a
   console line, and returned before registering the document — hence engine
   never ready + strip 0 + stuck capsule + zero logs.

**Fix (commits):**

| Commit | Content |
|--------|---------|
| this quick | `resolveFrameMediaBytes` (bytes-level, digest-verified read; the bitmap path now reuses it) |
| this quick | new `efxPaintMediaMaterialize.ts`: reads every referenced frame file for both roto collections at open, rebuilds the tracks with byte-carrying payloads, recomputes the revision; failures returned per key |
| this quick | `projectStore.openProject` materializes before hydration (registered documents stay REFERENCE-ONLY; the runtime installs the materialized twin), logs every per-key failure loudly; `_setPhysicPaintPackageDirProvider(() => dirPath.value)` finally wired in production |
| this quick | fail-loud everywhere: the compositor seam warns once per digest on provider-null and on every failed resolution; the launch-hydration caller logs the failure; `hydrateRotoPhysicalLaunchContext` skips reference-only keys for alpha prep with a per-key warning (the structural install still runs — one unreadable frame no longer kills the whole launch) |

**UAT re-run (G):** reopen the saved project → main canvas must render the
painted content, the Studio must reach "Engine ready" with the tracks strip

**The failing comparison:** parent gate `physicPaintBridge.ts:1697` —
`currentRevision !== payload.expectedRevision`. Parent side = the rebuild over
the parent's runtime store (the same 5-term fingerprint the child rebuilds at
staging, coordinator `!1779`). Both sides built from same-material bytes would
compare equal — so either a realm's records/terms drifted after launch, or a
carrier/mutation path between launch and the first edit rewrites one side.

**Trace round (2026-09-13, read-only + one new regression pin):**

- **The launch leg is PROVEN CLEAN** by
  `physicsPaintLaunchRevisionParity.test.ts` (new): parent runtime (bytes,
  materialized) → the real base64 transport round trip → a fresh-module
  child store install → the child's recomputed revision EQUALS the parent's.
  The transport handles VP8L bytes correctly; the on-disk frames verify
  (RIFF/VP8L magic and sha256 digests match the persisted references).
- **Found: the crash-recovery checkpoint was an unguarded cross-session
  leak.** `PhysicsPaintStudio.tsx` wrote `sessionStorage['efx-paint-session-
  document'] = JSON.stringify(document)` — raw bytes become JSON index
  objects (`{"0":82,...}`) the launch validator refuses — and
  `usePhysicsPaintLaunchIntegration` read it back on EVERY launch, scoped only
  by layerId, never cleared. The Studio window is REUSED across opens
  (`lib.rs` navigates the existing label), so sessionStorage survives: a
  checkpoint left by an earlier Studio session substitutes itself into a
  LATER launch's hydration — exactly the user's prime suspect (a
  reference-only/stale document shipping into the child realm). Post-G this
  would also dead the next open loudly (the alpha prep refuses index-object
  bytes). Fixed (see below).
- Each realm's records were verified field-by-field (records/breaks/
  loopClips/interpolation/overrides all carry identically through the launch);
  E's authority proof already established the parent runtime was all-bytes at
  the failing moment on the PRE-G build.

**Fix (this quick):**

| Commit | Content |
|--------|---------|
| `c3cec5c5` | test: RED — checkpoint must be transport-shaped (base64) and bound to its launch operationId; the launch-parity pin |
| this quick | `writeEfxPaintSessionDocumentCheckpoint(operationId, document)` / `readEfxPaintSessionDocumentCheckpoint(operationId)` (transport module): bytes cross storage as base64; a checkpoint is consumed ONLY by the launch that wrote it (a watchdog reload re-fetches the same stored context — same operationId — while a new launch ignores a leftover).
