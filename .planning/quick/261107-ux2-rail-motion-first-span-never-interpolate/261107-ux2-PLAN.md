<objective>
Fix the reported Rail Motion defect: the first span of a newly added Motion channel never interpolates because `applyAddChannelEdit` seeds the opening key with `easing: 'hold'`.

Purpose: live UAT on Phase 59. A rail with paint keys at frames 0, 4 and 9 plus an animated motion channel shows the painted stroke pixel-identical to frame 0 at frame 2 (first span flat), while frame 6 (second span) is a genuine intermediate pose. Root cause verified in code: the add-channel seeding authority writes ONE key at rail-local frame 0 with the identity value and `easing: 'hold'` (`app/src/components/physic-paint/roto/railMotionModel.ts:769-774`), and the evaluator short-circuits a hold OUTGOING key (`app/src/components/physic-paint/roto/railMotionEvaluator.ts:108`). Every later key is written as `'ease'` by `upsertRailMotionKey`, which produces the reported asymmetry. `applyAnimateEdit` already seeds with `'ease'` (`railMotionModel.ts:587-592`); the add-channel path is the outlier.

Fix at the seeding authority only: flip the seed to `'ease'`. Do NOT weaken the evaluator, do NOT change the `hold | ease` union, the segment semantics, the `pairedValue` sibling step-hold rule, the seeded frame (rail-local 0), the identity value or wiggle 0. A single-key channel is inert either way (the evaluator holds the last key at and after the end), so an untouched channel cannot start animating.

No migration: a project that already carries the old hold opening key keeps holding until the user selects that key in the Motion sheet and presses Ease (the Hold/Ease toggle exists at `app/src/components/physic-paint/view/PhysicsPaintWorkflowStrip.tsx:943/955-963`). Project rule is a clean break with no backward-compat or load-time rewrite code.

`workflow.tdd_mode` is on: Task 1 is RED-first (`type="tracer" tdd="true"`), Task 2 aligns the remaining pins and can only pass after Task 1.
</objective>
