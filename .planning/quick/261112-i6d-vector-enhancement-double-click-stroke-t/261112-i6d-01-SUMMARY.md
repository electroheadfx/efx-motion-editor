**Double-click path-edit entry through the icon's own session action, an Alt+click tangent break that both curve modes honour, and an orange glow/halo selection ring legible over orange paint**

## Accomplishments

- `ScriptStrokeOverlay` gained the optional `onStrokeDoubleClick` prop with a hit-tested `onDblClick` bound CONDITIONALLY on the interactive root only; `canvasPointOf` widened to `TargetedMouseEvent`.
- `requestAquarellePathEdit(mutationId)` in the watercolor adapter: vector-only, readability-gated, selection normalised to the double-clicked stroke, then the Edit path icon's ONE `enterPathEdit`.
- `breakAnchorTangent(anchors, index)` in `vectorPathHandles`: the one straight-corner write (`kind: 'bezier'`, both handles on the anchor), identity-returning no-op, `width`/`color` preserved, neighbours reference-identical.
- `isCornerAnchor` exported from `@efxlab/efx-watercolor/payload` as the single corner predicate.
- `VectorPathOverlay.startEditDrag`: Alt+anchor branch placed after the selection write and before `promoteAnchorForDrag` — one `onPathEdit`, no drag state, no pointer capture; handle hits keep priority so Alt on a handle dot still drags.
- Selection chrome: crisp `#f97316` ring (1.5) over a `#111111` dark halo (4/0.85) over a `#f97316` soft glow (8/0.35), all `vectorEffect="non-scaling-stroke"`, existing `vector-path-anchor-selection` testid kept.
- The anchor-width clamp pin now asserts `ANCHOR_WIDTH_MAX` instead of the literal 2, making it ceiling-relative for plan 02.

## Decisions Made

- The double-click delegates meaning to the adapter (the shared overlay only resolves the hit), keeping the vector-only law in one place.
- The Alt+click branch never consults the curve mode: the corner shape is the one representation `resolveCurveAnchors` preserves under Spline and Bézier collapses under the authored mode, so both modes share one write.
- Selection is written before the Alt branch so a click always selects the pressed vertex, even when the corner write is a no-op.
- No width constant was touched — plan scope boundary respected; the clamp pin was made constant-relative only.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's Spline fixture would actually have run Bézier**
- **Found during:** Task 2 (Alt+click tests)
- **Issue:** The plan described `editedStroke()` (no `curveMode`) as "Spline (default mode)". `DEFAULT_VECTOR_PATH_CURVE_MODE = 'spline'` is only the DRAW default; an absent stored mode resolves to `bezier` via `resolveAquarelleCurveMode`, so the pin would have silently exercised Bézier.
- **Fix:** The overlay Spline pin now passes `curveMode: 'spline'` explicitly and also asserts no handle dot is drawn (the spline view); the pure Spline survival pin stays in `vectorPathHandles.test.ts` through `resolveCurveAnchors(..., 'spline')`.
- **Files modified:** app/src/components/physic-paint/engine/VectorPathOverlay.test.ts
